# Task 0.4 report: Keyed-crypto + FPE extension contract with pure-Python references

Status: DONE

## What shipped

- `src/decoy_engine/execution/native/_crypto_ext.py` (556 LOC, under the 600 cap): the
  crypto/FPE native-boundary contract plus two pure-Python reference kernels that reproduce the
  shipped engine crypto byte-for-byte.
- `src/decoy_engine/errors.py`: added `MaskKeyRequiredError` (public typed exception, code
  `mask.key_required`) next to `MaskKeyDerivationError`, and to `__all__`.
- `tests/native/test_crypto_ext_contract.py`: the contract test suite (33 tests).

### Interfaces built (match the plan)

- `KeyedDerivationKernel.derive_batch(values: pa.Array | pa.ChunkedArray | list, *, mask_key,
  namespace, truncate) -> pa.Array`. `mask_key` is named `mask_key`, never `seed`. Accepts BOTH
  the typed-`pa.Array` form and the mixed-object Python-list fallback. The reference handles both;
  `CRYPTO_EXT_ABI` specifies that the compiled kernel accepts only `pa.Array` and rejects the list
  form with `mixed_object_not_native`.
- `FpeKernel.encrypt_batch / decrypt_batch(values, *, mask_key, namespace, tweak_column, config:
  FpeConfig) -> FpeBatchResult`. `FpeConfig` carries charset, separator preservation,
  checksum/Luhn mode, and join-group tweak, and its `_resolve()` mirrors the shipped strategy's
  `run` line-for-line (charset dedup preserving order, Luhn gated to an all-digit charset with no
  checksum, checksum priority over `validate_luhn`). `FpeBatchResult` carries the output array plus
  structured per-row `FpeRowError`s (redacted, never the cell value) and `QualityWarning`s; it also
  exposes `to_pylist()` so the plan's round-trip skeleton works verbatim.
- `reference_keyed_derivation()` and `reference_fpe()` factory functions returning the reference
  kernels.
- `HASH_KAT` / `FPE_KAT` known-answer vectors, generated by running the shipped primitives and
  pinned as module constants.
- `CRYPTO_EXT_ABI` doc block: ownership, thread model, packaging, Arrow C Data Interface
  expectations, and the fail-before-output contract.

### How the references reproduce shipped behavior (rolled nothing new)

- Keyed derivation reuses the shipped `_array_to_pylist`, `_is_missing`, `canonicalize_derive_source`,
  and `derive`, so output is byte-identical to `kernel/_scalar.hash_array` by construction while
  carrying the native mask_key naming and the fail-closed guard.
- FPE reuses the shipped value primitive (`fpe_encrypt_value` / `fpe_decrypt_value`) and the shipped
  `FpeStrategyHandler._residual_risk_warnings`, and reproduces the strategy's config resolution, key
  derivation (`derive(mask_key, namespace, FPE_KEY_LABEL)`, `FPE_KEY_LABEL` imported, not re-typed),
  tweak (`(join_group or column).encode("utf-8", errors="replace")`), null policy, and fail-closed
  error mapping. This stays byte-consistent with Task 0.3's `FpeKeyProvider`, which derives the same
  per-column key from the same imported label.

### Fail-closed contract (tested explicitly)

- `mask_key` None/empty raises `MaskKeyRequiredError` before any output, in both `derive_batch` and
  `encrypt_batch`/`decrypt_batch`.
- A missing/incompatible compiled extension raises `CryptoExtensionUnavailableError` before any
  staging; `load_compiled_crypto_kernel()` raises it in Phase 0 (extension not built until Phase 2).
- A per-row unencryptable value is recorded as a structured, redacted `FpeRowError` and its output
  row is None; the ABI documents that the execution boundary maps a non-empty error set to the
  shipped `StrategyError` kill, preserving the shipped whole-job fail-closed semantics.

## Concerns

- Per-row error surface vs shipped whole-job kill: the shipped `FpeStrategyHandler.run` raises
  `StrategyError` and kills the job on the first `FpeUnencryptableError` / `FpeChecksumError`. The
  native contract instead returns structured per-row errors (as the plan requires), and the ABI
  documents that the execution boundary must map a non-empty error set to the shipped kill. Phase 1
  must wire that mapping so native execution stays fail-closed at the job level; the contract does
  not silently change the failure mode by itself.
- Degenerate-charset handling: `FpeConfig._resolve()` raises `FpeConfigError` (a config-level
  fail-closed, mirroring the shipped `fpe_charset_degenerate`) rather than a per-row error, since a
  degenerate charset is a whole-column configuration fault. This is a new local exception type, not a
  shipped one; it is documented in the module and is the analogue of the strategy's
  compile/execution-time raise.
- `load_compiled_crypto_kernel()` is a Phase-0 stub that always raises; Phase 2 replaces its body
  with the real dynamic-library load and ABI-version check. The fail-before-output contract and its
  test are already in place.
