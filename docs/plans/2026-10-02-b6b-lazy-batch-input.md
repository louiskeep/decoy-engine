## Problem

B6a bounds the auto-chunk lane's output; its input is still a whole resident table. A caller that wants a bounded job today cannot get one on this lane, because a `LazySource` is refused before the lane is chosen:

- `_planner._runtime_source_rejections` returns a rejection for any `LazySource` without reading its metadata (`src/decoy_engine/execution/_planner.py:471-479`, prose from `_pipeline_sources.lazy_source_rejection`, `src/decoy_engine/execution/_pipeline_sources.py:180-206`). Its docstring calls the guard "unreachable in production" because only relationship jobs carry a `LazySource` (`_isolated_worker.py:216-217` sets `lazy=has_relationships`).
- The job then falls to the full-frame continuation, which materializes every source with `resolve_resident_sources` (`_pipeline.py:554-560`, `_pipeline_sources.py:68-119`) and masks it on pandas. The unified slice declines it too: its cheap admission requires a resident `pa.Table` (`_unified_slice_admission.py:304-309`).
- The lane itself slices a resident table: `_slices` (`_pipeline_auto_chunk.py:146-148`) feeds B1's `run_mask_chunked`, and B6a's streamed lane builds its schema rule from `source.slice(0, chunk_size_rows)` (`_pipeline_auto_chunk.py:295-297`).
- So the isolated worker keeps single-table jobs eager on purpose. Its own test records why: making them lazy once made a 200,000-row job decline auto-chunk, run full-frame and crash under a low rlimit cap (`tests/unit/execution/test_isolated_worker_streaming.py:114-124`). The worker's docstring names the eager load a "documented roadmap follow-up" (`_isolated_worker.py:104-109`).

The refusal is not needed. Every runtime gate the planner applies reads only row count, schema and per-column null count (`_planner.py:480, 487-493, 516-521, 535-579`), and a Parquet footer gives all three: `LazySource.num_rows` and `.schema` read only the footer (`src/decoy_engine/profile/_readers.py:139-147`), and `LazySource.column_null_counts()` returns exact footer null counts, or `None` when a row group lacks statistics (`_readers.py:149-174`). The byte estimator already prices lazy sources this way (`_mem_estimate_arrow.py:254-290`, "complete statistics give an exact count, otherwise the field's `nullable` flag stands"). B1's entry point already takes any iterable of tables (`native/_chunked_entry.py:426-441`).

Measured on this base (probe `b6b/probe_mem.py`, B6a's native benchmark source at 10,000,000 rows, 361 MiB Parquet with 1,048,576-row row groups, one process under the devbox test lock, peak reset after imports): `pq.read_table` takes 2.1 s and adds 1,270 MiB; reading the same file through `ParquetFile.iter_batches(batch_size=50_000)` and re-cutting it into 50,000-row tables takes 2.1 s and adds 500 MiB. That last figure is not bounded: with PyArrow 25.0.1's default `pre_buffer=True` (the companion benchmark environment; the locked PyArrow 24.0.0 defaults to `False`), `pa.default_memory_pool().max_memory()` during a whole-file `iter_batches` grew from 93 MiB at 2,000,000 rows to 383 MiB at 10,000,000 rows (probe `b6b/probe_mem2.py`), about the file's size, so reading through today's `LazySource.open_batches` (which opens `pq.ParquetFile(self.path)` with the installed version's defaults, `_readers.py:126`) would itself grow with rows on 25.0.1. With `pre_buffer=False` and `buffer_size=8 MiB` the pool peak was 60 MiB at 2M and 61 MiB at 10M, 55 MiB on the same 10M rows written as one row group, and the read took 0.9 s to 1.2 s. The out-of-core route reads through the same handle (owner question 1).

## Established solutions

How engines that stream bounded input do it, and what B6b takes from each:

- **Arrow C stream interface and `RecordBatchReader`.** Arrow's interchange contract for streaming is a pull-based stream of record batches with one schema fixed up front (`ArrowArrayStream`: `get_schema`, then `get_next` until end; pyarrow exposes it as `RecordBatchReader` and `__arrow_c_stream__`). B1's `run_mask_chunked(config, chunks: Iterable[pa.Table])` is already this shape: it pulls chunks, fixes the schema from the first and refuses drift (`native/_chunked_entry.py:336-346`). B6b feeds it a pulled stream instead of slices.
- **`pyarrow.parquet.ParquetFile.iter_batches`.** Decodes a file one batch at a time (`batch_size`, `row_groups`, `use_threads`); `pre_buffer` (default `False` on the locked 24.0.0, `True` on 25.0.1) coalesces reads for high-latency filesystems, and `buffer_size` enables buffered column reads. The engine's own `LazySource` is built on it (`_readers.py:101-180`, `open_batches` at `:119-137` takes the schema and the iterator from one open handle). The platform's B5 bounded reader uses the same API, one row group at a time with `use_threads=False` (decoy-platform `feat/b5-native-pricing`, `docs/plans/2026-10-02-b5-native-admission-pricing.md` section 4.5). On the locked PyArrow 24.0.0 and companion PyArrow 25.0.1 environments, `iter_batches` filled batches across row-group boundaries. Its documented contract is nevertheless a maximum batch size, not an exact non-final chunk-boundary contract. (Probe `b6b/probe_rg.py` on both versions: 20 one-row groups at `batch_size=7` gave 7, 7, 6, and 250,000 rows in 33,333-row groups at `batch_size=50_000` gave five batches of 50,000, with and without `pre_buffer=False, buffer_size=8 MiB`. Probe `b6b/probe_schema.py` on 25.0.1, with a twelve-column table that includes a dictionary and an all-null column, did yield short batches at row-group ends: 33,333, 16,667, 16,666, 33,333, 1, ...) Probe `b6b/probe_schema.py` also found that `pa.Table.from_batches(batches, schema=pf.schema_arrow)` `equals` `pq.read_table` with `check_metadata=True` for string, large string, int with nulls, float, bool, timestamp with and without zone, date, decimal, dictionary, all-null, non-nullable fields with field metadata, schema metadata, pandas-written files, `uuid` and `json` extension types, and files written with and without statistics.
- **`pyarrow.dataset.Scanner.to_batches`.** The same decoder behind a scan scheduler with `batch_readahead` (default 16 batches) and `fragment_readahead` (default 4 files); the docs say raising either "will increase RAM usage", and recommend a smaller `batch_size` "if scanned record batches are overflowing memory". Measured in probe `b6b/probe_mem.py` at 10M rows: 674 MiB added with default readahead and 702 MiB with readahead 1, against 500 MiB for `ParquetFile.iter_batches`; on a file written as one row group it added 1,618 MiB (it holds the whole row group). B6b does not use it: one local file needs no fragment scheduling, and its readahead is exactly the memory B6b is bounding.
- **Polars streaming engine (`scan_parquet` then `sink_parquet`).** Splits the scan into morsels sized from the core count and row width, and runs the plan without materializing either side; if any node cannot stream, `sink_parquet` fails rather than silently going in memory. B6b keeps that rule: the input streams only when the output streams (Design 2), and a run that cannot stream says why.
- **DuckDB Parquet scans.** The row group is the unit of scan parallelism, each thread holds one vector of about 2,048 rows per column, and a larger row group means more memory per thread. B6b reads with buffered column-chunk I/O instead (Design 3a), so a large row group costs read buffers, not the whole row group; section 10's one-row-group cell measures it.

Custom code, and why: `rechunk` is the only new custom data-motion primitive. It defensively preserves exact resident chunk boundaries if a conforming reader yields short batches. The remaining new code is routing-fact, lifecycle and evidence orchestration. Exact boundaries matter because B6b's guarantee is chunk-for-chunk equality with the resident lane (B1 evidence counts calls per chunk, row errors carry chunk-based row offsets, and B2's parity contract is per chunk boundary). The evidence accumulator (Design 4) follows the same online-aggregation shape as a streaming `GROUP BY` partial state: fold each record into running totals, keep nothing per record.

## Guarantee (pinned)

Terms. The **resident twin** of a `run_pipeline` call is the same call with every `LazySource(p)` in `sources` replaced by `pq.read_table(p)`, which is what the isolated worker passes today (`_isolated_worker.py:113-116`) and what B6a's guarantee is stated over. A **gated column** is a column the planner reads a null count for: an integer column, or a `bucketize` source column (`_planner.py:487-493, 514-521`). A lazy source has **footer facts** when every gated column of its table has an exact footer null count (`column_null_counts()` is not `None` for it).

For every `run_pipeline` call on a job with no FK relationships, whose `LazySource` tables have footer facts:

1. **Same route and same result as the resident twin.** The call takes the same execution route, the same auto-chunk and B7 split decisions with the same reasons, and the same lane. Its result equals the twin's: outputs (`equals(..., check_metadata=True)`) when not streamed; when streamed, the same sink calls in the same order with batches equal under B6a guarantee 1 (a), and, with `ParquetTransactionalSink`, published files byte-identical to the twin's; the same timings keys, `boundary_conversion_ms` (exact on the native route, non-negative on the oracle route, as B6a test 5 compares them), warnings, `code_set_corpora`, `chunked_route` and `chunked_route_by_table` evidence, vault entries, `table_kinds`, row errors, and raised error type and code; and `quality_metrics` equal to the twin's except the two keys of guarantee 5 (`input` blocks and `execution.loaded_fully_in_memory`). A lazy table that lacks footer facts declines auto-chunk with reason `lazy_source_null_count_unavailable` naming the columns, and the call then equals today's behavior for that table (materialized at its point of use).
2. **Bounded input and output data working set.** On a streamed run, excluding the explicitly unbounded vault side channel, the data-bearing input/output working set is bounded by the configured chunk size, B6a's output row-group bounds, reader buffers, and the largest encoded Parquet page or dictionary page. The reader/re-cut stage retains fewer than `2 * chunk_size_rows` source rows. Passthrough output can retain source-backed buffers up to B6a's one-row-group output bound. This guarantee is independent of total table row count when the source's maximum encoded page size is itself bounded. It is not a byte-budget guarantee for an arbitrarily large single page. Every routed `LazySource` table on a streamed run is read as batches and never materialized: `LazySource.to_table`, `pq.read_table` and `ParquetFile.read` are never called for it. Per-chunk evidence is folded into an accumulator whose state is O(columns + distinct warnings and corpora), not O(chunks) (Design 4). Section 10's scaling bars (M2 across 2M, 10M and 50M rows, R across row-group layouts) measure the whole run instead of trusting this paragraph.
3. **The input streams only when the output streams.** A routed run whose output stays resident (any B6a Design 2 reason) materializes each lazy table exactly once, before the lane, and runs B6a's resident path unchanged. Whole-output consumers (validators, quarantine, fidelity, post-validation) therefore always see resident sources, as today.
4. **Lazy sources not retained as a route or split candidate are resolved before the route executors.** A `LazySource` that is not retained as a route or split candidate is materialized before the unified slice is tried, so a small single-table lazy job gets the unified slice exactly as its twin does. Transform-bearing tables keep today's path (transformed once, as resolved).
5. **Evidence, never silent.** Every routed table carries an `input` block next to B6a's `output` block (`quality_metrics["auto_chunk"]["input"]` for a single table, the same block per table in `auto_chunk.tables` for a split): `mode` (`lazy` or `resident`), `reason`, and on lazy tables `source_row_groups` and `source_max_row_group_rows` (footer values). On a run where every source streamed lazily, `quality_metrics["execution"]["loaded_fully_in_memory"]` is `False`; otherwise it keeps today's `True`. The payload is JSON-safe and deterministic.
6. **Atomic publish and clean exit unchanged.** B6a guarantee 3 holds for every failure B6b adds (a changed source, a read error, a row-count mismatch): nothing is published, the session aborts once, and the source file handle is closed on every exit.
7. **Resident callers unchanged.** A call whose sources are all `pa.Table` behaves exactly as on B6a: outputs, sink calls and `quality_metrics` byte-identical, except that a routed table's `auto_chunk` block gains `input: {"mode": "resident", "reason": "resident_source"}`.

Relationship-bearing jobs keep their TB-1 behavior (out-of-core and sequential consume `LazySource` natively); B6b does not touch those routes.

## Non-goals

B6c (the platform's sub-256-MiB eager route, platform adoption of `LazySource` or the sink); CLI adoption (B4 or a follow-up); lazy CSV, fixed-width or cloud sources (`LazySource` is a local Parquet handle; the platform's B5 reader owns CSV framing and byte budgets); a byte-budgeted input reader, `read_dictionary`, owned-buffer copies or readahead; FK, sequential and out-of-core routes and the D-phase work; transform-bearing tables on the lane (the planner already refuses them, `_planner.py:323-329`); generation and mixed jobs; changing B1's `run_mask_chunked`, B6a's output lane or its eligibility rule, `ParquetTransactionalSink`, the chunk size or the threshold; bounding the vault; changing what `run_pipeline_isolated`'s driver reads back; the Phase E 100M gate.

## Design

### 1. API: the caller passes a `LazySource`

No new entry point and no new knob. `run_pipeline(config, sources)` already accepts `Mapping[str, pa.Table | LazySource]` (`_pipeline.py:151`). A caller who wants bounded input and output passes `LazySource(path)` for each table plus a `TransactionalSink`, the same "structural bounded shape" the out-of-core route already documents (`_residency_warning.py:1-12`). Callers on this base:

- **The isolated worker.** `_isolated_worker._run` loads every manifest table as a `LazySource` (`_load_sources(..., lazy=True)` for every job, replacing `lazy=has_relationships` at `:216-217`; `_load_sources` keeps its parameter). The failure its test recorded cannot recur: a lazy table now gets the same auto-chunk decision as a resident one (guarantee 1). `run_pipeline_isolated` and the routing probe (`_probe.py:255-263`) inherit it.
- **Library callers** who build `LazySource` themselves.
- The platform worker and the CLI pass resident tables without a sink (`decoy-platform api/jobs/v2_runner.py:298-310`; `decoy/src/decoy/cli/run.py:618-637`) and are unchanged until B6c or B4 opt in.

The documented meaning changes in three places (Design 9): a `LazySource` is now admitted to auto-chunk and to the B7 split; it streams when the output streams; otherwise it is materialized at one defined point.

### 2. Where each lazy table is resolved

One decision, made in two steps, never revisited:

0. **One routing snapshot.** `capture_source_facts(caller_sources, table_kinds)` reads each mask-kind `LazySource`'s footer once (`num_rows`, schema, `column_null_counts()`, row-group count and largest row-group rows) into a frozen `SourceFacts`. `decide_chunk_route` (`_pipeline_chunk_route.py:31-73`) captures it and returns it beside its decision, so `_pipeline.py` gains no line. `lazy_stream_candidates` returns `Mapping[str, SourceFacts]`, not a set. `decide_chunk_route`, `decide_multi_table_split`, `_runtime_source_rejections`, `input_modes`, `run_multi_table_split`, and `run_auto_chunk` receive this single captured mapping. The planner consumes the supplied facts and does not reopen lazy metadata. `run_auto_chunk(..., expected: SourceFacts)` passes the exact routing snapshot to `open_input`. The physical-plan hash consumes the same representation. `classify_job` gains a keyword `source_facts: Mapping[str, SourceFacts] | None = None`; a direct caller that omits it gets facts captured inside the call, as before.
1. **Before the unified slice** (`_pipeline.py`, replacing the `resolve_resident_sources` call at `:554-560`, which moves above `run_from_pipeline_locals` at `:546`): `resolve_resident_sources` gains `keep_lazy: Mapping[str, SourceFacts]` and leaves those `LazySource` entries untouched. `keep_lazy = lazy_stream_candidates(...)`, a free function over the snapshot: the mask-kind tables whose source is a `LazySource`, that are not transform-bearing-unprepared, when either the job routed chunked (`route_chunked`) or the job has two or more mask tables (a B7 split is still possible). Every other `LazySource` (not retained as a route or split candidate: single-table jobs that did not route chunked, generate-bearing jobs, transform-bearing tables) is resolved here exactly as `resolve_resident_sources` resolves it today. The result is rebound to `caller_sources`, so the unified slice, the split decision and the mask step all see the same mapping. Relationship jobs reach this point only on the full-frame route, where nothing streams and the unified slice declines them (`_unified_slice_admission.py:272-273`), so for them only the position of the call moves.
2. **After the output mode is decided** (`_pipeline_generate_mask.run_generate_and_mask_steps`, right after B6a's `decide_output_mode` at `:158-172`): `input_modes(...)`, a free function, names each kept-lazy table `lazy` when `out_mode == "streamed"` and the table is the routed table or a dispatched split table, else `resident` with the output reason (`no_sink`, `validators_present`, `split_full_frame_present`, ...) or `not_dispatched`. Tables named `resident` are materialized once here with `materialize_source` (`_pipeline_sources.py:55-65`) into the mapping the step uses (`merged_sources`), and the step returns that mapping in `GenerateMaskStepResult` so `run_pipeline`'s finalize and post-validation (`_pipeline.py:634, 667`) read resident tables. On a streamed run those consumers are absent by B6a's rule, and the mapping still holds the `LazySource` objects (paths, no data).

`_pipeline.py` stays at its 679-line ratchet (`tests/sentry/test_module_size.py:479`): the call moves and gains one keyword; the candidate set is computed in `_pipeline_sources`.

### 3. The batch input

New module `execution/_chunked_input.py` (orchestration cap 600 lines), logic in free functions:

- `open_input(source, *, table, chunk_size_rows, expected, native_threads) -> InputChunks`: `first: pa.Table`, `chunks: Iterator[pa.Table]` (the first chunk then the rest), an idempotent `close()`, and `block()` (the evidence of guarantee 5). For a `pa.Table` it yields `source.slice(start, chunk_size_rows)`, today's `_slices` (`_pipeline_auto_chunk.py:146-148`), so resident runs are unchanged.
- For a `LazySource`: `opened = source.open_batches(chunk_size_rows, pre_buffer=False, buffer_size=INPUT_BUFFER_BYTES, use_threads=native_threads > 1)` (one open handle, `_readers.py:119-137`; Design 3a). `LazySource.open_batches` returns an explicit `OpenedLazyBatches` owner containing `schema`, `num_rows`, row-group facts, `batches`, and an idempotent `close()` that calls `ParquetFile.close()`. `open_input` owns it before comparing facts. Any `BaseException` during comparison or first-chunk priming closes it before re-raising. After successful construction, `InputChunks.close()` owns the same idempotent close, and `_run_streamed` invokes it in `finally`. (`open_batches` has no caller in `src/` today; its return type changes freely.) Before the first batch `open_input` compares the handle's footer row count and schema (`check_metadata=True`) with `expected`, the routing snapshot for this table (Design 2 step 0); a difference raises `ExecutionError(code="lazy_source_changed")` naming the table, before any chunk is masked. Batches are re-cut with `rechunk(batches, schema, chunk_size_rows)`: accumulate batches, and whenever the pending rows reach `chunk_size_rows`, emit `pa.Table.from_batches(pending, schema=schema).slice(0, chunk_size_rows)` and keep the remainder; at the end emit the remainder if non-empty. Chunk k therefore holds rows `[k * chunk_size_rows, (k + 1) * chunk_size_rows)`, the resident slicing exactly. Emitted chunks are views of at most two reader batches of at most `chunk_size_rows` rows each, so a view pins no more than that (B5's owned-buffer copy exists because its reader batches are larger than its chunks; here they are not). After the last batch the yielded row total must equal the footer `num_rows`, else `ExecutionError(code="lazy_source_row_count_mismatch")`, raised before the lane returns and so before commit.
- The handle is closed on every exit: exhaustion of `chunks` calls the owner's `close()`, and `_run_streamed`'s `finally` calls it again (idempotent), so a masking error, a sink error or `KeyboardInterrupt` leaves no open descriptor on the source.
- Read errors (truncated file, corrupt page, file removed) propagate with pyarrow's own exception type through B6a's `write_batches` loop; B6a's session aborts (B6a Design 8).

**3a. Reader options (frozen by section 10).** `LazySource.open_batches` gains `pre_buffer: bool | None = None`. When `None`, it omits the argument from `ParquetFile`, preserving the installed PyArrow version's existing behavior. B6b passes explicit `pre_buffer=False`, `buffer_size=INPUT_BUFFER_BYTES`, and its selected `use_threads` value. `buffer_size` (default 0) and `use_threads` (default `True`) are keyword-only with pyarrow's own defaults, so a call that omits them is today's call. `INPUT_BUFFER_BYTES` is 8 MiB, a module constant. `LazySource.iter_batches` (the out-of-core route's reader) is not changed.
- `pre_buffer=False`: pyarrow documents `pre_buffer` as coalescing reads and issuing them in parallel on a background I/O pool, for high-latency filesystems. On a whole-file iteration of a local file the probe above (25.0.1, where it is the default) shows its pooled bytes growing with the file, which is the one thing B6b exists to prevent. Passing it explicitly makes B6b's behavior the same on 24.0.0 and 25.0.1.
- `buffer_size=8 MiB`: pyarrow's buffered column-chunk reads; without it the reader holds a whole column chunk, and the probe's one-row-group file held 380 MiB (pool) against 55 MiB with it. 8 MiB is the size the probe used; it is frozen with the bars, not tuned after measurement.
- `use_threads=(native_threads > 1)`: the job's thread budget covers decoding, as B5's reader does (`use_threads=False` there). A one-thread job decodes on one thread (the probe's single-threaded reads of 10M rows took 2.1 s to 2.6 s against 0.9 s to 1.3 s threaded; section 10's W bar includes it).
These options do not change decoded values or schemas: decoding is the same code path, and test 1 checks equality against `pq.read_table` under exactly these options.

### 4. The lane

`_pipeline_auto_chunk.run_auto_chunk` takes `source: pa.Table | LazySource`. A `LazySource` is accepted only together with a sink (the streamed lane); anything else is a programming error (`AssertionError`), because Design 2 materializes every non-streamed lazy table first. `_run_streamed` opens `open_input`, builds B1's schema rule from `inputs.first` instead of `source.slice(0, chunk_size_rows)` (`:295-297`), and passes `inputs.chunks` to `run_mask_chunked` in place of `_slices(...)` (`:298-310`). B6a's `stream_table` and everything after it are unchanged. The `input` block joins `quality_metrics["auto_chunk"]` beside `output` (`:402-403`). The dispatcher and legacy resident paths keep `_slices` and receive only resident tables.

Replace B6a's list-backed `OutputFreeResults` with an online `OutputEvidenceAccumulator`. Its `append` updates timings, conversion totals, stable warning union, code-set corpora and per-column route evidence, then discards the `ExecutionResult`. Its retained state is O(columns + distinct warnings/corpora), not O(chunks). It lives in `_chunked_output_sink.py` (where `OutputFreeResults` is, `:151-155`) and produces exactly what B2's aggregators produce from a list (`aggregate_chunk_timings`, `aggregate_chunk_warnings`, `aggregate_chunk_code_set_corpora`, `aggregate_chunked_route_evidence`, the `boundary_conversion_ms` sum, `_pipeline_auto_chunk.py:395-409`), so the streamed lane's `quality_metrics` are unchanged; B1 only calls `append` on its `chunk_result_sink` (B6a Design 3), and `run_auto_chunk` reads the accumulator's results instead of calling the list aggregators. The resident lane keeps its list (it already holds the whole output). Each aggregator's fold is a free function so mutation testing reaches it.

**4a. Spill directory (dennis B6a MEDIUM-3).** B6a's schema hold-back spills to `tempfile.mkdtemp(prefix="_decoy_hold_")` (`_chunked_output_sink.py:277`), which lands in `TMPDIR`, often a different and smaller filesystem than the output. The spill directory now comes from the sink: `ParquetTransactionalSink` exposes a read-only `spill_parent` property (its target's parent, the same directory its `_decoy_stage_*` staging uses, `_transactional_sink.py:255`), and the hold-back creates `_decoy_hold_*` there with `tempfile.mkdtemp(prefix="_decoy_hold_", dir=spill_parent)`. A streaming sink without `spill_parent` streams normally; if a hold-back actually needs to spill, the run raises `ExecutionError(code="hold_back_spill_unavailable")` naming the table, and the session aborts. Nothing reads `TMPDIR` for the spill.

`run_multi_table_split` (`_pipeline_multi_table.py:274-290`) passes each dispatched table's source as it is (a `LazySource` or a table) and copies the `input` block into the table entry as it copies `output` (`:222-225`). Tables are opened one at a time, in config order, each after the previous table's last chunk is written. `_table_entry` reads `num_rows`, which a `LazySource` serves from the footer (`:213`).

### 5. Planner: footer facts for a `LazySource`

`_runtime_source_rejections` evaluates a `LazySource` with the same gates as a table, through one small adapter in the new module, `source_facts(src) -> SourceFacts` (`num_rows`, `schema`, `null_count(column) -> int | None`). For a `pa.Table` it reads the table as today; for a `LazySource` it uses the snapshot of Design 2 step 0 and reads nothing. A gated column whose footer count is `None` adds the rejection `lazy_source_null_count_unavailable: column(s) ... of table ... have no footer null count; auto-chunk declines rather than read the column to count nulls`. No data page is read to decide. The `isinstance(src, LazySource)` branch (`_planner.py:471-479`) and `lazy_source_rejection` (`_pipeline_sources.py:180-206`) are removed. `_planner.py` is at 596 lines against the 600 cap and must not cross it; the builder moves the gated-column null-count reads into the adapter call so the net change is not positive.

The physical-plan compiler calls the same `classify_job` (`physical/_compiler.py:111`, `:259`), so it follows. Two bookkeeping changes keep it honest: `_resident_source_fact` (`physical/_inputs.py:263-281`) records a `LazySource` as `(name, "lazy_source", num_rows, ((column, type, footer_null_count_or_None), ...))`, rendered by the same `SourceFacts` representation routing uses, instead of a bare marker, because those facts now decide the route and must change the plan hash; and `physical/_reasons.py` defines `CODE_CHUNKED_LAZY_SOURCE_NULL_COUNT_UNAVAILABLE` but relies on the existing coded-prefix extractor (`_CODE_PREFIX_RE`, `physical/_reasons.py:195`), which already picks up the `lazy_source_null_count_unavailable: ...` prefix; no matching regex is added, so translation cannot emit the code twice. The old lazy pattern and code stay, so `tests/physical/test_compiler_reasons.py:55-62` (a pure prose-to-code test) is unchanged.

### 6. Side channels

- **Profiling, first-chunk schema, carry.** `profile_source(config)` profiles from the config's `sources:` descriptors with a bounded sample (`profile/_source.py:46-51`), on both runs. ### 8. Failure modes and cleanup

| Failure | Behavior | Visible after |
|---|---|---|
| Source file changed between routing and the read (row count or schema) | `lazy_source_changed` before the first chunk; session aborts (a no-op before any write) | Nothing at target, handle closed |
| Source missing at routing | The footer read in Design 2 step 0 raises `FileNotFoundError` before any output decision; the publish session never opens | Nothing; zero sink calls |
| Source deleted after routing, before `open_input` | `FileNotFoundError` at open, before the first chunk; session aborts once | Nothing |
| Hold-back must spill and the sink has no `spill_parent` | `hold_back_spill_unavailable`; session aborts | Nothing |
| Corrupt page or truncated file mid-stream | Pyarrow's exception propagates through `write_batches`; session aborts once | Nothing; staging and spill cleanup attempted best-effort, as B6a |
| Fewer or more rows than the footer says | `lazy_source_row_count_mismatch` at end of stream, before commit | Nothing |
| Gated column without footer null count | Declines auto-chunk (`lazy_source_null_count_unavailable`); materialized at its point of use, as today | Today's result for that table |
| Masking, schema, row-error, commit or post-stream failure | B6a Design 8, unchanged | As B6a |
| `KeyboardInterrupt` during the read | Same as an error; the source handle is closed | Nothing |
| Process killed | No cleanup; B6a's orphan rules; the source is only read | Never a partial target |

### 10. Merge evidence: performance and memory

Bounded local benchmark, merge evidence under the standing Rust rule, not the Phase E gate.

**Configurations.** (a) **baseline** = B6a: `pq.read_table(source)` then `run_pipeline(config, {t: table}, sink=ParquetTransactionalSink(staging))` then `_isolated_worker._finalize_outputs`; (b) **candidate** = B6b: the same with `{t: LazySource(source)}`. Both use production defaults otherwise (`stream_chunked_output=True`, `native_threads=1`, `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`). For both, the peak counter is reset (write `5` to `/proc/self/clear_refs`) after imports and config construction and before the read, and `VmRSS` there is the floor, so the baseline's increment includes its read and the candidate's includes its lazy read. Wall time spans from the floor to `_finalize_outputs` return for both (read, mask, publish). Each trial also records lifetime peak (`ru_maxrss`), `pa.default_memory_pool().max_memory()` and whether the routing probe ran (a counter around `_probe.probe_peak_bytes`).

**Workloads.** B6a's two (`scripts/bench-auto-chunk/bench_worker_sink.py:42-56`): the native workload (hash, redact, truncate, passthrough strings) and the oracle-reroute workload (adds a deterministic categorical column), each written once with 1,048,576-row row groups in an unmeasured step, at 2,000,000, 10,000,000 and 50,000,000 rows, plus the native 10,000,000-row source rewritten with `row_group_size=10_000_000` (one row group). The 50M default-row-group sources are prepared with a bounded `ParquetWriter` loop: one deterministic 1,048,576-row table at a time, one continuing RNG, and a final remainder. `Table.nbytes` is accumulated from those tables; no full 50M table exists during preparation. The special 10M one-row-group source retains one-shot preparation. Preparation records peak RSS and rejects an artifact if preparation exceeds 3 GiB. (The 2M and 10M sources use the same loop, so all sizes share one generator; their bytes therefore differ from B6a's fixtures, and the reference hashes are this run's own.) The record states each source's file size, accumulated `Table.nbytes`, row-group count and preparation peak RSS.

**Cells, each a separate invocation.** The lesson from B6a: one exclusive benchmark held the machine test lock for 5.5 hours and stalled other work. So the harness takes the lock (`/home/cam/.cache/pytest-one.lock`) per trial process, never per cell; each trial appends one JSON line to `results.jsonl` keyed by `(cell, config, index)`; a cell invocation skips trials already recorded, so an interrupted cell resumes; `summarize` computes every bar from the file. Expected durations are from B6a's timings and printed before a cell starts.

**Bars.** Percentiles are nearest rank (with five or three trials p95 is the maximum).

- M1 (lower than resident input), per route family: candidate p95 run increment at 10M is at most 0.5 times baseline p50 run increment at 10M.

- M-base: candidate p95 run increment at 2M is at most baseline p50 run increment at 2M plus 64 MiB (the lazy path costs no more than resident input at the smallest size).
- W, per route family at 2M and 10M: candidate p50 wall at most 1.10 times baseline p50, and candidate p95 at most 1.15 times baseline p95. At 50M wall is recorded, with no bar.
- Every candidate trial under its ceiling.

**Frozen.** The reader options of Design 3a (including `INPUT_BUFFER_BYTES`), the ceilings, M1, M2, M-base, W, the workloads, sizes, trial counts and percentile method are frozen by the reviewed revision of this plan. A surviving mutant that can change chunk boundaries, the route or its reason, the input mode, materialization count, cleanup or evidence is build work: a new test kills it or dennis accepts an equivalence argument. ## Known issues (tech debt, not blockers)

- **Large pages.** With buffered reads (Design 3a) the probe's one-row-group 10M file stayed within read buffers, and section 10 bars it (R). `buffer_size` does not cap a single encoded page or a dictionary page, which the reader holds whole; guarantee 2 names it. The `input` block records `source_max_row_group_rows` so an operator can see the layout. The platform's B5 prices a whole-row-group envelope for its own reader, which is more conservative; the two are consistent (a smaller engine footprint inside a larger platform price).
- **Footer statistics required for integer and bucketize columns.** A file written without statistics declines auto-chunk for a table with such columns (guarantee 1's exception). It runs correctly, resident.
- **Parquet only.** `LazySource` is a local Parquet handle; CSV and fixed-width sources stay resident in the engine (the platform reads them with its own bounded reader).
- **Who benefits today.** `run_pipeline_isolated` (whose only in-repo caller is the routing probe) and library callers. The platform worker and the CLI keep resident inputs until B6c or B4.
- **Vault memory** is unbounded in distinct values, as B6a records; guarantee 2 excludes it.
- **Zero-row lazy sources.** Zero-row files at a forced threshold of zero are unspecified: `InputChunks.first` can be `None`, while the lane needs a first table for its schema rule. Zero-row lazy jobs remain resident until explicit parity coverage is added (a zero-row lazy table is never a route or split candidate).
- **Guarantee 4's wording.** A lazy table is resolved early only when it is not retained as a route or split candidate; a large routed job with no sink is intentionally retained lazy until output mode is decided, then materialized once (guarantee 3).
- **Spill needs a sink that names a place.** A third-party streaming sink without `spill_parent` fails a run whose schema hold-back must spill (Design 4a), where B6a would have used `TMPDIR`. Only oracle-route columns outside B1's schema rule that stay all-null across many chunks reach that path.
- **Driver read-back.** `run_pipeline_isolated`'s parent still reads every staged table back (`_isolated_run.py:575-578`), as B6a records.
- **Decode threads follow `native_threads` coarsely.** A job with `native_threads > 1` lets pyarrow decode on its own CPU pool (sized to the host), not on exactly `native_threads` threads.
- **A source changed in place after the footer check.** The footer comparison catches a changed row count or schema before the first chunk, and the row-count check at the end catches a short or long read; a same-shape rewrite during the read is not detected. Callers stage inputs they own (the isolated worker reads its own staging copies).
