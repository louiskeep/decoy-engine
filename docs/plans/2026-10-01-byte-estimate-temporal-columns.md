## Problem

With the default `use_byte_estimate_routing=True`, `run_pipeline` raises `AttributeError: 'datetime.date' object has no attribute 'encode'` for a mask table with a date column. Row count does not matter: a 3-row resident table crashes. `use_byte_estimate_routing=False` runs the same jobs fine.

When it triggers (probed on main `25710b5a`, 3-row tables, `bet2/trigger_probe*.out`). The full-frame byte estimate is computed inside `admission_signals` before the route is decided, whether or not the router will read it. With byte-estimate on, it runs over every column of every mask-kind table in two job shapes:

- No mask table declares `transforms`: always. This holds for configured columns (masked or passthrough) and for columns absent from the config alike; for `execution_mode` `auto`, `full_frame`, `sequential` and `out_of_core`; with `auto_chunk=False`; with `use_probe_routing=False`; with or without relationships; and in generate+mask jobs (the generate tables are skipped, the mask tables are still priced).
- Some mask table declares `transforms`: only when `execution_mode="auto"`, the job has relationships, every table is mask-kind and every transform-bearing table is resident (prepared). The prepared tables then go through `table_size_spec_from_table`, which does not crash; the untransformed mask tables in the same job still go through the profile adapter and do crash (probe S: FK job, transform on the parent, date column on the child).

Which columns crash depends on the source. A caller-passed resident `pa.Table` crashes on every type in the table below whose profile label is outside `_FIXED_WIDTH_DTYPE_BYTES` (the sampler is reached). A lazy file source has no sample, so `object`-label columns (date, time, decimal, binary) are UNPRICEABLE and do not crash; the lazy crash is the `ValueError` for labels the table does not list (tz timestamps, non-ns durations, float16, category). Generate-only jobs and jobs with no mask table never call the estimator.

Trace: `execution/_pipeline.py:441` -> `_pipeline_routing_signals.py:553` (`routing_signals`) -> `_transforms_admission.py:312` (`admission_signals`) -> `_pipeline_routing_signals.py:338` (`byte_estimate_full_frame_fits`) -> `_mem_estimate_schema.table_size_spec_from_profile` -> `sample_average_string_bytes` (`len(v.as_py().encode("utf-8"))`).

Root cause. `table_size_spec_from_profile` decides a column's width class from `ColumnProfile.dtype`, which is the pandas dtype label (`canonical_dtype_label`). It treats every label not in `_FIXED_WIDTH_DTYPE_BYTES` as a string and samples it. pandas reports many non-string Arrow types as `object` or as a label the table does not list, so they reach the string sampler or the `ColumnSizeSpec` "unrecognized dtype" `ValueError`. The defect is the binary split "numpy fixed label, else string". The 2026-09 nullable-extension fix (`boolean`/`Int64`/`Float64` added to the table) patched one instance of the same class by adding labels; adding more labels would only move the crash to the next type.

The catalogue probe shows the scope is wider than temporal types. Through `run_pipeline` with byte-estimate on, 27 catalogue types crash today (all run with byte-estimate off):

| Profile label | Arrow types | Failure |
|---|---|---|
| `object` | date32, date64, time32[s], time32[ms], time64[us] | `AttributeError` in the sampler |
| `datetime64[ns, <tz>]` | timestamp s/ms/us/ns with tz | sampler (resident) or `ValueError` unrecognized dtype (lazy) |
| `timedelta64[s/ms/us]` | duration s/ms/us | same |
| `float16` | halffloat | same |
| `object` | decimal32/64/128/256, binary, large_binary, binary_view, fixed_size_binary, uuid (ext), bool with nulls | `AttributeError` in the sampler |
| `object` | string_view with nulls | `ArrowNotImplementedError` (`drop_null` has no view kernel) |
| `category` | dictionary of string / large_string / binary | `ValueError` unrecognized dtype |

Naive timestamps, `duration[ns]`, ints, floats, bool without nulls, string, large_string, json (ext), bool8, opaque, null type and dictionary of int work today. time64[ns] and the nested types are refused earlier by the profiler (separate issue, see Known issues).

The prepared-table adapter `table_size_spec_from_table` already reads Arrow types (`_arrow_size_label`) and does not crash, but it prices on Arrow storage width, which undercounts the resident form the estimator models (below).

## Owner direction

Cam, 2026-10-01: "bound memory, don't predict pandas." The roadmap item is §RUST-PATH-ESTIMATOR in `decoy-platform/docs/ROADMAP.md` (PR #80). This fix exists to stop the crash and to never underestimate. It does not try to model the pandas footprint precisely. Where a column's representation is wrapped (dictionary, run-end encoding, extension) or otherwise uncertain, the plan takes the simplest conservative rule: price it as nullable, or mark it UNPRICEABLE. Those choices only raise estimates, and they are intentionally coarse. A reviewer who finds a case where they over-price has found the intended behavior, not a defect; a case where they under-price or crash is a defect.

UNPRICEABLE is the safe choice for an uncertain string column, safer than a fixed string ceiling. A column marked UNPRICEABLE makes `byte_estimate_full_frame_fits` return `None`, which `decide_execution_route` treats as "does not fit" (no estimate-admitted full_frame). The job then either routes bounded or goes through the existing probe recovery, which admits full_frame only from a measured run, never from the estimate (§3.5, `_pipeline_routing_signals.py` ~254 and ~293). Nothing in that path calls the sampler, so it cannot crash on the column. A fixed per-cell string ceiling would not be a true upper bound (strings have no length limit) and could admit an unsafe full_frame, so this plan does not use one.

## Guarantee and non-goals

Guarantee: with default knobs, the byte estimate never raises for a column whose type the profiler accepts. Every column is either priced from a fixed per-cell cost, priced from a sampled byte length (string/binary family only), or marked UNPRICEABLE (routes bounded, the existing §3.5 rule). String-column estimates and every route decision that worked before stay identical, except the intended changes listed under Design.

Non-goals: the profiler refusals (time64[ns] with sub-microsecond values, nested types), the advisory disk preflight (`out_of_core/_spill_estimate.py`), generate-table pricing, any change to the K constants or the route rules.

## Design

### What the estimator prices

The estimator's basis is the resident pandas form a full_frame run materializes: a string cell costs its payload plus a 57-byte pointer and `str` header (`_STR_OBJECT_OVERHEAD_BYTES`). Arrow storage width is the wrong number for types pandas holds as Python objects. Measured with `to_pandas()` defaults (pyarrow 24, CPython 3.10, `resident_probe.out`):

| Arrow type | Arrow bytes/row | pandas dtype | Resident bytes/row |
|---|---|---|---|
| date32 / date64 | 4 / 8 | object (`datetime.date`) | 40 |
| time32 / time64 | 4 / 8 | object (`datetime.time`) | 48 |
| decimal128 / decimal256 | 16 / 32 | object (`Decimal`) | 112 |
| timestamp (any unit, tz or naive) | 8 | datetime64 | 8 |
| duration (any unit) | 8 | timedelta64 | 8 |
| int8 with nulls | 1 | float64 | 8 |

So "price as fixed width" here means a fixed per-cell cost read off the Arrow type with no sampling, and that cost is the resident cost: numpy itemsize for types pandas holds natively, pointer plus a measured Python object size for types it holds as objects. Pricing date32 at 4 bytes would undercount the full_frame peak by 10x, the unsafe direction. The Arrow storage widths from the bug report (date32 4, date64 8, time32 4, time64 8, timestamp 8, duration 8, decimal by byte width) stay recorded in the classifier table for reference and for the disk-width follow-up.

### One classifier, keyed on the Arrow type

New module `execution/_mem_estimate_arrow.py` (keeps `_mem_estimate_schema.py` and `_mem_estimate.py` under the 600-LOC cap) with one function:

`classify_column(arrow_type: pa.DataType, *, has_nulls: bool) -> ArrowSizeClass`

`ArrowSizeClass` is one of: `Fixed(label)` (a label in `_FIXED_WIDTH_DTYPE_BYTES`), `Declared(width_bytes)` (variable-width `object` with an exact known payload, no sampling), `Sampled(decoded_type)` (string or binary family, sampled), `Unpriceable(reason)`. Rules, applied after unwrapping extension types to their storage type, dictionary to its value type and run_end_encoded to its value type (for the string and binary family the wrapper also decides `Sampled` versus `Unpriceable`, below):

- int/uint: itemsize label (`int8`..`uint64`); with nulls `float64` (pandas widens to float64; this is today's profile label, so the estimate is unchanged).
- bool: `bool` (1); with nulls a new label `pyobject[bool]` = 8 (object array of the `True`/`False`/`None` singletons, pointer only).
- float16/32/64: new label `float16` = 2, `float32`, `float64`.
- timestamp, any unit, with or without tz: `datetime64[ns]` (8). duration, any unit: `timedelta64[ns]` (8).
- date32, date64: new label `pyobject[date]` = 40. time32, time64: new label `pyobject[time]` = 48. decimal32/64/128/256: new label `pyobject[decimal]` = 112. Each is `8 + sys.getsizeof(<value>)`, measured; `Decimal` measured 104 at 7, 18, 38 and 76 digits.
- string, large_string, binary, large_binary, string_view, binary_view: `Sampled` only when the column's representation is one of these forms, each at most one normalization step from a plain type: a plain `string`/`large_string`/`binary`/`large_binary`; a view type (one cast); an extension type whose storage is one of the four plain types (one unwrap); a dictionary whose value type is one of the four plain types (one decode). Every other string or binary representation is `Unpriceable("<arrow type>: wrapped string representation, not sampled")`, with no sampling and no decode. That covers a dictionary of a view type (`dictionary<string_view>` has no `array_take` kernel on pyarrow 24 or 25, so `dictionary_decode` and `cast` both raise, `bet3/wrap_probe.out`), any run-end-encoded string or binary, a dictionary of an extension type, and an extension over a view, dictionary or run-end type. A `bytes` cell costs payload + 41, so pricing binary as a string at payload + 57 over-prices by 16 bytes, the safe direction.
- fixed_size_binary[n] (and uuid through its `fixed_size_binary(16)` storage): `Declared(n)`. The payload is exact from the type; same 16-byte safe over-price.
- dictionary: classify the value type, with `has_nulls` forced as below. A dictionary of a plain string or binary type samples its decoded values. This over-prices a resident `category` column, which is the safe direction, and the masked output is decoded anyway.
- run_end_encoded: classify the value type, with `has_nulls` forced as below; a run-end-encoded string or binary column is `Unpriceable` (above).
- null type: `Declared(0.0)` (today's value: profile `object`, sampled width 0.0).
- list, large_list, list_view, large_list_view, fixed_size_list (incl. fixed_shape_tensor storage), struct, map, dense/sparse union, month_day_nano_interval, and any type not named above: `Unpriceable("<arrow type> has no resident-size model")`. That is an explicit, documented estimate (route bounded), never a crash and never a guess.

New labels go into `_FIXED_WIDTH_DTYPE_BYTES` with a comment giving the measurement. `_VARIABLE_WIDTH_DTYPES` is unchanged.

### Sampler

`sample_average_string_bytes` becomes vectorized and type-checked. It only accepts the `Sampled` representations listed above and applies exactly one normalization step, chosen from the array's top-level type, to an `Array` or a `ChunkedArray`:

- plain `string`/`large_string`/`binary`/`large_binary`: none.
- `string_view`/`binary_view`: `cast` to `large_string`/`large_binary` (works on Array and ChunkedArray, `bet3/wrap_probe.out`).
- extension with plain storage: `arr.storage` for a `pa.ExtensionArray`; a `pa.ChunkedArray` has no `.storage`, so rebuild it as `pa.chunked_array([c.storage for c in arr.chunks], type=arr.type.storage_type)`, zero-copy. `pc.binary_length` has no kernel for `extension<arrow.json>` (`ArrowNotImplementedError`, `bet2/ext_probe.out`), so passing the original array with only the type rewritten fails AT5's JSON pin.
- dictionary with plain value type: `dictionary_decode()` for an Array, `cast(arr.type.value_type)` for a ChunkedArray.

The result must be one of the four plain types; then `pc.sum(pc.binary_length(arr)) / (len - null_count)`. `binary_length` is the UTF-8 byte length for string arrays (parity checked on non-ASCII input in `misc_probe.out`), so string values are unchanged. Any other input, including a representation the classifier marks `Unpriceable` and any array that would need a second step, raises `TypeError` naming the Arrow type before any Arrow kernel runs. The classifier never sends such a column here, so the `TypeError` is a guard against a future misroute, not a path a job can reach. There is no recursive normalization: a representation that would need one is UNPRICEABLE by the classifier, which is simpler and cannot under-price. This also removes the per-value Python loop, which today runs over every resident row.

### Where the Arrow type comes from

`has_nulls` decides 1 byte versus 8 for int8 and bool (and 2 or 4 versus 8 for int16/int32 and the unsigned types), so it must never come from a sample. `ColumnProfile.null_count` is sample-derived on both paths: `profile_source` profiles the configured file source with `residency="bounded"` and `sample_rows=10_000` even when the caller passes a resident table. Probed (`bet2/null_probe.out`): a 50,000-row Parquet file with int8 and bool columns whose nulls start at row 30,000 profiles as `int8` / `bool` with `null_count=0`, while pandas holds them as `float64` (8.0 bytes/row) and `object`. Today both the resident and the lazy path price those columns at 1 byte. That is a pre-existing underprice this fix closes; it is not new behavior.

- Resident table: the resident column's own Arrow type. For a column whose top-level type is not wrapped, `has_nulls = resident_column.null_count > 0`. `pa.Table.column(...).null_count` is exact over the whole resident table for such a column (metadata on the buffers, no scan, no sample), so it is the authority; the profile's `null_count` is not consulted. For a column whose top-level type is run_end_encoded, dictionary or an extension type, `has_nulls = True`, with no decode and no inspection of children. The outer `null_count` can hide logical nulls: a run-end-encoded int8 or bool array with a null run reports `null_count == 0` (the null is in its values child), and pandas still materializes it as `float64` / `object` with 3 nulls; a dictionary whose values hold a null reports `null_count == 0` too (`bet3/wrap_probe.out`, pyarrow 24 and 25). Forcing `True` is coarser than walking the children, and it only matters for int/uint below 64 bits and bool, where it can only raise the price. Per the Owner direction, no metadata-walking helper is added. The resident type also wins over the profile label when they disagree (it is what actually gets materialized). This removes the documented workaround at `tests/physical/test_unified_slice_input_formats.py` ~625.
- Lazy table (`LazySource`): the Arrow type from the footer schema through the `LazySource.schema` property (a property, not a method; metadata only, no row read). Nullability is proven from metadata or assumed:
  1. Exact count from statistics: read the footer metadata (`pq.read_metadata(source.path)`, footer only). If every row group has a statistics object for the column with `has_null_count` true, `has_nulls` is the sum of those counts > 0. A file with zero row groups has no nulls.
  2. Otherwise, the footer field's `nullable` flag: `nullable=False` (Parquet `REQUIRED`) proves no nulls; `nullable=True` means `has_nulls=True`.
  3. `has_nulls=False` is passed only when step 1 counts zero or step 2 reads `nullable=False`. A positive profile `null_count` also forces `True` (cheap, and it can only widen).
  Parquet statistics and the `REQUIRED` flag describe the logical column, so they count as metadata that proves a lazy column null-free even when the footer schema reports a dictionary or extension type. Parquet has no run-end encoding, so a lazy column is never run-end encoded.
  The lookup lives on `LazySource` as a metadata-only method (`column_null_counts() -> dict[str, int | None]`, `None` when any row group lacks the count), so `_readers.py` stays the one module that opens Parquet footers. Top-level columns map to the Parquet leaf with the same path; anything nested is already UNPRICEABLE and skips the lookup. pyarrow writes `nullable=True` unless the schema says otherwise, so a file with no statistics prices int8 and bool at 8 bytes. That is the conservative direction and is listed as intended change 4. `Sampled` columns stay UNPRICEABLE, as today.
- No Arrow type at all (table absent from `caller_sources`, for example a loader-backed table): labels whose representation can carry a null mask are priced conservatively. Map `int8`, `int16`, `int32`, `uint8`, `uint16`, `uint32`, `Int8`, `Int16`, `Int32`, `UInt8`, `UInt16` and `UInt32` to `float64`; map both `bool` and `boolean` to `pyobject[bool]`. Do not use the sampled `null_count` to narrow them. Any other label is kept only when it is in `_FIXED_WIDTH_DTYPE_BYTES`, else UNPRICEABLE. Measured (`bet3/wrap_probe.out`): pandas `Int8`, `UInt16` and `boolean` arrays cost 2, 3 and 2 bytes per row, which revision 2 priced at 1, 2 and 1; the mapped prices are 8. These fallback changes only increase estimates. Never sample without a type, never raise on an unknown label.

### Intended estimate changes (the only ones)

1. Types that crashed now get an estimate (the 27 types above). No previous value to preserve.
2. Lazy tables: date, time, decimal, bool-with-nulls and fixed_size_binary columns that were UNPRICEABLE (profile label `object`, no sample) become priced from the footer type. Lazy string and binary columns stay UNPRICEABLE. A lazy table whose only unpriceable columns were these can now route by byte estimate instead of always bounded. This is a routing change for a path that worked; it is the correct result of the root-cause fix, and AT6 pins it. If Cam wants zero lazy-route movement, the fallback is to keep `Fixed` results on lazy tables UNPRICEABLE for object-resident labels only; that keeps two code paths and is not recommended.
3. Prepared tables (`table_size_spec_from_table`): date32 4 -> 40, date64 8 -> 40, time 4/8 -> 48, int-with-nulls storage width -> 8, bool-with-nulls 1 -> 8; binary, decimal, dictionary, view and extension columns go from UNPRICEABLE to priced. All increases or unpriceable-to-priced; none lowers an estimate. For the pin table below, prepared `raw_data_bytes` moves 27,790 -> 29,190, equal to the profile adapter's figure.
4. Nullability no longer comes from the profile sample. An int8/int16/int32/unsigned or bool column the sample saw as null-free now prices at 8 bytes when the resident column has a null anywhere, or, on a lazy table, when the footer statistics count a null or cannot prove none and the field is `nullable=True`. On the pyarrow writer's defaults (statistics on, `nullable=True`) a lazy column with complete statistics and no nulls keeps its narrow price. Every such move is an increase. It can move a job that fit full_frame by a sampled undercount onto a bounded route; that is the fix for the HIGH gate finding, and AT11/AT12 pin it. int64, uint64 and float columns are unaffected (their nullable form is also 8 bytes).
5. Wrapped and uncertain representations (revision 3). A resident run-end-encoded, dictionary or extension column of int/uint below 64 bits or bool prices as nullable (8 bytes) regardless of its outer `null_count`. A dictionary of a view type, a run-end-encoded string or binary column, and any other string representation more than one normalization step from a plain type are UNPRICEABLE. With no Arrow type, the pandas nullable labels `Int8`..`UInt32` and `boolean` price at 8 bytes. Each is an increase or a priced-to-UNPRICEABLE move, never a decrease, and each was either a crash or an under-price before. They are coarse on purpose (Owner direction); a later estimator under §RUST-PATH-ESTIMATOR replaces this model rather than refining it.

## Known issues (not fixed here)

- time64[ns] with non-microsecond values is refused by the profiler (`profile/_readers.py:175`, `ArrowInvalid: Value 7 has non-zero nanoseconds`) under both flag values. Separate bug, separate plan.
- Nested types (list family, struct, map, union) and fixed_shape_tensor are refused by the pandas profile walk before routing. This fix classifies them UNPRICEABLE so they are safe if the profiler ever admits them.
- The full-frame byte estimate is computed for every job with a mask table and no transforms, at any row count and under any `execution_mode` (see Problem), but only relationship-bearing pure-mask jobs under `auto` read it (`admission_signals` docstring). An estimator defect therefore kills jobs that never use the estimate. Making the signals lazy is a worthwhile follow-up, but it would also hide estimator defects from single-table tests, so it does not replace this fix.
- `_spill_estimate._source_disk_width_bytes` prices date, time, tz and non-ns duration columns at `max_length` or the free-text ceiling. Advisory only (warns, never rejects) and over-estimates; a follow-up can reuse `classify_column` with the Arrow storage widths recorded in it.
- Generate tables: `table_size_spec_from_generate_table` is not wired into routing yet. When it is, typed generators such as `windowed_date` should price through the same classifier on their declared output Arrow type instead of staying UNPRICEABLE.
- The string model (UTF-8 length + 57) is exact for ASCII but not a per-cell upper bound for other text. CPython stores a `str` at 1, 2 or 4 bytes per character chosen by its widest character, with a larger header for non-ASCII (PEP 393). Measured (`bet2/ext_probe.out`, `sys.getsizeof + 8`, which matches `memory_usage(deep=True)`): one emoji 61 estimated vs 88 actual, `"é"` 59 vs 82, one CJK character followed by 100 ASCII characters 160 vs 284, one emoji followed by 100 ASCII characters 161 vs 488. All-Latin-1 or all-CJK text over-prices (`"é" * 100`: 257 vs 181). Not changed here: string estimates are pinned by AT5 and changing them moves routes this fix promises to keep; the measured route slope and the 1.3x margin sit on top of this model and may absorb part of the gap, but nothing guarantees it. A column dominated by ASCII text with one wider character per value can be under-priced by about 3x (approaching 4x as values grow, since one astral character makes every character 4 bytes). A follow-up should price from the widest code point per value (computable in Arrow without a Python loop), with its own route-movement review.
- The `pyobject[*]` costs are CPython object sizes measured on 3.10 x86-64. The test for each label computes `8 + sys.getsizeof(value)` at test time and asserts the table value is not below it, so an interpreter change that grows an object fails the suite instead of silently under-pricing.
