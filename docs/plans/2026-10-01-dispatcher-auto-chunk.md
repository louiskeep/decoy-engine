## Problem

`run_pipeline` already chunks large single-table mask jobs on its own ("auto-chunk", default on). The decision and the lane today:

- **When.** `_pipeline_chunk_route.decide_chunk_route` calls `_planner.classify_job` once (that one call also feeds the `explain_plan` stamp) and routes chunked when `auto_chunk` is true and the mode is `chunked`. The planner requires exactly one mask table, no generate tables, no FK relationships, the pandas substrate, scalar work only, every strategy passing `check_chunked_compatibility`, no `when:` predicate, no fpe join group, date_shift only with an explicit `date_format`, and, on the loaded source: a resident `pa.Table` (a `LazySource` is rejected by `lazy_source_rejection`), at least `auto_chunk_threshold_rows` rows (default `AUTO_CHUNK_THRESHOLD_ROWS_DEFAULT = 100_000`), chunk-stable dtypes (integers only when null-free; string, float, bool, temporal and null types), no extra loaded frames, and the bucketize, group_key, text_mask, code_set and bucket_perturb source gates.
- **Lane.** `_pipeline_generate_mask.run_generate_and_mask_steps` calls `_pipeline_route_exec.run_mask_chunked`, which slices the resident table into zero-copy `chunk_size_rows` slices (default `CHUNK_SIZE_ROWS_DEFAULT = 50_000`), drains the pandas oracle `_chunked.run_mask_pipeline_chunked`, and joins the chunks with `concat_masked_chunks` (strict, no type promotion except null-typed chunks to the agreed type) and `combine_chunks`.

So the lane choice runs backwards. Below the threshold, the default-on unified slice (`_unified_slice`, Task 4.5) runs eligible jobs on native kernels. Above it, `_unified_slice_admission.cheap_admission` declines because `route_chunked` is set, and the job runs chunk by chunk on pandas. The largest jobs take the slowest lane. B1 made `decoy_engine.run_mask_chunked` the production-shaped chunked entry point (benchmark runs R074 and R075 measured the dispatcher against the pandas oracle on a 1M-row table); nothing calls it yet. Auto-chunk also records only `mode: chunked`; nothing says which backend masked each column.

## Guarantee (pinned)

For every `run_pipeline` call:

1. **When is unchanged.** For the same inputs, `route_chunked`, the existing `quality_metrics["auto_chunk"]` keys (`mode`, `chunk_size_rows`, `threshold_rows`, `source_rows`, `chunk_count`, `reason`) and the `explain_plan` stamp are the same as today. B2 changes only the lane that executes a job already routed to chunked.
2. **Lane.** A routed table runs through `run_mask_chunked` (B1), which picks the native or the oracle route for the whole table. Three cases run today's lane (`run_mask_pipeline_chunked`, unchanged) instead: the kill switch `chunked_dispatcher_enabled=False`, the metadata-parity gate (a source schema carrying any schema metadata other than characterized pandas metadata; Design 3), and the type-parity gate (Design 3). All are recorded (guarantee 5).
3. **Output identity.** The routed output table equals the same call with `chunked_dispatcher_enabled=False`: same column names and order, Arrow types, field nullability, values (nulls and row order included) and schema metadata, checked with `Table.equals(other, check_metadata=True)`. This holds whichever lane and route ran, for any valid `native_threads`, and with or without the compiled companion. The routed output keeps equalling the forced full-frame run (`auto_chunk=False`) on values and types, as `tests/unit/execution/test_auto_chunk_routing.py` asserts today.
4. **Side channels.** Vault entries are the same pairs in the same order as today's lane. Row errors fail closed with `RowErrorsFailedError`, nothing quarantined, as today. The warnings tuple and `quality_metrics["code_set_corpora"]` equal today's.
5. **Evidence, never silent.** Every routed result carries `quality_metrics["auto_chunk"]["lane"]` (`dispatcher` or `legacy_oracle`), `["lane_reason"]` (`null` on the dispatcher lane), `["native_threads"]`, and `quality_metrics["chunked_route"]`: `native_admitted`, `reroute_reason`, and per configured column `column`, `strategy`, `planned_backend`, `executed_backend` and `calls`. A column planned for Rust that ran on pandas is visible together with the reason. The payload is JSON-safe and deterministic: two runs with the same inputs and companion state produce equal `quality_metrics`. Elapsed time lives in `ExecutionResult.timings` only.
6. **Threads.** `native_threads` is an `int` from 1 to 1024 inclusive (not `bool`), default 1. B2 validates 1 to 1024 on the `run_pipeline` surface itself: `require_positive_int` first, then an explicit rejection of values greater than 1024, both raising `ExecutionError(code="invalid_execution_knob")` with the other knobs, before profiling or dispatcher preflight. It reaches the compiled kernels on the dispatcher lane and changes no output byte.
7. **No mid-run fallback.** The lane and the route are fixed before the first chunk is masked. An error after that propagates with its existing type and code; nothing retries on another lane.
8. **Non-routed calls unchanged.** A call that does not route chunked never enters the new code: outputs and `quality_metrics` are byte-identical to today, including the all-default `quality_metrics == {}` golden contract, for any valid knob values of `native_threads` and `chunked_dispatcher_enabled`. Invalid values fail early under guarantee 6.

## Non-goals

Changing when auto-chunk triggers (planner gates, threshold, the `chunk_size_rows` default or its meaning); multi-table dispatch (B7); platform or CLI wiring (B3, B4), admission pricing for native cost and threads (B5), and release or artifact work (B3, B5 and the phase-boundary release); incremental output sinks or lazy batch input (B6a, B6b): the routed output is still fully materialized and concatenated; widening native admission (Phase C), including tables with unconfigured columns, which B1 vetoes to the oracle route (`uncovered_columns`); native admission for unconfigured passthrough columns is program slice B8, which reopens B1's admission contract and so stays out of B2; transforms on the chunked route (A8 keeps transform-bearing tables off it); changing `run_mask_chunked`, the oracle `run_mask_pipeline_chunked`, the unified slice, or `classify_job`; adaptive or byte-based chunk sizing; the Phase E 100M-row performance gate (B2 carries its own bounded merge benchmark, section 11); showing the lane in `explain_plan`, which stays a static classification.

## Design

### 1. Where it plugs in

`_pipeline_route_exec.py` is at 597 lines against the 600-line cap, so the lane logic goes in a new module `execution/_pipeline_auto_chunk.py`:

```
run_auto_chunk(config, source, *, table, engine_version, registry, adapter, vault_writer,
    chunk_size_rows, key_provider, native_threads, dispatcher_enabled)
    -> tuple[outputs, timings, boundary_conversion_ms, warnings, quality_metrics]
```

`_pipeline_route_exec.run_mask_chunked` keeps its name, its five-part return and its current parameters, gains `native_threads: int = 1` and `dispatcher_enabled: bool = True`, and becomes a delegate to `run_auto_chunk`. Existing imports (`tests/physical/test_characterization_chunked.py`, `physical/drivers/_chunked.ResidentChunkedAggregatorAdapter`) keep working; the adapter forwards the two new parameters, and `tests/physical/test_lossless_forwarding.py` is extended for them.

`run_pipeline` gains two keyword arguments next to the auto-chunk knobs: `native_threads: int = 1` and `chunked_dispatcher_enabled: bool = True`, validated in the existing fail-early block before profiling or dispatcher preflight (`native_threads` with `require_positive_int`, then an explicit `native_threads > 1024` rejection with `ExecutionError(code="invalid_execution_knob")`, since `require_positive_int` alone accepts 1025; `chunked_dispatcher_enabled` with `require_bool`) and threaded through `run_generate_and_mask_steps` to the routed call. They are runtime resource knobs like `auto_chunk`, never config fields, so they stay out of `pipeline_config_hash`. `_pipeline.py` sits at its exact ratchet in `tests/sentry/test_module_size.py`: 635 lines on this base, 679 on a base that contains A8 (`feat/engine-owned-transforms`). B2 builds against whichever base it is on and adds no net lines there: the builder keeps the ratchet by moving lines out (for example the auto-chunk paragraph of the docstring into `_pipeline_routing`'s module docstring, which it already points to), never by raising or loosening the ratchet. `_pipeline_auto_chunk.py` stays under the 600-line goal and must not exceed 700 lines.

### 2. Lane selection (once per routed table, before any chunk is masked)

In order:

1. `dispatcher_enabled` is false: legacy lane, `lane_reason = "dispatcher_disabled"`.
2. The metadata-parity and type-parity gates (section 3) find anything they cannot reconcile: legacy lane. `lane_reason` lists every finding, sorted and joined with `; `: a `legacy_metadata_parity:pandas_<kind>` finding for each uncharacterized part of `b"pandas"` schema metadata (section 3), `legacy_metadata_parity:other` when the schema has any other schema-level key, and `legacy_type_parity:<column>:<type>` for each column the type gate refuses. Characterized pandas metadata produces no finding.
3. Otherwise: dispatcher lane.

The gates read only the config and the source schema. Every chunk is a slice of one resident table, so the source schema is exactly chunk 0's Arrow schema, the one B1 rev5 admits from. The legacy lane is exactly today's code path (`run_mask_pipeline_chunked` plus `concat_masked_chunks`), so its output is today's by construction.

### 3. Type parity with today's lane

B1's schema rule (`native/_chunked_schema_rule.py`) differs from today's lane in three places, because today every chunk goes through pandas (`to_pandas`, then `Table.from_pandas(..., preserve_index=False)` in `_pandas_adapter.py` ~326):

- Passthrough columns (configured passthrough without `when:`, and unconfigured columns kept under the passthrough policy) are taken from the source Arrow column, with the source field's type, nullability and field metadata. Today they carry the pandas round-trip type, `nullable=True` and no field metadata.
- String-output columns (hash, truncate, redact with a string `redact_with`) are cast from `null` to `string` per chunk. Today a chunk whose output column is all null comes back `null`; `concat_masked_chunks` then casts it to `string`, except when every chunk is null, where the output stays `null`.
- No chunk carries schema metadata. Today the output carries the first chunk's `pandas` metadata, unless the first chunk needed a cast in `concat_masked_chunks` (a null-typed column that another chunk types), in which case it carries none: `c.cast(target)` uses the metadata-free target schema, and `pa.concat_tables` keeps the first table's schema.

Probes on 2026-10-01 (pyarrow 24.0.0, pandas 2.3.3; `Table.from_pandas(t.to_pandas(), preserve_index=False)` on two-row columns) found these round-trip changes among planner-admitted types:

- Type changes, values kept: `large_string` to `string`; `time32[s]` and `time32[ms]` to `time64[us]`; `date64[ms]` to `date32[day]` when values are whole days.
- Value loss: `date64[ms]` with sub-day milliseconds becomes `date32[day]` with the sub-day part dropped.
- Value-dependent type or error: `time64[ns]` becomes `time64[us]` when every value is microsecond-aligned, and `to_pandas()` raises `ArrowInvalid` ("has non-zero nanoseconds") when any value is not. Revision 1 wrongly listed time64 as keeping its type; only `time64[us]` does.
- Kept type and values: `string`, float32/64, bool, null-free int8 through uint64 (including the uint64 maximum), date32, `time64[us]`, timestamp in `s`, `ms` with `UTC`, `us`, and `ns` with a non-UTC zone, duration in `s` and `ns`, and `null`.

A source built by `Table.from_pandas` from a frame with extension dtypes (pandas `StringDtype`, nullable `Int8`, `boolean`) or `DataFrame.attrs` carries `b"pandas"` schema metadata recording them (`numpy_type: "string"`, `"Int8"`, `"boolean"`, `"attributes"`). Today's lane restores those dtypes in `to_pandas()` and writes the same metadata back. B1 strips schema metadata from every chunk, and a reconstruction from the stripped output records `object`, `int8` and `bool` instead: equal values and types, but `Table.equals(..., check_metadata=True)` is false (reproduced by Codex and again on 2026-10-01). This is the metadata-parity gate's reason to exist.

The probes are pointers, not the specification; acceptance test 0 characterizes today's actual lane, including errors.

From that characterization the builder writes one function and one table in `_pipeline_auto_chunk.py`:

- `legacy_chunk_type(column_kind, source_type, output_all_null)`: the Arrow type today's lane gives column `c` in one chunk, where `column_kind` is passthrough, string-output, or natively masked faker. Columns that ran on B1's oracle route under a strategy outside the schema rule already carry the oracle's per-chunk type and need no mapping.
- `LEGACY_PASSTHROUGH_CAST`: source types whose today-type is reached from the source value by `pyarrow.compute.cast(..., safe=True)` for every value. Expected entries: `large_string` to `string`, and `time32` (any unit) to `time64[us]`.

A passthrough source type whose round trip changes the type and is not in `LEGACY_PASSTHROUGH_CAST` sends the table to the legacy lane (section 2, step 2). Expected: `date64`, because pandas truncates sub-day milliseconds while a safe cast would raise. Narrower, never wider: an admitted type the characterization did not cover also goes to the legacy lane.

`time64[ns]` is legacy-only for any column, configured or unconfigured, whatever its strategy: today's lane converts the whole chunk with `to_pandas()`, so one non-aligned value makes today's lane raise while the dispatcher's Arrow passthrough would succeed, and today's type depends on the values. The gate is schema-only and does not inspect values, so it cannot tell the two apart. Reason: `legacy_type_parity:<column>:time64[ns]`.

**Metadata parity.** Every normal pandas-authored Parquet file carries `b"pandas"` schema metadata through a Parquet write and read, so gating all of it would keep most pandas-origin inputs off the dispatcher. B2 admits a conservative characterized subset. The dispatcher lane never copies producer metadata: for an admitted source it regenerates metadata from the reconciled first chunk with the installed pandas and pyarrow (step 4 below), as today's lane does. That is correct exactly when today's lane gives the same output for the source with and without its schema metadata, which is what the characterization checks.

The source schema's metadata is admitted when it is absent or empty, or when all of these hold. Each failed condition adds the named finding, and the table takes the legacy lane:

- The only schema-level key is `b"pandas"`. Any other key: `legacy_metadata_parity:other`.
- The value parses as a JSON object. Otherwise `legacy_metadata_parity:pandas_malformed` is the only pandas finding; the gate never raises, and the legacy lane then fails as today's lane does (`JSONDecodeError` from `to_pandas()` in the probe).
- `attributes` is absent or `{}`. Otherwise `legacy_metadata_parity:pandas_attributes` (non-empty `DataFrame.attrs`).
- `index_columns` is `[]` or exactly one `{"kind": "range", "name": null, "start": <int>, "stop": <int>, "step": <int>}` entry with integer bounds and a non-zero step (any start, stop and step otherwise). Otherwise `legacy_metadata_parity:pandas_index`: a stored index column, a named RangeIndex, or a MultiIndex.
- `column_indexes` is `[]` or exactly one entry with `name: null`, `pandas_type: "unicode"`, `numpy_type: "object"` and metadata `null` or `{"encoding": "UTF-8"}`. Otherwise `legacy_metadata_parity:pandas_column_index`.
- `columns` has exactly one entry per source field, with keys exactly `name`, `field_name`, `pandas_type`, `numpy_type`, `metadata`, and `name` equal to `field_name` and to the field's name. Each entry's (`pandas_type`, `numpy_type`) pair is in the admitted list below, and its `metadata` is `null`, except `datetimetz`, where it is exactly `{"timezone": <string>}`. The entry must also agree with the Arrow field it describes: the field's type is the one `Table.from_pandas` produces for that pair (same integer or float width, `bool`, `string`, `date32`, `duration[ns]`, a timezone-naive timestamp of the pair's unit for `datetime`, and for `datetimetz` a timezone-aware timestamp whose timezone exactly equals the metadata's `timezone`). Metadata kept while a caller replaced or cast the column can disagree with the field, and today's lane then follows the metadata (UTC metadata on an `America/New_York` field comes out as `timestamp[ns, UTC]`), so a mismatch gives `legacy_metadata_parity:pandas_column:<column>`. An entry whose `numpy_type` is a pandas extension dtype name (`string`, `Int*`, `UInt*`, `Float*`, `boolean`, `category`, or any other non-NumPy name) gives `legacy_metadata_parity:pandas_extension_dtype:<column>`; any other failure (unknown pair, unknown column metadata, extra or missing keys, a name mismatch, a missing or extra entry) gives `legacy_metadata_parity:pandas_column:<column>`.
- `creator` and `pandas_version` are not checked: today's lane regenerates them from the installed versions, and the probe shows a stale `pandas_version` gives byte-identical output.

Admitted (`pandas_type`, `numpy_type`) pairs, all NumPy-backed: (`unicode`, `object`); each of `int8` through `int64` and `uint8` through `uint64` with the same `numpy_type`; (`float32`, `float32`), (`float64`, `float64`); (`bool`, `bool`); (`datetime`, `datetime64[ms]`), (`datetime`, `datetime64[us]`), (`datetime`, `datetime64[ns]`); (`datetimetz`, `datetime64[ns]`); (`object`, `timedelta64[ns]`), which is how pyarrow 24 records a NumPy timedelta column; (`date`, `object`). An all-null object column (`pandas_type: "empty"`) and every other pair are not admitted. The planner's own type gates still apply on top; the list widens nothing the planner refuses.

Probe on 2026-10-01 (pyarrow 24.0.0, pandas 2.3.3; `DataFrame.to_parquet` then `pq.read_table`, 60 rows routed through today's auto-chunk lane in 16-row chunks with hash, redact and truncate columns plus the probed column as passthrough; script and output in the session scratchpad, `b2_pandas_meta_probe.py`). For every admitted shape the output with the producer's metadata equalled, with `check_metadata=True`, the output for the same source with schema metadata removed, and also equalled `Table.from_pandas(chunk0.to_pandas(), preserve_index=False).schema.metadata` regenerated from the metadata-free first output chunk. Shapes probed: object strings with and without nulls, int8, int16, int32, int64, uint8, uint16, uint32, uint64 (including the type maximum), float32, float64 with NaN, bool, `datetime64` in `ns` (with and without NaT), `us`, `ms`, and `s` (Parquet stores it as `timestamp[ms]`), tz-aware `ns` in UTC and `America/New_York`, `timedelta64[ns]`, `datetime.date` objects, all of these together, `to_parquet(index=False)`, and RangeIndexes with start 5 and with step 2. Every admitted shape matched; none moved to the gated list. For the gated shapes:

- StringDtype, nullable `Int8`, `Int64`, `Float64` and `boolean`: values and types equal, metadata bytes differ (`numpy_type` is the extension name in today's output). Must stay legacy.
- Non-empty `attrs`: metadata bytes differ (`attributes` kept today). Must stay legacy.
- A non-range index stored as `__index_level_0__`: today's lane restores it as the index and drops it from the output, so even the columns differ. Must stay legacy.
- Malformed JSON: today's lane raises `JSONDecodeError`. Stays legacy so the failure is today's.
- A named RangeIndex, a named columns index, non-null column `metadata`, and a `b"pandas"` key next to another key all gave identical output today. They stay gated in B2 because they are not part of the conservative subset; admitting them later needs only a characterization change.

A source built in memory by `Table.from_pandas` takes the same rule; acceptance test 3a covers both origins. Field-level metadata does not trigger the gate: today's lane drops it and reconciliation step 3 drops it too.

Reconciliation after the dispatcher lane drains (`run_auto_chunk`, before returning):

1. `concat_masked_chunks` joins the chunks as today.
2. Each column gets its whole-output today-type: `null` when `legacy_chunk_type` is `null` for every chunk, otherwise the single non-null type the chunks agree on (the same rule `concat_masked_chunks` applies). Passthrough casts use `LEGACY_PASSTHROUGH_CAST` with `safe=True`; a failed cast raises `ExecutionError(code="chunked_schema_mismatch")` naming table, column and both types. Casting an all-null `string` column to `null` is lossless.
3. Every field becomes `nullable=True` with no field metadata, as `Table.from_pandas` produces.
4. Schema metadata (for a source whose schema metadata is absent, empty, or admitted pandas metadata; nothing from the source's metadata is copied): if chunk 0 has no column whose `legacy_chunk_type` is `null` while the whole-output type is not, attach `pa.Table.from_pandas(first.to_pandas(), preserve_index=False).schema.metadata`, where `first` is chunk 0 cast to its per-chunk today-types; otherwise attach none. This costs one pandas conversion of one chunk per job.

Acceptance test 3 checks the result against today's lane with `check_metadata=True`. A fixture the reconciliation cannot match moves to the legacy lane through a gate; the test itself changes only under the test-protection rules.

### 4. Dispatcher lane execution

The lane produces the same slices as today (`source.slice(start, chunk_size_rows)` for `start` in `range(0, num_rows, chunk_size_rows)`) and calls:

```
run_mask_chunked(config, slices, table=table, engine_version=engine_version, registry=registry,
    adapter=adapter, vault_writer=vault_writer, chunk_result_sink=chunk_results,
    key_provider=key_provider, base_row_offset=0, native_threads=native_threads)
```

`adapter` is `run_pipeline`'s pandas adapter, so B1's `adapter_requested` veto does not fire. `run_mask_chunked` runs the oracle's eager preflight first (B1 guarantee 3), so config errors carry today's codes in today's order.

**Per-table fallback.** The native-or-oracle choice is B1's, made once per table before the first chunk is masked: when the native lane refuses the table, the same call runs B1's oracle route, and the refusal is recorded in `reroute_reason`. Refusals that can reach an auto-chunked table: a strategy the chunked native route vetoes (categorical, bucket_perturb, group_key, date_shift, code_set, text_mask and the rest of `CHUNKED_ROUTE_VETOED_STRATEGIES`), a non-native fallback policy, no kernel or pool, `uncovered_columns` (unconfigured columns kept under the passthrough policy), a faker column over a non-string source, `crypto_extension_unavailable` and `index_extension_unavailable`. The `when_predicate_not_native` and `adapter_requested` refusals cannot arise from `run_pipeline` (the planner rejects `when:`, and the adapter is pandas); if one ever does, it is recorded the same way. B7 reuses this per-table choice for each independent table.

Established pattern: other engines with an optional accelerated backend also fall back per unit of work at plan time and report why. Apache Gluten (Velox under Spark) falls back unsupported operators to vanilla Spark and reports a fallback reason per operator. Spark RAPIDS with `spark.rapids.sql.explain=NOT_ON_GPU` logs why each operator stayed on the CPU. Polars' streaming engine runs operations it does not support on the in-memory engine. All three decide before execution and never switch partway through a stream. B2 does the same (guarantee 7). After the first chunk the vault writer and the chunk-result sink already hold that chunk's side effects, so a retry on another lane would duplicate them.

Schema drift on a later chunk cannot happen here: every chunk is a slice of one resident table, so every slice has the source's Arrow types, and an all-null slice keeps its column's type rather than becoming `null`-typed. If B1's `native_chunk_schema_drift` ever fires, it propagates as the typed `ExecutionError` B1 defined, on either route.

B1 rev5's passthrough exception (a nullable integer above 2^53 comes back exact instead of rounded) cannot reach a routed table: the planner admits integer columns only when null-free, and null-free integers, the uint64 maximum included, round-trip exactly through pandas.

### 5. Results and evidence

- `timings`: `aggregate_chunk_timings(chunk_results)`, as today. Native chunk results carry one record per column per chunk (B1), so the rollup has the same shape.
- `boundary_conversion_ms`: sum over chunks (zero on the native route), plus the one metadata conversion from section 3.4.
- `warnings`: `aggregate_chunk_warnings(chunk_results)`. `quality_metrics["code_set_corpora"]`: `aggregate_chunk_code_set_corpora(chunk_results)`. Both as today.
- `quality_metrics["chunked_route"]`: `aggregate_chunked_route_evidence(chunk_results)` with each column's `elapsed_ms` removed. On the legacy lane the same shape is built from `plan_column_backends` (planned backends) with `executed_backend = pandas_oracle`, `calls` equal to the chunk count, `native_admitted = false` and `reroute_reason = lane_reason`, so both lanes report alike.
- `quality_metrics["auto_chunk"]`: today's six keys plus `lane`, `lane_reason` and `native_threads`, on routed runs only. Non-routed runs stamp exactly what they stamp today.
- One INFO log line per routed job naming the table, lane, `native_admitted` and `reroute_reason`. It contains no values.

### 6. Threads

`native_threads` defaults to 1, matching B1's library default. Production callers pass their admitted reservation (B5 prices it; B3 and B4 pass it). It is forwarded only on the dispatcher lane; the legacy lane and every non-routed route ignore it. The unified slice's own threading is not changed.

### 7. Companion not installed

The engine imports and runs without the companion. B1's preflight probes the crypto kernel only for tables with a hash column, and the index kernel only for tables with a faker column. A missing or ABI-incompatible companion sends that table to B1's oracle route with `crypto_extension_unavailable` or `index_extension_unavailable`, and evidence reports those columns as planned `rust_companion` or `rust_pool_select`, executed `pandas_oracle`. Tables using only redact, truncate and passthrough need no companion and run on the native route (`arrow_python`). Output is the same in every case (guarantee 3).

### 8. Chunk size

Unchanged: a fixed row count, `chunk_size_rows` (default 50,000), caller-set, validated as today and recorded in the stamp. Reasons:

- Values do not depend on chunk boundaries for any admitted strategy; that is the value-keyed contract the planner enforces.
- Keeping today's boundaries keeps the chunk-result count, the vault entry order and the metadata source (chunk 0) the same as today, which the identity guarantee relies on.
- Row-count batches are the established pattern for this kind of engine: pyarrow's dataset scanner defaults to `batch_size = 131_072` rows, and DuckDB stores row groups of 122,880 rows.

A different default, or byte-aware sizing for wide rows, is a performance decision that needs a measured run first. It belongs with B6a and B6b, which bound memory, or to a follow-up after Phase E. B2 does not change it.

### 9. Composition with A8 and lazy sources

B2 does not touch routing, so A8 (`docs/plans/2026-09-30-engine-owned-transforms.md`, rev15) holds unchanged. A transform-bearing table fails `check_chunked_compatibility` with `per_table_transforms_present`; the planner turns that into a full-frame fallback with the coded reason, transforms run before masking on the full-frame route, and the new module is never entered. A `LazySource` is rejected by the planner's runtime gate, so auto-chunk never sees one and B2 never materializes one. Lazy-source admission to full-frame under `auto` (A8's rule) is decided earlier, by `resolve_execution_route`, which B2 does not change. Whichever of A8 and B2 merges second rebases and keeps both slices' acceptance tests green unchanged.

### 11. Merge evidence: performance and memory

The program's standing Rust merge rule needs "faster, within its declared memory ceiling". B1's runs (R074, R075) measured the dispatcher directly, not through `run_pipeline`, so they are not B2's evidence. B2 adds a bounded local benchmark. It is merge evidence, not the Phase E 100M gate.

- **Harness.** A new `scripts/bench-auto-chunk`, next to `scripts/bench-unified-slice`. It calls `run_pipeline` with default auto-chunk knobs (threshold 100,000, chunk size 50,000, so 20 chunks).
- **Workload.** B1's representative shape, generated exactly as follows. `rng = numpy.random.default_rng(20261001)`; `k = rng.integers(0, 10**9, size=1_000_000, dtype=numpy.int64)`; one `pa.table` built directly from Python strings (no pandas, so no schema metadata) with four null-free `string` columns, in this order: built element-wise over `k.tolist()`: `email` = `[f"user{v:09d}@example.com" for v in ks]` (hash, namespace `bench_ns`), `secret` = `[f"secret-{v:09d}" for v in ks]` (redact), `zip` = `[f"{v:09d}" for v in ks]` (truncate, length 3), `ref` = `[f"keep-{v:09d}" for v in ks]` (passthrough), where `ks = k.tolist()`. Global seed 42. The record states the source's raw Arrow size (`Table.nbytes`) for each configuration. 1M rows keeps the run well inside the devbox's shared memory cap of about 12 GB.
- **Configurations.** (a) dispatcher off; (b) dispatcher on, `native_threads=1`; (c) dispatcher on, `native_threads=4`; (d) the same table plus one unconfigured column `extra` = `f"x{k:09d}"`, so B1 reroutes to its oracle route (`uncovered_columns`), on and off; (e) the workload rebuilt as `pa.Table.from_pandas(df, preserve_index=False)` from a frame with `df.attrs = {"bench": "b2"}`, so its pandas metadata takes the legacy lane with `legacy_metadata_parity:pandas_attributes`, on and off. (d) and (e) measure what default-on B2 costs the jobs it does not speed up.
- **Method.** Each trial runs in a fresh subprocess, one at a time, with no other heavy test process on the box: either as a benchmark test under `/home/cam/bin/pytest-one`, or as a single script process that takes the same lock. Thread environment pinned (`native_threads` as above; `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`). One warmup trial per configuration, discarded, then seven measured rounds. Each round runs every configuration once, in an order shuffled by a seeded RNG (seed and order recorded), so load or thermal drift spreads across configurations instead of landing on one. Reported per configuration: all seven wall times of the `run_pipeline` call, their p50 and their maximum (max-of-seven), and each trial's peak RSS. Seven samples cannot support a p95, so none is reported or gated here; a p95 bar needs at least 3 warmups and 20 measured trials and belongs to certification (Phase E). The record names the CPU, and the pyarrow, pandas, engine and companion versions.
- **Correctness-oracle isolation.** Generate each dispatcher-off reference in a separate, unmeasured subprocess. Every measured subprocess constructs the fixed-seed source, executes exactly one assigned configuration, captures its own `ru_maxrss` (`resource.getrusage(RUSAGE_SELF).ru_maxrss`, KiB on Linux, recorded in bytes) as soon as `run_pipeline` returns, and then writes its output (Arrow IPC) plus JSON evidence for the parent. The parent performs `Table.equals(..., check_metadata=True)` against the reference outside every measured subprocess. Reference generation, reference loading, and cross-result comparison never contribute to a measured trial's RSS. The measured figure is whole-process on purpose: interpreter start, imports and source construction count toward the ceiling, because a production worker pays them too.
- **Correctness.** Every measured trial's output `equals(..., check_metadata=True)` its configuration's dispatcher-off reference, and (b) and (c) report `native_admitted = true` with zero oracle fallbacks in `chunked_route`. A trial that fails either check fails the run.
- **Declared memory ceiling (before measuring).** 2.0 GiB peak RSS for every measured trial process, where GiB means 2 x 1024^3 bytes = 2,147,483,648 bytes. This is an absolute safety ceiling for this 1M-row workload, not a scaling claim: it says nothing about memory at other row counts or widths. Working default; Cam may adjust.
- **Bars.** (b) and (c) have lower p50 and lower max-of-seven than (a). Every measured trial stays under the ceiling. For (d) and (e), dispatcher-on p50 is at most 1.05 times dispatcher-off p50 (the cost of the gates, preflight and evidence); the 1.05 factor is a working default Cam may adjust. Missing a bar stops for Cam, as the standing rule says.
- **Recording.** Each run gets the next benchmark run ID and a row in the sprint and testing ledger. The plan, CHANGELOG and docs quote a B2 speed figure only as "measured" with that run ID. This plan states no B2 speed figure.

## Known issues (tech debt, not blockers)

- Tables with unconfigured columns kept under the passthrough policy run on B1's oracle route (`uncovered_columns`). That is correct and visible in evidence, but many real configs leave columns unconfigured, so partial-mask jobs run wholly on pandas until program slice B8 admits unconfigured passthrough columns natively.
- Uncharacterized pandas metadata shapes stay legacy: extension dtypes, non-empty `attrs`, non-trivial indexes, named columns indexes, unknown column metadata, malformed JSON, and any pair outside section 3's list. B2 accelerates metadata-free and characterized pandas-origin Parquet, not Parquet generally. Non-pandas schema keys also stay legacy. How often real inputs carry the gated shapes is not measured; widening the subset is a characterization change plus a plan gate.
- `time64[ns]` tables take the legacy lane, since the gate cannot inspect values.
- Library callers get `native_threads=1` unless they pass a budget; platform and CLI pass reservations from B3, B4 and B5.
- The routed output is still fully materialized and concatenated; peak memory includes the whole output (B6a).
- `date64` passthrough tables, and any other type the characterization cannot reconcile, use the legacy lane.
- Today's output schema metadata depends on chunk 0 (it is absent when chunk 0 needed a null cast, and differs from full-frame metadata in that case). B2 reproduces this for identity rather than fixing it. Making it match full-frame is a separate, deliberate output change.
- Metadata reconstruction costs one pandas conversion of one chunk per job.
- A `large_string` chunk holding more than 2 GiB of string data cannot be cast to `string` and raises `chunked_schema_mismatch`. Whether today's lane has the same limit is not characterized; at the default chunk size it needs values averaging over 40 KiB.
- `explain_plan` does not show the lane, because the lane depends on companion availability at run time; the run's own `quality_metrics` does.

## Rollout

- Engine only, size S-M. The kill switch `chunked_dispatcher_enabled=False` restores today's lane without a revert.
- The platform's isolated worker and the CLI call `run_pipeline`, so their large single-table jobs switch lanes only when they pin an engine release that contains B2 (B3, B4). Output is unchanged; `quality_metrics` gains the keys above.
- Ships in the Phase B paired engine and companion release, after B1.
- Gates: Codex plan gate, Sonnet build, dennis, Codex final, under the review-rounds rules. Engine slice: merges under the standing Rust rule after the merge hold lifts, with section 11's run as its speed and memory evidence.
