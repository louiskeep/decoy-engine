## 0. Frame

### 0.1 What a CLI user can do after this row

- Point a `decoy run` target at S3 (`type: s3` with `bucket` and `key`; schema at
  `config/_targets.py:68`). The run uploads each output under a fresh run prefix and then moves
  one pointer object. Consumers read `<dir>/<pipeline>/CURRENT`, which holds the run id, then
  `<dir>/<pipeline>/runs/<run_id>/MANIFEST`, then the files it lists. No existing object is
  overwritten; the only object a run changes is its own pipeline's `CURRENT`.
- GCS targets (`type: gcs`, `config/_targets.py:102`) are refused with
  `layout.cloud_target_unsupported`. The GCS write store is a separate slice, EC5, built only
  when the owner pays for a real-bucket GCS run (Q-D); CC5 then lifts the refusal.
- Point a `decoy run` source at S3 or GCS (`config/_sources.py:258`, `:317`), including an S3
  `endpoint_url` (MinIO, R2). The CLI downloads the one named object into a private scratch
  arena, reads it with the same readers as a local file, and removes the copy on every exit.
- Use the credentials the machine already has: the AWS default chain (environment, shared config
  and credentials files, SSO, container and instance metadata) and Google Application Default
  Credentials. The CLI stores nothing and asks for nothing.
- Get the same strict and best-effort delivery as a local run (DELIV): strict delivers every
  table or none; best-effort drops a failed table and its dependents; a post-scan block withholds
  the run; a run that loses the pointer race exits 3 and leaves nothing a consumer can reach.
- `decoy validate` checks the cloud layout offline (one bucket, one directory, legal key shapes,
  a pipeline name) with value-free `layout.*` codes.

## 1. Guarantee

> A `decoy run` whose targets are all S3 under one bucket and one key directory `<dir>`, for a
> pipeline named `<pipeline>`, writes each delivered output as a new object under
> `<dir>/<pipeline>/runs/<run_id>/` with a create-only precondition, then a create-only
> `MANIFEST` in the same prefix, and makes the run current by one conditional write of
> `<dir>/<pipeline>/CURRENT` against the version it read when the run opened. Strict delivers
> every table or leaves nothing a consumer can reach through `CURRENT`; best-effort uploads only
> the tables `plan_delivery` delivers. A run whose pointer write is definitively rejected
> delivers nothing and exits 3. A run whose pointer write has an unknown result never deletes
> its objects and never restores the vault. No object that existed before the run is changed,
> except that pipeline's `CURRENT`, which only ever goes from a run id to a run id. No
> credential, secret reference, SDK message, bucket-internal path beyond what the user typed, or
> data value reaches stdout, stderr, `--json`, logs, the run result or evidence.

GCS targets carry the same guarantee once CC5 lifts their refusal.

Threat model (claudeorchestrator ruling, also DELIV): accidental leaks only. A hostile principal
with write access to the bucket can always replace objects; the plan does not defend against one.

Named limits (15): an abandoned run prefix after a crash or a failed upload with an unknown
result; an incomplete multipart upload after SIGKILL; the vault window of DELIV 12.1; a pointer
write with an unknown result (`uncertain`); a noncurrent version left by a delete on a versioned
bucket; spooled source rows left in the temp root after SIGKILL until CC4 calls
`sweep_scratch()`.

## 2. Established solutions

Search run (2026-11-12): AWS S3 user guide, "How to prevent object overwrites with conditional
writes" and "conditional requests"; AWS what's-new, Nov 2024 (If-Match on PutObject and
CompleteMultipartUpload); GCS "Request preconditions" and JSON API `objects.insert`; Delta Lake
"multi-cluster writes to Delta Lake storage in S3" (2022) and later put-if-absent commits; the
lakehouse atomicity write-ups (Iceberg, Delta, Hudi); in the codebase, DELIV 4.4 and 7.1, F22
5.0 to 5.4, the platform's `api/jobs/v2_cloud_materialize.py`, engine `connectors/_clients.py`.
Installed sources read: the botocore S3 service model (`IfMatch` and `IfNoneMatch` on
`PutObjectRequest` and `CompleteMultipartUploadRequest`, `IfMatch` on `DeleteObject`), moto 5.2.2
`moto/s3/responses.py` (enforces both on `put_object` and `If-None-Match: *` on
`complete_multipart_upload`), s3transfer 0.19 `manager.py` (no `If*` upload arguments),
google-cloud-storage 3.12.0 `fileio.py` (`BlobWriter` takes `if_generation_match` and `retry`;
`retry=None` disables retries).

Found and followed:
- Put-if-absent for immutable data files: S3 `If-None-Match: *` on PutObject and
  CompleteMultipartUpload; GCS `ifGenerationMatch=0` ("succeed only if there are no live
  versions"). Delta Lake's commit log relies on exactly this to make one writer win a name.
- Put-if-unchanged for the pointer: S3 `If-Match: <etag>`; GCS `ifGenerationMatch=<generation>`.
  A loser gets 412 Precondition Failed; S3 can also answer 409 ConditionalRequestConflict to a
  concurrent conditional write, and 404 when the object named by `If-Match` is gone. This is the
  table-format pattern: immutable files under a unique prefix, then one compare-and-swap of a
  small metadata pointer (Iceberg's catalog pointer swap; git `update-ref <ref> <new> <old>`
  locally, which DELIV already follows).
- A commit whose response is lost is not a failed commit. Table formats treat a commit with an
  unknown outcome as "check, then report unknown", never as "roll back"; Iceberg's
  `CommitStateUnknownException` is the named case. This plan does the same (4.3 step 8).
- A manifest written before the pointer names exactly what a run made visible (Iceberg manifest
  lists, Delta's `_delta_log` entries).
- Never overwrite live keys: the UX map 5.2 cloud recipe. The platform's temp-key, copy and
  delete pattern (`v2_cloud_materialize.py`) overwrites the canonical key and is not followed.

Custom code left: the key-directory rule (4.2), the outcome mapping onto DELIV's receipt (4.4),
and the re-read after a pointer write with an unknown result (4.3 step 8). All small.

### 3.2 Failure modes the design must hold

- F1, overwrite of live data: closed by create-only uploads and a run prefix nobody else uses.
- F2, older run replaces newer: closed by the conditional `CURRENT` write against the version
  read at open, never a blind put.
- F3, a pointer write that may have landed is read as a loss and the run deletes a current
  run's objects: closed by deleting only after a definitive rejection on a single attempt with no
  SDK resend (4.3 step 8); every other result keeps the objects and the vault.
- F4, cloud target or source silently skipped on some route: closed by keeping the refusal for
  every route but `decoy run` (and `validate`, which checks offline), behind one function, and
  by giving the source loader a cloud arm instead of its `path` skip.
- F5, SDK text leaking identity or paths: closed by fixed error words in `connectors/_clients.py`
  for both providers and errors raised after the `except` block, so `__cause__` and
  `__context__` are both None.
- F6, credentials stored or echoed: the CLI never constructs a credential, never passes static
  keys, refuses `credentials_ref`.
- F7, a store that ignores preconditions: closed by refusing `endpoint_url` on targets in V1
  (Q-C) and by self-tests of both test doubles (AT-C31, AT-C32).
- F8, abandoned local copies of source rows: closed by the F25 scratch arena, reclaimed on every
  caught exit; after SIGKILL a named limit until CC4.
- F9, two pipelines in one directory moving one pointer: closed by a pointer per pipeline (Q-A).

### 4.2 The cloud root rule

All targets of a run are cloud targets of one type (`s3`, or `gcs` after CC5), one `bucket`, one
`region` (S3), and one key directory `<dir>`: the part of `key` (S3) or `object` (GCS) before
its last `/`, empty when there is no `/`. Each target's basename is the part after the last `/`.

The pipeline name is `pipeline_name_for` inside a project. Outside a project it is the config's
declared `name:`, checked by the engine rule `is_valid_pipeline_name`; a cloud-target config
outside a project with no valid `name:` is refused.

- Mixed file and cloud targets, two types, two buckets, two regions or two directories:
  `layout.delivery_root_split` (DELIV's code, exit 1). It is the same single-root rule as kind A,
  so it lives in the same function.
- `layout.cloud_target_invalid` (new): a key or object that starts with `/`, ends with `/`, has
  an empty, `.` or `..` segment, has a control character, has a basename equal to `MANIFEST`
  (equality only: `MANIFEST.csv` passes), or shares its basename with another table's target; or
  no pipeline name outside a project. Matching uses `re.fullmatch` (recurring defect 1). The
  message names the table and the rule, never the key.
- `layout.cloud_target_unsupported` (new): `credentials_ref` set, `endpoint_url` set on a target,
  `quarantine.enabled: true`, `--chunked`, or `type: gcs` on a target until CC5. The message
  names the table and the field name.

The rule is offline (no network), so `decoy validate` and the run gate run it before anything is
read. Objects land at `<dir>/<pipeline>/runs/<run_id>/<basename>`; the manifest at
`<dir>/<pipeline>/runs/<run_id>/MANIFEST`; the pointer is `<dir>/<pipeline>/CURRENT`. The key
the user wrote is never itself written (Q1). This layout mirrors DELIV's local
`out/<name>/LATEST` and freezes at REL-GATE (Q-A).

### 4.3 Run order, kind `cloud_prefix`

DELIV 4.2 steps with the cloud arm:

1. Gate: `layout_issues` runs the cloud root rule (CC1).
2. `DeliverySink.open`: kind `cloud_prefix` when every target is cloud. It mints the run id with
   `new_run_id(started, invocation_id, extra_blocks=6)`, all 32 hex of the invocation id (there
   is no folder to clash on, so uniqueness rests on the UUID). It opens an engine-rooted
   `ScratchArena` (`ScratchArena.open()`, no `under=`) as the upload spool and builds the engine
   `CloudDeliveryStage.open(store, prefix, run_id, arena, targets)` (EC4), where `targets` is
   the `(table, basename)` pairs of `CloudRoot` in sorted table order. Construction is per kind and
   is not part of DELIV's `SinkStage` protocol (F8 ruling). The stage:
   a. runs `head_bucket` and compares the `x-amz-bucket-region` response header with the
      client's region; a mismatch raises `wrong_region` (S3 only);
   b. reads `CURRENT` (`read_small` with limit 65, so at most 66 bytes are fetched and a longer
      object is `pointer_invalid`; absent is a valid state) and records its version (S3 ETag,
      GCS generation, or absent);
   c. refuses with `pointer_invalid` when `CURRENT` is present and `read_value(raw, is_run_id)`
      gives None.
   Any connector error here fails the run before an upload, exit 3.
3. Routes write through `sink.write_table` into arena paths. `write_targets` admits a cloud
   entry only when its `Placer` is the `cloud_prefix` sink's (CC2, `C:io/_targets.py`, F2
   ruling); every other placer keeps today's skip. The cloud `Placer` (`C:io/_cloud.py`) maps
   the entry's `key` or `object` to its table (basenames are unique, 4.2) and calls
   `stage.stage_path(table)`, which records the table and returns
   `arena.local_path("out-<n><suffix>")`, where `<n>` is the table's position in `targets` and
   `<suffix>` the basename's suffix (F25 3.3 asks for positional component names).
   `resolve_target_format` and `target_format_issues` read the suffix from the basename of
   `key` or `object` for a cloud entry. The files sit under the arena's 0700 root. The arena is
   an upload spool, never a publication stage: the stage calls `create_file` and `local_path`
   only, never `local_stage_path`.
4. Post-scan as DELIV step 4.
5. `plan_delivery(config, outcomes)`, where outcomes now cover cloud-target tables (EC0).
6. Nothing to deliver: `sink.abort()`; the arena is reclaimed; the bucket is untouched.
7. `sink.deliver(decision, before_visible)` calls the protocol's
   `stage.deliver(decision, before_visible)`; the sink never branches on kind (DELIV AT-14b).
   Inside the cloud stage:
   a. upload each table `decision` delivers, create-only, from the file `stage_path` recorded
      for it, then the create-only `MANIFEST` (6.5); a table the decision does not deliver is
      never uploaded; on any upload failure, withdraw the objects this run created (`MANIFEST`
      first, F12) and return `nothing`, `publication_failed`;
   b. `before_visible()`: vault then evidence, each with its backup (DELIV `PreVisible`);
   c. the stage enters state `committing` in the statement before it sends the conditional
      `CURRENT` write with this run's id (DELIV `CurrentPointer.swap` semantics: the value read
      at open is the expected value; any other value refuses);
   d. on `replaced` the sink state becomes `delivered` in the statement that receives it;
   e. discard or restore the vault and evidence backups (4.4 table); reclaim the arena.
8. Pointer write results (EC3 `ObjectPointerStore`, one request per attempt: S3 client
   `max_attempts: 1`, GCS `retry=None` on every `put_if` and `put_new`). The store maps the
   backend's answer to `replaced`, `stale` or `unknown` and never compares values; the re-read
   after `unknown` and its compare with this run's id happen once, in DELIV's `CurrentPointer`,
   for every backend (F9 ruling). The ruling said the store returns `uncertain`; this plan uses
   a fourth store value, `unknown` ("may or may not be applied"), because DELIV's local store
   already returns `uncertain` for "applied, fsync failed", and a re-read there would show this
   run and hide the durability doubt. `CurrentPointer` still returns only `replaced`, `stale` or
   `uncertain`:
   - won: delivered.
   - 412 or 404: a definitive rejection (`stale`); the write was not applied.
     `delivery_pointer_moved`; withdraw this run's objects; restore the backups.
   - 409: inside the store, re-read the version; when it still equals the expected version,
     send the write once more (both racers can get 409 with the pointer unchanged); a second
     409, a 412, a 404, or a re-read showing another version is `stale` as above. This resend
     stays in the store because it compares versions, which only the backend has.
   - anything else (timeout, 5xx, connection reset, an exception from the SDK that is not a
     classified rejection): the store returns `unknown`. `CurrentPointer` re-reads `CURRENT`
     once: equal to this run's id gives `replaced` (delivered); any other value, or a failed
     re-read, stays `uncertain` with `publication_commit_uncertain`. Objects and vault are kept,
     because the write may still be applied after the re-read and a deletion would leave
     `CURRENT` naming a missing run. Whether `uncertain` exits 0 is owner question Q-E.
   - `committing` ends in the statement that receives any classified result (`replaced`,
     `stale`, or `uncertain` after the re-read), so a Ctrl-C during the withdraw that follows a
     definitive rejection is reported as that rejection, not as `uncertain` (F10).
   - `KeyboardInterrupt` while in `committing`: no re-read, no delete, no restore; the receipt
     is `uncertain` with `publication_commit_uncertain`; the interrupt propagates, exit 130.

No lock is taken: the conditional write is the compare-and-swap (UX map 5.2: "an equivalent ...
lock is acceptable only if it also compares the recorded version"). Two runs of one pipeline into
the same `<dir>` both upload under their own run prefixes; the second `CURRENT` write loses.
Runs of two pipelines into one `<dir>` use two pointers and do not interact.

### 4.5 Credentials and permissions

The CLI never reads, writes, prints or forwards a credential. It builds `S3Config` and
`GCSConfig` with only bucket, region, prefix and (for sources) `endpoint_url`; `access_key_id`,
`secret_access_key` (`connectors/s3.py:110-138`) and `service_account_json`
(`connectors/gcs.py:50`) stay unset, so the SDK walks its default chain. `credentials_ref` is
refused (4.2), because the engine treats it as opaque and only the platform resolves it
(`config/_targets.py:7`). AWS profile and region come from the environment (`AWS_PROFILE`,
`AWS_REGION`, `AWS_DEFAULT_REGION`) or the config's `region`; with neither, botocore's own
default applies and the region check of 4.3 step 2a refuses a mismatch. No `--profile` flag in
V1. A CLI sentry fails on any CLI module that passes those three config fields or imports `boto3`
or `google.cloud.storage` directly (6.7 class 5 lists the spellings).

Permissions a target needs, named in the docs page (CC3) and in the hint after an
`access_denied` at open:
- S3: `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:AbortMultipartUpload` on
  `<dir>/<pipeline>/*`; `s3:ListBucket` on the bucket (with a prefix condition if wanted).
  Without `s3:ListBucket`, S3 answers 403, not 404, for an absent `CURRENT`, so the first run into
  a new directory fails `access_denied`; `head_bucket` needs it too.
- GCS: `storage.objects.get`, `storage.objects.create`, `storage.objects.delete` on the bucket
  (the `roles/storage.objectUser` role covers them).
- Sources: S3 `s3:GetObject` (and `s3:ListBucket` for a 404 on a missing object); GCS
  `storage.objects.get`.

- Engine connector errors carry a fixed text and a `kind` (EC1); the CLI prints
  `table <name>: cloud target unavailable (<kind>)` or `cloud source unavailable (<kind>)` from

### 4.7 Cloud sources

`read_source` (`C:src/decoy/cli/_sources.py:168`) and `iter_source_chunks` (`:193`) take an
optional `arena: ScratchArena`. A source with `type: s3` or `type: gcs` calls

`object`), streamed by `ObjectStore.iter_object` into `arena.create_file(component)` (0600
before the first byte), then read by the existing local reader on `arena.local_path(component)`.
Components are positional (`src-0`, `src-1`, ...) in sorted source order (F25 3.3).

The arena is opened and reclaimed by the run route (CC3, `C:run/_execute.py`):
- one predicate (F4 ruling): `source_is_materialized` (`C:_native_gate.py:200-205`) widens to
  "a `path` string, or `type` `s3` with a `key` string, or `type` `gcs` with an `object`

- plain route: `_load_sources_from_config` opens one engine-rooted arena in a `with` around its
  loop, so the copies are gone on every caught exit; its skip (`C:run/_execute.py:239`) already
  calls the widened predicate, so a cloud source is read, never skipped;
- `--chunked`: `_run_chunked_mask` opens one arena in a `with` around the whole chunk loop
  (`C:run/_execute.py:66-140`), and its own `path` skip at `:112` is replaced by a call to the
  same predicate. The arena outlives every generator it feeds, so cloud sources work on
  `--chunked` (Q6 decided).

`--preview` is unchanged (F3): it reads no source (`C:run/_prepare.py:259-262`,
`C:run/_execute.py:361`), so it never reaches the loader, the spool or the refusal.
`prepare_preview` does not run the cloud root rule: `layout_issues` returns no issue for a
preview placement (`C:io/_placement.py:177-178`), and a preview writes no target, so the targets
it ignores need no check.

After SIGKILL the arena stays in the temp root, owner-only, until CC4 calls `sweep_scratch()`
(F25 S5, consumer row C1). A full disk during the spool raises the CLI's own `OSError(ENOSPC)`,
which the run maps to the capacity exit 5 (F25 3.3, rule 3).

### 4.9 Design notes

- Principles: one owner per fact (4.1); dependency rule (the CLI calls the engine stage; the
  engine never knows the CLI); open for a new backend through `PointerStore`, `ObjectStore` and
  `SinkStage`, the three seams expected to grow (Azure, SFTP, F02).
- Established pattern: section 2.
- House style: typed `CloudRoot`, `PointerState`, `PutResult` and `CloudOutput` objects; the
  `route` token is a closed Literal over one shared refusal core, not a behaviour flag, and the
  store type picks the backend; comments say why.

## 5. Hostile cases by surface

- Keys from the config are untrusted input that builds object names (4.2 rule, AT-C04).
- `CURRENT` contents are untrusted (another tool may write it): read bounded, decoded only when
  it is a run id (`is_run_id`, DELIV); a present non-run-id value refuses the run at open
  (AT-C29); a value that changes during the run loses the conditional write (AT-C08).
- SDK messages are untrusted text (EC1, AT-C10).
- A store or double that ignores preconditions (AT-C31, AT-C32; `endpoint_url` refused on
  targets).
- A response lost in flight (AT-C19, AT-C26, AT-C27).

### 6.2 Exit paths

- Success: `CURRENT` moved; arena reclaimed; backups discarded (DELIV `_flow.py` success path,
  `C:src/decoy/cli/run/_flow.py:72-81`).
- Refusal at the gate (exit 1): nothing contacted; no arena opened.
- Connector error at sink open (exit 3): arena reclaimed; nothing uploaded.
- Decision `deliver=False` (exit 3 or 4): arena reclaimed; nothing uploaded.
- Upload failure (exit 3): created objects deleted; arena reclaimed; backups untouched.
- Pointer rejected (exit 3): created objects deleted; backups restored.
- Pointer uncertain (exit 0, warning): objects kept; backups discarded.
- `KeyboardInterrupt` before `committing`: `abandon()` reaches the sink callback; created
  objects deleted; exit 130.
- `KeyboardInterrupt` in `committing`: `uncertain`; objects kept; backups discarded; exit 130.
- `KeyboardInterrupt` after `replaced`: delivered; exit 130.
- SIGKILL: arena left until CC4's sweep; objects under the run prefix left (named limit);
  incomplete multipart uploads left (named limit).

- `decoy run`, plain route: through the sink (`C:src/decoy/cli/run/_execute.py:267`, `execute`).
- `decoy run --chunked` with a cloud target: refused (`layout.cloud_target_unsupported`); the
  chunked writer appends per table (`C:_targets.py:498`), which cannot be create-only in V1.

  around the chunk loop (4.7).

- `decoy run --preview`: unchanged; reads no source, writes nothing, contacts no bucket (4.7).

  `check_cloud_endpoints_supported` as today (`C:extras.py:123`).
- Platform: unchanged (PARKED); the engine stage is its future seam.

### 6.4 FK shapes

- Parent and child both cloud targets: best-effort drops the child with a failed parent and
  never uploads it (DELIV AT-3 rerun with `s3` targets, AT-C05).
- Two parents, one failed: the child is dropped, the good parent uploaded.
- Table-level cycle: the component drops whole, nothing of it uploaded.
- Generate `reference` parent with a cloud target: the edge from `generation_order` applies
  unchanged (`generation/synthesize.py:226`).

### 6.5 Fields

- `PointerState`: `raw: bytes | None`, `version: str | None` (ETag or generation as text).
- `PutResult`: `won | rejected | conflict | unknown`.
- `ConnectorError.kind`: `ConnectorErrorKind` (EC1).
- `CloudRoot`: `type`, `bucket`, `region`, `dir`, `pipeline`, `basenames` (per table).
- `CloudOutput`: `scheme`, `bucket`, `key`; `display()` gives the URI.
- `TableDelivery.output` (`run_result/_model.py:282-287`): the basename for cloud outputs (Q4).
- `CURRENT` object: the run id as UTF-8 plus `\n`, nothing else (the same bytes as `LATEST`).
- `MANIFEST` object: UTF-8, first line `decoy-cloud-manifest 1`, then one line per delivered
  table in sorted table order, `<table>\t<basename>\t<sha256 hex of the staged file>`, each
  ending in `\n`. Table names pass the engine's table-name rule, which allows no tab or newline.
  A reader refuses a missing or unknown first line.

### 6.6 Output surfaces

- stdout and stderr (`C:src/decoy/cli/run/_render.py`, `C:src/decoy/cli/run/_errors.py`):
  table names, codes, fixed words, the URI built from typed parts.
- `--json` `outputs` and `output_dir`: the URIs (Q4).
- Run result and evidence: basenames, digests, run id, no bucket; `--result PATH` is local.
- The bucket: `runs/<run_id>/` objects, `MANIFEST` and `CURRENT`.
- Logs and spans: no new attributes.

### 6.7 Recurring-defect catalog walk

1. Anchored validation: the key rule, `is_run_id` and the `MANIFEST` first line use
   `re.fullmatch`; AT-C04 feeds `a/b\n`, AT-C29 feeds `<run_id>\n\n`.
2. Strict wire and stored types: `CURRENT` and `MANIFEST` are bytes formats, no model; the
   ledger `PublishedOutput` and `CloudOutput` are frozen dataclasses with `str` fields checked at
   construction; `ConnectorErrorKind` is a closed Literal checked with `get_args` in AT-C42.
3. No exception context: one raise-after-`except` policy for S3 and GCS (EC1); AT-C10 asserts
   `__cause__ is None and __context__ is None` on both providers.
4. Versioned read models: the `MANIFEST` first line carries the format version and a reader
   refuses an unknown one (AT-C37); `CURRENT` is one versionless value checked by `is_run_id`.
5. Normalized guard scanners. Engine outbound S3 arm, covered shapes: `boto3.client("s3")`,
   `boto3.resource("s3")`, `boto3.Session(...).client(...)`, `boto3.session.Session().client(...)`,
   `from boto3 import client`, `from boto3 import session`, `import boto3 as b` then `b.client`,
   `botocore.session.get_session().create_client(...)`. CLI credentials sentry, covered shapes:
   `import boto3`, `import boto3 as x`, `from boto3 import ...`, `import google.cloud.storage`,
   `from google.cloud import storage`, `from google.cloud.storage import ...`,
   `importlib.import_module("boto3")` with a literal; keyword arguments `access_key_id`,
   `secret_access_key`, `service_account_json` on any call. Each shape has a seeded case.
   Deliberate evasion is V2-LOG.
6. No reaching into private modules: the CLI imports `decoy_engine.connectors` and
   `decoy_engine.publication` public names only; `ObjectPointerStore` and `CloudDeliveryStage`
   are exported.
7. No hidden CI failures: the GCS-double job fails when Docker or the container is missing
   (no skip marker that passes); no `continue-on-error`.
8. One input, one trust class per entry point: user keys go through the cloud root rule; the
   arena components are program names (`src-<n>`, `out-<n><suffix>`) through F25's
   `validate_component`; neither path takes the other's input.
9. Mutations on the final head: each slice reruns its mutations after its last code change and
   records the head.
10. Allowlisted helpers are still checked: `_clients.py` is the only allowed S3 and GCS
    construction site, and its callers are scanned by `(path, name)`; no forwarding helper is
    added to an allowlist.
11. No raised caps: `WALK_FLOOR` (`tests/sentry/test_outbound_clients.py:49`, 151) is not
    raised; `baselines/gcs-call-kwargs.json` gains no row (the store passes `timeout` and
    `retry` explicitly); module caps are not raised (9).

## 12. Owner questions

Builders work on the working answers. Each answer is asked of the owner before the slice named.

- Q-A, pointer scope (before CC1; the layout freezes at REL-GATE). Where does a pipeline's
  pointer live? (a) `<dir>/<pipeline>/CURRENT` with runs under `<dir>/<pipeline>/runs/` (one
  pointer per pipeline, like local `out/<name>/LATEST`); (b) `<dir>/CURRENT` for the whole
  directory (two pipelines in one directory overwrite each other's pointer and consumers read the
  wrong data); (c) a new config key naming the prefix. Working answer: (a).
- Q-B, what a best-effort consumer can read (before EC4). After a best-effort run, how does a
  reader know which tables were delivered? (a) a create-only `runs/<id>/MANIFEST` written before
  `CURRENT`, listing each delivered table, its file and digest; (b) nothing: the reader lists the
  run prefix and treats a missing file as dropped; (c) change UX map 5.2 to say the pointer is a
  bare run id. Working answer: (a).
- Q-C, `endpoint_url` (before CC1). MinIO, R2 and other S3-compatible stores: (a) allow on
  sources, refuse on targets (reads need no preconditions; a store that ignores them would let
  two runs overwrite each other's pointer); (b) refuse on both; (c) allow on targets after a
  probe that a second create-only write is refused, which leaves probe objects behind. Working
  answer: (a); targets wait for V2 and a proven probe.
- Q-D, real-bucket evidence (S3 before CC2 merges; GCS before EC5 starts). Test doubles can be
  wrong about preconditions. (a) moto and, later, the pinned GCS double only; (b) plus one real
  S3 run and one real GCS run of the store's precondition cells, by the orchestrator, which
  costs a bucket and a few requests. Working answer: slices build on the doubles; the real S3
  run (409, 404, `IfMatch` on `DeleteObject`, the region header) is asked before CC2 merges,
  because it is cheap and covers the cells moto may model wrongly; EC5 and CC5 wait for the
  owner to pay for the GCS run.
- Q-E, exit code of a cloud `uncertain` pointer result (before EC4). When the pointer write's
  result is unknown and the one re-read does not show this run, should the run (a) exit 0 with
  the `publication_commit_uncertain` warning, like DELIV's local fsync case, or (b) exit 3?
  Timeouts are far more common than fsync failures. Recommended and working answer: (a), because
  the objects and vault are kept and may be current, and a nonzero exit would make a scheduler
  rerun a run that may already be the current one.
- Q-F, when row 64 is DONE (before CC3 merges). (a) at CC3, with GCS targets (EC5, CC5) as a tail
  tied to the Q-D spend; (b) only after CC5. Recommended and working answer: (a), because S3
  targets and both source types are the V1 value and GCS targets are already refused with a
  clear code, so row completion should not wait on a spend decision.
- Q-G, withdrawing this run's own objects (before EC4). F26 r3 (engine `812a1a9e`) records
  "Decoy never deletes from customer buckets", while Q8 below deletes this run's created objects
  after a definitive loss or a failed upload. (a) record that withdrawing objects this run
  created in this invocation, each by a version-conditioned delete, is cleanup of its own failed
  write and not retention or deletion of customer data; (b) never delete, and leave a lost run's
  objects for a lifecycle rule. Recommended and working answer: (a), because the delete names
  only the exact version this run wrote, so no object that existed before the run, or that
  anyone else wrote, can be removed.
