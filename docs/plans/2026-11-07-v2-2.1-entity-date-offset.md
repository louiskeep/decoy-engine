## 1. FRAME

### 1.1 What exists today (read before designing)

The sprint text says "`date_shift` takes an `entity_key` column". The engine already has most of
the mechanism, under another name:

- **Plain `date_shift`** (`execution/_strategies/_date_shift.py`). Per-value keyed offset:
  `min_days + int.from_bytes(derive(mask_key, namespace, _canonicalize_source(date_value))[:8],
  "big") % range_size`. HKDF-SHA256 then HMAC-SHA256 (`determinism/_derive.py`). Same date, same
  shift. Two dates of one patient get unrelated shifts, so intervals and order break. The V1
  `transforms/date_shift.py` HMAC/MD5 path is legacy and not used by the V2 handler.
- **`group_by` (HC-3a, shipped 2026-07-17, undocumented in `docs/strategies.md`).** Same formula,
  but the digest input is the canonical value of a sibling entity column, read from a pre-mask
  snapshot (`ctx.group_anchor_snapshots`, built by the full-frame and sequential adapters from
  `_runner.date_shift_group_columns`). Compile refuses it with `when`, inside `nested`, on an FK
  date column and with `preserve_values` (`plan/_checks_date_shift.py`). Every native, physical
  and unified-slice executor declines it (`date_shift_group_by_not_native`), out-of-core refuses
  all `date_shift`, and the chunked route is byte-identical to full frame
  (`tests/unit/execution/test_chunked.py::TestChunkParityGroupBy`).
- **`windowed_date`** generates `anchor + offset` with a per-row seeded draw keyed on the row
  index; it does not shift existing dates per entity. **`derived`** has no keyed operation. Neither
  expresses this.

So "every date for one entity moves by the same keyed offset" already holds for `group_by` on one
table. Probes on main `b5b1ad16` (scratch scripts, rerunnable; section 2) show what does not hold:

1. **Key-domain leak (confirmed end to end).** `group_by`'s offset uses the same derivation as
   `hash`: `derive(mask_key, ns, canonical(entity))`. A `hash` column on `patient_id` in the same
   namespace as a `group_by: patient_id` date column publishes the digest the offset comes from.
   From the masked output alone the probe recovered 3 of 3 source dates exactly
   (`offset = min + int(hash_hex[:16], 16) % range`). The same holds for a `group_key` column
   (raw digest) in that namespace. This is the roadmap row 24b class (a cell value reproduces a
   key-derivation input), here through a sibling column rather than a label.
2. **Cross-table type drift.** `patient_id` as `int64` in one table and as the string `"123"` in
   another canonicalise differently (`_encode_int` vs UTF-8), so one patient gets two offsets.
   Probe: same date, same namespace, `2019-03-14` vs `2020-01-22`. Silent.
3. **No consistency check.** Two entity-anchored columns in one namespace with different
   `min_days`/`max_days` give one entity different offsets (the reduction depends on the range),
   and two date columns of one table anchored on the same entity column but given different
   namespaces do the same. Both break the admission-to-discharge interval silently.
4. **Value-bearing error.** A float entity value reaches `_canonicalize_source`, whose
   `float_canonicalization_unsupported` message includes `repr(value)` (an ID).
5. **Overflow.** A parseable date shifted past pandas' range (`2262-04-11`) raises a bare
   `OverflowError` ("Overflow in int64 addition") from `parsed + to_timedelta(...)`, failing the
   whole run untyped. This is also true of plain `date_shift` today.

### 1.2 Problem

Per-entity date shifting needs an option whose offset (a) cannot be read off any other masked
column, (b) is the same for one entity across columns and tables that share a namespace, whatever
the key's storage type, (c) is refused at compile when the config would silently break that
consistency, and (d) is honoured identically, or declined with a coded reason, on every route.

### 1.3 Guarantee (the whole promise)

For every `date_shift` column with `provider_config.entity_key: K` in namespace `N`, with
resolved range `[min_days, max_days]`:

- G1 (one offset per entity). Every row whose entity value `e` is usable (section 3) shifts by
  `off(N, e) = min_days + int.from_bytes(derive(mask_key, N, ENTITY_SOURCE(e))[:8], "big") %
  (max_days - min_days + 1)`, whatever column, table, chunk, route or run it is in.
- G2 (intervals and order). For two usable rows of one entity in such columns, the shifted dates
  differ by exactly the source difference (whole days; time of day is kept by the format), so
  order and intervals are preserved.
- G3 (consistency is enforced, not assumed). Compile refuses a config where two `entity_key`
  columns in one namespace have different resolved ranges, or where two `entity_key` columns of
  one table name the same entity column with different namespaces.
- G4 (domain separation). `ENTITY_SOURCE(e)` starts with byte `0xFF`, which no
  `_canonicalize_source` output can start with, so no `hash`, `group_key`, `fpe`-key, plain
  `date_shift` or `group_by` derivation can equal it, in any namespace.
- G5 (routes). The Python handler is the only executor. Full-frame, sequential and chunked (auto
  chunk and `run_mask_pipeline_chunked`) give byte-identical output; native full-frame, sequential
  native, native chunked, unified slice and physical shadow decline with
  `date_shift_entity_key_not_native:<column>`; out-of-core declines all `date_shift` with its
  existing reason.

**Definition of done.** G1 to G5 hold (property and route tests, section 8); every refusal is
coded and value-free; the leak (section 1.4) is in `docs/what-we-cannot-prove.md`; the option is in
`docs/strategies.md` and the CHANGELOG; configs without `entity_key` are byte-identical to main
(output and serialised plan), `group_by` included.

**Non-goals.** Preserving day of week or season (later option, per the sprint); sub-day offsets;
excluding a zero offset (section 9); changing `group_by` or plain `date_shift` in any way (the
`group_by` leak and the overflow crash are follow-ups, section 11); `entity_key` on a `nested`
child, with `when`, with `preserve_values`, or on an FK date column (refused); native or
out-of-core kernels; `unmask` reversal (date_shift stays "irreversible" in `unmask.py`); an
entity-key option for `bucket_perturb` or `text_mask` date spans; refusing unknown
`provider_config` keys (a typo `entity_kye` falls back to per-value shifting, as any unknown key
does today; section 9).

### 1.4 Leak accepted (to `docs/what-we-cannot-prove.md`)

- Intervals and order within an entity are exact by design. Anyone who knows one true date of an
  entity (a public admission, a birth date) learns its offset and so every date of that entity in
  every column and table of the namespace.
- The offset is bounded: a shifted date `d'` came from `[d' - max_days, d' - min_days]`.
- When the range includes 0, about one entity in `max_days - min_days + 1` is not moved at all
  (existing `validators/_leak_check.py` threshold handles the per-cell view).
- The sequence of intervals of one entity is itself a quasi-identifier (a long, distinctive
  treatment history). Date shifting is not HIPAA Safe Harbor (45 CFR 164.514(b)(2) removes all
  date elements finer than the year); it is a technique an Expert Determination may accept. Decoy
  calls it pseudonymisation (`_technique_class.py` already classes `date_shift` so).
- Rows with a null or empty entity value fall back to the plain per-value shift: equal source
  dates in those rows shift equally, and their intervals are not kept.
- The mask secret holder can recompute every offset from a source entity value.

## 2. Established solutions

Searches run (2026-11-07, WebSearch): MIMIC-IV per-patient date shifting; HHS de-identification
guidance on date shifting under Expert Determination; OMOP and i2b2 date-shift practice; Google
Cloud DLP `DateShiftConfig` with `context` and `crypto_key`; keyed-HMAC per-resource date offsets
(Aidbox FHIR de-identification); the PhysioNet `deid` and Philter tools. Two pages could not be
fetched from this sandbox (`docs.cloud.google.com`, `www.health-samurai.io` are outside the
session's network allowlist); their content below comes from search-result extracts of the
official API reference pages. In the codebase: `transforms/date_shift.py`,
`execution/_strategies/_date_shift.py`, `transforms/windowed_date.py`, `transforms/derived.py`,
`determinism/_derive.py`, `generation/pool/_canonicalize.py`, every `group_by` reader (an AST walk,
27 sites, section 5), the draw-site catalogue and providers, the native config gate, the
out-of-core compatibility table, the reason registry, roadmap row 24b.

Findings:

- **MIMIC-IV (PhysioNet).** "A single date shift was assigned to each `subject_id`"; dates move
  into 2100 to 2200; intervals within one patient are consistent; two patients with the same
  shifted year are not from the same real year (physionet.org/content/mimiciv,
  mimic.mit.edu/docs/iv/modules/hosp/patients). Per-entity, one offset per subject, applied in
  every table that carries `subject_id`: the model G1 follows.
- **Google Cloud DLP `DateShiftConfig`.** `upper_bound_days`/`lower_bound_days` (inclusive, each
  at most 365250 days), `context` ("the field that contains the context, for example an entity
  id") and `crypto_key`; "this results in the same shift for the same context and crypto_key";
  the two are set together and only on table items. This is exactly the keyed per-entity design;
  the bound cap is adopted (section 3).
- **Keyed HMAC of the entity id.** Aidbox derives a resource's offset from
  `HMAC(dateShiftKey, resource.id)`, "deterministic per resource but unpredictable without the
  key". A practitioner guide warns against deriving offsets from the plaintext MRN without a
  secret and against a single global offset (it lets an attacker realign everyone from one known
  date). Decoy's derivation is keyed by the admitted mask secret (no unkeyed fallback exists).
- **OHDSI/OMOP practice** (OHDSI forum, "Skewing of timestamps on a per-patient basis"): a
  per-patient skew of all timestamps, typically within about ±180 days; usually skipped because
  OMOP stays behind a firewall. **i2b2 / MIMIC-II notes**: a uniform random day shift per record,
  criticised for confidentiality in arXiv 2209.09631. **UC Davis CTSC tip sheet**: per patient a
  random integer in ±365 excluding zero, same shift for all the patient's dates.
- **HHS guidance** (hhs.gov de-identification page): Safe Harbor removes date elements finer than
  the year; anything else, date shifting included, needs Expert Determination. Practitioner
  summaries add that the offset is per patient, not per record, and is itself a re-identification
  key to protect.

Design follows: the Google DLP keyed-context model (offset = keyed PRF of the entity id, reduced
into an inclusive day range, bound cap 365250) on the engine's existing HKDF-then-HMAC envelope
(RFC 5869, RFC 2104), which is what `group_by` already does, plus a domain-separation prefix as
roadmap row 24b prescribes. Custom code: the option parser, the entity text encoding (needed
because the shared canonicaliser is type-sensitive, finding 2), the consistency checks and the
overflow guard. Zero exclusion (UC Davis) is a non-goal for consistency with plain `date_shift`.

## 3. Behaviour

Config (`provider_config` of a `date_shift` column; a namespace is already required):

| Key | Type | Default | Meaning |
|---|---|---|---|
| `entity_key` | non-empty string naming another column of the same table's `columns` | absent | turn on per-entity offsets |
| `min_days` / `max_days` | existing; with `entity_key` they must be plain ints in `[-365250, 365250]` | -365 / 365 | inclusive offset range; reversed bounds are swapped, as today |

```yaml
tables:
  - name: admissions
    columns:
      - name: patient_id
        strategy: hash            # the key may itself be masked; the anchor is read pre-mask
        namespace: patient_ids
      - name: admitted_on
        strategy: date_shift
        namespace: patient_dates
        provider_config: {entity_key: patient_id, min_days: -180, max_days: 180, date_format: "%Y-%m-%d"}
      - name: discharged_on
        strategy: date_shift
        namespace: patient_dates  # same namespace and range: same offset per patient
        provider_config: {entity_key: patient_id, min_days: -180, max_days: 180, date_format: "%Y-%m-%d"}
  - name: labs
    columns:
      - name: subject             # a different column name for the same entity is fine
        strategy: passthrough
      - name: drawn_at
        strategy: date_shift
        namespace: patient_dates
        provider_config: {entity_key: subject, min_days: -180, max_days: 180, date_format: "%Y-%m-%d %H:%M:%S"}
```

**Entity source encoding (`ENTITY_SOURCE`).** `b"\xffdate-shift-entity/v1\x00" + text(e)` where
`text(e)` is:

| Entity cell | `text(e)` |
|---|---|
| null (`None`, NaN, NA, NaT) or `""` | no entity: the row uses the plain per-value shift (its own date as the digest input, plain domain), as `group_by` does |
| `int` or numpy integer (not `bool`) | ASCII decimal of `int(e)` (so `123` and `"123"` agree, finding 2) |
| `str` (incl. `numpy.str_`) | `_canonicalize_source(e)` (NFC UTF-8; no trimming or case folding: `" 123"` is another entity) |
| `Decimal` | UTF-8 of `str(e)` (`Decimal("123")` agrees with `123`; `Decimal("123.0")` does not) |
| `date` (not `datetime`) | ISO `YYYY-MM-DD` |
| `bool`, `float`, `datetime`/`Timestamp`, `bytes`, anything else | run fails: `StrategyError` `runtime.date_shift_entity_key_unsupported_value`, message names table, column, entity column and the Python type name only |

Why `0xFF` is unreachable (G4): every `_canonicalize_source` branch yields one byte for `bool`, a
4-byte length starting `0x00` for `int` (`_encode_int`, any body under 2^24 bytes), or valid UTF-8
(`str`, `Decimal`, `date`, aware `datetime`, the `str()` fallback); `0xFF` never occurs in UTF-8.
So no canonical source of any strategy equals or prefixes an entity source. The trailing `0x00`
after the tag keeps the tag prefix-free against any future `0xFF` label (row 24b).

Per cell of the date column: unchanged from today (parse with `date_format` or detect; null source
stays null; unparseable non-null records a `format_error` `RowError` and is never emitted
unflagged), except:

- the offset comes from G1;
- **overflow**: a row whose shifted value would leave pandas' `Timestamp` range records a
  `format_error` `RowError` with the fixed reason "shifted date is outside the supported date
  range" and keeps its cell for the row-error rule (fail or quarantine), instead of the bare
  `OverflowError`. Checked on the int64 nanosecond values before the add.

**Failure modes.** Codes are new unless marked existing; section 7 has the registry change.

| Failure | When | Behaviour |
|---|---|---|
| `entity_key` truthy but not a string, empty after `strip()`, naming no `columns` entry of the table, or naming the date column itself | compile | `plan.date_shift_entity_key_invalid`, path `...provider_config.entity_key` |
| `entity_key` set and `min_days`/`max_days` not a plain int (`bool`, `"5"`, `5.0`) or outside ±365250 | compile | `plan.date_shift_entity_key_invalid`, path names the bound |
| `entity_key` with `group_by`, `preserve_values` or `when`, as a `nested` child, or on a date column that is an FK endpoint | compile | `plan.date_shift_entity_key_unsupported_combination`, path names the conflicting key; message says which |
| two `entity_key` columns in one namespace with different resolved ranges; or two `entity_key` columns of one table naming the same entity column in different namespaces | compile | `plan.date_shift_entity_key_inconsistent`, path names the second column |
| unsupported entity cell type | run | `runtime.date_shift_entity_key_unsupported_value` (raised after the `except` closes: no `__cause__`/`__context__`) |
| missing or misaligned anchor snapshot (an adapter wiring error) | run | existing `runtime.date_shift_group_anchor_snapshot_missing` / `_misaligned`; the message names the option actually set |
| shifted date out of range | run | `format_error` `RowError` (existing trigger) |
| native full-frame, sequential native, native chunked, unified slice, physical shadow | routing | declined by `date_shift_config_rejection`: `date_shift_entity_key_not_native:<column>` (route evidence string, same convention as `date_shift_group_by_not_native`); runs on the Python handler |
| out-of-core | routing | existing `date_shift` refusal in `out_of_core/_compat.py`; falls back |
| a raw plan (no compile) with an invalid `entity_key` | run | `runtime.date_shift_invalid_config` (existing), from the same parser |

All checks run inside `check_date_shift_group_by_refs` (both compile branches and
`run_config_only_checks`), so `checks_passed` gains no name and is byte-identical for every config.
Messages carry table, column, option names and integer bounds only; never a cell value.

## 4. Design notes

- **Structure added.** One option on an existing strategy; one small module owning the option. No
  new strategy, so the strategy catalog, proof manifest, capability matrix, technique,
  distribution, leak-check, residual-PII, leakage and column-access strategy tables are untouched
  (`date_shift` is already classified in each). `wizard_options` unchanged: not offered in the V1
  wizard.
- **One place per fact** (`transforms/dates/entity_offset.py`):
  - the option name `ENTITY_KEY_OPTION = "entity_key"`, the label `ENTITY_OFFSET_LABEL`, the bound
    cap;
  - `parse_entity_key(provider_config) -> EntityKeyConfig | EntityKeyFault | None` (one parser;
    the compile check maps `FaultKind` to plan codes through a module-level dict with a totality
    test, the handler maps any fault to `runtime.date_shift_invalid_config`; no code parameter, no
    mode flag);
  - `date_shift_anchor(provider_config) -> Anchor | None`, `Anchor(column, domain)` with `domain`
    an enum `VALUE_KEYED_GROUP` (`group_by`) or `ENTITY` (`entity_key`): the one accessor every
    runtime site uses to find the anchor column (section 5);
  - `entity_source(value) -> bytes | None` (None for no entity; raises a typed fault for an
    unsupported type).
  Placed beside `transforms/date_preserve.py`, the precedent for a date-option module shared by
  the plan checks and the handler; a sub-package because `transforms/` holds 25 modules.
- **Handler.** `_shift_rows` today builds the digest sources inline. It becomes: a source builder
  per anchor domain (plain/`group_by` keeps the existing loop byte for byte; entity uses
  `entity_source`), one shared `derive_sources` call, one shared reduction, and an entity-only
  overflow guard implemented as a separate step called only from the entity path (no flag
  argument; plain `date_shift` keeps its current behaviour, including the overflow crash). The
  handler reads `ctx.mask_key` directly into `DeriveContext.for_column` as today, so no
  secret-shaped local is bound and the secret-material census does not change.
- **Determinism.** Pure function of `(mask_key, namespace, range, entity text, date)`: chunking,
  row order and route cannot change it. `SEED_PROTOCOL_VERSION` unchanged (new domain, no envelope
  change). One draw site `mask.date_shift_entity` (family `source_keyed_hmac`, entropy root
  `mask_key`, identity `group_key`, partitionable, null-entity rows fall back to `mask.date_shift`)
  appended at the end of `DRAW_SITES` as a standalone constant (the `MASK_FORMULA_DRAW_SITE`
  precedent), its provider one line in `_SOURCE_KEYED_PRIMITIVE` (`"derive"`), and the
  `MASK_STRATEGY_TO_SITE` comment `# + mask.date_shift_entity` (the map stays one site per
  strategy, like `text_mask`). The catalogue pin test is an equality pin of the published
  catalogue, not a ratchet: it gains exactly the appended entry and the map digest.
- **Memory.** One extra `bytes` per usable row during the column's derivation, as `group_by`
  today; no new whole-table state.
- **House style.** Typed `EntityKeyConfig` and `Anchor` instead of re-reading dict keys; no flag
  arguments; comments explain why.

## 9. Known limits

- Entity text normalisation is limited to int/decimal-text agreement; `"0123"`, `" 123"`,
  `"ABC"`/`"abc"` and `Decimal("123.0")` are distinct entities. Users normalise upstream.
- Consistency across tables is checked per namespace and per table; compile cannot know that two
  differently named key columns in different namespaces are the same entity. One namespace per
  entity kind is documented; two entity kinds sharing a namespace share offsets for equal IDs.
- Null or empty entity values fall back to per-value shifting silently (no warning: a per-chunk
  count would make chunked warnings differ from full frame). Owner question Q2.
- An offset of zero is possible when the range includes 0 (as plain `date_shift`).
- Unknown `provider_config` keys are ignored, so a misspelt `entity_key` gives plain per-value
  shifting. A strict option set for `date_shift` would change V1 configs that carry stray keys;
  follow-up Q3.
- Python-only executor; native and out-of-core decline. Large entity-keyed tables run on the
  Python handler at today's `group_by` speed.
- Intervals are exact; see section 1.4.
