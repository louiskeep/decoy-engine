## Problem

`run_pipeline` sends a mask job with more than one mask table to one full-frame pandas adapter call, whatever the tables' sizes:

- The planner's chunked gate refuses it: "chunked execution masks one table per run" (`execution/_planner.py` 295 to 299).
- The unified slice refuses it: `len(table_kinds) != 1` (`execution/_unified_slice_admission.py:276`).
- So `_pipeline_generate_mask.run_generate_and_mask_steps` takes its `else` branch (around line 142) and calls `adapter.run(plan, merged_sources, ...)` once. The pandas adapter converts every source table to pandas before masking any of them (`execution/_pandas_adapter.py` around 210), masks every node on pandas, and converts every table back.

A 1M-row table masks on the chunked dispatcher when it is the only table in the job (B2, measured 3.0x faster at p50 than the previous lane in run `B2-BENCH-2026-10-01-1M`). The same table, submitted next to an unrelated 10-row lookup table, masks on pandas with every table's pandas frame resident at once. Only the platform's own Phase 1 streaming route handles several large tables, and it calls the chunked oracle per table outside `run_pipeline`.

B7 makes `run_pipeline` treat each independent table the way it would treat that table alone: a table that would auto-chunk as a single-table job runs through B2's dispatcher lane, one table at a time; the rest run in one full-frame adapter call, exactly as today.

## What "independent" means

Two mask tables in one job are independent when masking one never reads the other's data. In the engine today, the only cross-table data read during masking is the FK machinery:

- FK parent columns are snapshotted before masking and children are resolved against the parent's source-to-masked map (`_pandas_adapter.py` around 255 to 266, `_dispatch_mask_node` via `relationship_graph.parents_of`); `order_work` adds dependency edges only from FK edges and composite-to-FK-child edges (`execution/_runner.py:209`).
- Everything else is keyed by table: every work node carries its own `table` and reads `frames[node.table]`, and the adapter skips a node whose table is not among its frames (`if node.table not in frames: continue`); the per-job sinks on `StrategyContext` (code-set evidence, pinned corpus records, date-shift anchors) are keyed by `(table, column)` (`execution/_adapter.py` around 158 to 174 and the field comments there); pool-cache identities are deterministic functions of config and seed.
- Namespaces do not carry data between tables. `build_namespace_registry` is a pure function of config and FK relationships (`relationships/_namespace.py:167`), and every chunk-admitted strategy derives its output from the namespace seed and the value itself (the value-keyed contract the chunked gate enforces, `execution/_chunked.py` 176 to 183). Two tables sharing a namespace therefore mask the same source value to the same output in any order and in any process.
- The job seed is a function of `global_settings.seed` only (`plan/_seed.py`), so restricting a config to one table does not change any seed.
- Randomness: the unseeded paths draw from a fresh `default_rng()` per handler call, so no shared stream couples tables. The same property makes their output differ between any two invocations, so a job containing one can never be compared exactly between split-on and split-off. Such jobs do not split (job gate 9). The unseeded mask paths in `execution/_strategies` today are: non-deterministic `categorical` (`_categorical.py:215`), non-deterministic `shuffle` (`_shuffle.py:54`), and `nested` wrapping either of them in non-deterministic mode (`_nested.py` forwards the parent's `deterministic` to the child seed). Every other mask strategy is seeded from `mask_key`, `job_seed` or config text (non-deterministic `faker` and `composite` draw from `job_seed`; `formula` seeds `random.Random` from the column name and formula text), so it repeats across invocations.

Definition used by B7: a job's mask tables are independent when the job has no FK edges at all, that is `RelationshipGraph.edges` is empty and the config has no `relationships` block. A job with any FK edge keeps today's routing for every table, including tables outside the FK component (Known issues). Acceptance test 1 pins the definition, including a namespace shared across a dispatched and a non-dispatched table.

## Guarantee (pinned)

For every `run_pipeline` call:

1. **Nothing changes unless a table is dispatched.** The split engages only when every job gate in Design 2 holds and at least one table passes the table gate. No-split jobs may execute the read-only decision helper `decide_multi_table_split`, but never enter `run_multi_table_split`; their existing execution branch remains unchanged. Their outputs, `quality_metrics`, warnings, timings and errors are byte-identical to the same call with `multi_table_dispatch_enabled=False`, for any valid knob values (for jobs gated out by unseeded randomness, everything except the random columns' values, which differ between any two calls today).
2. **Per-table "when" equals the single-table rule.** A table is dispatched exactly when the same table, submitted alone as a single-table job with the same knobs and its own source, would route chunked (same planner gate, same threshold). The reason recorded for a table that is not dispatched is the reason that single-table job would record.
3. **Output contract of a split job.** Compared with the same call with `multi_table_dispatch_enabled=False` (the split-off run), for a call where the split engages (by job gate 9 always a repeatable job), for any valid `native_threads`, with or without the compiled companion:
   - (a) `outputs` has the same keys in the same order.
   - (b) Every full-frame-group table, and every echoed extra source, `equals(..., check_metadata=True)` its split-off counterpart: today's full-frame shape, pandas schema metadata included.
   - (c) Every dispatched table `equals(..., check_metadata=True)` that table's single-table reference: the output of `run_pipeline` on the job's config restricted to that table (its `tables:` entry, and its `sources` and `targets` entries where present; every other key unchanged), with `sources={table: <its resident source>}` and the same knobs. By guarantee 2 that reference routes chunked on B2's dispatcher lane, so a dispatched table follows B2's output contract exactly: against its split-off counterpart it has the same column names in the same order and the same rows in the same order; every masked column has the same values and null positions, a nullable field with no field metadata, and the same Arrow type except B2 guarantee 3 (b)'s two pinned cells (an all-null string-output column is `string`; an all-null native Faker column with a string-valued provider is `string` when B1's native route ran); every passthrough column present in the split-off output equals the source column, with its field equal to the source field under `check_metadata=True`; and `schema.metadata is None`.
   - (d) A split job's result can therefore hold both shapes at once: dispatched tables in B2's Arrow-exact shape with no schema metadata, full-frame-group tables in today's pandas shape with `b"pandas"` metadata. This is B2's owner-approved pre-GA route-dependent shape (B2 Design 10), now decided per table instead of per job. B7 adds no pandas reconstruction to dispatched tables. Converging the full-frame route onto the Arrow-exact contract is §ROUTE-OUTPUT-CONTRACT, not B7.
   Jobs using a vault writer retain the existing full-frame execution and mutation boundary (job gate 7).
4. **Side channels, as permutations.** `warnings` is a permutation of today's tuple, `timings` carries the same multiset of `(strategy_type, column)` keys, and `quality_metrics["code_set_corpora"]` the same entries; their order follows execution order (Design 6). `fidelity_report` and `post_validation` run unchanged, after every table has masked, over the outputs of guarantee 3: for a full-frame-group table they see today's output; for a dispatched table they see its B2-shaped output, exactly as the single-table route does, so their results equal the split-off run's whenever the dispatched tables' output schemas equal the split-off schemas apart from schema metadata. Split calls have no validators and no quarantine (job gates 6 and 8).
5. **Deterministic order and error precedence.** Dispatched tables run one at a time in `tables:` config order, then the full-frame group runs once. The first unit that raises ends the call with that error, and no later unit starts. Two declared differences from today:
   - **Row-error aggregation.** A dispatched table that reports a row error raises `RowErrorsFailedError` at once, carrying the first failing chunk's records, the behavior single-table auto-chunk already has on both B1 routes (`_pipeline_routing.py` "Row-error honesty"; `native/_route_diagnostics.py`, `_chunked_oracle.py`). Today the job collects row errors from every table and raises one `RowErrorsFailedError` from finalize (`_pipeline_finalize.py` around 426). Both fail closed with the same error class and return no output; jobs with quarantine enabled or validators configured are not split (job gates 6 and 8), so no row a job would quarantine today is turned into a failure and no validator report is skipped.
   - **First reported failure.** Today independent work runs in lexicographic `(table, columns)` order (`order_work`, `execution/_runner.py:209`); B7 runs dispatched tables in config order before the full-frame group. When two independent tables would both fail, the error B7 reports first may name a different table (tables configured `z, a`: B7 reports `z`, today reports `a`). Which tables fail does not change; only which failure surfaces.
6. **Threads.** Active native kernel parallelism for the one dispatched table is bounded by `native_threads` (B2's knob, 1 to 1024, validated by `require_lane_knobs`); sequential table execution never multiplies that active-work budget. The companion may retain its single process-wide host-sized Rayon pool (`decoy-engine-native/src/threads.rs`); resident workers and their stacks are included in whole-process RSS, which section 11 measures. Output bytes do not depend on `native_threads`.
7. **Memory.** No more than one dispatched table's B2 working set is alive at a time, and the full-frame group holds pandas frames only for its own tables. Design 7 states the bound against today; section 11 measures it.
8. **Evidence, never silent.** Every split call records, per mask table, whether it was dispatched and why or why not, and per dispatched table B2's lane fields and per-column planned and executed backends (Design 8). The payload is JSON-safe and deterministic.

## Non-goals

FK-linked tables, and jobs where any FK edge exists (sequential and out-of-core routes, phase D); mixed generate and mask jobs (F2); jobs with unseeded randomness, a vault writer or validators (job gates 7 to 9; transactional vault staging would be a broader design); native admission for unconfigured columns (B8: until it lands, such tables are dispatched but B1 reroutes them to its oracle route with `uncovered_columns`); converging the full-frame route's output shape with B2's (§ROUTE-OUTPUT-CONTRACT); releases and platform or CLI wiring (B3, B4, B5); changing B1's `run_mask_chunked`, B2's `run_auto_chunk`, lane selection or join, the planner's single-table classification, the unified slice, or the pandas adapter; dispatching tables below `auto_chunk_threshold_rows` (they stay in the full-frame group, Known issues); running tables concurrently; incremental output sinks or lazy batch input (B6a, B6b); the platform's Phase 1 streaming route; the Phase E 100M-row gate (B7 carries its own bounded merge benchmark, section 11).

## Design

### 1. Where it plugs in

New module `execution/_pipeline_multi_table.py` (at most 600 lines), with two entry points and the free functions the tests grade:

```
decide_multi_table_split(config, *, plan, registry, graph, substrate, caller_sources,
    table_kinds, auto_chunk, auto_chunk_threshold_rows, dispatcher_enabled,
    split_enabled, vault_writer_present) -> MultiTableSplit | None

run_multi_table_split(split, config, *, resident_sources, engine_version, registry,
    adapter, chunk_size_rows, key_provider, native_threads, plan, graph,
    namespace_registry, unconfigured_column_policy, generate_output_tables)
    -> tuple[outputs, timings, boundary_conversion_ms, warnings, quality_metrics, row_errors]

split_reproducibility_stamp(split, *, chunk_size_rows, auto_chunk_threshold_rows)
    -> dict[str, Any]
```

`MultiTableSplit` is a frozen dataclass: `dispatched: tuple[str, ...]` in config order, `full_frame: tuple[str, ...]` (the remaining mask tables, config order) and `reasons: Mapping[str, str]` (one entry per mask table). `decide_multi_table_split` is read-only (it reads config, the plan, source schemas and Arrow row and null counts) and returns `None` when a job gate fails or no table passes the table gate. `caller_sources` is `run_pipeline`'s `caller_sources` (it may hold a `LazySource`); `resident_sources` is what `resolve_resident_sources` returned.

`run_generate_and_mask_steps` gains two parameters, `caller_sources` and `multi_table_dispatch_enabled` (it already receives `native_threads` and `chunked_dispatcher_enabled` from B2). Before its existing `if route_chunked:` branch it calls `decide_multi_table_split` with `dispatcher_enabled=chunked_dispatcher_enabled`, `split_enabled=multi_table_dispatch_enabled` and `vault_writer_present=vault_writer is not None`; on a non-`None` result it calls `run_multi_table_split` instead of `adapter.run`, then continues with the same `stamp_execution_metrics` and fidelity code, passing the split (the vault step is a no-op there, since a split job has no vault writer). The single-table `route_chunked` branch and the plain `adapter.run` branch are untouched. `run_multi_table_split` takes no vault writer and passes `vault_writer=None` to every unit.

`_pipeline_finalize.stamp_execution_metrics` gains `multi_table_split: MultiTableSplit | None = None`. When it is `None`, the function is unchanged. When it is set, the function stamps `quality_metrics["auto_chunk"]` unconditionally as `merge_lane_stamp(split_reproducibility_stamp(...), mask_quality_metrics)`, B2's merge function, in place of `auto_chunk_stamp`. This is needed because `auto_chunk_stamp` reports `mode: full_frame` whenever `route_chunked` is false, and a split call has `route_chunked == False`. The adapter-identity stamp is unchanged.

`run_pipeline` gains one keyword argument next to B2's two: `multi_table_dispatch_enabled: bool = True`, validated with `require_bool` in the existing fail-early block, never a config field, so it stays out of `pipeline_config_hash`. `_pipeline.py` is 679 lines on this base, exactly its ratchet in `tests/sentry/test_module_size.py`. B7 adds no net lines there: the builder keeps the ratchet exactly as B2 did (moving docstring lines into `_pipeline_routing`'s module docstring), never by raising or loosening it.

### 2. Job gates (all must hold, else `None`)

1. `auto_chunk` is true, B2's `chunked_dispatcher_enabled` is true, and `multi_table_dispatch_enabled` is true. Either kill switch restores today's multi-table behavior; with the dispatcher off there is no speed to gain, so B7 does not move tables onto B2's legacy chunked pandas lane.
2. The call reached the full-frame continuation: layer-1 routing chose `full_frame` (explicit or `auto`) and the unified slice did not run. Like single-table auto-chunk, an explicit `execution_mode="full_frame"` does not prevent dispatch.
3. At least two mask tables and no generate tables.
4. Independence: `graph.edges` is empty and `config.get("relationships")` is empty.
5. The resolved substrate is `pandas`.
6. Quarantine is not enabled (`(config.get("quarantine") or {}).get("enabled")` is falsy, the same read as `_pipeline_finalize.py` around 408). Chunk-admitted strategies can emit row errors (date_shift, code_set, bucketize), and the chunked route fails closed on them, so a quarantine-enabled job stays whole.
7. No vault writer: `vault_writer_present` is false. Today the pipeline adds vault entries once, after every table has masked (`_pipeline_generate_mask.py` around 172), so a later table's failure leaves the caller's writer untouched. A split would let B2 add a dispatched table's entries chunk by chunk (B1 contract, per-chunk vault entries) before a later table fails, leaving partial entries visible to a caller that catches the error or writes the vault later. A job with a vault writer stays whole.
8. No validators: `config.get("validators")` is empty. Today finalize runs validators before raising row errors (`_pipeline_finalize.py` around 387 onward) and raises `ValidatorFailedError` with its report first. A dispatched table's row error would raise inside the split before validators run, changing the public failure class and dropping the report. A job with validators stays whole.
9. No unseeded randomness: no mask work node in the plan resolves to an unseeded path. The free function `unseeded_random_nodes(plan) -> tuple[tuple[str, str, str], ...]` returns `(table, column, strategy)` for every node whose `ColumnSeed` has `strategy` in `UNSEEDED_RANDOM_STRATEGIES = {"categorical", "shuffle"}` with `deterministic` false, or `strategy == "nested"` with `deterministic` false and a child `strategy` in that set. It reads the plan only, so a `when:`-gated node counts whether or not it matches any rows. Acceptance test 2 enumerates the live strategy registry so a new unseeded path fails CI until it is added here.

### 3. Table gate (per mask table, in config order)

A table is dispatched when the single-table chunked rule holds; otherwise it joins the full-frame group with that rule's reason:

`_planner._chunked_rejection(config, mask_tables=[t], generate_tables=[], work=..., ordered_work=..., substrate=..., source_tables={t: caller_sources[t]} if t in caller_sources else {}, auto_chunk_threshold_rows=...)` returns `None`, with `work` and `ordered_work` built once from the job's plan exactly as `classify_job` builds them (`build_work_list(plan, registry)`, then `order_work(work, graph)`). Passing only `t`'s own source makes the "extra loaded frames" check (`_runtime_source_rejections`) pass for siblings while every other runtime gate applies unchanged: a missing source or a `LazySource` (`lazy_source_rejection`), the size threshold, chunk-stable dtypes, and the bucketize, group_key, text_mask, code_set and bucket_perturb source gates. The reason recorded is the joined rejection string, identical to that single-table job's `rejections["chunked"]`.

There is no second table gate. Revision 2 had one for B2's metadata-parity and type-parity lane gates; B2 removed them before it merged (B2 revision 4), and `select_lane` now sends a table to the legacy lane only under the kill switch, which job gate 1 already excludes. A table B7 dispatches therefore always runs on B2's dispatcher lane, the same lane it would take alone.

The gate reads only config, the plan, source schemas and Arrow row and null counts; no values. Decision order and reasons are deterministic.

### 4. Execution

1. **Dispatched tables, one at a time, in config order.** For each, call `_pipeline_auto_chunk.run_auto_chunk(config, resident_sources[t], table=t, engine_version=..., registry=..., adapter=..., vault_writer=None, chunk_size_rows=..., key_provider=..., native_threads=..., dispatcher_enabled=True)` through the module attribute, so B2's spies on `run_auto_chunk` see every call. B2 slices the table, runs B1's `run_mask_chunked`, which picks its native or oracle route for the whole table before the first chunk (B2 Design 4, "per-table fallback"), and joins the chunks with `join_dispatcher_chunks`. It returns `({t: masked}, timings, boundary_conversion_ms, warnings, quality_metrics)`; B7 keeps the output table and the small per-table results and holds no reference to the chunk list, which is local to B2's `_run_dispatcher`.
2. **Then the full-frame group, once.** If the group has tables, or the caller loaded extra sources that are not mask tables, call `adapter.run(plan, group_sources, ...)` with today's arguments, where `group_sources` is `resident_sources` minus the dispatched tables, in their original order. The adapter skips work nodes of tables it has no frame for. Extra loaded frames therefore keep being echoed in `outputs` as today. The group's row errors flow to finalize as today.
3. **Assemble.** `outputs` is rebuilt in the key order today's single adapter call produces (the order of `resident_sources`, which the adapter echoes), taking each table from its unit.

Established pattern: per-unit plan-time fallback is how Apache Gluten (operators that Velox cannot run fall back to vanilla Spark with a recorded reason) and Spark RAPIDS (`spark.rapids.sql.explain=NOT_ON_GPU`) handle a partly accelerated plan; B2 already cites both and applies the rule per table. B7 applies the same unit, a table, to jobs with several of them.

### 5. Output contract in a split job

B7 takes each unit's output as that unit produces it and adds no casts, metadata or reconstruction of its own.

- **Dispatched tables.** The output is `run_auto_chunk`'s, which is the output the same table gets as a single-table auto-chunk job: `run_generate_and_mask_steps` reaches `run_auto_chunk` through the `_pipeline_route_exec.run_mask_chunked` delegate with the same arguments, and a split job, like a routed single-table job, has no validators, no quarantine and no vault writer that could change the output afterwards. B2's contract therefore applies unchanged (B2 guarantee 3): masked values route-neutral, string-output columns `string`, passthrough columns the source column exactly, no schema metadata. The single-table reference in guarantee 3 (c) restricts the config to one table; that changes nothing a dispatched table reads, because the job seed comes from `global_settings.seed` only, namespaces are pure functions of config, and B1 reads its own table's entry (see "What "independent" means"). Test 4 pins the reference identity.
- **Full-frame-group tables.** They run today's code on a subset of frames. With no FK edges, nothing in the adapter reads another table's frame, so their outputs are today's, pandas schema metadata included.
- **Why no reconstruction.** Revision 2 rebuilt whole-table pandas metadata on dispatched tables so that a split job's output would equal today's byte for byte. B2's merged contract removed pandas metadata from the auto-chunk route on purpose, and Cam's direction is that the Rust path does not reproduce pandas quirks. Rebuilding it inside B7 would make the same table come out in two shapes on the chunked route depending on whether it had a sibling, and would add a pandas conversion to every dispatched table. The per-table rule keeps one shape per route: a table's shape depends only on whether it ran chunked, as it already does for single-table jobs crossing `auto_chunk_threshold_rows`.
- **What a consumer sees.** One result may carry dispatched tables without schema metadata next to full-frame tables with it, and a passthrough column of a dispatched table may keep a type (`large_string`, `time32`, `date64`, `time64[ns]`), nullability or field metadata that the same column in a full-frame table loses. Masked values are equal on both. CHANGELOG and the compatibility contract state this (section 12).

### 6. Results and ordering

- `timings`: dispatched tables' B2 timings in config order, then the group's. `boundary_conversion_ms`: the sum over units (B2's per-chunk sum per dispatched table, zero on B1's native route, plus the group's).
- `warnings`: each dispatched table's B2 warnings in config order, then the group's; no de-duplication across units (today's adapter keeps a warning emitted by two tables twice, and so does B7).
- `quality_metrics["code_set_corpora"]`: the concatenation of the units' entries, in the same order.
- `row_errors`: the group's only (dispatched tables raise instead, guarantee 5).

### 7. Threads and memory

**Threads: sequential tables, whole budget each.** Considered: running dispatched tables concurrently with the budget split between them. Rejected because it raises peak memory to several tables' working sets at once, makes error precedence depend on timing, and gives no gain when the companion kernels already spread one column's batch over `native_threads`. Established pattern: morsel-driven query engines (Leis et al., SIGMOD 2014, the design DuckDB follows) give all worker threads to one pipeline's morsels at a time rather than partitioning threads across independent pipelines, and Spark's default FIFO scheduler gives the first job priority on all executors while its stages have tasks. The active-work budget B5 prices therefore stays `native_threads` for any number of tables. `native_threads` bounds active kernel work, not resident threads: the companion's process-wide Rayon pool is sized to the host (`threads.rs`), and its idle workers count toward whole-process RSS (guarantee 6).

**Memory bound.** Today a split-eligible job holds, at its peak: every resident source, the pandas frames of every mask table at once (`_pandas_adapter.py` around 210), and every output. With B7 the peak is at most: every resident source (unchanged; the caller loaded them), the finished outputs of tables already masked (they are returned, as today), plus the larger of (a) one dispatched table's B2 working set (its chunk list, the concatenated table and its combined copy inside `join_dispatcher_chunks`, B2 Known issues) and (b) the full-frame group's adapter working set, which covers only the group's tables. B7 never holds two dispatched tables' working sets at once. This is a structural lifetime bound, not a claim that RSS falls between tables: source frames, accumulated outputs, allocator arenas and native workers stay resident. Section 11 checks the result as measured bars.

### 9. Companion not installed

The new module imports nothing from the companion. Per dispatched table, B1's preflight probes only the kernels that table's columns need; a missing or ABI-incompatible companion sends that table to B1's oracle route (`crypto_extension_unavailable`, `index_extension_unavailable`), recorded per column as planned `rust_companion` or `rust_pool_select`, executed `pandas_oracle`. Tables with only redact, truncate and passthrough run natively without it (`arrow_python`). The output contract holds either way (guarantee 3); the one companion-dependent cell is B2's native Faker all-null type, which the single-table reference reproduces under the same companion state.

## Known issues (tech debt, not blockers)

- **Mixed output shape in one result.** A split job returns dispatched tables in B2's Arrow-exact shape (no schema metadata, passthrough columns as the source) and full-frame-group tables in today's pandas shape (guarantee 3 (d)). Masked values are equal. This extends B2's approved route-dependent shape to tables within one job; §ROUTE-OUTPUT-CONTRACT converges the routes. B3 and B4 check their writers against both shapes before pinning a release with B7.
- Tables below `auto_chunk_threshold_rows` in a multi-table job stay on full-frame pandas: the unified slice, which runs small single-table jobs natively, is single-table by design. A per-table unified slice, or one-chunk dispatch of small tables, is a follow-up that needs its own measured run.
- Any FK edge keeps the whole job on today's routes, including tables outside the FK component. Splitting by connected component belongs with the FK work in phase D.
- Quarantine-enabled multi-table jobs are not split.
- Jobs with unseeded randomness (non-deterministic categorical or shuffle, or nested over either), a vault writer, or validators stay on the full-frame path. Unseeded strategies are excluded from every exact split-on/off comparison because their output differs between any two calls today. Splitting vault jobs would need transactional vault staging.
- Multi-table row errors: a dispatched table raises `RowErrorsFailedError` with its first failing chunk's records only, where today one combined payload covers every table (guarantee 5). Same error class; both fail closed.
- Independent hard failures may surface in a different order: B7 reports the first failing table in config order among dispatched tables, today the first in lexicographic work order (guarantee 5).
- A code-set corpus changed on disk during a run could be pinned at different per-table times than on today's lexicographic full-frame path. This requires external mid-run file mutation and is low probability.
- Allocator retention may keep high-water RSS elevated after a dispatched table finishes; the memory bound is structural, and section 11's bars measure the result.
- On a split call `auto_chunk.mode` is `"chunked"` even when some tables ran full-frame; the platform's route label reads that key (`decoy-platform` `api/jobs/v2_node_runs.py:193`, main `61912b2f`) and will say `legacy_chunked`. B3 reads `auto_chunk.tables` and `auto_chunk.lane` instead.
- `explain_plan` does not show the per-table split; the run's `quality_metrics` does.
- Pre-existing on main, recorded by B2: with the default `use_byte_estimate_routing=True`, `run_pipeline` raises `AttributeError` before routing for a mask table with a `date32`, `date64`, `time32`, `time64` or time-zone-aware column (`_mem_estimate_schema.sample_average_string_bytes`). Multi-table jobs with such columns reach B7 only with the flag off until that defect's own slice fixes it.
- Tables with unconfigured columns are dispatched but run on B1's oracle route until B8.
- Outputs are fully materialized and concatenated per table (B6a).
- Library callers get `native_threads=1` unless they pass a budget; platform and CLI pass reservations from B3, B4 and B5.
