## 1. Why + what
Phase D will add Rust FK payload kernels inside the existing OOC (DuckDB+Arrow) and SEQ (pandas) routes. Before any kernel lands, D0 freezes the two things every later FK-kernel slice is graded against:

1. A **strict-parity comparator + a characterized, frozen BASELINE** of exactly where the OOC FK route (`run_fk_out_of_core`) and the pandas oracle (`PandasExecutionAdapter.run`) currently agree vs. diverge at the strict level (exact Arrow schema incl. type width + field metadata, row + column order, null-vs-NaN, int64-vs-float64). The existing value-normalized harness folds those divergences away; D0 does NOT claim they are gone. D0 pins the current reality, including the KNOWN GAPS (§4), so no later kernel slice can widen the divergence undetected. Each known gap is filed as its own tracked item for a separately gated resolve-or-accept decision; D0 fixes none of them.
2. A **native-execution witness**: a test-side mechanism, patched at the real lookup bindings and attributed per fixture, that observes which kernel entrypoint produced a masked column and distinguishes the native path from a fallback. D0 asserts the **negative baseline** (no native FK-payload entrypoint exists or ran; the chain-FK OOC run is served entirely by the pyarrow fast path / Python reference kernels) and exposes the reusable assertions a later slice flips to the positive.

D0 ships **no kernel and no product-code change**: comparator, witness, characterization, and case table are all test-side. It runs on ONE already-admitted acyclic shape: the parent to child single edge the existing harness already builds (`_build_single_edge`, a chain of length 1). No routing, admission, or compatibility change.

## 2. Scope
**In (all under `tests/parity/`, no `src/` edit):**
- A strict comparator helper with INDEPENDENT, separately-callable checks: exact schema equality incl. field metadata (`schema.equals(..., check_metadata=True)`), type width / int64-vs-float64, row order, column order, cellwise value equality, and null-distinguished-from-NaN. Each check has its own positive (equal-input) and negative control proving it bites; not one combined negative.
- A **baseline characterization** test on the chain single edge for the admitted OOC parent-key strategies ({hash, redact, truncate, passthrough}): assert, per dimension, the current OOC-vs-oracle result -- EQUAL where it holds, and the EXACT pinned delta where it does not (the §4 known gaps). Green because it matches reality; it does not assert strict parity holds.
- The **witness** helper: spies installed at the `_mask`-module lookup bindings (§4), scoped around the OOC call only, attributing observations per single-strategy fixture; exposes `assert_legacy_path_only` / `assert_native_ran` with a missing-observation control (fails if zero relevant entrypoints observed) and a fallback-vs-native distinction. D0 asserts `assert_legacy_path_only` passes and `assert_native_ran` fails today.
- A **known-gaps note** in `tests/parity/` (extend `SEMANTIC_DIFFERENCES.md`) listing each strict divergence, its exact current delta, and its tracked backlog item; plus concise design notes (helper ownership; the standard Arrow `Table.equals`/`schema.equals(check_metadata=True)` comparison pattern and pytest patch-where-looked-up pattern used -- the established-methodology account).

**Out:** no Rust kernel; no change to any `src/` behavior or schema; no hot-path product instrumentation; no routing/admission/compat change; no SEQ work (D2a+); no new shapes beyond the existing chain single edge; no `src/decoy_engine/kernel/` edit; no fix to any characterized gap (each is a separate gated item).

## 4. FRAME: source survey (verified on `49b88677`; strict differences confirmed by the r1 oracle probe)
- OOC mask seam `src/decoy_engine/execution/out_of_core/_mask.py`: `mask_batch` (:288) / `mask_column` (:97) dispatch per column via `seed.per_column` / `column_seed.strategy` to scalar kernels **imported by name at :39** (`from decoy_engine.kernel import hash_array, passthrough_array, redact_array, truncate_array`). The names are therefore bound in the `_mask` module namespace: a spy MUST patch `decoy_engine.execution.out_of_core._mask.<name>` (patch-where-looked-up), NOT `decoy_engine.kernel.<name>`, or OOC calls are missed (r1 finding 2).
- Kernel layer `src/decoy_engine/kernel/_scalar.py`: `redact_array` (:112) / `truncate_array` take a pyarrow-vectorized fast path with a total, NON-raising guard that falls back to a frozen pure-Python reference (`_redact_array_reference` :93, `_truncate_array_reference` :150); the Python fallback itself CAN raise. `hash_array` (:74) is a pure-Python loop, no fast path. There is **no Rust/companion FK-payload execution at this seam** (pyarrow's own compute is native C++, but no Decoy Rust FK kernel exists); that is what D1+ add, so D0's witness establishes the detector and pins the negative baseline (r1 FRAME confirmation).
- Strict OOC-vs-oracle gaps that exist TODAY (the baseline D0 characterizes, not fixes): (a) schema-level `pandas` metadata -- the oracle round-trips through pandas and carries `pandas` schema metadata; the OOC path's `_fixed_output_schema` (`_runner.py:599`) preserves SOURCE metadata, so `check_metadata=True` differs; (b) preserved float NaN (OOC) vs null (oracle, folded by `pa.array(from_pandas=True)`); (c) fixed up-front FK output dtype (OOC) vs inferred dtype (oracle) -- the int64-vs-float64 narrowing; (d) empty / all-null column outcomes (inventory explicitly, do not assume equivalent). Each is pinned with its exact delta and a tracked item.
- Witness attribution (r1 finding 2): the scalar entrypoints receive no table/column identity, so attribution comes from FIXTURE CONSTRUCTION -- each baseline fixture masks exactly ONE strategy on ONE column, so a witnessed entrypoint call maps unambiguously to that (table, column, strategy). The spy is installed only around `run_fk_out_of_core`; the oracle (`PandasExecutionAdapter`) reaches the same kernels through its own module bindings, so patching the `_mask` bindings isolates observation to OOC. Controls: nonzero-coverage (expected entrypoint observed >= expected count) and missing-observation (zero observed -> fail).
- Witness design decision (tech-lead call, unchanged from r1): test-only (no `src/` instrumentation). A threaded per-column backend tag in `mask_batch` would be hot-path product code with no consumer until D1 (YAGNI); the test-side spy discharges the §5 "prove the kernel ran" requirement with zero `src/` change. r1 confirmed this is appropriate.
- Witness PROVENANCE (r2 finding 2): observing an entrypoint call is NOT proof the native path produced the output -- the scalar wrappers (`_scalar.py:112`) show one entrypoint can return via its fast path OR its fallback, so a future native kernel could run, fail, and have a fallback supply the actual output while a naive call-count still passes. The witness therefore records, per observation, a `path` tag ({native, legacy}) AND whether that call's RESULT was the one consumed into the masked output; `assert_native_ran(fixture)` passes only when a native-tagged, result-consumed observation exists for that fixture's output and no legacy/fallback call produced it. In D0 there is no native entrypoint, so the real OOC chain yields only legacy, result-consumed observations and `assert_native_ran` fails; the native-vs-fallback discrimination is proven with TEST DOUBLES (§6).

## 4b. Design notes (helper ownership + established patterns; r2 finding 4)
- **One place per fact.** The strict comparator and the witness each live in ONE new focused helper module under `tests/parity/` (the existing `test_out_of_core_fk_parity.py` is already 1,479 lines -- do not grow it with the new helpers; import them). The characterization fixtures' expected deltas are pinned as literals in ONE case-table module; the known-gaps note (`SEMANTIC_DIFFERENCES.md`) is the prose index pointing at those literals, not a second source of truth.
- **Established comparison pattern.** Exact Arrow equality uses pyarrow's own `Table.equals` / `Schema.equals(..., check_metadata=True)` (the library's documented strict-equality API), not a hand-rolled field walk; value/null/dtype checks use pyarrow compute, mirroring the existing harness's `to_pydict` approach but WITHOUT its normalizations.
- **Established spying pattern.** Kernel observation uses pytest's documented patch-where-looked-up monkeypatch pattern against the `_mask` module bindings; no custom import machinery.
- **Ownership of expected values.** Every expected delta and error code is a hardcoded literal asserted against the actual; none is computed from the output under test (a characterization that derives its expectation from the actual run is a no-op and is prohibited).

## 5. Contract (what D0 freezes)
The strict per-executor contract (program plan §6), expressed for the OOC executor on the chain shape, as a FROZEN BASELINE:
1. **Exact Arrow schema** incl. type width + field metadata -- pinned to the current result (EQUAL on structure/width where it holds; the `pandas`-metadata delta recorded as a known gap, not asserted equal).
2. **Row order** and **column order** equality (expected to hold today; asserted strictly).
3. **Null vs NaN** distinguished (not folded); the current OOC-preserves-NaN / oracle-nulls delta pinned as a known gap.
4. **int64 vs float64** width: the comparator checks it STRICTLY (no `1==1.0` fold, unlike the normalized harness) with a negative control proving the check bites. Probe-verified fact (I ran both routes at `49b88677` across int/int, int/float, float/int, null-ref and mixed-kind cases): no admitted+successful single-edge chain produces an output int64-vs-float64 divergence -- both routes agree. D0 therefore FREEZES that agreement (pins dtypes equal), honestly; it does not pin a nonexistent delta. A later kernel slice that narrows a dtype breaks this frozen agreement.
5. **Fail-closed symmetry**: where the oracle raises, OOC raises with the SAME exception type AND the same `ExecutionError.code` (not merely same class -- r1 finding 3); the accepted `out_of_core_fk_key_dtype_unsupported` reject-rather-than-drift outcome recorded per case with its exact code, never silent wrong output, and an assertion failure is never treated as that permitted rejection.
6. **Native-execution witness**: for the admitted cell, the harness asserts that the RESULT consumed into the masked column came from a native-tagged, result-consumed observation (not merely that a native entrypoint was called); D0 asserts legacy-path-only passes + native-required-fails, and proves the native-vs-fallback discrimination with test doubles (§6).
The guarantee handed to later slices: a kernel slice must introduce NO new strict divergence beyond this frozen baseline, and must flip the witness to native (fallback excluded) for the admitted cells it claims. The existing value-normalized harness is retained unchanged as regression evidence (§6 of the program plan); it does not discharge this contract.

**Independent comparator controls** (direct helper unit tests, not by breaking the real route): schema-structure, FIELD-METADATA, type-width/int-vs-float, row order, column order, cellwise value, and null-vs-NaN each get BOTH a positive control (equal input passes) and a negative control (one targeted difference fails). Include an explicit **same-position NaN positive control** (two arrays with a NaN at the same index compare EQUAL under the value check) alongside the null-vs-NaN negative, so "strict" does not reject unchanged NaN-bearing output.

**Witness provenance controls** (test doubles standing in for a future native+fallback dispatch): exactly these four scenarios, ONLY native-only-success satisfies the positive -- (1) native-only success -> `assert_native_ran` passes; (2) fallback/legacy-only -> `assert_native_ran` fails, `assert_legacy_path_only` passes; (3) native-attempted-then-fallback-supplied-result -> `assert_native_ran` fails (result not native-consumed); (4) missing observation (zero relevant calls) -> both fail. The doubles must drive observation of the ACTUAL returned-result provenance, never a preassigned `consumed=True` flag (r3). Coverage is per EXPECTED-MASKED COLUMN: each fixture asserts its expected-masked columns were each observed >= 1; it does NOT assert zero calls for edge fixtures -- D0-empty still masks the 3 parent rows, so parent columns ARE observed (r3 finding 2); only a column that masks nothing (e.g. a join-populated FK child column in `skip_columns`) yields no observation for that column. On the real OOC chain (no native entrypoint), scenario (2) holds for every fixture.

**Must pass unchanged**: the full existing `tests/parity/test_out_of_core_fk_parity.py` suite (normalized harness intact), `tests/parity/` + module-size + public-import-boundary sentries. No existing test weakened; the existing coded-error checks are not loosened.
