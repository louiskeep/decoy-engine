## 1. Guarantee

> Under `delivery.mode: strict` (the default) a `decoy run` either makes every output of the run
> visible together, or makes none of them visible and leaves the previous delivery and its vault
> untouched. Under `best_effort` it makes visible every table that passed, and drops each failed
> table together with every table that depends on it. A post-scan block withholds the whole run
> in both modes. A run that asks for post-scan and cannot evaluate it delivers nothing.

"Visible" means reachable through the path a consumer reads: `out/<name>/LATEST` (and the
derived `current` link) for a project run (run-folder kind R), or the target paths for a fixed
folder (kind A). Crash behaviour differs by kind (4.3). After the visibility point nothing turns
a delivered run into a "nothing delivered" exit; a later durability failure is a warning.

## 2. Frame

### 2.1 Problem

- Each table is written to its target as soon as it is ready (`_write_mask_outputs`, P4
  `src/decoy/cli/run/_execute.py`; `write_targets`, `src/decoy/cli/io/_targets.py:436`). Each
  file is atomic (row 61a). The run is not: a failure in table 3 of 5 leaves 1 and 2 written.
- The chunked loop (P4 `_run_chunked_mask` in `_execute.py`) writes per table through
  `write_chunked_output`.
- Post-scan is report-only (`compute_post_scan_integrity`,
  `src/decoy_engine/execution/_pipeline_finalize.py:470-503`). On `--chunked` it never runs and
  nothing says so.
- `RunLayout.commit_latest` (P4 `io/_layout.py`) moves `LATEST` with "later run id wins", not a
  compare-and-swap. A failed `LATEST` write is a warning with exit 0.
- `--evidence-out` is written after the outputs (`src/decoy/cli/run/_flow.py:101`); its failure
  exits 3 (`_evidence.py`, `EXIT_RUNTIME`) with the outputs already in place.
- `_commit_vault` (P4 `run/_vault.py`) replaces the vault and drops its backup before any output
  is written. The CLI vault writer is new per run (`vault_writer_for_config`, P4 `_prepare.py`),
  so a failed publish leaves the previous dataset next to a vault that cannot reverse it.

### 2.2 Terms

- **Stage.** Where outputs are written before any is visible. R: an F22 directory stage
  (`._decoy_publication_pending_<token>`) beside the run folder. A: a temp file per output.
- **Sink.** `DeliverySink` (`src/decoy/cli/io/_delivery.py`), the one CLI object every route and
  caller writes run outputs through. **Deliver** is its one step that makes the staged run
  current, after every table, the post-scan result and the vault and evidence writes.
- **Visibility point.** R: the `os.replace` of `LATEST`. A: the unlink of the batch journal.
- **Strict** delivers all or nothing (default). **Best-effort** delivers the good tables and
  drops a failed table with every table reachable from it (4.4); a post-scan block still
  withholds everything.
- **Single-root rule.** In both modes every file target and an enabled quarantine file resolve
  under one delivery root: the run folder (R) or one fixed folder with every output directly in
  it (A). Anything else is refused with `layout.delivery_root_split`, exit 1.

### 2.3 User-visible behaviour

```yaml
delivery:
  mode: strict        # strict | best_effort ; default strict, omitted from the dump
```

No CLI flag in V1. The mode is in the config so the result and config hash carry it (UX map
5.5). A non-default mode moves the config hash; the default moves no existing hash.

Exit codes come only from `derive_outcome` (`src/decoy_engine/run_result/_outcome.py:27-58`)
with one exit map, `RUN_EXIT_MAP`, in `src/decoy/cli/exit_codes.py`. RESULT C-EXIT adds
`EXIT_PARTIAL = 6` and `RUN_EXIT_MAP`; DELIV C3 reuses them. The map: `succeeded` 0, `findings`
4, `partially_delivered` 6, `failed` by category (`usage` 1, Click `parameter` 2, `runtime` 3,
`capacity` 5), and `cancelled` today's integer, measured in RESULT C-DOC2. Section 5 states each behaviour as
the inputs `(category, delivery_mode, delivery_outcome, blocking_failed)`. `derive_outcome`
returns `failed` for any non-None category before it looks at delivery (`_outcome.py:44-49`), so
an isolated best-effort table failure sets `category=None`, and a run that delivers nothing
because of failures sets `category="runtime"` (else zero delivered would read as `succeeded`).
An exception that propagates (strict) keeps today's `_errors.py` mapping, which RESULT moves onto
the same map.

Result document (RESULT E1, merged, no schema change): `delivery.mode`, `delivery.outcome`
(`delivered|partial|nothing`), per table `delivery.state` (`delivered|failed|withheld|dropped`),
`reason`, `dropped_because` (`run_result/_model.py:276-288`). DELIV fills them; RESULT renders.

CLI lines, one per non-delivered table, value-free:
`table <name>: withheld (decoy/delivery_withheld)`.

## 3. Established solutions

Search scope: the codebase (F22 publication, `src/decoy/_atomic.py`, P4) and the published
patterns below.

- Same-filesystem stage, fsync file and directory, `rename(2)`: PostgreSQL `durable_rename`
  (`src/backend/storage/file/fd.c`). F22 `publish_unit` (`origin/feat/f22-a3`,
  `publication/_publish.py`) does this for one directory unit; DELIV calls it.
- A pointer written last with an expected old state: git `update-ref <ref> <new> <old>`. DELIV's
  `LATEST` swap refuses any stale expected state.
- In-place replacement of several files: SQLite's rollback journal (sqlite.org/atomiccommit.html):
  backups, journal fsynced, directory fsynced, replace, then delete the journal as the commit.
  Kind A follows that order (4.3).
- Several independent files are not crash-atomic without a journal or a pointer; 4.3 says so.

Custom code left: the drop walk (`plan_delivery`) and the outcome mapping. Both are small and pure.

## 4. Design

### 4.1 One mechanism

| Concern | The one place | DELIV adds no second |
|---|---|---|
| Directory bind | F22 `publish_unit` | the sink never renames directories |
| Several files in one folder | the one-folder batch, moved to `src/decoy/_atomic_batch.py` (C0) | no temp-and-rename of the sink's own |
| File writes | `write_table`, `write_chunked_output` (`_targets.py:406`, `:466`) | called with stage paths |
| Destination identity | `_destination_key` (P4 `_placement.py`) | the root rule keys on it |
| Layout refusals | `layout.*` descriptors (P4 `io/_layout_errors.py`, `tests/sentry/io_policy/test_layout_errors.py`) | `layout.delivery_root_split` joins them |
| Status and exit | `derive_outcome` plus `RUN_EXIT_MAP` | no exit table of DELIV's own |
| Post-scan blocks delivery | `post_scan_verdict` (POSTSCAN-STREAM 4.8, 4.10) | no severity rule in DELIV |
| Pointer | `publication/_current.py` (E2a), also F22's deferred `CURRENT` (13.3) | one semantics |
| Delivery facts | F22 descriptor (R), batch journal (A, private), run result | no `decoy-delivery/v1` record |

### 4.2 Run order (both kinds)

1. Gate: `layout_issues` refuses a split root (C1). P4 `_check_chunked_tables` in `_execute.py`
   handles `--chunked` when the post-scan gate applies. If integrity was requested, it refuses as
   it refuses quarantine (`_ChunkedQuarantineError`). If relationships alone make the gate apply,
   it gives the interim warning and run-result record from 11. CR uses
   `post_scan_integrity_requested(config)` plus direct relationship inspection until C5 replaces
   both applicability checks with `post_scan_gate_applies(config)` from POSTSCAN-STREAM.
2. `DeliverySink.open(layout, config)`: refuses a split root with the same code (for `api.mask()`
   and `demo`, which skip the gate); opens the stage; R reads the pointer's raw bytes; A runs
   journal recovery under the folder lock (4.3).
3. Every route writes through `sink.write_table` or `sink.write_chunked`, which call the file
   writers with stage paths and no ledger. `sink.place_quarantine(config)` gives the engine a
   staged quarantine path. The sink records each table as `ok` or a failure code.
4. Post-scan: the engine raised `PostScanBlockedError` (or an isolated outcome `blocked`), or the
   run returned without a report while `post_scan_gate_applies(config)` is true. C2a uses
   `post_scan_integrity_requested(config)` until C5. Either withholds the whole run, exit 4.
   `--post-validate-enforce` with failed checks also withholds the whole run (today it skips the
   `LATEST` move, `run/_render.py:49-57`).
5. `plan_delivery(config, outcomes)` returns a `DeliveryDecision`.
6. If nothing is to be delivered: `sink.abort()`. Stage removed, pointer untouched.
7. Else `sink.deliver(decision, before_visible)`, which calls the stage's
   `deliver(decision, before_visible)` (the `SinkStage` protocol, 4.6):
   a. take the lock (4.5); R: re-read the pointer and compare with step 2, else
      `delivery_pointer_moved`;
   b. `before_visible()`: commit the vault keeping its backup, then write `--evidence-out` keeping
      its backup (one helper, `PreVisible`, 4.6);
   c. publish (4.3); state `delivering`, then `delivered` at the visibility point;
   d. release the lock; discard the vault and evidence backups, or restore them on any
      non-delivered outcome;
   e. fill the publication ledger (`ctx._published`) with final paths, only when delivered.
8. `_flow.py` `finally` calls `layout.abandon()` on an unfinished exit (`_flow.py:78-81`), which
   calls the abort callback the sink registered on the layout.

### 4.3 Root kinds

**Kind R (run folder).** All targets relative, inside a project. Root `out/<name>/<run-id>/`.

- Stage: an F22 directory transaction beside the run folder P4 made (`create_run_folder`, 0700,
  empty), so on one filesystem. Nested relative targets are allowed.
- Publish: `publish_unit(out, txn, request, ...)` judges the empty run folder and renames the
  stage onto it; then `HeldPointer.swap(expected, run_id)` replaces `LATEST`; then the CLI points
  `current` at the run (POSIX symlink, derived, warning on failure).
- The run folder takes the stage's mode on rename. AT-14 pins 0700.

| Crash point | Left on disk | Visible | Recovery |
|---|---|---|---|
| before bind | stage (F22 L2 litter), empty run folder | previous run | none |
| after bind, before `LATEST` | bound run folder, not current; vault `.bak` | previous run | none; the old vault is the `.bak` (12.1) |
| after `LATEST`, before `current` | `current` lags | new run | next delivery fixes `current` |

**Kind A (fixed folder).** Absolute targets, `--out-dir`, `api.mask()`, `demo`. Every output
directly in one folder.

C2a recognizes `fixed_folder` but passes it through to today's per-file writers. Between C2a and
C2b, `--out-dir` has exactly today's behaviour. Kind A has no strict delivery guarantee until C2b.
C2b replaces the pass-through with the batch below. The final V1 guarantee then covers kind A.

The batch in `_atomic_batch.py` owns the journal `.decoy-batch.journal`, a private file of the
batch protocol, not an engine record. Order (SQLite rollback journal):

1. Stage each output as a temp in the folder (`.<target>.decoy-<hex>.tmp`).
2. Take `_folder_lock(folder)`; if a journal exists, recover first (below).
3. Hard-link a backup of each existing target (`_backup`), and of each table dropped under
   best-effort (D-9).
4. Write the journal: per target its basename, its backup basename or `new`, its staged basename
   or `drop`; plus the vault and evidence backups `PreVisible` reports (absolute target path and
   backup). Fsync the journal.
5. Fsync the folder.
6. Replace each target (or unlink a dropped one), then fsync the folder.
7. Unlink the journal (the commit point), fsync the folder.
8. Unlink the backups; `PreVisible` discards its backups.

Recovery runs under the same lock at `open` and at the start of the batch: for each entry, put
the backup back, or unlink a `new` target; unlink staged temps; restore the vault and evidence
backups; fsync; unlink the journal; fsync. The new run's result carries `delivery_rolled_back`
(WARNING, exit unchanged). The reader is strict: schema 1, at most 64 KiB, entry names are
basenames of the batch shapes (`.<name>.decoy-<12 hex>.bak`, `.tmp`), extra entries only when
the backup is `.<name>.<16 hex>.bak` beside its target. Anything else refuses the run with
`publication_failed` and changes nothing.

Strict on A: all-or-nothing on every caught failure; after a crash the folder is mixed until the
next open or deliver in that folder rolls it back (Q1, Q3).

Nested relative targets on A are refused at `open` with `layout.delivery_root_split` (D-8
decision). The batch's lock is one `flock` on one folder (`_folder_lock`); nested targets need a
lock per subfolder in a fixed order, per-subfolder fsyncs and journal names with path components
(a wider trust class than basenames). That is over the 30-line bound, so V1 refuses and logs it.

### 4.4 Engine contracts

- `config/_delivery.py`: `DeliveryConfig(mode: Literal["strict","best_effort"] = "strict")`,
  `extra="forbid"`; field `delivery` on `PipelineConfig` (`config/_pipeline.py:149`), omitted
  from the dump while default.
- `delivery/_plan.py`: `plan_delivery(config: Mapping[str, Any], outcomes: Mapping[str,
  ReasonCode | None]) -> DeliveryDecision`. Pure. Settled:
  - Mode: parsed once through `parse_delivery_config(config.get("delivery", {}))`, a new
    function in `config/_parse.py` (the one place model validation is allowed) exported from
    `decoy_engine.config`; no mode parameter and no second copy of the default. An unknown
    mode raises a value-free `PipelineConfigError`; it never turns into best-effort. Only an
    absent key means the default (the dump omits the default block): an explicit `None`,
    `False`, `0`, `""` or `[]` reaches the parser and is refused, never read as strict.
  - `outcomes`: one entry per table that has a file target; `None` is ok, a code is the failure
    cause. Tables with no file target are not in `outcomes` and get no delivery state, but the
    walk still passes through them.
  - Table universe, checked before any state is computed, each breach a value-free
    `PipelineConfigError` with a fixed message: the file-target set is the declared tables
    (names in `config["tables"]`) whose `config["targets"]` descriptor has `type == "file"`
    (`config/_targets.py:31-43`), and `set(outcomes)` must equal it (no unknown outcome, no
    missing one). Validation does not tie target keys to tables, so a target key that names no
    table expects no outcome; every edge endpoint
    (relationship parent, relationship child, generate table, `reference` parent) must be a
    name in `config["tables"]`. Pipeline validation does not check relationship endpoints
    against tables (`config/_relationships.py:24`), so the planner fails closed here.
  - Graph source: the validated config dict, not `RelationshipGraph` (its nodes are
    `(table, columns)` and it needs a namespace registry, `relationships/_graph.py:113-130`).
    Edges are table to table: each `relationships[].parent.table` to each `children[].table`
    (`config/_relationships.py:45-48`), plus each generate table's `reference` parents from
    `generation_order(config)` (`generation/synthesize.py:226-252`). Self-edges are ignored.
  - Cycles: table-level cycles are accepted today (`fk_cycle` works on `(table, columns)` nodes,
    `_graph.py:264-311`, raise `:302`; full-frame takes cyclic configs,
    `execution/_pipeline_routing.py:58-83`, `:238`). The walk is a breadth-first reachability
    with a visited set, so a strongly connected component drops whole.
  - `dropped_because`: the smallest failed table name (sorted) from which the dropped table is
    reachable. No topological order is needed.
  - Strict: any failure gives every table `failed` or `withheld` and `deliver=False`.
  - Empty `outcomes` (a run with no file-target table): nothing failed and nothing is withheld,
    so `deliver=True` in both modes and the sink goes on to the vault and evidence commit. The
    rule is `deliver = any table delivered, or outcomes is empty`.
- `delivery/_stage.py`: `DeliveryStage.open(out, run_id, operation_id)` (per-kind
  construction), `stage_path(table, relpath) -> Path` (records the table each staged file
  belongs to), `abort()`, `deliver(decision, before_visible) -> DeliveryReceipt`. The last two
  are the members of the CLI sink's `SinkStage` protocol (4.6). `deliver` removes the staged
  files of every table `decision` does not deliver before it publishes (best-effort on R: "run
  without them", 5 row 3). It holds the pointer lock (4.5),
  calls `publish_unit` and maps every F22 outcome (table below). Receipt: `state`
  (`delivered|uncertain|nothing`), `cause` (a reason code or None). The RESULT 3.2 rule is exact:
  a table reads `delivered` only when the decision says `delivered` and the receipt is
  `delivered` or `uncertain` (the pointer moved, DELIV AT-12); on a `nothing` receipt every such
  table reads `none`, so `delivery.outcome` can never say delivered for a run whose pointer did
  not move.
- `publication/_current.py` owns one state-bearing signature for local and cloud stores:
  `PointerState(raw: bytes | None, version: bytes | str | None)`;
  `CurrentPointer(store: PointerStore, lock_parent: OutputDir, name: str)`;
  `read() -> PointerState`; `locked(timeout_s) -> ContextManager[HeldPointer]`; and
  `HeldPointer.swap(expected: PointerState, new: str) -> PointerResult`. `PointerResult` is the
  one closed result enumeration: `replaced|stale|uncertain|unknown|conflict`. `unknown` is an
  internal store answer that `CurrentPointer` resolves before returning. `conflict` means the
  request definitely failed after the one allowed 409 resend while the captured version was
  still current. `name` is `"LATEST"` for DELIV and `"CURRENT"` for cloud delivery. The run
  passes the state captured when it opened. `swap` never performs a fresh read to obtain its
  expected state. `read_value(state.raw, accept)` decodes and returns the value only when
  `accept(value)` (the CLI passes `is_run_id`, a fullmatch, P4 `_layout.py`), else `None` and a
  warning. The swap compares raw bytes, so an invalid value is still compared, never skipped.
- `PointerStore` seam in `publication/_current.py`: `CurrentPointer` holds the rule and a
  `PointerStore` holds the bytes and version token. `PointerStore.read() -> PointerState`;
  `PointerStore.replace_if(expected: PointerState, new: bytes) -> PointerResult`.
  `uncertain` means "applied, durability unknown"; `unknown` means "may or may not be applied"
  (a lost response from an object store). `LocalPointerStore(parent: OutputDir, name)` is
  DELIV's store: it owns the pointer lock (4.5), the small-file durable replace and the parent
  fsync, gives `uncertain` when the fsync fails after the replace, and never gives `unknown`.
  Its version token is the captured raw bytes. `HeldPointer.swap` passes the captured state to
  `replace_if`; on `unknown`, `CurrentPointer` reads the store once more and returns `replaced`
  when it holds `new`, else `uncertain`. This re-read checks an unknown outcome. It is not a
  fresh read that replaces the expected state. This re-read
  lives in `CurrentPointer` for every backend; a store never compares values and never
  decodes. `read_value` and `is_run_id` live only in `CurrentPointer`'s
  module. A store for another backend implements the two methods and takes no lock of its own
  unless its backend needs one.
- CLI-CLOUD construction is frozen as `CloudDeliveryStage.open(pointer, prefix, run_id, arena,
  targets)`: `DeliverySink.open` creates the project-shared local folder, constructs
  `CurrentPointer(store=ObjectPointerStore(...), lock_parent=<resolved-project-root>/out/<pipeline>,
  name="CURRENT")`, and passes the pointer. The engine stage never receives a bare store or
  derives the lock from its per-run arena.
- Reason codes, new `reasons/decoy/_delivery.py`, `since=UNRELEASED` per REG-RELEASE E2 (#506,
  open; E1b waits), a `changelog.d/` fragment, no `REGISTRY_VERSION` edit
  (`reasons/_registry.py:24`):

| Code | Kind | Outcome | Retry | Meaning |
|---|---|---|---|---|
| `decoy/delivery_withheld` | DECISION | PUBLICATION | NEVER | a good table not delivered |
| `decoy/delivery_dependent_dropped` | DECISION | PUBLICATION | NEVER | reachable from a failed table |
| `decoy/delivery_pointer_moved` | FAILURE | PUBLICATION | RETRY_OPERATION | another run moved the pointer (CAS loss only) |
| `decoy/delivery_rolled_back` | WARNING | PUBLICATION | NEVER | a crashed batch's journal was rolled back |

F22 codes stay the cause wherever F22 decides (D-7). `publication_failed` and
`publication_partial` (`reasons/decoy/_core.py:73-84`) stay the publish I/O causes.

Outcome mapping. Every F22 `Outcome` (`publication/_types.py:45-52` on a2) and every batch error
maps to one state. AT-28 runs over `get_args(Outcome)` and the batch codes.

| Source | Value | State | Cause |
|---|---|---|---|
| bind | `published`, `already_committed` | continue to the swap | none |
| bind | `commit_uncertain` | continue to the swap; at most `uncertain` | `publication_commit_uncertain` |
| bind | `refused` | nothing | F22's code (target occupied, lock timeout or unavailable, vault mismatch) |
| bind | `operation_conflict` | nothing | `publication_operation_conflict` |
| bind | `failed` | nothing | `publication_failed` |
| swap | expected stale | nothing | `delivery_pointer_moved` |
| swap | `conflict`, captured version still current after the one resend | nothing | `publication_failed` |

### 4.5 Locks

| Kind | Lock file | Taken | Held across |
|---|---|---|---|
| R | `out/<name>/.LATEST.decoy-lock` (F22 a1b `OutputDir.lock`, leaf `LATEST`) | once, by `DeliveryStage.deliver` via `CurrentPointer.locked` | CAS compare, `before_visible`, `publish_unit`, `swap` |
| cloud | the local `out/<name>/.CURRENT.decoy-lock`, through the same `CurrentPointer.locked` implementation | once, by `CloudDeliveryStage.deliver`, before its first upload | uploads, `before_visible`, the pointer request and all outcome handling, including restore, discard, backup retention or withdrawal |
| R | `out/<name>/.<run-id>.decoy-lock` | by `publish_unit` (a3 `_locked`) | judge and bind |
| A | `flock` on the folder fd (`_folder_lock`, `_atomic.py:595`) | at `open` (recovery only, released), then once by the batch entry | recovery, steps 3 to 7 |

Order is always the pointer lock, then the run-id lock. `HeldPointer.swap` uses the held lock and
never locks. Nothing re-locks a held file. F23 resume takes the same order. On A the vault and
evidence writes run before the folder lock; their backups reach the journal by name.
Two cloud runs on one machine therefore cannot interleave their vault and evidence commits. A run
on another machine has its own local vault and lock, so only the object-store pointer CAS
arbitrates between the machines.
For an all-cloud run, `DeliverySink.open` resolves the project through
`find_project(config.parent, project)`, whose implicit root is the config folder, and creates or
opens `<resolved-project-root>/out/<name>/` with the existing project output and claim machinery.
Every arena for that project and pipeline passes that same folder as `lock_parent`. A creation or
lock failure is a value-free refusal before any upload.

### 4.6 CLI side

- `io/_delivery.py`: `DeliverySink` with `RootKind` (`run_folder`, `fixed_folder`). At open
  the sink builds its stage for the `RootKind` (construction is per kind, since `open` takes
  different arguments per kind) and from then on holds it only as a `SinkStage` protocol:

### 7.2 POSTSCAN-STREAM (row 60)

The contract is POSTSCAN-STREAM section 4.10 (`2ec7a0c3`). DELIV relies on exactly this:

> `verification.postmask._blocked.post_scan_verdict(report)` is the one blocking decision
> (slice PS-2b). On a block the engine raises `PostScanBlockedError` (`reason` the first code in
> 4.8 order, `report` the value-free report with `verdict.codes`) and nothing has committed. It
> is raised inside `observed_commit` before `sink.commit()` on a sink route, in `execute_route`
> after the route returns on a no-sink route (the CLI's plain call), and in the isolated child,
> which surfaces as `IsolatedRunResult` outcome `blocked` (wired by PS-8 and PS-9). The gate takes
> no delivery mode. A requested post-scan with no report is a block on the CLI side.

DELIV maps `PostScanBlockedError` and outcome `blocked` to row 6 (nothing, exit 4, both modes)
and owns the missing-report block (row 7) and the `--chunked` refusal (slice CR), which
POSTSCAN-STREAM names as its dependency on row 61 (its section 1, exemptions). DELIV reads no
severity and imports nothing from `_blocked.py` but the exception.

POSTSCAN-STREAM owns one predicate for whether the post-scan gate applies to a config:
`post_scan_gate_applies(config)`, beside `post_scan_integrity_requested` in
`config/_post_scan.py`. Its gate, DELIV's row-7 missing-report rule and DELIV's chunked gate are
the three callers. A sentry test asserts that all three call this function and that no second
predicate exists. Its seeded mutation replaces one call with local config inspection and must
turn the sentry red.

Until the engine release carrying that predicate is pinned, CR uses
`post_scan_integrity_requested` for refusal and direct relationship inspection for the interim
warning. C5, after the POSTSCAN release is pinned, replaces those applicability checks and the
row-7 check with `post_scan_gate_applies`. CR still uses `post_scan_integrity_requested` only to
choose refusal from the two gate outcomes. For `--chunked` with declared relationships but no
requested integrity, CR follows the working owner answer in 11: it warns with a value-free
message and records in the run result that the relationship key check did not run. This is an
interim behaviour only. POSTSCAN-STREAM removes it when the chunked route runs the key check.

## 17. Pre-mortem

A new route writes straight to targets: G-ONE-DELIVERY-SINK (AT-25). The older of two racing
runs wins: CAS under the held lock (AT-19). Best-effort delivers an orphan through a cycle or a
generate reference: the reachability walk (AT-6, AT-7). Post-scan cannot run and the run
delivers: CR (AT-29), a missing report withholds (AT-37), an engine block gives exit 4 (AT-38).
A failed publish loses the old vault: `PreVisible` restore (AT-33). A SIGKILL on a fixed folder
leaves a silent mix: journal order and recovery (AT-21, AT-34). A delivered run reports
nothing: the visibility point sets `delivered` (AT-12, AT-31). `_layout.py` or `_atomic.py`
passes its cap: C0 moves the batch, C2a moves the pointer logic.
