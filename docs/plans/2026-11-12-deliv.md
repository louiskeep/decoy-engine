# DELIV: staged, all-or-nothing delivery for the CLI (roadmap row 61)

Rules consulted: `00-universal.md`, `risk-and-exceptions.md`, `development-loop.md`,
`feature-dev.md`, `architecture.md`, `cross-cutting-concerns.md`, `api-and-compatibility.md`,
`destructive-operations.md`, `testing.md`, `catalogs/recurring-defects.md` (all under
`/home/cam/dev-rules/`). Risk: R2 (data handling, publication, concurrency).

Engine base: origin/main 4bb95063. CLI base: origin/main 75d39ec plus open PR #213
(PROJECT-LAYOUT P4), which the CLI half depends on.

## 1. Guarantee

> Under `delivery.mode: strict` (the default) a `decoy run` either makes every output table of
> the run visible together, or makes none of them visible and leaves the previous delivery
> untouched. Under `best_effort` it makes visible every table that passed and was not blocked,
> and drops each failed or blocked table together with its FK dependents.

"Visible" means reachable through the path a consumer reads: `out/<name>/LATEST` and
`out/<name>/current` for a project run (the run-folder kind), or the target file paths for a
fixed folder (the fixed-folder kind). Crash atomicity differs by kind (section 4.3).

Non-goals are the "Out" list in 2.4. Findings there are recorded follow-ups, not blockers.

## 2. Frame

### 2.1 Problem

Today `decoy run` writes each table to its target as soon as that table is ready
(`src/decoy/cli/run/_execute.py:182-199` calls `write_targets`; `src/decoy/cli/io/_targets.py:436-463`
writes per table). Each file is atomic (row 61a, ATOMIC-OUTPUT #105). The run is not:

- A failure in table 3 of 5 leaves tables 1 and 2 at their targets, mixed with the old 3 to 5.
- Post-scan integrity (`src/decoy_engine/execution/_pipeline_finalize.py:470-503`) is
  report-only. A `fail` finding never stops a write.
- The chunked route (`_execute.py:48-114`, `_run_chunked_mask`) writes each table inside the
  loop. An exception in table N leaves tables 1 to N-1 delivered.
- `RunLayout.commit_latest` (`io/_layout.py`, called from `run/_render.py:49-57`) moves
  `LATEST` after the run with a "later run id wins" check, not a compare-and-swap against what
  the run saw at start.

The roadmap names DELIV as the owner of the "DELIV transactional sink" choke point (ROADMAP
section 4.1). Row 21b defers all-or-nothing across targets to this row.

### 2.2 Terms

- **Stage.** The private per-run place where every output of one run is written before any of
  it is visible. Run-folder kind: an F22 `immutable_directory/v1` stage
  (`._decoy_publication_pending_<token>`) beside the run folder. Fixed-folder kind: one temp
  file per target in the target folder (`staged_local_target`, `src/decoy/_atomic.py`).
- **Deliver.** The single step that turns the staged run into the current dataset. It runs
  once, after every table, post-scan and the vault commit.
- **Sink.** The one CLI object every route and caller writes outputs through:
  `DeliverySink` in `src/decoy/cli/io/_delivery.py`. After slice C4 it is the only caller of
  `write_targets`, `write_chunked_output`, `write_private_table` and the one-folder batch
  (sentry G-ONE-DELIVERY-SINK).
- **Strict.** Deliver all tables or none. Default.
- **Best-effort.** Deliver the good tables. Drop a failed or blocked table and, transitively,
  every table that is an FK child of a dropped table. Parents of a dropped child are delivered.
- **Delivery root.** The one folder all of a run's file outputs resolve under.
- **Single-root rule.** Under strict, every local file target and an enabled quarantine file
  share one delivery root: either the run folder (all targets relative, inside a project) or
  one fixed folder (all targets absolute or `--out-dir`, every file directly in that folder).
  Any other mix is refused at the gate with `decoy/delivery_root_split`, exit 1.
- **Delivery record.** `_decoy_delivery.json`, schema `decoy-delivery/v1`: value-free list of
  table names, states, formats and relative paths, plus the run id. Written into the stage
  before deliver. On the fixed-folder kind it is also the rollback journal.

### 2.3 User-visible behaviour

Config (YAML, engine-owned, new field `PipelineConfig.delivery`):

```yaml
delivery:
  mode: strict        # strict | best_effort ; default strict, omitted from the dump
```

No CLI flag in V1. The mode lives in the config so the run record and config hash carry it
(UX map section 5.5). A non-default mode moves the config hash, the same rule as
`post_scan.ner_findings`. The default does not move any existing hash.

Exit codes (`src/decoy/cli/exit_codes.py`, today 0 to 5):

| Code | When |
|---|---|
| 0 | every table delivered |
| 1 | config refused, including `delivery_root_split` |
| 3 | strict run with a table failure, a publish I/O failure, or a pointer moved by another run; nothing delivered |
| 4 | post-scan blocked delivery (strict: any block; best-effort: every table blocked) |
| 5 | existing capacity exit, unchanged |
| 6 | NEW `EXIT_PARTIAL`: best-effort delivered some tables and dropped at least one |

Result document (RESULT E1, `src/decoy_engine/run_result/_model.py`, already merged, no schema
change): `delivery.mode`, `delivery.outcome` (`delivered|partial|nothing|not_applicable`), and
per table `state` (`delivered|failed|withheld|dropped`), `reason`, `dropped_because`.
`derive_outcome` (`run_result/_outcome.py`) already maps best-effort partial to
`partially_delivered`. DELIV fills these fields. RESULT (row 62) renders them.

CLI lines, one per non-delivered table, value-free:
`table <name>: withheld (decoy/delivery_withheld)`.

## 3. Established solutions

Search scope: the codebase (F22 publication, `src/decoy/_atomic.py`, PROJECT-LAYOUT P4, the
UX map section 5) and the published patterns below. The design follows these; it invents no
commit protocol.

- Same-filesystem stage, fsync the file, fsync the directory, atomic `rename(2)`: PostgreSQL
  `durable_rename` (`src/backend/storage/file/fd.c`), python-atomicwrites. F22 `publish_unit`
  already implements this for one directory; DELIV calls it.
- A commit record or pointer written last, swapped with an expected old value: git
  `update-ref <ref> <new> <old>`, Delta Lake's `_delta_log` commit file. DELIV's `LATEST` CAS
  follows git's expected-old-value rule.
- In-place replacement of several files with a rollback journal and backups: SQLite rollback
  journal (sqlite.org/atomiccommit.html). DELIV's fixed-folder kind follows it at file
  granularity; the journal is the delivery record with `state: pending`.
- Two-phase commit over several independent files is not crash-atomic without a journal or a
  pointer. DELIV says so (section 4.3) instead of claiming it.

Custom code left: the transitive FK drop and the post-scan adapter. Both are small pure
functions over existing engine types; no library covers Decoy's report shape.

## 4. Design

### 4.1 One mechanism

One sink (`DeliverySink`), one decision function (`plan_delivery`, engine), one directory
publication (F22 `publish_unit`), one atomic file writer (`src/decoy/_atomic.py`), one
destination keying (`_destination_key` in `src/decoy/cli/io/_placement.py`, P4). DELIV adds no
second copy of any of them:

- The run-folder kind calls F22 `publish_unit`. It does not rename directories itself.
- The fixed-folder kind calls the one-folder batch, moved out of `_atomic.py` by slice C0. It
  does not write temp files itself.
- The single-root rule is one more check inside `layout_issues` (`_placement.py`, P4), keyed by
  `_destination_key` on each target's parent. `resolved_output_collisions` answers "do two
  outputs land on the same file"; the root rule answers "do all outputs land under one folder".
  Both run in the same pass over the same keyed paths. Collisions are reported first. The root
  rule runs only under strict.

### 4.2 Run order (both kinds)

1. Gate: `layout_issues` refuses a split root (strict only).
2. `DeliverySink.open(layout, config)` opens the stage and reads the pointer version
   (run-folder: `LATEST` content or absent; fixed-folder: none). On the fixed-folder kind it
   first recovers any `pending` journal (4.3).
3. Every route writes every table through `sink.write_table(name, ...)` or
   `sink.write_chunked(name, ...)`. The sink records each table's outcome (`ok` or a failure
   reason code). Nothing is visible yet.
4. The post-scan report (`quality_metrics["post_scan_integrity"]`) goes through
   `blocking_tables(report)` (engine).
5. `plan_delivery(config, outcomes, blocking, mode)` returns a `DeliveryDecision`: per table
   `delivered|failed|withheld|dropped`, `dropped_because`, and `deliver: bool`.
6. If `deliver` is false: `sink.abort()`. The stage is removed and the pointer is untouched.
7. If true: `sink.deliver(decision, before_visible=_commit_vault)`:
   a. take the destination lock;
   b. CAS check: the pointer still equals the value read in step 2, else
      `decoy/delivery_pointer_moved`, abort;
   c. `before_visible()` makes the vault durable (F22 rule V);
   d. remove dropped tables' staged files and write `_decoy_delivery.json`;
   e. publish (kind specific, 4.3);
   f. release the lock.
8. `_flow.py` `finally` calls `layout.abandon()` on any unfinished exit
   (`src/decoy/cli/run/_flow.py:78-81`). `abandon()` calls `sink.abort()` when the sink is
   still open. No edit to `_flow.py`.

### 4.3 Root kinds

**Run-folder kind (R)**: all targets relative, inside a project. Root `out/<name>/<run-id>/`.

- Stage: an F22 dir transaction beside `out/<name>/<run-id>/`, on the same filesystem by
  construction. CLI writers write into `local_stage_path()` (`fileaccess/_local.py:268`).
  Quarantine is placed in the stage too.
- Publish: `publish_unit` binds the stage onto the empty run folder in one durable rename
  (`fileaccess/_local.py:273-283`). Then `publication.swap_current(root, expected, run_id)`
  replaces `LATEST` durably. Then the CLI points `current` at the run (POSIX symlink, derived,
  best-effort; `LATEST` is authoritative).

| Crash point | Left on disk | Visible | Recovery |
|---|---|---|---|
| before bind | stage dir (F22 L2 litter), empty run folder | previous run | none needed; litter is limit 12.3 |
| after bind, before `LATEST` | bound run folder with record, not current | previous run | F23 adopts it via `already_committed` |
| after `LATEST`, before `current` | `current` lags one run | new run via `LATEST` | next delivery fixes `current` |

Strict guarantee on R: crash-atomic across all tables. A consumer reading `LATEST` sees the old
run or the new run, never a mix.

**Fixed-folder kind (A)**: absolute targets or `--out-dir`, all files directly in one folder.

- Stage: one `staged_local_target` temp file per target in that folder (same filesystem).
- Publish: the one-folder batch (today `publish_local_targets`, `src/decoy/_atomic.py:644-719`)
  with a new staged-path entry point. Under the folder flock (`_folder_lock`, `:595`): write
  `_decoy_delivery.json` with `state: pending` and fsync it; hard-link `.bak` backups;
  `os.replace` each staged file; fsync the folder; remove the backups and the journal.
- A caught failure rolls back from the backups (`_rollback`, `:622`).
- A crash between replaces leaves a mix plus a `pending` journal. The next sink open in that
  folder, under the same lock, finds the journal, restores from `.bak`, removes the journal and
  records `decoy/delivery_rolled_back` (WARNING) in the new run's result.

Strict guarantee on A: all-or-nothing on every caught failure. After a crash the folder is
mixed until the next run in that folder rolls it back. See owner Q1 and Q3.

**Cloud kind**: not built. Seam in 7.2.

### 4.4 Engine contracts

- `config/_delivery.py`: `DeliveryConfig(mode: Literal["strict","best_effort"] = "strict")`,
  `extra="forbid"`. Field `delivery` on `PipelineConfig` (`config/_pipeline.py:85-145`),
  omitted from the dump when default, as other default blocks are.
- `delivery/_plan.py`: `plan_delivery` is pure. It drops transitively over child edges of
  `config["relationships"]` (each `RelationshipConfig` parent to each child) and ignores
  self-loops. Cycles never reach it; they are refused earlier with `fk_cycle`
  (`relationships/_graph.py`). `dropped_because` is the first failed ancestor in topological
  order (`RelationshipGraph.ordering`).
- `delivery/_postscan.py`: `blocking_tables(report) -> Blocking(tables: frozenset, run: bool)`.
  - Severity `fail` blocks `table`. An FK finding blocks `child_table`.
  - Severity `error`, `table == ""`, or a non-empty `pass_failed_with` blocks the whole run
    (fail closed).
  - `info` and `warn` never block.
  - The CLI adds `post_validate_enforce` failed checks as a whole-run block before calling
    `plan_delivery`.
- `delivery/_record.py`: `DeliveryRecord` writer model and `DeliveryRecordRead` derived reader,
  using the `run_result` value-free leaf types (`SafeName`, `RelPath`, `Token`, exported from
  `run_result/__init__.py`). Strict types, no values, no messages.
- `delivery/_stage.py`: `DeliveryStage` over F22: `open(root, run_id, fa, operation_id)`,
  `stage_path`, `abort()`, `deliver(decision, before_visible)`. It builds the
  `PublicationRequest` and maps F22 outcomes: `already_committed` to delivered;
  `operation_conflict` and `publication_target_occupied` to `decoy/delivery_pointer_moved`.
- `publication/_current.py`: `read_current(root) -> str | None` and
  `swap_current(root, expected, new)`: lock, re-read, compare, durable small-file replace, and
  a parent fsync that raises. (On main a replace publish swallows its parent fsync failure; F22
  plan section 1.2.) This is the F22 a4 `CURRENT` remnant F22 deferred for want of a consumer.
- Reason codes in a new `reasons/decoy/_delivery.py`, all `since=UNRELEASED` per REG-RELEASE
  E2 (#506), named in a `changelog.d/` fragment, no `REGISTRY_VERSION` edit
  (`reasons/_registry.py:24`):

| Code | Kind | Outcome | Retry | Meaning |
|---|---|---|---|---|
| `decoy/delivery_withheld` | DECISION | PUBLICATION | NEVER | strict: good table not delivered |
| `decoy/delivery_dependent_dropped` | DECISION | PUBLICATION | NEVER | FK child of a dropped table |
| `decoy/delivery_findings_blocked` | DECISION | FINDINGS | CONFIGURATION_REPAIR | post-scan blocked this table |
| `decoy/delivery_root_split` | FAILURE | CONFIGURATION | CONFIGURATION_REPAIR | strict targets do not share a root |
| `decoy/delivery_pointer_moved` | FAILURE | PUBLICATION | RETRY_OPERATION | another run delivered first |
| `decoy/delivery_rolled_back` | WARNING | PUBLICATION | NEVER | journal from a crashed run was rolled back |

Existing `PUBLICATION_FAILED` and `PUBLICATION_PARTIAL` (`reasons/decoy/_core.py`) stay the
cause codes for a publish I/O failure. DELIV reuses them and adds no duplicate.

### 4.5 CLI side

- `src/decoy/cli/io/_delivery.py`: `DeliverySink`. Kind from `RunLayout`: `fixed` or `out_dir`
  means A, otherwise R. Methods `open`, `write_table`, `write_chunked`, `record_failure`,
  `abort`, `deliver`, `outcomes`. It owns no file protocol: it calls `write_table` and
  `write_chunked_output` with a stage path (R), or the batch (A).
- `run/_execute.py`: both branches write through the sink. `_write_mask_outputs` becomes the
  deliver step. Under best-effort the chunked loop catches `Exception` per table and records
  it; `BaseException` (Ctrl-C) propagates and aborts the run.
- `run/_render.py:49-57`: `commit_latest` shrinks to printing the delivery lines. The pointer
  move is inside `deliver`. About 15 lines, coordinated with the RESULT lane.
- `io/_layout.py`: `commit_latest` and `_read_latest` are replaced by calls into the engine
  pointer. The file shrinks.
- `exit_codes.py`: add `EXIT_PARTIAL = 6` (additive, MINOR). RESULT later owns the mapping.
- Callers: `api.py:578` and `cli/tokenize.py:371` already call `run._execute._write_mask_outputs`,
  so they reach the sink once C2a lands. `cli/demo.py:263` calls its own duplicate
  `_write_mask_outputs` (`demo.py:280-288`), which is deleted in C4. The detokenize output
  (`cli/tokenize.py:745`, one `write_private_table` file) is a single-target transaction under
  row 21b and is a named sentry exemption.

### 4.6 Design notes

- Single responsibility: today `_execute.py` decides when a table is visible and also runs the
  pipeline. Visibility moves to the sink, so a new route adds a `write_*` call, not a policy.
- Open/closed: root kinds are a `RootKind` enum with one implementation per kind inside the
  sink. CLI-CLOUD adds one kind without editing the routes.
- Deep module: callers see `open`, `write_*`, `deliver`, `abort`. Stage paths, locks, journals
  and pointers stay inside.
- Where facts live: the mode in `DeliveryConfig`; the decision in `plan_delivery`; per-table
  state in the delivery record and the result document (both written from one `DeliveryDecision`);
  destination identity in `_destination_key`.
- House style: `DeliveryDecision` is a typed context object passed whole; no flag arguments
  (strict versus best-effort is a value of `mode` read once by `plan_delivery`).

### 6.4 FK shapes

`RelationshipConfig` (`config/_relationships.py:37`): one parent, one or more children,
single or composite columns. Shapes and their drop rule:
- single parent to child: child dropped when the parent drops;
- composite key: same as single (the drop is per table, not per column);
- one parent, many children: every child dropped;
- child with two parents: dropped if either parent drops (AT-4);
- chain: transitive (AT-3);
- self-reference: ignored for dropping (AT-5);
- cross-table cycle: refused before the run with `fk_cycle` (`relationships/_graph.py:168`).

### 6.5 Fields

- `Delivery` (`src/decoy_engine/run_result/_model.py:276`): `mode` from `DeliveryConfig`
  (never `in_place` on these routes), `outcome` from the decision, `vault` unchanged.
- `TableDelivery` (`src/decoy_engine/run_result/_model.py:282`): `state`, `format`, `output`
  (`RelPath`, only when delivered), `reason` (the code), `dropped_because` (only when dropped).
  `state: none` is unused on these routes.
- `DeliveryRecord`: `schema`, `run_id`, `state` (`pending|committed`), and per table `name`,
  `state`, `format`, `path`, `reason`.

### 6.6 Output surfaces

- result document (`decoy-run-result/v1`), delivery record (`_decoy_delivery.json`);
- CLI stdout delivery lines and stderr errors (`run/_render.py`, `run/_errors.py`);
- the exit code;
- evidence (`--evidence-out`, schema unchanged) and spans (F30, no new attributes).

All carry codes and table names only (class 1).

## 7. Seams for other rows

### 7.1 F23 resume

- `DeliveryStage.open(..., operation_id)` passes the F22 `operation_id`. A resumed attempt with
  the same id that finds the run folder bound gets `already_committed`, treats it as delivered,
  and runs `swap_current` with the expected value from its own record.
- The delivery record lists per-table states, so F23 can tell which tables a crashed run staged.
- DELIV does not resume partial stages. F23 decides how.

### 7.2 CLI-CLOUD (row 64)

- `DeliverySink` picks a kind by `RootKind` (`run_folder`, `fixed_folder`). CLI-CLOUD adds
  `cloud_prefix`: stage under `<prefix>/runs/<run_id>/`, deliver by a conditional write of
  `<prefix>/CURRENT` (S3 `If-Match`, GCS `ifGenerationMatch`). `plan_delivery`, the record and
  the reason codes are reused unchanged.
- `publication/_current.py` takes a `FileAccess`, so a cloud `FileAccess` can implement the CAS.

### 7.3 RESULT exit 6 (row 62)

- DELIV fills `Delivery` and `TableDelivery` and adds `EXIT_PARTIAL = 6`. RESULT owns
  `run/_errors.py` and `run/_render.py` and moves the constant into its exit mapping. DELIV's
  `_render.py` hunk is the 15-line delivery-lines print only.

### 7.4 POSTSCAN-STREAM

The POSTSCAN-STREAM plan was not on disk when this was written. DELIV assumes:
- every route, including the chunked entry, puts a `post-scan-integrity/v2` report in
  `quality_metrics["post_scan_integrity"]` before the deliver step;
- findings keep `table`, `child_table` and `severity`, and the report keeps `pass_failed_with`.

DELIV does not change the `post_scan.integrity` default. Until POSTSCAN-STREAM merges, the
chunked route has no report and `blocking_tables(None)` returns no block. AT-9 pins this, and
limit 12.8 names it.

## 11. Owner questions

**Q1. Strict delivery to absolute or `--out-dir` targets.** The fixed-folder kind cannot be
crash-atomic without a pointer.
- (a) One-folder batch with backups, rollback on caught failures, journal recovery on the next
  run (this plan). Consumer paths stay the same.
- (b) Require a pointer root for strict: absolute targets become `<dir>/runs/<id>/` plus
  `CURRENT`. Crash-atomic, but every consumer path changes.
- (c) Refuse strict on fixed folders; force best-effort or a project.
- Recommend (a). Paths stay stable, every caught failure is covered, and the crash window is
  repaired by the next run. (b) can come in V2 as an opt-in.

**Q2. Best-effort isolation inside `run_pipeline` on the plain route in V1.** The engine has
no per-table isolation; a raise in one table aborts the pipeline.
- (a) V1 isolates only where the CLI owns the loop (chunked route, staging writes, post-scan).
  A plain-route engine failure delivers nothing (row 5).
- (b) Add per-table isolation to `run_pipeline` now. Touches `execution/` (fan-out frozen at
  104) and every strategy path.
- Recommend (a); log (b) as V2-LOG.

**Q3. Journal crash recovery in V1.** Needed only with Q1 (a).
- (a) In V1, inside C2b.
- (b) Cut: a crash mid-batch leaves a mix and `.bak` files; documented limit.
- Recommend (a). Without it a SIGKILL leaves mixed data that nothing reports, which is data
  loss under the V1 bar. It is about 60 lines and can become its own slice if C2b runs long.

## 17. Pre-mortem

Ways this goes wrong after it ships, and the plan's answer:
- A builder writes outputs straight to targets on a new route. Answer: G-ONE-DELIVERY-SINK
  (AT-25).
- Two runs into one project race and the older one wins. Answer: CAS (AT-19).
- Best-effort delivers an orphaned child. Answer: transitive drop (AT-3, AT-4).
- Post-scan crashes and the run delivers anyway. Answer: fail closed on `error` (AT-8).
- A SIGKILL mid-batch on a fixed folder leaves silent mixed data. Answer: journal recovery
  (AT-21, Q3).
- The chunked route delivers without a post-scan check before POSTSCAN-STREAM. Answer: named
  limit 12.8; AT-9 pins the behaviour so the change is visible when POSTSCAN-STREAM lands.
- `_layout.py` or `_atomic.py` passes its cap. Answer: C0 split first; C2a moves pointer logic out.
