## 1. FRAME

**Problem.** Hadoop and Kafka-era data arrives as Avro or ORC. Users convert it by hand to
Parquet or CSV before Decoy can read it, and convert the masked output back.

**Definition of done (the whole guarantee).**

- G1. `FileSource.format` and `FileTarget.format` accept `avro` and `orc`. S3 and GCS sources and
  targets do not (their literals stay `csv | parquet`; non-goal).
- G2. Reads go through Arrow with bounded memory on the streaming routes: `iter_avro_chunks` and
  `iter_orc_chunks` yield owned chunks within a caller `ChunkBudget`, decoding one group of Avro
  blocks or one ORC record batch at a time (never the whole file). Full reads (`read_avro`,
  `read_orc`) exist for resident routes, as `pq.read_table` does for Parquet.
- G3. Writes keep the schema. Avro: date, timestamp (`timestamp-millis`, `timestamp-micros`,
  `local-timestamp-millis`, `local-timestamp-micros`) and decimal keep their logical type;
  section 3.4 lists every type exactly. ORC: date, decimal and timestamp keep their type, with the
  unit and zone rules pyarrow's ORC format imposes (section 3.4). Writes publish atomically: a
  failed write leaves no file and an existing target untouched.
- G4. Profiling reads both: `profile_source` / `build_profile_source` give an exact row count,
  the schema and a bounded sample for both formats. Pre-scan (`profile_columns`) takes the frame
  a caller reads through these readers (the CLI wiring that does that is V1P-4.2).
- G5. A corrupt, truncated or unsupported file is refused with a reason code. No stack trace, no
  Rust panic and no data value reaches the caller, and the error carries no `__cause__` or
  `__context__`.
- G6. Dark: every config without `avro`/`orc` behaves byte-identically to main (section 7, AT-D).

**Non-goals.** Avro schema evolution across files (reader schema != writer schema); Schema
Registry and single-object/Confluent framing; Avro codecs other than `null`, `deflate`, `snappy`;
ORC compression choices beyond pyarrow's default; S3/GCS Avro or ORC; CLI wiring (V1P-4.2);
admitting Avro/ORC to the unified-slice lane, the out-of-core FK route or subsetting (section 4
says what each does instead); declared-casting binary contracts on Avro/ORC.

**Risk: R2.** New parsing of untrusted binary input, a new surface under the file-access policy,
new public API in `decoy_engine.io`, new reason identities (registry minor bump), and a published
config literal change. Reversible, no production mutation, not R3.

**Reuse check.** `io/bounded_reader.py` (`ChunkBudget`, `cut_batch`, `own_array`,
`BoundedReadError`) is reused for chunk cutting and the error base. `io/csv_framer.py` is the
in-repo precedent for framing records by bytes before a parser sees them; the Avro block framer
follows it. `profile/_readers_csv.py` is the precedent for a per-format `ProfileSource` module.
`profile/_fixed_width_writer.py` is the precedent for an engine writer that publishes through
`output_dir(...).begin("file", "replace")`. `fileaccess/adapters/arrow.py` gets the ORC calls.
The input-format parity plan's split (intake parity first, route parity second) is followed:
this slice is intake parity for Avro and ORC; route parity (out-of-core, unified slice) stays a
follow-up.

## 2. Established solutions

Searches run (2026-11-07): web searches for the Avro 1.11 specification (object container files,
sync marker, logical types), Polars' Avro reader and its streaming limits, Spark's
`SchemaConverters.toAvroType`, and PyArrow's ORC reader/writer and batch reading. The Apache Avro
site (`avro.apache.org`) is not reachable from this sandbox; the spec facts below were checked
against secondary sources (Wikipedia, the Apache Avro FAQ, the `twmb/avro` Go library docs, the
Arrow Rust `arrow_avro` crate) and against bytes written and read in local probes. In the
codebase: every format enumeration (section 4), `io/`, `profile/`, `fileaccess/adapters/`, the
file-access sentry and its registry, `run_result/_model.py`, declared casting, subset, unified
slice admission, capacity and job estimates.

Findings:

- **Avro object container file** (Avro spec, "Object Container Files"): header = magic
  `Obj\x01`, a metadata map (`avro.schema`, `avro.codec`) and a 16-byte sync marker; then blocks,
  each `long count, long size, bytes, sync`. The sync marker exists so a reader can find block
  boundaries and split a file (Apache Avro FAQ; Hadoop's `AvroInputFormat` splits at sync
  markers). Java's `DataFileStream.getBlockCount` and `avro-tools count` count rows from block
  headers without decoding. Codecs: `null` required, `deflate` and `snappy` (snappy blocks carry a
  CRC32) optional. Unknown logical types are ignored and the underlying type is read.
- **Polars 1.42** (installed): `read_avro(source, columns, n_rows)` and `DataFrame.write_avro`.
  No `scan_avro`, no batch iterator; `read_avro` returns the whole file. Third-party plugins
  (`jetliner`, `polars-avro`) add block-wise streaming; they are new dependencies, so not used.
  Probed behaviour, which drives the design:
  - Reads: `date`, `timestamp-millis/micros` (as UTC), `local-timestamp-millis/micros` (naive),
    `decimal` on `bytes` and `fixed`, `uuid` (string), `time-millis/micros` (as `time64[ns]`),
    `enum` (as a dictionary), nested records, arrays, `[null, T]` and `[T, null]` unions.
  - Panics (a `pyo3_runtime.PanicException`, a `BaseException`, uncatchable by `except
    Exception`): Avro `map`, `duration`, decimal precision above 38; writing a `Null` column.
  - Errors: unions of more than one non-null branch (`ComputeError`).
  - Silently wrong: `timestamp-nanos`, `local-timestamp-nanos` read as plain `int64`.
  - Codec: a block labelled `zstandard` holding uncompressed bytes decoded without error, so the
    reader cannot be trusted to refuse a codec it does not implement.
  - Writes: one block per call, a constant sync marker (`01 02 03 04` x 4), record name `""`
    (invalid per the spec's name rule). Writes `date`, `decimal` (bytes), naive timestamps as
    `local-timestamp-millis/micros`. Refuses `int8/16`, unsigned ints, tz-aware and `ns`
    timestamps, `time`, `duration`, dictionaries, and panics on `Null`.
  - Corrupt input: truncated header, bad magic, flipped sync, garbage and empty files all raise
    `ComputeError("OutOfSpec")`; a snappy CRC flip is detected; a block count larger than its
    data raises `OSError`. None of the probed messages carried a value, but the design never
    forwards library text anyway.
- **PyArrow 24 ORC** (installed): `pyarrow.orc.ORCFile` (`nrows`, `nstripes`, `schema`,
  `read_stripe`), `ORCWriter` (incremental `write`, accepts a file object over a descriptor), and
  `pyarrow.dataset.dataset(path, format="orc").to_batches(batch_size=...)`, which reads below a
  stripe (Arrow C++ `ORCFileReader::GetRecordBatchReader(batch_size)`). Probed: timestamps of any
  unit read back as `timestamp[ns]`; a tz-aware timestamp reads back with zone `UTC`;
  `large_string` reads back as `string`; unsigned ints, dictionaries, `time64` and `null` are not
  writable. Truncation fails the postscript parse (`OSError`); a wrong leading magic and a
  flipped byte inside a stripe are not detected (ORC has no data checksums).
- **Spark `spark-avro` `SchemaConverters.toAvroType`**: names the top-level record
  `topLevelRecord`, maps a timezone-aware timestamp to `timestamp-micros` and a naive one to
  `local-timestamp-micros`, and decimal to the `decimal` logical type. This slice follows that
  naming and mapping for the schema it writes.
- **fastavro** (MIT) is the reference Python Avro library (named in the sprint text). It is not
  installed and the slice may not add dependencies.
- **DuckDB 1.5.4** (installed) reads Avro only through its `avro` extension, which is not
  installed and would be downloaded at runtime: not used.

Design follows: the Avro spec's container framing (Hadoop's split-at-sync pattern) to cut a file
into block groups, each decoded by Polars; the Avro spec and Spark's `toAvroType` for the schema
the writer emits; Arrow's own ORC batch reader and `ORCWriter` for ORC; the existing
`cut_batch` for the byte budget. Custom code, and why: a block framer and header parser (about
150 lines; Polars exposes no block API and fastavro is not installed), a schema admission walk
over the header JSON (Polars panics on several valid schemas, so they must be refused before
Polars sees them), and the writer's type table and header rewrite (Polars writes an invalid
record name and cannot write UTC timestamps).

## 3. Behaviour

### 3.1 Config

```yaml
sources:
  events: {type: file, format: avro, path: in/events.avro}
  orders: {type: file, format: orc,  path: in/orders.orc}
targets:
  events: {type: file, format: avro, path: out/events.avro}
  orders: {type: file, format: orc,  path: out/orders.orc}
```

No new fields. The existing validators already forbid `layout` (fixed-width only) and the
delimited fields (csv only) on these formats.

### 3.2 Public API (`decoy_engine.io`; not re-exported at top level)

| Name | Shape |
|---|---|
| `iter_avro_chunks(path, budget, *, table, file_access=None, field_key="source.path")` | `Iterator[pa.Table]`, owned chunks within `budget` |
| `iter_orc_chunks(path, budget, *, table, file_access=None, field_key="source.path")` | same |
| `read_avro(path, *, table, file_access=None, field_key="source.path")` | `pa.Table`, whole file |
| `read_orc(path, *, table, file_access=None, field_key="source.path")` | same |
| `write_avro(data, path, *, table, schema=None, file_access=None)` | `data`: `pa.Table` or `Iterable[pa.Table]`; returns `path` |
| `write_orc(data, path, *, table, schema=None, file_access=None)` | same |
| `AvroMalformed`, `AvroSchemaUnsupported`, `OrcMalformed`, `TargetColumnTypeUnsupported`, `TargetSchemaMismatch` | `BoundedReadError` subclasses (coded, value-free) |

All six functions are `@fileaccess.entry_point`s and are listed in `fileaccess.ENTRY_POINTS`.
The source is opened with `open_read(FileRequest(FileRole.SOURCE, ...))`; the target with
`output_dir(FileRequest(FileRole.TARGET_OUTPUT, ...)).begin("file", "replace")`.
`schema=` fixes the write schema for an iterable (required when it may be empty); otherwise the
first chunk's schema is used. A `pa.Table` is one chunk.

### 3.3 Reads

**Avro.** The framer reads the header from the policy handle's binary stream, then walks blocks:
`count`, `size`, `size` bytes, 16-byte sync. It refuses: wrong magic, a header over 16 MiB, a
missing or non-string `avro.schema`, a short read anywhere, a negative count or size, a sync that
does not match the header's. A group of whole blocks is collected while its byte size stays
within `budget.chunk_budget_bytes` and its row count within `budget.max_chunk_rows` (one block
over either is decoded alone if it is within `budget.max_row_bytes * count`; otherwise refused
with `bounded_read_error`-family code `row_exceeds_max_row_bytes`). Each group is rebuilt as a
container (`header + blocks`) in memory and decoded by `pl.read_avro`; the result goes through
`cut_batch`. `read_avro` is the same loop with no budget, concatenated.

Schema admission (before any Polars call; the header JSON parsed with `json.loads`, size-capped):

| Avro schema element | Read as |
|---|---|
| `null` (only inside a 2-branch union), `boolean`, `int`, `long`, `float`, `double`, `bytes`, `string` | `bool`, `int32`, `int64`, `float32`, `float64`, `binary`, `string` |
| `date` | `date32` |
| `timestamp-millis` / `timestamp-micros` | `timestamp[ms|us, tz=UTC]` |
| `local-timestamp-millis` / `local-timestamp-micros` | `timestamp[ms|us]` |
| `decimal` on `bytes` or `fixed`, precision 1 to 38, 0 <= scale <= precision | `decimal128(p, s)` |
| `uuid` | `string` |
| `time-millis` / `time-micros` | `time64[ns]` (readable; not writable, section 3.4) |
| `enum` | `string` (decoded; the symbol list is not kept) |
| `fixed` without a logical type | `binary` |
| `record` (nested), `array` | `struct`, `list` (full read only: `cut_batch` refuses nested types on the chunked route with the existing `unsupported_column_type`) |
| `[null, T]`, `[T, null]` | nullable `T` |
| `map`, a union with two or more non-null branches, `duration`, `timestamp-nanos`, `local-timestamp-nanos`, decimal outside the range above, a top-level schema that is not a record | refused: `avro_schema_unsupported` |
| `avro.codec` other than absent, `null`, `deflate`, `snappy` | refused: `avro_schema_unsupported` |

Polars output types are normalised to the types a Parquet read of the same data gives:
`large_string`/`large_binary`/`large_list` to `string`/`binary`/`list` (a group that does not fit
32-bit offsets is refused with `row_exceeds_max_row_bytes`), dictionaries decoded. So every route
sees the same Arrow types it already handles for Parquet, and the chunked and full reads agree.

**ORC.** The first three bytes must be `ORC` (pyarrow does not check). Chunks come from
`pyarrow.dataset.dataset(handle.library_path(), format="orc").to_batches(batch_size=
budget.read_rows, use_threads=False)` through a new arrow-adapter function, then `cut_batch`.
`read_orc` is `ORCFile.read()` through the adapter. Schema and row count come from the file tail
(`ORCFile.schema`, `ORCFile.nrows`), which reads no stripe data.

**Profile sources** (`profile/_readers_columnar.py`): `AvroFileSource` and `OrcFileSource`
implement `ProfileSource`. Row count is exact for both: ORC from the tail, Avro by summing block
counts while seeking over block bytes (no decode). `schema()` decodes zero rows (Avro: the header
with no blocks; ORC: the tail). `sample_frame(n)` takes chunks until `n` rows. `to_frame()` is the
full read. `_build_file_source` dispatches the two new formats to them.

### 3.4 Writes

Writes are flat for Avro (no nested types; refused with `target_column_type_unsupported`) and
whatever pyarrow's ORC writer accepts for ORC. Before writing, each column is mapped by one table
per format; a column whose type has no row is refused, naming the table, column and Arrow type
(schema, never a value).

| Arrow type | Avro written | ORC written |
|---|---|---|
| `bool`, `int32`, `int64`, `float32`, `float64`, `string`, `large_string`, `binary`, `large_binary` | as is | as is (`large_*` read back as 32-bit) |
| `int8`, `int16`, `uint8`, `uint16` | widened to `int` (lossless) | `int8`/`int16` as is; unsigned widened to the next signed width |
| `uint32` | widened to `long` (lossless) | widened to `int64` |
| `uint64` | widened to `long` when every value fits, else refused | same |
| dictionary of a writable value type | decoded | decoded |
| `date32` | `int` + `date` | `date` |
| `timestamp[ms|us]` (naive) | `long` + `local-timestamp-millis|micros` | `timestamp`, read back as `ns` |
| `timestamp[ms|us, tz=UTC]` | `long` + `timestamp-millis|micros` | `timestamp`, read back as `ns, tz=UTC` |
| `timestamp[ns]`, with or without UTC | to `us` when no value has sub-microsecond digits, else refused | as is |
| timestamp with a zone other than UTC | refused | written; read back with zone `UTC` (same instant) |
| `decimal128(p, s)`, p <= 38 | `bytes` + `decimal(p, s)` | `decimal(p, s)` |
| `time32/64`, `duration`, `null`, `decimal256`, nested types (Avro) | refused | `time`, `duration`, `null`, `decimal256` refused |

So Avro to Avro round-trips every admitted read type except: `enum` comes back as `string`,
`fixed` (no logical type) as `bytes`, `fixed`-decimal as `bytes`-decimal, `uuid` loses its
annotation, `time-*` and nested types are refused on write. ORC to ORC round-trips every type
with timestamps at `ns` (and zone `UTC` when zoned).

Avro header written by the engine (not Polars'): magic, `avro.schema`, `avro.codec` = `null`, a
sync marker. The schema is Polars' schema with three changes: the record is named
`topLevelRecord` (Spark's name); each tz-UTC timestamp field's `local-timestamp-*` becomes
`timestamp-*` (same `long` encoding: the UTC-aware column is written by Polars as its naive UTC
wall clock, whose integer is identical); nothing else. Field names must match the Avro name rule
`[A-Za-z_][A-Za-z0-9_]*`; any other name is refused (`target_column_type_unsupported`, naming the
column) rather than written as an invalid file, as Spark does. Each chunk is encoded by Polars in
memory, its blocks are cut out by the framer and appended with the engine's sync marker, so a
streamed write holds one chunk at a time. The sync marker is the first 16 bytes of
`SHA-256(b"\xffdecoy.avro.sync/v1" + schema_json)`: deterministic output bytes for the same
schema and data (the spec asks for a random marker; determinism is the house rule; section 9).

ORC: `pyarrow.orc.ORCWriter` over the staged file descriptor (arrow adapter), one `write` per
chunk; stripes are cut by pyarrow.

Every chunk is cast to the write schema (`safe=True`) after the per-format mapping; a chunk that
cannot be cast is refused with `target_schema_mismatch` (table, column, the two Arrow types).

### 3.5 Failure modes

| Case | Outcome |
|---|---|
| Avro bad magic, short header, header over cap, schema not JSON | `AvroMalformed` (`avro_container_malformed`) |
| Avro truncated mid-block, size past EOF, sync mismatch, negative count/size | `AvroMalformed`, detail `table`, `block` index |
| Avro truncated exactly at a block boundary | reads as a shorter valid file (the format has no end marker; section 9) |
| Polars `ComputeError`/`OSError`/`PanicException` while decoding an admitted group (bad deflate, snappy CRC, bad UTF-8, count larger than data) | `AvroMalformed`, raised after the `except` block closes |
| Avro schema or codec outside section 3.3 | `AvroSchemaUnsupported` (`avro_schema_unsupported`), detail names the field path and the Avro type, never a default value or a symbol |
| ORC missing leading magic, postscript/footer parse failure, stripe decode error | `OrcMalformed` (`orc_file_malformed`) |
| ORC byte flipped inside a stripe | may decode as different values (no checksum; section 9) |
| Nested column on a chunked read | existing `UnsupportedColumnType` |
| Write: type not in section 3.4, invalid Avro name, `uint64`/`ns` loss | `TargetColumnTypeUnsupported` (`target_column_type_unsupported`); nothing published |
| Write: chunk not castable to the write schema | `TargetSchemaMismatch` (`target_schema_mismatch`); nothing published |
| Write: empty iterable with no `schema=` | `ValueError` (caller programming error, no data involved) |
| `MemoryError`, `ENOSPC`, `EDQUOT`, a policy denial | pass through with their class, as `guarded` already does |

Under a strict policy every library call goes through `guarded`/`guarded_iter` (so locators are
scrubbed); the coded errors above are raised for both policies because the library text is never
forwarded. All coded errors are `BoundedReadError` subclasses, so `profile_source`,
`estimate_job_capacity` and `run_pipeline` propagate them as they are (they are not
`ValueError`/`OSError`/`ArrowException`, so capacity's catch-and-wrap, whose message embeds the
exception text, never sees them).

## 5. Design notes

- **Structure added:** three modules in `io/` and one in `profile/`; no new package. Single
  responsibility: the framer knows bytes and the Avro grammar, nothing about files or policy;
  the per-format I/O modules own policy-bound open, decode, type mapping and publish; the profile
  module only adapts them to `ProfileSource`.
- **Open/closed:** the format literal is the one root. The new guard (section 6) walks
  `get_args()` of both literals and `OutputFormat`, so adding a format without a reader, writer,
  profile path or run-result value fails one test. Refactoring the existing three formats into a
  descriptor registry would touch V1 code paths and is not done; recorded as a follow-up.
- **One place per fact:** the Arrow-to-Avro and Arrow-to-ORC type tables live once each, in their
  I/O module, as data (a mapping from type predicate to cast), and the reference doc is generated
  from those tables by a test that compares the rendered table to the doc text.
- **Typed context, no flag arguments:** `write_avro`/`write_orc` take data, path and keyword
  identifiers only; no mode flags.
- **Determinism:** same input bytes give the same chunks for the same budget (block grouping is a
  pure function of block sizes and counts). Same table and schema give byte-identical Avro and
  ORC output (Avro: fixed sync marker derived from the schema, codec `null`; ORC: checked by
  test; if pyarrow's ORC footer is not deterministic the test is changed to a decoded-equality
  check and the doc says so).
- **Memory:** a chunked Avro read holds one block group (compressed bytes <= `chunk_budget_bytes`)
  plus its decoded Arrow table plus the chunk being yielded; deflate can expand the decoded table
  by its compression ratio (section 9). A chunked ORC read holds one `read_rows` batch plus
  pyarrow's per-stripe stream buffers. A streamed write holds one chunk and its encoded bytes.
- **Key labels:** the sync-marker hash input starts with `b"\xff"`, so no `_canonicalize_source`
  output can produce it (KEY-LABEL-SEP); it is not a key and derives nothing secret.

### File-access policy and the one exception this plan asks for

Every file open goes through the policy: the Avro source through `open_read` and
`handle.open_binary()` (raw byte reads, as the CSV framer does), ORC through
`handle.library_path()` inside the arrow adapter, targets through `output_dir().begin()`.

Decoding an Avro block group and encoding an Avro chunk need `pl.read_avro` and
`DataFrame.write_avro` over an in-memory `io.BytesIO`. The file-access sentry counts any
`polars.read_*`/`write_*` outside an adapter as a sink, and an in-memory buffer cannot be
capability-derived, so each needs one `file_access_registry.toml` entry. That registry is a
shrink-only ratchet (`file-access-registry` in `scripts/dev/sentry_registry.toml`). This plan
therefore asks the owner for an exception:

- Policy domain: file-access sink registry ratchet (D9). Scope: exactly two entries,
  `decoy_engine/io/avro_io.py` `_decode_group` / `polars.read_avro` and `_encode_chunk` /
  `polars.DataFrame.write_avro` (whatever the scanner names the method form), each with the rule
  text the CSV entries use ("in-memory bytes buffer of records the framer already read through a
  policy handle"). Risk R2. Rationale: Polars has no block API, and the only alternatives either
  read the whole file (no bounded memory, G2 fails) or stage source plaintext to a scratch file
  so a capability can be handed to Polars (more disk exposure of unmasked data than an in-memory
  buffer). Compensating controls: the two functions take `bytes`, never a path; a test asserts
  neither opens a file (they are called with the policy set to a deny-all `PreopenedFileAccess`
  and succeed); the registry count rises by exactly 2 and the ratchet report names both. Residual
  risk: none beyond today's CSV entries. Approver: owner (Cam). Expiry: when Polars or an
  installed dependency offers a block-level Avro reader over a file object.
- If the owner declines: Avro reads are whole-file only (adapter `polars.read_avro(handle.
  open_binary())`, no registry entry), `iter_avro_chunks` is not shipped and the chunked route
  refuses Avro sources with `avro_schema_unsupported`'s sibling code `avro_streaming_unsupported`;
  Avro writes take a whole table only and cannot write UTC timestamps (the header rewrite needs
  the encoded bytes in memory), so tz-aware timestamps are refused. G2 and part of G3 are then
  not met for Avro and the plan says so.

## 9. Known limits

- Avro has no end marker: a file cut exactly at a block boundary reads as a valid shorter file.
- Avro `null`/`deflate` blocks and ORC stripes carry no checksum: a flipped data byte may decode as
  a different value instead of failing. Snappy Avro blocks (CRC32) and ORC/Avro structure are
  checked.
- A deflate Avro block group can decode to more than `chunk_budget_bytes` (by the compression
  ratio) before `cut_batch` re-cuts it; the bound is on compressed input plus one decoded group.
- ORC keeps timestamps at `ns` (so the year range is 1677 to 2262) and zoned timestamps as `UTC`.
  Out-of-range ORC timestamps were not probed.
- Avro `enum`, `uuid`, plain `fixed`, `time-*` and nested types do not round-trip unchanged
  (section 3.4). `time-*` and nested types are refused on write.
- Decimal precision through `run_pipeline`: a probe on main shows a `decimal128(12, 2)` passthrough
  column comes back as `decimal128(2, 2)` on the default and chunked routes, for Parquet as for
  any format. This is pre-existing and out of scope (changing it would change V1 output); AT-R1
  compares against the Parquet route, and a follow-up is recorded.
- The Avro sync marker is deterministic, not random as the spec suggests. A source value crafted
  to contain the marker could confuse a third-party reader that splits files by scanning for it
  (it cannot confuse readers that use block sizes). Recorded in `what-we-cannot-prove.md`.
- Pydantic's error for an unknown `format` now lists five values instead of three; the config is
  refused exactly as before. This is the only text a V1 config can see change.
- Not admitted: unified slice, out-of-core FK route, subset (section 4). These are follow-ups.
