## 1. FRAME

**Problem.** The sprint doc's V1P-2.4 asked for "a `locale` setting on faker and composite
providers". A probe on `origin/main` (Faker 40.23.0) found that the setting already works for the
19 Faker-backed catalogue providers: `provider_config: {locale: de_DE}` reaches the pool builder and
`FakerAdapter` builds `Faker("de_DE")`. What is wrong is what the engine says and how it fails:

1. Every Faker-backed capability row declares `supported_locales=("en_US",)`, although the
   providers work in up to 107 locales. The CLI cockpit, the capability matrix and the platform
   picker read these rows.
2. An invalid locale (`xx_YY`) fails at run time with a raw `AttributeError` from Faker, with no
   reason code.
3. A real locale that lacks the method (`address_state` in `fr_FR`) fails at run time as a
   `capability_violation`, which names the wrong cause.

**Definition of done.**

1. Each Faker-backed catalogue row declares the locales where its Faker method works under the
   pinned Faker version, from one generated table.
2. A generator script writes the table; a drift test regenerates it in memory from the installed
   Faker and fails when they differ, or when the Faker version recorded in the table is not the
   installed one.
3. `FakerAdapter` refuses a locale outside the provider's declared list with the existing
   `provider.unsupported_locale` code, naming provider and locale only, before Faker is built.
4. Default behavior is unchanged: no locale still means `en_US`, and every config that runs today
   still runs with byte-identical output.

**Boundaries (non-goals).**

- A plan-compile check against `supported_locales`. It needs a plan-phase reason code (the
  existing `provider.unsupported_locale` is an execution-phase outcome), and new codes wait for
  REG-RENUMBER (row 8). Recorded as the follow-up V1P-2.4b.
- Coherent non-US addresses (city, region and postcode that agree). Faker's address fields are
  independent per call, and `composite_address` and `composite_city_state_zip` read
  `us_localities.csv`. Non-US locality data needs a licensed source (for example GeoNames postal
  codes, CC BY 4.0). Recorded as V1P-2.4c.
- Composite and Mimesis rows: unchanged (composites stay `en_US`; Mimesis declares its own).
- Custom providers registered through `register_faker_provider_v2`: not checked (no catalogue row).
- `internal/faker_setup.py` (the legacy V1 `faker_type:` path) is not touched.

**Risk: R2.** Public capability rows change (compatibility surface) and an error's code changes for
already-failing configs. Rollback: revert; nothing is persisted.

**Reuse check.** `faker.config.AVAILABLE_LOCALES`; `_FAKER_METHOD_MAP` and `_FAKER_DEFAULT_KWARGS`
in `providers_v2/_faker_adapter.py` (the single map from provider to Faker method); the existing
generator-plus-drift-test pattern (`scripts/gen_capability_matrix.py` and
`tests/sentry/test_capability_matrix.py`).

## 2. Established solutions

Search run (2026-11-06): Faker's own locale model (`faker.config.AVAILABLE_LOCALES`, per-locale
provider packages with fallback to the default provider, so a method missing from a locale package
may still resolve or may raise `AttributeError`); Mimesis declares locales per provider in its
`Locale` enum, which the engine's Mimesis adapter already uses for `supported_locales`. Probe of
Faker 40.23.0 across all 107 locales and the 19 catalogue methods (one seeded call each, about 4
seconds): 17 providers work in all 107; `person_phone` in 104; `address_state` in 69.

Design follows: declare support from observed behavior of the pinned library, as the Mimesis
adapter declares from its enum, and keep the observation as generated data with a drift test, the
engine's existing pattern for derived tables. Computing it at registry build is rejected: it costs
seconds on every process start.

## 3. Behavior

| Case | Today | After |
|---|---|---|
| no locale | `en_US` | unchanged |
| supported locale (`de_DE` on `person_first_name`) | works | unchanged, byte-identical |
| invalid locale (`xx_YY`) | raw `AttributeError` at run time | `ProviderError` `provider.unsupported_locale` at run time, naming provider and locale |
| real locale lacking the method (`fr_FR` on `address_state`) | `capability_violation` at run time | `provider.unsupported_locale` at run time |
| capability row `supported_locales` | `("en_US",)` | the observed list, `en_US` included |

The refusal happens in `FakerAdapter` before any `Faker(locale)` is built, on both `generate` and
`generate_batch`, for catalogue providers only.

## 4. Design notes

- **One table, one place.** New `providers_v2/_faker_locales.py` holds `FAKER_VERSION`,
  `ALL_LOCALES` (the observed full list) and `UNSUPPORTED` (provider to the locales it fails in).
  `supported_locales(provider)` derives the tuple. The table is written by
  `scripts/gen_faker_locales.py` and never edited by hand (header says so).
- **Compact data.** A full per-provider list would be 19 x 107 entries; storing the full list once
  plus exclusions keeps the module small (about 60 lines) and readable in review.
- **Probe definition.** A provider supports a locale when one call of its mapped Faker method, with
  the adapter's default kwargs, on `Faker(locale)` seeded with a fixed seed, returns without
  raising. The script and the drift test share this function, so the definition lives in one
  place (the script imports it from a small helper the test also imports).
- **Adapter check.** `FakerAdapter` already receives a capabilities lookup; it reads the declared
  locales from it, so the adapter and the registry cannot disagree.

## 5. Choke points and guards

| Rule | Choke point | Guard | Mutation |
|---|---|---|---|
| Declared locales match the pinned Faker | `_faker_locales.py`, written only by the script | `tests/sentry/test_faker_locales.py`: regenerate in memory and compare; version check | hand-edit one exclusion out of the table |
| Every Faker-backed catalogue row uses the table | `_real_registry._faker_cap` | test: each Faker-backed row's `supported_locales == supported_locales(provider)` | revert one row to `("en_US",)` |
| The adapter refuses undeclared locales | `FakerAdapter` locale check (one helper used by both entry points) | tests for `generate` and `generate_batch`, invalid and method-lacking locales | remove the check from `generate_batch` |

## 7. Acceptance tests (written first)

1. Drift: the in-memory regeneration equals the committed table, and `FAKER_VERSION` equals the
   installed `faker.VERSION`.
2. Rows: every Faker-backed catalogue row's `supported_locales` equals the table's list and
   contains `en_US`; `person_phone` and `address_state` exclude the probed locales.
3. Adapter: for an invalid locale and for `fr_FR` on `address_state`, both `generate` and
   `generate_batch` raise `ProviderError` with `provider.unsupported_locale`; the message names
   provider and locale and no generated value.
4. Unchanged output: a seeded `generate_batch` with no locale, with `en_US` and with `de_DE` equals
   the output from `origin/main` (golden values captured on `origin/main` before the change).
5. End to end: a `strategy: faker` config with `provider_config: {locale: fr_FR}` on
   `address_state` fails with `provider.unsupported_locale`; the same with `de_DE` runs.
6. Guards in section 5.

## 8. Known limits

- The table is only as good as one probe call per locale: a method that works for some seeds and
  fails for others would be declared supported. None was seen in the probe; the drift test pins
  today's behavior.
- A Faker upgrade changes the table; the drift test makes that visible in the lock-bump change.
- Unsupported locales still fail at run time, not at plan compile (V1P-2.4b).
