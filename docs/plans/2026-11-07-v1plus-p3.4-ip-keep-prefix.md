## 1. FRAME

**Problem.** The engine has no IP-address mask. Today an IP column gets `faker` `ipv4` (the
profiler's recommendation) or `hash`, both of which destroy the network structure that network
analytics, firewall-rule tests and fraud features depend on ("all requests from one /24", "same
/48 site"). X-10 asks for a mask that keeps the subnet prefix.

**Property kept (the whole guarantee).** For a column masked with `strategy: ip_prefix`,
`keep_bits_v4: N4` and `keep_bits_v6: N6`, under one `(mask_key, namespace)`:

- P1 (verbatim prefix). Every output address has the same family as its input, and its first
  `N` bits (N = N4 for IPv4, N6 for IPv6) equal the input's first `N` bits.
- P2 (prefix preservation below N). For any two inputs `a`, `b` of the same family, the outputs
  share a common prefix of exactly the same length as the inputs do (Crypto-PAn's defining
  property, applied to the bits after `N`).
- P3 (bijection and determinism). Per family the mapping is a permutation of the address space
  that fixes the first `N` bits: distinct addresses never collide, and the same address always
  maps to the same output within the namespace, across runs, processes, chunk boundaries and
  routes.
- P4 (IPv4-mapped consistency). `::ffff:a.b.c.d` maps to `::ffff:` followed by the IPv4 output
  for `a.b.c.d`, so a column that mixes the two spellings of one host still joins.

**Leak accepted (documented in `docs/what-we-cannot-prove.md`).**

- The first `N` bits are published as-is. They identify the network, and through public
  registries (RIR whois, BGP tables, GeoIP databases) the organisation, ISP and approximate
  location. A /24 can be a single household or small office. For IPv6, a prefix longer than 64
  bits keeps part of the interface identifier, which for SLAAC EUI-64 addresses carries a MAC
  address; 6to4 addresses (`2002::/16`) carry an IPv4 address in bits 16 to 47, which a
  `keep_bits_v6` of 48 publishes.
- P2 keeps the subnet structure below `N`. The prefix-preserving literature shows this structure
  can be attacked: an adversary who knows or can inject some real address pairs (for a database:
  can cause rows with known addresses to be written, for example by signing up from a known IP)
  learns the keyed bit function along those prefixes and can de-anonymise further bits of other
  addresses sharing them (Brekne, Årnes and Øslebø 2005, packet-injection and frequency attacks
  on Crypto-PAn and tcpdpriv `-A50`); and the preserved structure plus public information lets
  an analyst infer topology and identify servers (Coull, Wright, Monrose, Collins and Reiter,
  NDSS 2007). The strategy is pseudonymisation, not anonymisation.
- Family, the count of distinct addresses (P3) and, with P1, the per-network frequency
  distribution are kept.
- The mapping is invertible by anyone holding `mask_key` and the namespace (it is a keyed
  permutation, like `fpe`). Without a configured secret, `mask_key` is the job seed, so the
  config holder can invert it.

**Definition of done.** P1 to P4 hold on every non-null output row (property test, section 8);
the Crypto-PAn published vectors pass; malformed cells never reach the output unflagged; every
route either produces identical output or declines with a coded reason; the leak above is in
`docs/what-we-cannot-prove.md`; the option is in `docs/strategies.md` and the CHANGELOG.

**Non-goals.** Anything keeping more than P1 to P4. Specifically: no format preservation of the
input spelling (output is canonical text, section 3); no CIDR network values; no unmask
(reversal) support; no pass-through of special addresses; no `text_mask` span support (the
`ipv4` detector's `per_detector_strategy` keeps its current choices); no generate mode; no native,
out-of-core or unified-slice kernel; no change to the `ipv4` detector, the profiler's
recommendation or any default.

**Risk: R2.** New privacy logic (a keyed pseudonymisation primitive and its documented leak), a
reason-registry minor bump, and a new entry in the determinism and strategy registries.
Rollback: revert the commits; nothing is persisted and no existing derivation changes
(`SEED_PROTOCOL_VERSION` unchanged).

**Reuse check (sprint rule: `derived` or `formula` first).** `derived` is a closed grammar with
no function calls and no keyed operation; it cannot express a keyed bit mapping. `formula` can
express a weak cousin for IPv4 on octet boundaries only
(`".".join(value.split(".")[:3]) + "." + str(randint(0, 255))`), but it is not keyed by the mask
key (its RNG is seeded per formula and is order-dependent), not a bijection (collisions), not
joinable across tables, not prefix-preserving below the kept octets, and cannot parse IPv6. So
this slice is new logic over a published primitive, not a named option over existing code.

**Host: a small new strategy, not an option on `fpe` or `hash`.** The brief prefers an option on
an existing strategy; the two candidates do not fit:

- `fpe`: Crypto-PAn is not FF1. None of `fpe`'s options (`charset`, `preserve_separators`,
  `validate_luhn`, `checksum`, `fpe_join_group`) apply, and FF1 cannot carry the host bits itself:
  NIST SP 800-38G requires `radix ** length >= 1,000,000`, so 8 host bits (a /24) are refused.
  Worse, `fpe` runs on six routes outside the Python handler (sequential native, native chunked,
  physical shadow binding, out-of-core Group (b) native and Python, text-mask FPE spans) and its
  native config parser `FpeConfig.from_mapping` ignores unknown keys. An `ip` option on `fpe`
  would be silently ignored by any of those routes that forgot to decline it, producing FF1 over
  the digits of the address: wrong output, prefix destroyed, and fail-open. The existing
  `checksum` option already needs a hand-written decline at five of those sites.
- `hash`: outputs hex digests; not an address.

A new strategy name is unknown to every native, out-of-core and unified-slice allowlist, so those
routes decline it by construction, and the strategy registries' totality guards force each
registry to classify it. The cost is one entry per registry (section 7), all guarded.

## 2. Established solutions

Searches run (2026-11-07): web searches for the Crypto-PAn paper, reference implementation and
test vectors; yacryptopan source, README and test suite (fetched from
`github.com/diekmann/yacryptopan`, BSD licence, PyPI 1.0.2); the IETF ipcrypt draft
(`draft-denis-ipcrypt`, ipcrypt-pfx mode; full text not fetchable from this sandbox, table of
contents only); attacks on prefix-preserving anonymisation (Brekne et al. 2005; Coull et al.
2007; Ribeiro et al. NDSS 2008, which surveys both); tcpdpriv `-A50` and Ylonen's attack note;
Microsoft Presidio anonymizer operators; Tonic's IP address generator; Google Analytics IP
anonymisation. In the codebase: every `ipv4`/`ipv6`/`ipaddress` use (the `ipv4` detector and
validator, the `faker` `ipv4` recommendation, `generation/_bounds.py`), `geo_generalize`,
`derived`, `formula`, `transforms/fpe.py`, `transforms/_ff1.py`, the strategy registries and the
determinism protocol.

Findings:

- **Crypto-PAn** (J. Xu, J. Fan, M. Ammar, S. Moon, "Prefix-Preserving IP Address Anonymization:
  Measurement-based Security Evaluation and a New Cryptography-based Scheme", ICNP 2002) is the
  established prefix-preserving construction: output bit `i` is input bit `i` XOR the top bit of
  `AES_K(prefix_i || pad)`, where `prefix_i` is the input's first `i` bits and `pad` is
  `AES_K(K2)` filling the remaining bits; the 256-bit key is `K || K2` (AES-128 key, pad seed).
  It is a bijection, deterministic, and prefix-preserving by construction (Theorem 1 of the
  paper). The reference C++ implementation (Jinliang Fan, Crypto-PAn 1.0) ships a 100-address
  sample trace and its anonymised output under a fixed key; yacryptopan's test suite checks
  against exactly that trace and extends the construction to IPv6 by running the same per-bit
  rule over 128 bits (IPv4 is placed in the top 32 bits of the 128-bit block, which is why its
  IPv6 tests reproduce the IPv4 vectors).
- **ipcrypt-pfx** (IETF Internet-Draft `draft-denis-ipcrypt`, work in progress) standardises a
  prefix-preserving mode in native address size that handles IPv4 through the IPv4-mapped form;
  it is a draft (not citable as a standard, and its vectors could not be fetched here), so the
  design follows Crypto-PAn and records ipcrypt-pfx as the likely future standard (section 9).
- **tcpdpriv `-A50`** is table-based prefix preservation (not keyed, not reproducible across
  runs); Crypto-PAn replaced it for exactly that reason. Ylonen's note and Brekne et al. show both
  fall to injection.
- **Presidio** has no IP-specific operator (replace, redact, mask by character, hash, encrypt);
  **Tonic**'s IP generator emits random addresses with a v4/v6 ratio and optional consistency,
  without prefix preservation. Neither keeps network structure.
- **Truncation precedent for the defaults:** Google Analytics' IP anonymisation zeroes the last
  octet of IPv4 and the last 80 bits of IPv6, i.e. keeps /24 and /48 (sources are third-party
  documentation of that behaviour). The defaults below follow it; the difference is that this
  strategy pseudonymises the host bits instead of zeroing them, so distinct hosts stay distinct.
- **Codebase:** no IP masking exists. The `ipv4` detector and validator (`detection/`) and the
  profiler's `faker` `ipv4` recommendation are untouched (non-goal). `geo_generalize` is ZIP and
  H3 only. `transforms/_ff1.py` already uses `cryptography`'s AES; this slice uses the same
  package for one AES-128 ECB block call per bit. Stdlib `ipaddress` parses and is strict (it
  rejects leading-zero octets, surrounding whitespace, trailing newlines, non-ASCII digits and
  CIDR suffixes; probe recorded below).

Feasibility probe (scratch, not committed): a 30-line Crypto-PAn over `cryptography` reproduced
all 100 reference-trace pairs, yacryptopan's four published IPv4 and IPv6 examples, and, with the
first 24 bits forced verbatim, the reference host octet for all 100 pairs (the composition P1 + P2
relies on). Throughput with one batched ECB call per address (all prefix blocks in one `update`):
about 260,000 IPv4 /24 values per second, 85,000 full IPv4, 29,000 IPv6 /48 and 18,000 full IPv6
on one core, before the per-column distinct-value memo.

Design follows: Crypto-PAn (Xu et al. 2002) for the per-bit function, key layout and pad; the
yacryptopan IPv6 extension (same rule over 128 bits); keep-prefix as Crypto-PAn with the first
`N` per-bit flips forced to zero, which is the reference output's host bits under the input's
verbatim prefix. Custom code is the 60-line primitive (no maintained Crypto-PAn package is in the
lock, and adding one is barred: yacryptopan needs PyCryptodome, a new dependency) plus the parse,
format and config handling around it.

## 3. Behaviour

Config (`provider_config` of a column with `strategy: ip_prefix`; a namespace is required):

| Key | Type | Default | Meaning |
|---|---|---|---|
| `keep_bits_v4` | int, 0 to 31 | 24 | IPv4 bits kept verbatim |
| `keep_bits_v6` | int, 0 to 127 | 48 | IPv6 bits kept verbatim |

`0` is full Crypto-PAn (mode (b) of the slice brief: prefix-preserving with no verbatim prefix).
Both modes are the same construction with a different `N`, and the reference vectors test `N = 0`
directly, so they ship together rather than one being deferred; the docs say plainly that
`N = 0` does not hide the network from the attacks in section 1.

Per cell:

| Input | Output |
|---|---|
| null | null (no keyed draw) |
| IPv4 dotted quad (`ipaddress.IPv4Address`) | IPv4 dotted quad, P1/P2 with `keep_bits_v4` |
| IPv6, any RFC 4291 text form, any case | RFC 5952 canonical text (lower case, `::` compression), P1/P2 with `keep_bits_v6` |
| IPv4-mapped IPv6 (`::ffff:a.b.c.d`, any spelling) | `::ffff:` + the IPv4 output for `a.b.c.d` (P4); built as a string, not through `str(IPv6Address)`, whose form for mapped addresses changed in Python 3.13 |
| Other IPv4-embedding IPv6 (6to4, NAT64, Teredo, deprecated `::a.b.c.d`) | treated as plain IPv6 (section 9) |
| special addresses (private, loopback, link-local, multicast, ULA, documentation, unspecified, broadcast) | no special case. A range whose length is at most `N` (10/8, 192.168/16, 127/8, 169.254/16, 224/4, fe80::/10, fc00::/7, ff00::/8 with the defaults) stays in range by P1; a longer one (0.0.0.0, 255.255.255.255, `::`, `::1`, a /24's network and broadcast addresses) maps like any other address |
| malformed (see below) | left in the frame and recorded as a `format_error` `RowError`, so the D8 gate fails the run (`RowErrorsFailedError`) or quarantines the row; never emitted unflagged |

Malformed means any non-null cell that is not a `str`, or a string `ipaddress.ip_address` rejects,
or an IPv6 address with a zone (`%eth0`; the zone is an interface name and is refused rather than
kept or dropped), or a CIDR value (`10.0.0.0/8`; `ipaddress.ip_address` rejects it). No stripping
or normalisation happens before parsing: `" 10.0.0.1"`, `"10.0.0.1\n"` and `"010.0.0.1"` are
malformed. The row-error reason is fixed text naming the column and the strategy, never the value.

Special addresses: keeping them verbatim was rejected because a regular address could then map
onto a kept one (a collision, breaking P3); cycle-walking around the reserved set restores the
bijection but breaks P2 for pairs whose walk lengths differ. Refusing them was rejected because
real logs carry `127.0.0.1` and private addresses routinely, and with the defaults the common
ranges stay in range anyway.

Failure modes (codes are new unless marked existing; section 6 has the registry change):

| Failure | When | Behaviour |
|---|---|---|
| unknown key in `provider_config` (a typo such as `keep_bit_v4` would otherwise fall back to the default and keep more or fewer bits than intended) | plan compile | `PlanCompileError` `plan.ip_prefix_unknown_option`, path names the key |
| `keep_bits_*` not an `int`, or a `bool`, numeric string, float or negative | plan compile | `plan.ip_prefix_keep_bits_invalid` |
| `keep_bits_v4 >= 32` or `keep_bits_v6 >= 128` (the column would pass through unmasked) | plan compile | `plan.ip_prefix_keeps_whole_address` |
| `ip_prefix` as a `nested` child (`provider_config.strategy: ip_prefix`) | plan compile | `plan.ip_prefix_unsupported_in_nested` (the nested JSON round trip and the flattened-leaf row-error index have the problem `top_code` refuses for; not worth the machinery here) |
| no namespace | run | `StrategyError` `runtime.ip_prefix_requires_namespace` |
| any of the config faults above reaching the handler without compile (raw plan) | run | same parser, `StrategyError` with the runtime twin `runtime.ip_prefix_config_invalid` |
| malformed cell | run | `format_error` row error (existing trigger) |
| native kernel, unified slice, native chunked | routing | declined by construction (not in `NATIVE_KERNEL_STRATEGIES`); existing decline codes |
| out-of-core FK route | routing | declined (existing code `out_of_core_row_error_strategy_unsupported`: the route has no row-error channel), falls back to sequential or full-frame |
| chunked FK gate | compile | not in `CHUNK_SAFE_STRATEGIES`: existing refusal code for a non-chunk-safe strategy on an FK edge |

All messages carry the column, table, option name and the allowed range only. Config option
values are operator config, not data, but none is echoed except the integer bit counts. Every
value-free error is raised outside the `except` block (recurring defect 3).

`when:` is allowed: the strategy is row-local and writes strings into a string column, so the
gated subset is masked and the rest passes through as `when` documents for every strategy.

Uniqueness and collisions: P3 makes the mapping collision-free per address. Uniqueness is over
addresses, not spellings: `2001:DB8::1` and `2001:db8:0:0:0:0:0:1` are one address and produce one
output, so the output's distinct-string count can be lower than the input's.

## 4. Design notes

- **Structure added.** One strategy (a new variant of the strategy registry, which keeps
  growing), one primitive module, one transform module. Open/closed: the strategy is added by
  registering a handler and one entry in each classification table; each table already has a
  totality guard against `SCALAR_HANDLERS`, so no shared `if/elif` changes. Deep module: the
  handler sees `IpPrefixConfig` and one `mask_ip(value) -> str | None` call; parsing, family
  dispatch, the mapped-form rule and Crypto-PAn stay behind it.
- **One place per fact.**
  - Option names, types, defaults, ranges: `IpPrefixConfig.from_provider_config` in
    `transforms/network/ip_prefix.py`. The compile check and the handler both call it (the
    `code_set` / `joint_mask` pattern: config validation lives with the transform and is used
    at compile and as the run-time backstop). The catalog's `wizard_options` reads the names and
    defaults from the same module's constants.
  - Key label: `CRYPTOPAN_KEY_LABEL = b"cryptopan-key/v1"` in the primitive module, domain
    separated from `FF1_KEY_LABEL`.
- **Keying.** `derive(mask_key, namespace, CRYPTOPAN_KEY_LABEL)` gives 32 bytes, used exactly as
  the Crypto-PAn key: bytes 0 to 15 are the AES-128 key, bytes 16 to 31 are encrypted to form the
  pad. One key per namespace, like `hash`: columns in one namespace share the mapping (joins
  hold), different namespaces get unrelated mappings. No new secret parameter. The handler builds
  `CryptoPan(OpaqueBox(derive(ctx.mask_key, namespace, CRYPTOPAN_KEY_LABEL)))` in one expression,
  and the constructor builds the AES encryptor from `box.open()[0][:16]` and the integer pad
  inline, so no frame local holds key bytes (the object has `__slots__` and a fixed `__repr__`).
  Expected secret-material census growth: zero entries; the build runs
  `scripts/secret_material_census.py` and stops for the owner if any entry appears (section 10).
- **Determinism.** Per-cell and source-keyed: the output is a pure function of
  `(mask_key, namespace, keep_bits, value)`, so chunking, row order and partitioning cannot change
  it. One new draw site `mask.ip_prefix` (family `source_keyed_hmac`, entropy root `mask_key`,
  identity `source_value`, partitionable, null rows draw nothing), appended at the end of
  `DRAW_SITES` as a standalone constant in `_draw_sites_mask.py` (the `MASK_FORMULA_DRAW_SITE`
  precedent; append-only, so the pinned digests gain one entry and the map digest changes).
  `SEED_PROTOCOL_VERSION` is unchanged: no existing derivation changes.
- **Speed.** One `encryptor.update` per address over the `L - N` prefix blocks (ECB here is the
  raw block-cipher PRF Crypto-PAn specifies, one independent block per bit, not a confidentiality
  mode), plus a per-column dict memo over distinct values. Oracle routes only; a native kernel is
  a later slice if a customer needs the speed.
- **Routes.** The Python handler runs on every route that runs `SCALAR_HANDLERS`: full-frame
  oracle, `auto_chunk` / chunked oracle, sequential (S2, the default for FK jobs). Native chunked,
  unified slice, native sequential seam and out-of-core decline by construction. Every route that
  runs it runs the same handler, so parity is by construction and checked by test (section 8).
- **Classification entries** (one each, all guarded): `TECHNIQUE_CLASS_BY_STRATEGY`
  `pseudonymisation`; distribution behaviour: the value that means "keeps cardinality exactly"
  (chosen against that module's definitions in the build); native capabilities `_Ortho`
  keyed, row-local, `row_error_modes=("format_error",)`; `ALWAYS_KEYED_STRATEGIES`;
  leak-check `SHAPE_PRESERVING` (the output shares a verbatim prefix with the input by design,
  so the transformative-output leak check would flag every row); `_column_access`
  `_SCALAR_STRATEGIES`; out-of-core `_DEFERRED_GROUP_B` entry with the existing row-error code.
- **Catalog.** `namespace_required=True`; `join_safe=True` (injective and deterministic per
  address with the defaults); `wizard_options` = the two keys; `offer_in_wizard=False` while the
  track is dark (the V1P-2.3 precedent: a new entry visible in the CLI is held until CLI-REL;
  section 10).
- **House style.** Typed `IpPrefixConfig` (frozen dataclass) instead of dict reads; no flag
  arguments (the family is dispatched on the parsed address type); comments say why.

YAML example:

```yaml
tables:
  - name: access_log
    columns:
      - name: client_ip
        strategy: ip_prefix
        namespace: client_ip
        provider_config:
          keep_bits_v4: 24   # default; keep the /24
          keep_bits_v6: 48   # default; keep the /48 site prefix
  - name: sessions
    columns:
      - name: ip
        strategy: ip_prefix
        namespace: client_ip  # same namespace: same mapping, so the two columns join
```

## 5. Choke points

| Rule | Choke point | Guard test | Mutation that must turn it red |
|---|---|---|---|
| Every `ip_prefix` column's options are validated, at compile and at run | `IpPrefixConfig.from_provider_config`, called by `check_ip_prefix_config` (compile, both branches and `run_config_only_checks`) and by the handler | compile test per refusal code; a handler test with a raw `ColumnSeed` that skips compile and gets the same refusal | delete the unknown-key check from the parser (both tests red); delete the `check_ip_prefix_config` call from `_compile.py` (compile test red, handler test still green, proving the backstop is separate) |
| No route other than the Python handler runs `ip_prefix` | the native, unified-slice and out-of-core allowlists (`NATIVE_KERNEL_STRATEGIES`, `_SUPPORTED_WORK_STRATEGIES`) | route tests that run an `ip_prefix` job on each route's entry point and assert the decline reason code in the route evidence and output equal to the oracle | add `"ip_prefix"` to `_SUPPORTED_WORK_STRATEGIES` (out-of-core test red); add it to `NATIVE_KERNEL_STRATEGIES` (native test red) |
| Every strategy is classified in every registry | the existing totality guards over `SCALAR_HANDLERS` (determinism map, capabilities, technique class, distribution behaviour, leak check, column access, catalog) | those guards, unchanged | remove `ip_prefix` from `MASK_STRATEGY_TO_SITE` (`test_draw_site_inventory_coverage.py` red) |
| Key derivation is pinned and domain-separated | `CRYPTOPAN_KEY_LABEL` in the primitive module | golden test: a fixed 32-byte mask key, namespace and five addresses produce pinned outputs end to end through the handler | change the label to `FF1_KEY_LABEL` (golden red) |
| The primitive is Crypto-PAn | `transforms/network/_cryptopan.py` | reference-trace and yacryptopan vectors | use the low bit of the AES output instead of the top bit (vectors red); mask the pad with `L - pos - 1` bits (vectors red) |
| Malformed cells never pass unflagged and messages are value-free | the handler's single parse call | malformed-cell test (each spelling in section 3 records `format_error`; the run fails by default) and a sentinel-value test over every error, row-error reason and warning | swallow the parse error and emit the input (malformed test red); put the value in the row-error reason (sentinel test red) |

The parser is the choke point for the option rule; the allowlists are the choke point for routes.
Both are enforced by construction (an unvalidated config cannot reach `mask_ip`, because the
handler only holds an `IpPrefixConfig`; a route without `ip_prefix` in its allowlist cannot run it).

## 9. Known limits

- Output is canonical text, not the input's spelling (an exploded IPv6 input comes back
  compressed; upper-case hex comes back lower case).
- CIDR values, zone IDs and integer-encoded addresses are malformed, not masked. A column of
  firewall rules with `/len` suffixes needs a later option (Crypto-PAn maps a prefix to a
  prefix, so it is possible).
- IPv4 embedded in 6to4, NAT64, Teredo and IPv4-compatible IPv6 is pseudonymised as IPv6 bits
  (no leak below `N`, but not consistent with the IPv4 mapping, unlike the IPv4-mapped form).
- Special single addresses lose their meaning (section 3).
- Python per-bit AES: tens of thousands of IPv6 values per second per core before the memo. A
  native kernel is out of scope.
- `ipcrypt-pfx` (IETF draft) may become the standard prefix-preserving IP encryption; if it does,
  a later mode can follow it with its own vectors. Crypto-PAn is not the same mapping.
- The attacks in section 1 are not mitigated. The remedies in the literature (for example
  re-keying per dataset, or Brekne et al.'s proposals) trade away P3's cross-run stability; a
  per-run key is already available by choosing a fresh namespace or secret.
