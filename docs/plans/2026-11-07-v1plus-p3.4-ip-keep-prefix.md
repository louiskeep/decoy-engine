## 1. FRAME

**Problem.** The engine has no IP-address mask. Today an IP column gets `faker` `ipv4` (the
profiler's recommendation) or `hash`, both of which destroy the network structure that network
analytics, firewall-rule tests and fraud features depend on ("all requests from one /24", "same
/48 site"). X-10 asks for a mask that keeps the subnet prefix.

**Property kept (the whole guarantee).** For a column masked with `strategy: ip_prefix`,
`keep_bits_v4: N4` and `keep_bits_v6: N6`, under one `(mask_key, namespace)`. "Class" below means
one of: IPv4 (dotted quad, or the IPv4-mapped spelling `::ffff:a.b.c.d`, both mapped by the IPv4
rule), or IPv6 outside `M = ::ffff:0:0/96`.

- P1 (verbatim prefix). Every output is in the same class as its input. An IPv4 output's first
  `N4` bits equal the input's (for the mapped spelling: those of the embedded IPv4, and the output
  keeps the `::ffff:` spelling). An IPv6 output's first `N6` bits equal the input's.
- P2 (prefix preservation below N). For two inputs `a`, `b` of the same class, the outputs share a
  common prefix of exactly the same length as the inputs (Crypto-PAn's defining property). One
  exception within the IPv6 class: when exactly one of `a`, `b` lies in the key-chosen /96 block
  `Q` that the block swap moves (section 3), the pair carries no P2 claim. Pairs from different
  classes (an IPv4 or mapped address against another IPv6 address) carry no P2 claim: `::1` and
  `::ffff:1.2.3.4` share 80 input bits but, with the defaults, 48 output bits.
- P3 (bijection and determinism). The mapping is a permutation of each class's address space
  (2^32 for IPv4, 2^128 - 2^32 for IPv6) that fixes the first `N` bits: distinct addresses never
  collide, within a class or across classes, and the same address always maps to the same output
  within the namespace, across runs, processes, chunk boundaries and routes.
- P4 (IPv4-mapped consistency). `::ffff:a.b.c.d` maps to `::ffff:` followed by the IPv4 output for
  `a.b.c.d`, so a column that mixes the two spellings of one host still joins.

**Leak accepted (documented in `docs/what-we-cannot-prove.md`).**

- The first `N` bits are published as-is. They identify the network, and through public
  registries (RIR whois, BGP tables, GeoIP databases) the organisation, ISP and approximate
  location. A /24 can be a single household or small office. For IPv6, a prefix longer than 64
  bits keeps part of the interface identifier, which for SLAAC EUI-64 addresses carries a MAC
  address; 6to4 addresses (`2002::/16`) carry an IPv4 address in bits 16 to 47, which a
  `keep_bits_v6` of 48 publishes.
- P2 keeps the subnet structure below `N`. The prefix-preserving literature shows this structure
  can be attacked: an adversary who knows or can inject some real address pairs (for a database:
  can cause rows with known addresses to be written, for example by signing up from a known IP)
  learns the keyed bit function along those prefixes and can de-anonymise further bits of other
  addresses sharing them (Brekne, Årnes and Øslebø, PET 2005: packet-injection and frequency
  attacks on Crypto-PAn and tcpdpriv `-A50`); and the preserved structure plus public information
  lets an analyst infer topology and identify servers (Coull, Wright, Monrose, Collins and Reiter,
  NDSS 2007). With `N = 0` (full Crypto-PAn) the network itself is exposed to these attacks. The
  strategy is pseudonymisation, not anonymisation.
- Class, the count of distinct addresses (P3) and, with P1, the per-network frequency
  distribution are kept. With few host bits a row maps to itself often (rate about 2^-(L-N),
  where L is 32 or 128): a quarter of rows at `keep_bits_v4: 30`.
- The mapping is invertible by anyone holding `mask_key` and the namespace (it is a keyed
  permutation, like `fpe`, and `unmask` reverses it). Without a configured secret, `mask_key` is
  the job seed, so the config holder can invert it.

**Definition of done.** P1 to P4 hold on every non-null output row (property test, section 8);
the Crypto-PAn published vectors pass; malformed cells never reach the output unflagged; every
route either produces identical output or declines with a coded reason; `unmask` reverses the
column; the leak above is in `docs/what-we-cannot-prove.md`; the option is in `docs/strategies.md`
and the CHANGELOG.

**Non-goals.** Anything keeping more than P1 to P4. Specifically: no format preservation of the
input spelling (output is canonical text, section 3); no CIDR network values; no pass-through of
special addresses; no `text_mask` span support (the `ipv4` detector's `per_detector_strategy`
keeps its current choices); no generate mode; no native, out-of-core or unified-slice kernel; no
change to the `ipv4` detector, the profiler's recommendation or any default.

**Risk: R2.** New privacy logic (a keyed pseudonymisation primitive, its inverse, and its
documented leak), a reason-registry minor bump, new entries in the determinism, strategy and
post-validation registries, one secret-material census entry (owner exception, section 11), and a
change to published listings (proof manifest, capability matrix). Rollback: revert the commits;
nothing is persisted and no existing derivation changes (`SEED_PROTOCOL_VERSION` unchanged).

**Reuse check (sprint rule: `derived` or `formula` first).** `derived` is a closed grammar with
no function calls and no keyed operation; it cannot express a keyed bit mapping. `formula` can
express a weak cousin for IPv4 on octet boundaries only
(`".".join(value.split(".")[:3]) + "." + str(randint(0, 255))`), but it is not keyed by the mask
key (its RNG is seeded per formula and is order-dependent), not a bijection (collisions), not
joinable across tables, not prefix-preserving below the kept octets, and cannot parse IPv6. So
this slice is new logic over a published primitive, not a named option over existing code.

**Host: a small new strategy, not an option on `fpe` or `hash`.** The brief prefers an option on
an existing strategy; the two candidates do not fit:

- `fpe`: Crypto-PAn is not FF1. None of `fpe`'s options (`charset`, `preserve_separators`,
  `validate_luhn`, `checksum`, `fpe_join_group`) apply, and FF1 cannot carry the host bits itself:
  NIST SP 800-38G requires `radix ** length >= 1,000,000`, so 8 host bits (a /24) are refused.
  Worse, `fpe` runs on six routes outside the Python handler (sequential native, native chunked,
  physical shadow binding, out-of-core Group (b) native and Python, text-mask FPE spans) and its
  native config parser `FpeConfig.from_mapping` ignores unknown keys. An `ip` option on `fpe`
  would be silently ignored by any of those routes that forgot to decline it, producing FF1 over
  the digits of the address: wrong output, prefix destroyed, and fail-open. The existing
  `checksum` option already needs a hand-written decline at five of those sites.
- `hash`: outputs hex digests; not an address.

A new strategy name is unknown to every native, out-of-core and unified-slice allowlist, so those
routes decline it by construction, and the strategy registries' totality guards force each
registry to classify it. The cost is one entry per registry (section 6), all guarded.

## 2. Established solutions

Searches run (2026-11-07): web searches for the Crypto-PAn paper, reference implementation and
test vectors; yacryptopan source, README and test suite (fetched from
`github.com/diekmann/yacryptopan`, BSD licence, PyPI 1.0.2); the IETF ipcrypt draft
(`draft-denis-ipcrypt`, ipcrypt-pfx mode; full text not fetchable from this sandbox, table of
contents only); attacks on prefix-preserving anonymisation (Brekne et al. 2005; Coull et al.
2007; Ribeiro et al. NDSS 2008, which surveys both); tcpdpriv `-A50` and Ylonen's attack note;
Microsoft Presidio anonymizer operators; Tonic's IP address generator; Google Analytics IP
anonymisation. In the codebase: every `ipv4`/`ipv6`/`ipaddress` use (the `ipv4` detector and
validator, the `faker` `ipv4` recommendation, `generation/_bounds.py`), `geo_generalize`,
`derived`, `formula`, `transforms/fpe.py`, `transforms/_ff1.py`, `unmask.py`, the strategy
registries, the determinism protocol and its provider registry, the post-validation checks, the
proof manifest, and `generation/pool/_canonicalize.py` (for the key-label analysis, section 4).

Findings:

- **Crypto-PAn** (J. Xu, J. Fan, M. Ammar, S. Moon, "Prefix-Preserving IP Address Anonymization:
  Measurement-based Security Evaluation and a New Cryptography-based Scheme", ICNP 2002) is the
  established prefix-preserving construction: output bit `i` is input bit `i` XOR the top bit of
  `AES_K(prefix_i || pad)`, where `prefix_i` is the input's first `i` bits and `pad` is
  `AES_K(K2)` filling the remaining bits; the 256-bit key is `K || K2` (AES-128 key, pad seed).
  It is a bijection, deterministic, prefix-preserving by construction (Theorem 1 of the paper),
  and invertible bit by bit with the key. The reference C++ implementation (Jinliang Fan,
  Crypto-PAn 1.0) ships a 100-address sample trace and its anonymised output under a fixed key;
  yacryptopan's test suite checks against exactly that trace and extends the construction to IPv6
  by running the same per-bit rule over 128 bits (IPv4 is placed in the top 32 bits of the
  128-bit block, which is why its IPv6 tests reproduce the IPv4 vectors).
- **ipcrypt-pfx** (IETF Internet-Draft `draft-denis-ipcrypt`, work in progress) standardises a
  prefix-preserving mode in native address size that handles IPv4 through the IPv4-mapped form;
  it is a draft (not citable as a standard, and its vectors could not be fetched here), so the
  design follows Crypto-PAn and records ipcrypt-pfx as the likely future standard (section 9).
- **tcpdpriv `-A50`** is table-based prefix preservation (not keyed, not reproducible across
  runs); Crypto-PAn replaced it for exactly that reason. Ylonen's note and Brekne et al. show both
  fall to injection.
- **Presidio** has no IP-specific operator (replace, redact, mask by character, hash, encrypt);
  **Tonic**'s IP generator emits random addresses with a v4/v6 ratio and optional consistency,
  without prefix preservation. Neither keeps network structure.
- **Truncation precedent for the defaults:** Google Analytics' IP anonymisation zeroes the last
  octet of IPv4 and the last 80 bits of IPv6, i.e. keeps /24 and /48 (sources are third-party
  documentation of that behaviour). The defaults below follow it; the difference is that this
  strategy pseudonymises the host bits instead of zeroing them, so distinct hosts stay distinct.
- **Codebase:** no IP masking exists. `transforms/_ff1.py` already uses `cryptography`'s AES; this
  slice uses the same package for AES-128 ECB block calls. Stdlib `ipaddress` parses and is strict
  (it rejects leading-zero octets, surrounding whitespace, trailing newlines, non-ASCII digits and
  CIDR suffixes; probe recorded below).

Feasibility probe (scratch, not committed; rerun by the plan reviewer): a 30-line Crypto-PAn over
`cryptography` reproduced all 100 reference-trace pairs, yacryptopan's four published IPv4 and
IPv6 examples, and, with the first 24 bits forced verbatim, the reference host octet for all 100
pairs (the composition P1 + P2 relies on). Throughput with one batched ECB call per address (all
prefix blocks in one `update`): about 260,000 IPv4 /24 values per second, 85,000 full IPv4, 29,000
IPv6 /48 and 18,000 full IPv6 on one core, before the per-column memo.

Design follows: Crypto-PAn (Xu et al. 2002) for the per-bit function, key layout, pad and inverse;
the yacryptopan IPv6 extension (same rule over 128 bits); keep-prefix as Crypto-PAn with the first
`N` per-bit flips forced to zero, which is the reference output's host bits under the input's
verbatim prefix. Custom code is the primitive (about 90 lines with the inverse; no maintained
Crypto-PAn package is in the lock, and yacryptopan needs PyCryptodome, a new dependency) plus the
parse, class dispatch, block swap, format and config handling around it.

## 3. Behaviour

Config (`provider_config` of a column with `strategy: ip_prefix`; a namespace is required):

| Key | Type | Default | Meaning |
|---|---|---|---|
| `keep_bits_v4` | int, 0 to 30 | 24 | IPv4 bits kept verbatim (at least 2 host bits stay keyed) |
| `keep_bits_v6` | int, 0 to 126 | 48 | IPv6 bits kept verbatim |

`0` is full Crypto-PAn (mode (b) of the slice brief: prefix-preserving with no verbatim prefix);
the owner chose to ship it now (section 10). Both modes are the same construction with a different
`N`, and the reference vectors test `N = 0` directly. The docs say plainly that `N = 0` does not
hide the network from the attacks in section 1. The upper caps keep at least two keyed host bits:
one host bit would make each output its input or its one sibling.

Per cell:

| Input | Output |
|---|---|
| null | null (no keyed draw) |
| IPv4 dotted quad (`ipaddress.IPv4Address`) | IPv4 dotted quad, Crypto-PAn over 32 bits with `keep_bits_v4` |
| IPv4-mapped IPv6 (`::ffff:a.b.c.d`, any spelling) | the string `"::ffff:"` + the IPv4 output for `a.b.c.d` (P4). Built as a string so the output does not depend on how `ipaddress` renders mapped addresses (its `str()` form for them changed in CPython 3.13; the engine supports 3.10 to 3.12 today, `pyproject.toml` `requires-python`) |
| other IPv6, any RFC 4291 text form, any case | Crypto-PAn over 128 bits with `keep_bits_v6`, then the block swap below; RFC 5952 canonical text (lower case, `::` compression) |
| other IPv4-embedding IPv6 (6to4, NAT64, Teredo, deprecated `::a.b.c.d`) | treated as plain IPv6 (section 9) |
| special addresses (private, loopback, link-local, multicast, ULA, documentation, unspecified, broadcast) | no special case. A range whose length is at most `N` (10/8, 192.168/16, 127/8, 169.254/16, 224/4, fe80::/10, fc00::/7, ff00::/8 with the defaults) stays in range by P1; a longer one (0.0.0.0, 255.255.255.255, `::`, `::1`, a /24's network and broadcast addresses) maps like any other address |
| malformed (see below) | left in the frame and recorded as a `format_error` `RowError`; never emitted unflagged (the full-frame and sequential routes fail the run or quarantine the row; the chunked oracle fails the run on the first row error, `_chunked_oracle.py:464-480`, since it has no quarantine) |

**Block swap (keeps P3 exact for IPv6).** Mapped addresses use the IPv4 rule, so the IPv6
Crypto-PAn `g` is applied only to IPv6 addresses outside `M`. `g` is a bijection on all 2^128
addresses that fixes the first `N6` bits, so one key-chosen /96 block `Q` (sharing `M`'s first
`N6` bits) maps into `M`, where mapped outputs live, and `M`'s own image block `P = g(M)` is left
unused. The handler computes `P`'s 96-bit prefix once per key; for an IPv6 input whose `g` output
has `M`'s prefix, it replaces that prefix with `P`'s. The result is a bijection of
IPv6-outside-`M` onto itself (`Q` now lands in the free block `P`), and the inverse undoes it (an
output in block `P` came from `Q`). When `Q = M` (always when `N6 >= 96`) nothing moves. Only
inputs in `Q` lose P2 against other IPv6 inputs; with the defaults `Q` is one key-chosen /96 among
the 2^48 /96 blocks of `::/48`, so a real dataset touches it with probability about 2^-48 per key
(2^-16 at `N6 = 80`). Without the swap those inputs would collide with mapped outputs (a P3 break,
raised by the plan review).

Malformed means any non-null cell that is not a `str`, or a string `ipaddress.ip_address` rejects,
or an IPv6 address with a zone (`%eth0`; the zone is an interface name and is refused rather than
kept or dropped), or a CIDR value (`10.0.0.0/8`; `ipaddress.ip_address` rejects it). No stripping
or normalisation happens before parsing: `" 10.0.0.1"`, `"10.0.0.1\n"` and `"010.0.0.1"` are
malformed. The row-error reason is fixed text naming the column and the strategy, never the value.

Special addresses: keeping them verbatim was rejected because a regular address could then map
onto a kept one (a collision, breaking P3); cycle-walking around the reserved set restores the
bijection but breaks P2 for pairs whose walk lengths differ. Refusing them was rejected because
real logs carry `127.0.0.1` and private addresses routinely, and with the defaults the common
ranges stay in range anyway.

`when:` is allowed: the strategy is row-local and writes strings into a string column, so the
gated subset is masked and the rest passes through as `when` documents for every strategy.

Failure modes. Codes are new unless marked existing; section 7 has the registry change.

| Failure | When | Behaviour |
|---|---|---|
| unknown key in `provider_config` (a typo such as `keep_bit_v4` would otherwise fall back to the default and keep more or fewer bits than intended) | plan compile | `PlanCompileError` `plan.ip_prefix_unknown_option`, path names the key |
| `keep_bits_*` not an `int`, or a `bool`, numeric string, float or negative | plan compile | `plan.ip_prefix_keep_bits_invalid` |
| `keep_bits_v4 > 30` or `keep_bits_v6 > 126` (fewer than two keyed host bits; at 32/128 the column would pass through unmasked) | plan compile | `plan.ip_prefix_keeps_too_many_bits` |
| two `ip_prefix` columns in one namespace with different resolved `keep_bits_v4` or `keep_bits_v6` (the catalog says `join_safe`; differing keep lengths give different outputs for one address, so the join would silently break) | plan compile | `plan.ip_prefix_namespace_keep_bits_mismatch`, modelled on `FPE_JOIN_GROUP_NAMESPACE_MISMATCH` (`plan/_checks_fpe_join.py:180`) |
| `ip_prefix` as a `nested` child (`provider_config.strategy: ip_prefix`) | plan compile | `plan.ip_prefix_unsupported_in_nested` (the nested JSON round trip and the flattened-leaf row-error index have the problem `top_code` refuses for; not worth the machinery here) |
| no namespace | run | `StrategyError` `runtime.ip_prefix_requires_namespace` |

| chunked FK gate | compile | not in `CHUNK_SAFE_STRATEGIES`: existing refusal for a non-chunk-safe strategy on an FK edge |

**One parser, two codes (no forwarding `code` parameter, no mode flag).**
`parse_ip_prefix_config(provider_config) -> IpPrefixConfig | IpPrefixConfigFault` returns either
the typed config or a frozen fault value `IpPrefixConfigFault(kind: FaultKind, option: str)`,
with `FaultKind` an enum (`UNKNOWN_OPTION`, `KEEP_BITS_INVALID`, `KEEPS_TOO_MANY_BITS`). Each
caller maps the fault to its own registry: the compile check through a module-level
`_PLAN_CODE: dict[FaultKind, str]` (a test asserts it covers every `FaultKind`), the handler and
`unmask` to `runtime.ip_prefix_config_invalid`. Both raise after the parse returns, so no
exception context is attached (recurring defect 3). The namespace-consistency and nested checks
are whole-config, compile-only checks in the same compile function.

All messages carry the column, table, option name and the allowed range only; the only config
values echoed are integer bit counts. No cell value appears in any message.

Uniqueness and collisions: P3 makes the mapping collision-free per address, across both classes.
Uniqueness is over addresses, not spellings: `2001:DB8::1` and `2001:db8:0:0:0:0:0:1` are one
address and produce one output, so the output's distinct-string count can be lower than the
input's. `1.2.3.4` and `::ffff:1.2.3.4` produce different strings with the same embedded IPv4
output (P4).

**Reversal.** `unmask_pipeline` reverses an `ip_prefix` column with the same key and reports
`reversed_unverified`, like `fpe`: Crypto-PAn is unauthenticated, so a wrong key yields plausible
wrong addresses with no signal. Inversion is the published bit-by-bit inverse (each recovered
input bit feeds the next prefix), with the swap undone first and mapped outputs inverted by the
IPv4 rule. Today's default branch (`unmask.py:387-394`, "does not retain the information needed to
invert") would be false for a keyed permutation, which is why the slice implements reversal
rather than a refusal; the inverse also serves as the test oracle for P3.

## 4. Design notes

- **Structure added.** One strategy (a new variant of the strategy registry, which keeps
  growing), one primitive module, one transform module. Open/closed: the strategy is added by
  registering a handler and one entry in each classification table; each table already has a
  totality guard against `SCALAR_HANDLERS`, so no shared `if/elif` changes. Deep module: the
  handler sees `IpPrefixConfig`, a `CryptoPan` object and one `mask_ip(value) -> str` call per
  distinct value; parsing, class dispatch, the mapped rule, the block swap and Crypto-PAn stay
  behind it. `unmask` sees one `unmask_ip(value)`.
- **One place per fact.**
  - Option names, types, defaults, ranges: `parse_ip_prefix_config` in
    `transforms/network/ip_prefix.py`, used by the compile check, the handler and `unmask`. The
    catalog's `wizard_options` reads names and defaults from the same module's constants.
  - Key label: `CRYPTOPAN_KEY_LABEL` in the primitive module.
- **Key label (cannot be a canonical source).** `hash` emits
  `derive(mask_key, namespace, canonical(value)).hex()`, so a label that some cell canonicalises to
  would let a `hash` column in the same namespace print the Crypto-PAn key. Every branch of
  `generation/pool/_canonicalize.py::_canonicalize_source` (the one canonicaliser `hash_array`
  uses, via `kernel.canonicalize_derive_source`) yields one of: one byte (`bool`); a 4-byte
  big-endian length whose first byte is `0x00` for any length under 2^24 bytes, then the body
  (`int`, via `_encode_int`); or valid UTF-8 (`str`, `Decimal`, `date`, `datetime`, and the
  `str()` fallback that `bytes` cells take). The label is
  `CRYPTOPAN_KEY_LABEL = b"\xffdecoy-cryptopan-key/v1"`: longer than one byte, first byte not
  `0x00`, and not valid UTF-8 (`0xFF` never occurs in UTF-8). The build also lists every other
  `derive(` call site in `src/` whose source is caller data and confirms each goes through that
  canonicaliser or a UTF-8 encode (the list goes in the build record), so "no canonical source
  equals the label" holds for every keyed strategy, not only `hash`. The same hole exists today for
  `FF1_KEY_LABEL` (`b"ff1-key/v1"` is valid UTF-8); that is out of scope here and is a follow-up
  the coordinator has raised with the owner (section 9).
- **Keying.** `derive(mask_key, namespace, CRYPTOPAN_KEY_LABEL)` gives 32 bytes, used exactly as the
  Crypto-PAn key: bytes 0 to 15 are the AES-128 key, bytes 16 to 31 are encrypted to form the pad.
  One key per namespace, like `hash`: columns in one namespace share the mapping (joins hold, given
  the keep-bits consistency check), different namespaces get unrelated mappings. No new secret
  parameter. The handler follows the FPE precedent: `key_box = OpaqueBox(derive(ctx.mask_key,
  namespace, CRYPTOPAN_KEY_LABEL))`, then `CryptoPan(key_box)`; the constructor builds the AES
  encryptor from `box.open()[0][:16]` and the pad inline, with no secret-named local.
- **Secret material and the census** (owner exception, section 11). Exactly one new census entry:

  | file | function | name | arrival | verdict |
  |---|---|---|---|---|
  | `decoy_engine/execution/_strategies/network/_ip_prefix.py` | `IpPrefixStrategyHandler.run` | `key_box` | `box:call:derive` | `boxed` |

  No other entry: the draw-site provider reuses the generic `SourceKeyedHmacProvider` (no new
  function takes `mask_key`; next bullet); `unmask` builds its `CryptoPan` inline inside
  `unmask_pipeline`, whose `mask_key` is already a census entry (`boxed`), so only that entry's
  line number moves; the primitive's constructor takes `box: OpaqueBox` (not bytes-annotated, not a
  secret-shaped name). The build runs `scripts/secret_material_census.py --write`, and if the
  derived list differs from this table it stops and reports instead of choosing a verdict.
  The pad (`AES_K(K2)`) is secret-derived material: it is held only as an `int` in a `__slots__`
  attribute of the `CryptoPan` instance, whose `__repr__` is fixed, so a traceback rendering
  frame locals shows the fixed repr, never the pad; it is never logged or returned. The census
  does not track `int` attributes, so this is recorded here as reasoning, not as a census verdict.
  The AES key itself lives inside the `cryptography` cipher context.
- **Determinism and draw-site provider.** Per-cell and source-keyed: the output is a pure function
  of `(mask_key, namespace, keep_bits, value)`, so chunking, row order and partitioning cannot
  change it. One new draw site `mask.ip_prefix` (family `source_keyed_hmac`, entropy root
  `mask_key`, identity `source_value`, partitionable, null rows draw nothing), appended at the end
  of `DRAW_SITES` as a standalone constant in `_draw_sites_mask.py` (the `MASK_FORMULA_DRAW_SITE`
  precedent; append-only, so the pinned digests gain one entry and the map digest changes). Its
  provider is one line in `_draw_site_providers.py`'s `_SOURCE_KEYED_PRIMITIVE`
  (`"mask.ip_prefix": "derive"`): the site's keyed draw is a single `derive` with a fixed source
  (the label), which `SourceKeyedHmacProvider` reproduces; the per-value Crypto-PAn arithmetic is
  the transform's, as FF1 is for `mask.fpe`. This satisfies the import-time totality check
  (`_draw_site_providers.py:269-277`) without a dedicated provider class like `FpeKeyProvider`,
  which would add two `mask_key` census entries. `SEED_PROTOCOL_VERSION` is unchanged.
- **Speed.** One `encryptor.update` per address over the `L - N` prefix blocks (ECB here is the raw
  block-cipher PRF Crypto-PAn specifies, one independent block per bit, not a confidentiality
  mode), plus a per-column memo bounded at 65,536 distinct values (`functools.lru_cache` on a
  closure created per handler run and discarded with it). Oracle routes only.
- **Routes.** The Python handler runs on every route that runs `SCALAR_HANDLERS`: full-frame
  oracle, `auto_chunk` / chunked oracle, sequential (S2, the default for FK jobs). Native chunked,
  unified slice, native sequential seam and out-of-core decline by construction. Every route that
  runs it runs the same handler, so parity is by construction and checked by test (section 8).
- **Compile wiring without growing `plan/_compile.py`.** `check_ip_prefix_config(config)` is
  called from inside `check_fpe_join_groups` (`plan/_checks_fpe_join.py`), which both compile
  branches and `run_config_only_checks` already call. That module is the namespace and join
  consistency check, which is what the keep-bits mismatch refusal is; it is the same move V1P-3.3
  made inside `check_fpe_charset_config`. Consequences: `_compile.py` is untouched (no pin raise,
  no comment folding; V1P-3.1 owns the comments at `_compile.py:537-553`), `checks_passed` and the
  serialised plan are unchanged for every config, and the ip_prefix checks report under the
  existing `fpe_join_groups` name (section 9). If the owner prefers a dedicated check name, that
  needs the pre-slice dedup of the three check-name lists (`_compile.py:306-350`, `:386-430`,
  `:590-615`) or one owner exception for V1P-3 (section 11).
- **Classification entries** (one each, all guarded): `TECHNIQUE_CLASS_BY_STRATEGY`
  `pseudonymisation`; distribution behaviour: the value that means "keeps cardinality exactly"
  (chosen against that module's definitions in the build); native capabilities `_Ortho` keyed,
  row-local, `row_error_modes=("format_error",)`, `quarantine_required` true;
  `ALWAYS_KEYED_STRATEGIES`; leak-check `SHAPE_PRESERVING` (the output shares a verbatim prefix
  with the input by design); `_column_access._SCALAR_STRATEGIES`; out-of-core `_DEFERRED_GROUP_B`
  entry with the existing row-error code; methodology registry entry for the primitive.
- **Post-validation and residual-PII classification.** `validation/post/_checks/_leakage.py`
  treats any source value reappearing in a substitution column as a leak; `ip_prefix` permutes
  within a prefix, so another row's real address can legitimately appear as an output and every
  post-validation run would fail. It joins `_VALUE_REUSE_STRATEGIES` (positional fixed-point
  check: a row that maps to itself warns). In `verification/postmask/residual_pii.py` it joins
  `_SUBSTITUTION_STRATEGIES` (positional identity at 50% or more fails, at 5% or more warns: the
  expected self-map rate is 2^-(L-N), at most 25% under the caps, so a fail means the mask did not
  fire and a warning flags a small host space) and `_PRODUCES_PII_LIKE_VALUES` (an `ipv4` detector
  hit on the output is expected). It does not join `_REUSES_SOURCE_VALUES` (that set's "only full
  positional identity fails" rule fits strategies that re-emit the source multiset; this one does
  not), so the comment there that says it mirrors `_VALUE_REUSE_STRATEGIES` gains "except
  `ip_prefix`, a keyed substitution".
- **Catalog and published listings.** `namespace_required=True`; `join_safe=True` (injective and
  deterministic per address, and the namespace check keeps keep-bits consistent); `wizard_options`
  = the two keys; `offer_in_wizard=False`. A proof card is added to `scripts/gen_proof_manifest.py`
  (no waiver) and `docs/proof-manifest.json` and `docs/capability-matrix.md` are regenerated:
  both are published listings, so the strategy becomes publicly listed on merge, which is why the
  owner holds the merge until CLI-REL.
- **House style.** Typed `IpPrefixConfig` and `IpPrefixConfigFault` (frozen dataclasses) instead
  of dict reads; no flag arguments (the class is dispatched on the parsed address; compile and run
  map faults themselves); comments say why.

YAML example:

```yaml
tables:
  - name: access_log
    columns:
      - name: client_ip
        strategy: ip_prefix
        namespace: client_ip
        provider_config:
          keep_bits_v4: 24   # default; keep the /24
          keep_bits_v6: 48   # default; keep the /48 site prefix
  - name: sessions
    columns:
      - name: ip
        strategy: ip_prefix
        namespace: client_ip  # same namespace and keep bits: same mapping, so the columns join
```

## 9. Known limits

- Output is canonical text, not the input's spelling (an exploded IPv6 input comes back
  compressed; upper-case hex comes back lower case).
- P2 does not hold across classes (IPv4 or mapped against other IPv6) or for a pair with exactly
  one address in the key-chosen /96 block `Q` that the swap moves (with `N6` up to 96, a given /96
  of real data is `Q` with probability about 2^-(96-N6) per key).
- CIDR values, zone IDs and integer-encoded addresses are malformed, not masked. A column of
  firewall rules with `/len` suffixes needs a later option (Crypto-PAn maps a prefix to a prefix,
  so it is possible).
- IPv4 embedded in 6to4, NAT64, Teredo and IPv4-compatible IPv6 is pseudonymised as IPv6 bits (no
  leak below `N`, but not consistent with the IPv4 mapping, unlike the mapped form).
- Special single addresses lose their meaning (section 3).
- The ip_prefix compile checks report under the existing `fpe_join_groups` check name, so a
  `checks_passed` reader cannot tell them apart; a dedicated name needs the owner decision in
  section 11.
- Python per-bit AES: tens of thousands of IPv6 values per second per core before the memo. A
  native kernel is out of scope.
- `ipcrypt-pfx` (IETF draft) may become the standard prefix-preserving IP encryption; if it does, a
  later mode can follow it with its own vectors. Crypto-PAn is not the same mapping.
- The attacks in section 1 are not mitigated. The remedies in the literature (for example
  re-keying per dataset, or Brekne et al.'s proposals) trade away P3's cross-run stability; a
  per-run key is already available by choosing a fresh namespace or secret.
- Follow-up (not this slice): `FF1_KEY_LABEL` is valid UTF-8, so a `hash` column in the same
  namespace holding `"ff1-key/v1"` prints the FF1 key; the coordinator has raised it with the
  owner.
