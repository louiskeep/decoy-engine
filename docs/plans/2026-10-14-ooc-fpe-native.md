# fpe native on the out-of-core route

Rules consulted: dev-rules `00-universal.md`, `risk-and-exceptions.md`, `development-loop.md`, `autonomous-operation.md`, `architecture.md`; engine `CLAUDE.md` (established-methodology, module size, explain-why comments). Grounding: the 2026-10-14 bottleneck audit (OOC fpe measured ~1519s/10M = the per-cell Python loop) + a 2026-10-14 FRAME confirming this is straightforward kernel-wiring that mirrors the already-shipped OOC categorical / bucket_perturb native slices. Base: engine `origin/main` @ `4038b7c0`.

## 0. Why + scope
fpe is ADMITTED on the out-of-core (OOC) route today (`_GROUP_B_SUPPORTED_STRATEGIES`, `out_of_core/_compat.py:34`) but masks per-cell in Python: `out_of_core/_mask_group_b.py:117-196` `fpe_array` runs `for value in _array_to_pylist(values): fpe_encrypt_value(...)`. That loop is the ~1519s/10M bottleneck for any 5M+ FK job with an fpe payload column. The compiled FF1 kernel already exists and is byte-parity-proven on the SEQ and chunked routes (`native/_fpe_ext.py` `_CompiledFpeKernel.run` / `BoundFpeKernel` / `native_fpe`). This slice swaps the OOC fpe backend from the per-cell Python loop to that compiled kernel, inside the already-admitted path. NO new Rust, no ABI change, no `_compat.py` admission change.

**In scope:** fpe PAYLOAD columns on the OOC route take the compiled kernel when eligible; the existing Python `fpe_array` stays as both the reference and the declined-fallback path. This mirrors the OOC categorical slice (`out_of_core/_categorical_native.py` + the `_mask.py:149-159` native-else-Python dispatch).
**Out of scope / DECLINE to the existing Python `fpe_array` (byte-identical):** a truthy `checksum` config (the kernel has no checksum path), a missing `namespace`, an `FpeConfig` that fails `_resolve()` (duplicate/degenerate charset), and a non-exact-`string` source (incl. `large_string`). These are exactly the SEQ/chunked `_fpe_admit` gates (`_sequential_native_ops.py:213`). fpe stays PAYLOAD-only on OOC: it is already off the FK parent-key / REMAP surface (`_compat.py:447` `_INITIAL_SUPPORTED_STRATEGIES` only), so there is no key-path wiring.

## 1. Risk
R2 (privacy-relevant masking; FF1 reversibility/joinability). Output must be byte-identical to the oracle. It is the SAME compiled kernel SEQ/chunked already prove byte-identical, called per OOC batch; FF1 is deterministic per value with no cross-batch state, and the tweak/key/charset are built by the same `build_ff1_tweak`/`derive` the current OOC Python path uses, so the tweak is byte-identical too. Acceptance compares OOC-native to the full-frame oracle on the strict parity contract + a native witness, and asserts the declines + fail-closed parity.

## 2. The code change (mirror the OOC categorical slice exactly)
- **NEW `out_of_core/_fpe_native.py`** (~150 LOC; template `out_of_core/_categorical_native.py`):
  - `decline_reason(seed, cfg) -> str | None`: the `_fpe_admit` logic (checksum / namespace / `FpeConfig.from_mapping(cfg)._resolve()` error) + `source_is_string` (exact `pa.string()`), returning the existing coded reasons.
  - `FpeColumnDecision` / `TableFpePlan` with a per-batch `gate()` doing the pinned-type / drift abort copied from `_categorical_native.py:138-170` (the DuckDB-sourced batch type must match the pinned `string`; drift aborts, as hash/categorical already do).
  - `native_fpe_array(values, *, native, mask_key, namespace, column) -> pa.Array`: calls the compiled kernel via `native.kernel.run(values, mask_key=..., namespace=..., tweak_column=..., config=<prepared FpeConfig>, forward=True, native_threads=native.native_threads)` (the correct API is `BoundFpeKernel.kernel.run(...)` matching `_sequential_native_ops.py:241`; `BoundFpeKernel` is defined in `_sequential_native_ops.py:190`, NOT `_fpe_ext.py`, and has no top-level `run()` — Codex LOW). Retain the resolved `FpeConfig` on the column decision (resolve once in `prepare_table`, not per batch). Raise `fpe_fail_closed_error(result.errors, column)` (`native/_fpe_route.py:44`) when `result.errors` is non-empty (same first-failure `StrategyError` code the oracle raises). **Null/empty handling (Codex MED):** do NOT copy categorical's untyped `pa.nulls(n)` short-circuit — fpe always emits `pa.string()` and validates tweak/key BEFORE the value loop (`_mask_group_b.py:140,153`). Either keep that pre-loop validation and return `pa.nulls(n, type=pa.string())` for an all-null/empty batch, or let the kernel handle the empty/all-null array directly; pin the output type to `string` unconditionally.
- **`out_of_core/_hash_run.py`**: a lazy `_fpe_kernel()` loader (parallel to `_index_kernel()`, using `load_compiled_fpe_kernel` + `BoundFpeKernel`); an `fpe_seeds` block in `prepare_table` (parallel to the categorical block `:223-239`); carry `TableFpePlan` on `TableHashPlan` with `fpe_for(column, batch)` (parallel to `categorical_for`, `:117`); an `FPE_DISPOSITION_KEY` in `metrics()` (`:262`).
- **`out_of_core/_mask.py`**: add an `fpe_native` param to `mask_column` and dispatch to `native_fpe_array` at the fpe branch (`:143-146`) when present, else the existing `fpe_array`; compute `fpe_native = hash_plan.fpe_for(...)` in `mask_batch` (parallel to the categorical_native dispatch `:370-374`). `masked_output_type` / `group_b_output_type` need NO change (fpe emits `string` either way).
- **No change** to `_compat.py` (fpe already admitted), `_mask_group_b.py` (`fpe_array` stays as reference + declined path), or the drivers (`_runner.py`, `_stream_driver.py` already thread `hash_plan` into `mask_batch`, so fpe rides the existing object).

## 3. Acceptance matrix (the spec)
Mirror the OOC categorical slice's suite (`tests/parity/test_phase_d_d1b2_categorical_native*.py` + `_disposition`/`_pinning`/`_witness`) plus the group-B parity/routing suites (`tests/parity/test_out_of_core_group_b_parity.py`, `test_out_of_core_group_b_routing.py`). Each cell compares OOC-native vs the full-frame oracle (and vs the OOC Python path with the kernel hidden) on the strict parity contract.
- **O1 native fpe payload byte-parity + output-type pin**: an fpe payload column on an OOC FK job is byte-identical to the oracle, across row counts / batch boundaries, incl. nulls, empty, all-null, and "" passthrough; the output column is `pa.string()` in every case. **Witness must be consumed-output evidence, not disposition alone (Codex MED):** use a marking kernel (or output-insertion check) that proves the native RESULT is actually written into the output, PLUS a negative control that discards the native result and fails — mirror `tests/parity/test_phase_d_d1b2_categorical_witness.py:53,86`. Exclude the kernel loader's self-test from execution evidence.
- **O2 declines (route to the Python `fpe_array`, byte-identical, coded reason)**: (a) `checksum` set → `fpe_checksum_not_native`; (b) `namespace` missing → `fpe_requires_namespace_stays_python`; (c) degenerate/duplicate charset → the `FpeConfigError`-derived reason; (d) non-string / `large_string` source. Assert the disposition reports the Python backend + the reason.
- **O3 fail-closed parity**: an unencryptable value raises the SAME `StrategyError` code as the oracle (`fpe_fail_closed_error`), at per-batch granularity (unchanged from the current per-batch Python path).
- **O4 type-pin / drift abort**: a DuckDB batch whose fpe column type drifts from the pinned `string` aborts (same as hash/categorical), not silently mis-masks.
- **O5 routing**: `run_pipeline` dispatches a large fpe-payload FK job to OOC and the output is byte-identical to full-frame (extend `test_out_of_core_group_b_routing.py`); native witness present under companion, Python path under ci-mirror.
- **O6 mixed job**: fpe native beside hash + categorical native on one OOC job; each reports its own disposition, no cross-contamination; fpe stays payload-only (no fpe on the OOC native key surface — unchanged).
- **O7 coverage completeness (Codex plan-gate asks)**: exercise BOTH OOC drivers (`_runner.py` reorder + `_stream_driver.py`) so fpe rides each `hash_plan`; a missing fpe column + a type-drift batch both abort (O4 is drift; add missing-column); a mid-run genuine kernel FAULT aborts fail-closed with NO Python fallback (distinct from a per-value unencryptable row-error); companion-unavailable runs the Python `fpe_array` byte-identical (ci-mirror); first-error ordering is oracle-identical when one batch holds MULTIPLE different failure codes; and the existing fpe config variants (join_group, separators, Luhn/charset options) stay byte-identical native vs oracle.

## 4. Failure modes (reproduce, do not smooth)
- A checksum / non-string fpe column silently going native → O2 (must decline to the Python path).
- Batch-boundary divergence (the kernel per batch vs the oracle whole-column) → O1 across batch sizes; FF1 is per-value so it must match, pin it.
- Fail-closed granularity or code change vs the oracle → O3.
- DuckDB batch type drift silently mis-masking → O4.
