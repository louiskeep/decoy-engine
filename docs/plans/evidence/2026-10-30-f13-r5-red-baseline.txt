== HIGH: `_types._parse_vault` mutants 73 and 75 (class: validation strictness at a parse boundary) ==

Decision. The field of a `vault:` reference was percent-decoded twice: once by `parse_qsl(...,
errors="strict")` and again by `unquote(fld, errors="strict")`. Mutants 73/75 made the second decode
lenient; they survived because no test pinned the field for any input where the two decodes differ.
Of the two closures the handoff allows, "make the second decode strict as well" is already the shipped
code (that IS what 73/75 mutate), so pinning it would freeze the double decode (`%25ff` rejected, `%2525`
read as `%`, `%2541` read as `A`: a KV key holding a literal `%` could not be named). The fix removes the
second decode: each component (mount, path, field) is decoded exactly once, strictly. Blast radius: only
refs whose field contains `%25` followed by two hex digits change meaning (they now mean the literal
`%xx`); every other accepted ref parses to the same SecretRef as before.

Fixed at the class, not the instance (two more accept-by-default holes on the same boundary, both
behavior changes, both noted here and pinned in the same table):
  - a `%` not followed by two hex digits (`%`, `%zz`, `%4`) passed through `unquote` unchanged in the
    mount, path and field; RFC 3986 2.1 says `%` only ever starts an escape, and the module docstring
    claims RFC 3986 strictness, so it is now `bad_secret_ref`;
  - a control character in the decoded field (`%00`, `%0a`) was accepted while the mount and path
    segments already rejected one; the field now follows the same rule.
Not changed (pinned as-is so the contract is explicit): the query is form-decoded as `parse_qsl`
defines it (`a+b` is `a b`, `%2B` is `+`); the mount and path are not (`+` literal). Local refs
(`env:`, `file:`) are not URIs and are untouched (a file path may contain a bare `%`).

== MEDIUM: the r3 assertions deleted in r4 (class 8: removed assertions) ==

Both deleted tests are restored in tests/secret_providers/test_r3_contract.py under their original
names, with the r3 scenario verbatim (the same `_MutatingProvider` with flips at describe /
resolve-before / resolve-after; the same `StubClient` whose shared token is re-authenticated mid-read).
The one adaptation the r4 API forces: r3 closed the class by DETECTION (snapshot the client context,
verify after the read, fail the load), so the r3 assertions were `SecretProviderUnavailable` and
`len(default_cache()) == 0`. r4 closed it STRUCTURALLY (one immutable ResolveContext per load keys the
cache and is handed to `resolve`), so the mutation cannot reach the read: the load succeeds for the
keyed tenant. The restored assertions are therefore: the read used the keyed context (tenant A /
tok-a) whatever the client says after the flip; the cache holds exactly that tenant's entry and
nothing under the other tenant's key (a B read misses, a later A read hits and still holds A's secret);
a cache miss after `clear()` re-reads with the keyed context, never with the re-authenticated token.
Nothing was weakened: every r3 assertion that is still true under r4 is kept, and the two that r4 made
false by design (fail + empty cache) are replaced by the stronger r4 outcome (correct value + correct
key), stated in the test.
