## 1. Why + what
The out-of-core (DuckDB + Arrow) route admits the `hash` strategy but computes it in pure Python (`kernel/_scalar.hash_array`, a per-value `derive(...).hex()` loop) inside the OOC mask seam. The native-chunked route already masks `hash` through the compiled companion kernel (`execution/native/_kernels_keyed.native_keyed_hash` -> `_crypto_ext.load_compiled_crypto_kernel().derive_batch`), graded byte-for-byte against the same pure-Python reference via KAT vectors. D1a routes the OOC seam's `hash` COMPUTE through that SAME existing companion kernel for the columns whose Arrow type the compiled kernel admits, so admitted OOC hash masking runs on Rust/Arrow instead of a Python loop. No new Rust, no ABI change.

D1a is the FIRST slice that makes OOC masking native, so it carries the native-OOC mechanism risk (companion load + ABI gate, whole-column single path / never half-native, per-column backend decision pinned up front, the program's no-silent-fallback contract, parity + the native-execution witness). It is deliberately scoped to `hash` ALONE, the simplest operator (stateless per value, a direct `derive_batch` replacement), so the mechanism is proven on the simplest case before categorical (per-run prepared state) and bucket_perturb (pandas parse + Rust offset) follow. Codex affirmed this hash-only-first slicing, the `derive_batch` reuse, and preserving the no-companion capability.

## 2. Scope
**In:**
- In the OOC mask seam (`execution/out_of_core/_mask.py`, the `hash` branch in `mask_column` and the `mask_batch` per-column loop), route the `hash` compute through the companion crypto kernel (`native_keyed_hash` / `load_compiled_crypto_kernel().derive_batch`) for a column WHEN BOTH hold: (a) the companion loads and is ABI-compatible, and (b) the column's Arrow type is in the compiled kernel's admitted set (`execution/native/_requirements.is_admitted_native_hash_type`). The whole column takes ONE path (native OR Python), never half-native within a column.
- **Per-column backend decision, pinned once at run/table-prep (finding #3):** the native-vs-Python decision for each hash column is computed a SINGLE time before any batch streams, from the companion load result (computed once per run) and the column's up-front Arrow type (the OOC output schema is already resolved from the plan via `masked_output_type` before data is seen). The decision is immutable for the run; there is NO mid-stream backend switch, and a companion that loads at prep but faults mid-run ABORTS the run (fail-closed) rather than silently switching a half-streamed column to Python. This mirrors the native-chunked preflight's once-per-table `_downgrade_to_oracle(decision, reason)` decision (`native/_dispatch.py`).
- **Native eligibility is NOT OOC admission (finding #1):** OOC already ADMITS hash for every type (Python `hash_array` canonicalizes any value). The compiled kernel admits only `utf8/large_utf8/bool/int8..int64/uint8..uint64` plus a tz-AWARE timestamp (`_ADMITTED_NATIVE_HASH_TYPES` + the tz-aware branch, mirrored from `canonicalize.rs::is_admitted_type`). So a hash column of a non-admitted type (float, decimal, tz-naive timestamp, null-typed/all-null) keeps the Python path with a recorded reason (below); only admitted-type columns go native. D1a changes the COMPUTE path for the admitted subset, not what OOC admits.
- **No silent fallback; declined-with-a-caller-visible-reason (finding #4, program §5):** program §5 requires every cell to be exactly {native-admitted + parity + compute-witness} OR {declined with a caller-visible reason}; nothing silently falls back. When D1a does NOT take the native path for a hash column (companion absent/ABI-incompatible, or type not admitted), the Python `hash_array` path STILL RUNS (no capability regression, which Codex affirmed) but the per-column backend is RECORDED as the Python path WITH a structured reason, surfaced through the backend-evidence channel the native route already uses (`execution/native/_chunked_evidence`: `planned_backend` vs `executed_backend`, vocabulary `RUST_COMPANION` / `PANDAS_ORACLE`). Reason codes mirror `_dispatch`'s existing strings: `crypto_extension_unavailable` (companion absent/ABI-incompatible) and `hash_input_type_not_native_admitted:{column}:{arrow_type}` (type not admitted). Log-hygiene: reasons carry strategy, column name and Arrow type only, never cell/key/expression values.
- **Parity + witness (graded against the D0 harness):** add OOC hash cases asserting native output strict-equal to the pandas oracle (`tests/parity/_strict_compare.py`, modulo the frozen D0 known gaps) AND equal to the Python-reference hash, with the D0 `_kernel_witness` proving the native kernel produced the hash column's output (executed_backend = native-result-consumed) when the decision is native, and Python-path-only when declined.
- **Witness attribution hardening (dennis D0 L1, finding #5):** the D0 witness already keys provenance per returned object (`_provenance[id(result)]`), but attributes a column by concatenated-INPUT equality (`_combine`/`_tokens`/`_matched`), which cannot disambiguate when one column is masked by MULTIPLE native calls (one per streamed batch) or when two columns carry equal values. D1a hardens column attribution to per-call identity/context so a multi-batch native column and an equal-valued sibling are told apart, and adds a control that fails under the old concat-equality logic. The four D0 provenance controls stay intact.

**Out:** categorical + bucket_perturb native-OOC (separate follow-up slices, mechanism now proven); SEQ route (D2); any change to the companion crate / ABI / the native-chunked route; any change to the OOC admission allowlist or routing; any change to the Python `hash_array` kernel itself; the full 100M/200M growth proofs (D4c); FK-key hashing semantics (the parent-key allowlist already includes hash; D1a changes the COMPUTE path, not what is admitted).

## 5. Behavior-preservation contract
1. **Byte-identical output:** OOC hash output is identical whether computed native or Python, for every admitted hash cell (KAT-pinned reference equality; asserted on the OOC path).
2. **Oracle parity:** OOC native hash output is strict-equal (D0 `_strict_compare`, modulo the frozen D0 known gaps) to the pandas oracle, on an FK-chain hash column and a non-FK hash column.
3. **Per-batch == whole-column:** streamed per-batch native hash equals the single-pass hash (per-value determinism, the invariant the Python `mask_batch` already relies on).
4. **Never half-native:** a column is masked entirely by one path; the decision is pinned at run/table-prep and a mid-run companion fault aborts rather than switching path.
5. **No silent fallback (program §5):** every hash column is exactly {native + parity + executed_backend=native-consumed} OR {Python path + executed_backend=pandas WITH a caller-visible reason code}. The declined path still masks the column (no capability regression) but is never silent.
6. **Witness:** when native, the witness proves the native kernel produced the hash column's output (executed_backend native-result-consumed, per-call-identity attribution); when declined, Python-path-only. No existing test weakened; `hash_array` untouched.

- **Boundary cases (finding #6):** empty batch / empty column; a column with nulls interleaved (null rows preserved, non-null rows hashed); truncate present vs absent; an admitted column whose batches stream in >1 RecordBatch (multi-call attribution).
- **Never-half-native:** a targeted test that a column cannot mix native + Python within a run (construct via the companion-availability seam + a simulated mid-run fault asserting ABORT, not switch).
- **Witness attribution hardening (finding #5):** the four D0 provenance controls still pass; a NEW control proves correct attribution across MULTIPLE native calls on one column AND across two columns carrying EQUAL values (the multi-call / equal-value case the old concat-equality logic could silently misattribute); and the existing D0 legacy-path-only control is RE-RUN under forced companion-unavailability on the OOC path (resolves rev 1's D0-legacy-only contradiction: the witness is exercised on both paths, not asserted legacy-only in principle).

D1a asserts the native path is not a time or peak-memory regression against the Python baseline on a representative admitted column; it does NOT run the 100M/200M proofs (D4c).
- **Must pass unchanged:** the full D0 parity suite + `tests/parity/test_out_of_core_fk_parity.py` (normalized harness) + the OOC route's existing tests + module-size/import-boundary sentries. No existing test weakened; `hash_array` itself untouched.
