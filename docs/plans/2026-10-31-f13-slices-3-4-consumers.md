## 2. Established solutions (cited, from knowledge; not re-fetched this session)

- Vault Agent (HashiCorp): the agent authenticates (auto-auth), caches nothing for the app, and renders secrets to a file through a `template` stanza or a token to a file sink; the application reads a local file and never holds Vault credentials. Applied here: for the CLI the sanctioned external-store path is a `file:` reference fed by Vault Agent, Kubernetes Secret volume or systemd `LoadCredential` (`$CREDENTIALS_DIRECTORY`), with zero new Decoy code. The engine's native `vault://` adapter stays opt-in and is not wired into the CLI in this plan (secret-providers.md: the caller authenticates first).
- Docker/Compose and Kubernetes secrets guidance: prefer a mounted file (`/run/secrets/NAME`) over an environment variable, because env is inherited by child processes and visible in `/proc/<pid>/environ` to the same user and in crash dumps. Applied: `file:` is documented first, `env:` second (CI), no implicit default.
- The Twelve-Factor "config in the environment" convention: the ref names an env var, the value is not in the config file. Applied: `env:NAME` stays; the config never holds a secret.
- Key hierarchy by HKDF with a distinct `info` per purpose (RFC 5869 section 3.2, NIST SP 800-108 domain separation): the platform already does this (`api/keys/derive.py:28-35`, `:68-86`); the new secret is one more labeled child of the master. Cited in the new function's docstring (project rule: cite the source pattern).
- Rotation by versioned reference (Vault KV v2 `version=`): already the engine design (`secret-providers.md` "Rotation"); this plan adds only the honest consumer-side statement (section 7).
- OpenSSH refuses a private key file that is group- or world-accessible ('UNPROTECTED PRIVATE KEY FILE'); GnuPG warns about unsafe permissions on its home directory and keys. Adopted for `file:` secrets by owner decision, implemented in the engine file provider on the opened descriptor (slice E1, section 3.6). The same check done as a path `stat` before an open is the classic check-then-use race, which is why it is placed where the file is opened.

### 3.4 Consumer secret-error boundary (value-free by construction)

Class: value-bearing cause chain at a consumer boundary (catalog class 1). The engine already projects provider failures to registered codes with constant text and no chained cause (`secret_providers/_errors.py:101-168`, `_call_closed` in `_preflight.py`); this plan gives each consumer the same structure for the code that sits outside the engine.

- Platform registry: a new platform-local module `api/keys/mask_secret_errors.py`, following the existing precedent of a typed error plus a code frozenset (`SEED_ERROR_CODES`, `api/seeds/secrets.py:58`; the platform has no single code registry, verified by grep). It holds `MASK_SECRET_ERROR_CODES` and a fixed-message table: `master_key_invalid`, `master_key_unavailable`, `kms_unavailable`, `mask_key_derivation_failed`, `mask_secret_ref_not_allowed`. These are NOT registered in the engine registry (owner decision). Messages are constants; none formats a length, path, provider name or env value.
- Source fix (one structure for every caller): `api/keys/master.py` and `api/keys/kms.py` raise `MasterKeyError(code)` (a `ValueError` subclass, so existing `except ValueError` handlers keep working) with the fixed message for the code, constructed and raised OUTSIDE any `except` block (record the code inside the handler, raise after it, as the engine does). `KmsError`/`KmsUnavailableError` keep their types but lose their formatted messages. `_decode_env_key` (`master.py:101-114`) is in scope too: its second `base64.b64decode(raw)` runs inside an `except` (so a failure chains to the first one) and its frame locals hold the raw env text, so the decode is restructured to record a failure flag inside the handler and raise `MasterKeyError('master_key_invalid')` after it. Startup (`api/main.py:1389`), job start (`derive_mask_job_seed_int`), the token-vault key (`api/crypto/vault_key.py:96`) and the new helper all inherit it, so no per-caller wrapper can be forgotten.
- Helper residual: `instance_key_provider()` additionally catches anything else raised while deriving (an HKDF failure, a missing `cryptography` import) and re-raises `MaskSecretConfigError("mask_key_derivation_failed")` after the handler, with `__cause__` and `__context__` both `None` (a `raise ... from None` inside the handler is NOT enough: `__context__` is kept and only `__suppress_context__` is set, so it is not used).

- CLI boundary: one function `mask_secret_error_text(exc)` in the new shared helper maps a `MaskSecretError` to a CLI-owned constant for the four codes the old pins can produce (`missing_mask_secret`, `weak_mask_secret`, `bad_secret_ref`, `keyed_strategy_requires_secret`), and passes the engine's already-constant text through for the F13 codes after 4b. ### 3.6 `file:` secret permissions (slice E1, engine, R2)

Decision (owner): refuse a `file:` secret unless the file is owner-only, implemented where the file is opened. Verified gap: the engine file provider does not check today (`_local.py:65-73`).

- Mechanism: in `FileSecretProvider._read`, open with `os.open(locator, os.O_RDONLY)`, then `os.fstat(fd)` on that descriptor, refuse when `st.st_mode & 0o077` is non-zero, then read from the same descriptor and close it in a `finally`. No `O_NOFOLLOW`: the Kubernetes secret volume layout is a symlink chain, and `fstat` on the descriptor reports the final target's mode, which is the file whose bytes are read. Skipped when `os.name == "nt"` (NTFS ACLs are not inspected; documented). Pipes and other non-regular files are not special-cased: their mode comes from the same descriptor.
- Registered code: a new engine reason `secret_file_permissions_unsafe` in `reasons/runtime/_secret_provider.py` (phase `RESOLVE`, outcome `CONFIGURATION`, retry `CONFIGURATION_REPAIR`, same shape as `SECRET_MATERIAL_INVALID` at `:62-68`), a new error class in `secret_providers/_errors.py` added to the `_CLOSED` table (`:101-111`) so the admission boundary rebuilds it from the code alone, constant text with no path, mode or uid. Catalog docs (`docs/reasons.md`, `docs/security/secret-providers.md`) gain the code; additive to `decoy-reasons/v1`.
- No bypass setting, no environment override: a knob that turns the check off is an unsafe configuration default (`config-secrets-and-supply-chain.md`).
- Consequence stated plainly: existing test fixtures that write a `file:` secret with the default umask (engine `tests/unit/test_de02_keyprovider.py`, `tests/secret_providers/test_r4_mutation_kills.py`, `test_refs_and_descriptor.py`, `tests/property/test_keyprovider_invariants.py`, `tests/integration/_f29_jobs.py`; CLI tests with `file:` refs, about 24 grep hits) must create the file 0600. That is a fixture correction, not a weakened assertion. CLI behavior is unchanged until 4b pins an engine that has E1 (4a documents permissions as the operator's responsibility; the recipe in 3.2 already uses `umask 077`).

## 4. Guarantee (invariants as properties)

- **P1 (no seed key).** No engine entry called from `api/` or `src/decoy/` runs with a key derived from `job_seed`. Every keyed run, vault write, vault read and unmask in both consumers uses a provider whose `mask_key()` is at least 32 bytes.
- **P2 (one key per job/command).** Within one platform job, every table, route, chunk and the vault writer use the same provider object. Within one CLI command, the run and the vault use one admitted key.
- **P3 (no tenant-chosen source).** A platform job config can never cause the server to read an env var, file or provider named by the job author.
- **P4 (value-free).** No secret, derived secret, derived mask key, reference text or secret-bearing path appears in any consumer output surface (section 6.5), for success and every failure code.
- **P5 (fail closed with a registered code).** Every secret failure surfaces as an engine-registered code (`reasons.runtime`, `reasons/runtime/_part2.py:358` and `_part3.py:255` and the seven F13 codes) or one of the platform codes in 3.4 (or the E1 code, 3.6), never a 500 or an unclassified exception.
- **P6 (rotation is explicit).** A key change never silently re-keys or invalidates a vault: the failure is `vault_key_mismatch` and the docs say so (section 7).
- **P7 (no unprovided entry).** No engine entry is reachable from `api/` or `src/decoy/` without an explicit provider argument: the wrapper signatures require it and the sentry rejects a call that omits it.
- **P8 (owner-only file secrets).** A `file:` secret readable by group or other is refused at the descriptor that is read, with a registered value-free code, on POSIX.

## 7. Rotation, stated honestly

- A key change is: a different master key (platform), a different secret behind the same ref, a different ref, or a different `key_version`. Effect: every keyed output (hash, fpe, date_shift, shuffle, tokenize, deterministic, composite-FK) gets a new identity, so joins against earlier output break. That is the engine's stated re-key semantics (`secret-providers.md`: "change it to rotate output identity intentionally").
- Existing vaults are not re-encrypted, not migrated, not invalidated and not detected. A vault opens only under the exact key that wrote it; any other key fails `vault_key_mismatch` (Fernet authentication). The vault header carries no key identifier (`vault.py:284-290`: `format, seed_protocol_version, ambiguous_dropped, chunk_rows, chunk_count`), so Decoy cannot say which key a vault wants. No command re-keys a vault; adding a key-id field is a `decoy-vault/v2` change and is not proposed here (Q6, default applied).
- Platform: replacing or restoring the master key (`key_restore.py`) makes every existing job vault unreadable; `POST /unmask` returns 422 `vault_key_mismatch`. The platform records the master-key fingerprint at acknowledgement time (`models.py:2207`, `get_master_key_fingerprint`), not per job vault (not verified further), so it cannot tell an operator which fingerprint a given vault needs. Operators must keep the old master key as long as old vaults must be unmaskable. The upgrade-determinism gate (`api/golden`, `tests/test_golden_determinism_gate.py`) is expected to report CHANGED for every keyed pipeline after 3b; that is the correct signal and must be documented, not suppressed.
- CLI: keep the old ref (`file:` path, env value, or Vault `version=N`) for as long as old vaults matter. For Vault KV the old version stays readable until destroyed; "incident invalidation" (destroy the version) deliberately makes the vault unmaskable.
- Seed-keyed vaults from older engines: no migration and no recovery path (owner ruling 2026-10-31, applied; slice 0 plan Q1 closed the same way). After the pin bump the new engine refuses them with `weak_mask_secret` (slice 0).
- The platform and CLI docs gain this section verbatim in substance (4a docs, 3a docs). Rollback consequences are in section 8a.

## 11. Self-attack (mechanism, counter-case, covered?)

- Required keyword parameter (class 4). Counter: a caller passes `key_provider=None` explicitly. Covered: the wrappers reject `None` (`isinstance` against `KeyProvider`) and T8b has a `None` cell; mutation: remove the check, the cell fails.
- AST sentry. Counter: the call is wrapped (`functools.partial`, a helper forwarding `**kw`), or dispatched with `getattr`. Covered: fail-closed on anything unresolvable, `getattr` on `decoy_engine` rejected, seeded evasions in T8a. Residual: a dynamic import by string; a V2 note.
- Once per attempt (class 3). Counter: iteration children and sequential re-admission attempts each resolve their own. Covered by T7(a): same master gives the same bytes, a changed master fails closed. The plan does not claim cross-attempt immutability.
- Ephemeral preview key. Counter: someone "fixes" preview determinism by deriving from the master. Covered: T20 spy and the key-directory check; the code comment cites the spec section that forbids it (`preview_parent.py:844-849`). Counter: the key travels through `request.json`. Covered by T20.
- Source-level fixed-code master errors. Counter: another path in `api/keys/` raises a formatted message later. Covered by the T19 AST rule over both files. Counter: the base64 decode chains the raw env text through a handler. Covered: `_decode_env_key` restructured (3.4) and T6 renders locals. Counter: `KmsError` raised from a third-party exception keeps `__cause__`: the KMS client wrapper records only `type(exc).__name__` into the code decision and raises after the handler (existing line `kms.py:154` already does `from None` inside the handler; T6 asserts both `__cause__` and `__context__` are `None`, which that pattern does not satisfy, so the line changes).
- E1 descriptor check. Counter: the path is swapped to a symlink between `os.open` and `fstat`. Covered: both act on the same descriptor, which is already bound; race test. Counter: the file is a FIFO. Accepted, mode comes from the descriptor; reading a FIFO blocks as it does today (unchanged). Counter: root reading another user's 0600 file. Not refused (mode only, owner decision); documented. Counter: a filesystem that reports 0777 for everything (some network and mounted volumes) refuses a valid deployment. Accepted and stated in the docs; the operator copies the secret to a local tmpfs/volume with 0400. Counter: ACL-only systems. Mode bits include the ACL mask for group; the check is conservative there. Counter: Windows. Skipped by design, documented.
- `mask_secret_ref` rejection (class 6). Counter: the key arrives nested, upper-cased or in a YAML anchor. Covered: T10 walks the parsed `global_settings` after YAML parse and after `model_dump`; engine `extra="forbid"` rejects other spellings. Counter: a new ingress appears. Covered by the generated T3 walk.
- CLI helper dedup (class 9). Counter: `decoy.mask()` is documented as a port of `run.py` (`api.py:116`) and a future edit changes one copy. Covered: one helper imported by all callers and a sentry that no other module defines `_is_valid_mask_secret_ref` or writes `["mask_secret_ref"] =`.
- CLI error projection. Counter: a new handler prints `str(exc)` for a `MaskSecretError`. Covered by the handler sentry (3.4). Counter: on 4b the engine text and the CLI text diverge. Covered: pass-through for F13 codes, CLI constants only for the four legacy codes, snapshot in T13.
- Continuity claim (T17). Counter: an engine health fix between 0.16.0 and R-a changes keyed bytes. Covered by T17 as a stop, not by assertion in this plan; I did not diff the engines (section 15).
- Docs-only dev recipe (3.2). Counter: a user substitutes a weak value for `openssl rand -hex 32`. Not closable by code (length only is certified); documented.
