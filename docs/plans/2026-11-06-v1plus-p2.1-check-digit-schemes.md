## 1. FRAME

**Problem.** `decoy_engine.checksums` knows seven check-digit schemes, all US or global (luhn, npi,
iban, vin, isbn13, ean13, gtin). The V1+ international detectors (V1P-2.2) and generators
(V1P-2.3) need to validate and compute check digits for the main non-US national identifiers.

**Definition of done.**

1. `checksums.validate(scheme, value)` and `checksums.calc_check_digit(scheme, body)` accept nine
   new schemes: `gb_nhs` (UK NHS number), `ca_sin` (Canadian SIN), `in_aadhaar` (Indian Aadhaar),
   `au_tfn` (Australian TFN), `de_idnr` (German Steuer-IdNr), `fr_nir` (French NIR),
   `es_dni` (Spanish DNI), `es_nie` (Spanish NIE), `it_codice_fiscale` (Italian codice fiscale,
   personal 16-character form).
2. Each new scheme passes the published examples from its python-stdnum module, and a property
   test: for valid bodies, `validate(body + calc_check_digit(body))` is true, and single-character
   changes to a valid value are caught where the scheme promises it.
3. **Dark:** no existing behavior changes. FPE checksum mode keeps exactly its current seven-scheme
   set; the new schemes are refused there with the existing `plan.fpe_checksum_unknown_scheme`
   code. The built-in validator names (`luhn`, `npi`, `iban`, `vin`) are unchanged.
4. A guard test fails when a scheme is registered without test vectors or with only one of its two
   functions.

**Boundaries (non-goals).**

- No detectors, providers, strategies or disguises (V1P-2.2, V1P-2.3, V2).
- No FPE support for the new schemes. Several of them have bodies with no valid check digit (NHS,
  TFN) or letter check characters; FPE support needs its own design in V1P-2.3.
- No identifiers without a check digit (UK NINO, Indian PAN): they are format rules, which belong
  to detectors.
- No new reason codes; no registry version change; no new dependency.

**Risk: R2.** Additive public-API change (`decoy_engine.checksums` is public) and a change to the
FPE admission set, which is privacy logic. Rollback: revert the commit; nothing is persisted.

**Reuse check.** `python-stdnum` (LGPL-2.1, already a core dependency, `>=2.2`; this module already
uses it for luhn, iban, isbn, ean) provides validation for all nine and check-digit calculation for
`fr_nir`, `es_dni`, `es_nie`, `it_codice_fiscale`, plus the underlying algorithms (`luhn`,
`verhoeff`, `iso7064.mod_11_10`) for `ca_sin`, `in_aadhaar`, `de_idnr`. Only `gb_nhs` and `au_tfn`
need a hand-written check-digit calculation (stdnum validates but does not compute them).

## 2. Established solutions

Search run (2026-11-06): python-stdnum 2.2 module docs and source for each identifier (installed in
the engine lock); Microsoft Presidio predefined recognizers (pattern lists per country); NHS Digital
data dictionary for the NHS number modulus 11 algorithm; ATO TFN algorithm as implemented in
stdnum `au.tfn`.

Findings: python-stdnum is the established open-source reference for national identifier checks and
is what this module already follows. Presidio's recognizers use the same algorithms (and some
delegate to stdnum-style checks). There is no reason to hand-write what stdnum provides.

Design follows: stdnum for validation everywhere; stdnum's `calc_check_digit(s)` where it exists;
stdnum's generic algorithms (`luhn`, `verhoeff`, `iso7064.mod_11_10`) for SIN, Aadhaar and IdNr;
hand-written calculation only for NHS (modulus 11, weights 10 to 2; remainder giving 10 has no valid
check digit) and TFN (weights 1, 4, 3, 7, 5, 8, 6, 9, 10; sum modulo 11 is 0), each checked against
stdnum's validator in tests.

## 3. Behavior

| Scheme | Body passed to `calc_check_digit` | Returns | Validation source |
|---|---|---|---|
| `gb_nhs` | 9 digits | 1 digit; `ValueError` when the body has no valid check digit | `stdnum.gb.nhs` |
| `ca_sin` | 8 digits | 1 digit (Luhn) | `stdnum.ca.sin` |
| `in_aadhaar` | 11 digits | 1 digit (Verhoeff) | `stdnum.in_.aadhaar` |
| `au_tfn` | 8 digits | 1 digit; `ValueError` when the body has no valid check digit | `stdnum.au.tfn` (9-digit form) |
| `de_idnr` | 10 digits | 1 digit (ISO 7064 mod 11,10) | `stdnum.de.idnr` |
| `fr_nir` | 13 characters (Corsican `2A`/`2B` allowed) | 2 digits | `stdnum.fr.nir` |
| `es_dni` | 8 digits | 1 letter | `stdnum.es.dni` |
| `es_nie` | `X`, `Y` or `Z` plus 7 digits | 1 letter | `stdnum.es.nie` |
| `it_codice_fiscale` | 15 characters | 1 letter | `stdnum.it.codicefiscale`, 16-character personal form only |

Contract notes (stated in the module docstring):

- `validate` follows stdnum's normalisation: separators and spaces are accepted, as stdnum's
  `is_valid` accepts them. Existing schemes are unchanged.
- `calc_check_digit` expects a compact body (no separators). A malformed body raises `ValueError`.
- A computed check digit does not guarantee `validate` passes when the scheme also has non-checksum
  format rules (Aadhaar's leading digit and palindrome rule, IdNr's digit-repetition rule, SIN's
  leading digit). This is the same contract `npi` already has (leading 1 or 2).

Failure modes:

| Failure | Behavior |
|---|---|
| Unknown scheme | `ValueError` naming the known schemes (unchanged) |
| Malformed body (wrong length, letters where digits are required) | `ValueError`; never a stdnum exception leaking out |
| NHS or TFN body with no valid check digit | `ValueError` saying the body has no valid check digit |
| New scheme used in FPE `checksum:` | refused at plan compile, `plan.fpe_checksum_unknown_scheme`, message lists the FPE schemes |
| New scheme reaching the FPE runtime directly | refused by the runtime's own check (`transforms/_fpe_checksum.py`), same set |

Error messages carry the scheme name and the expected body shape, never the value.

## 4. Design notes

- **Structure.** No new module. The two dispatch tables in `checksums.py` stay the one place
  schemes are registered. The new entries are table-driven (a small helper wraps a stdnum module's
  `is_valid`, and one wraps stdnum's `ValidationError` into `ValueError`), so each scheme is one
  validator line and one calculator line, not a pair of hand-written functions.
- **One place per fact.** A new private frozenset `_FPE_CHECKSUM_SCHEMES` in `checksums.py` names the
  schemes FPE checksum mode admits (the current seven). `plan/_checks.py` and
  `transforms/_fpe_checksum.py` read it instead of `_KNOWN_SCHEMES`, so "known" and "FPE-eligible"
  stop being the same fact. Adding a scheme no longer silently admits it to FPE.
- **Principles applied** (`architecture.md`): open for extension through the registry rather than
  branching at call sites; parallel tables (`_VALIDATORS`, `_CHECK_DIGIT_FUNCS`,
  `_SCHEME_REQUIRED_CHARSET`, `_FPE_CHECKSUM_SCHEMES`) are tied together by guard tests, not by
  hand.

## 5. Choke points

| Rule | Choke point | Guard test | Mutation that must turn it red |
|---|---|---|---|
| Every scheme has both functions and test vectors | `_VALIDATORS` and `_CHECK_DIGIT_FUNCS` in `checksums.py` | new `test_every_scheme_has_vectors_and_both_functions`, parametrized over `checksums._KNOWN_SCHEMES` (walks the real registry) | register a scheme in `_VALIDATORS` and `_CHECK_DIGIT_FUNCS` with no vector entry |
| FPE admits only FPE-eligible schemes | `_FPE_CHECKSUM_SCHEMES`, read by `plan/_checks.py::check_fpe_checksum_scheme` and `_fpe_checksum.py` | new test: every non-FPE scheme is refused at plan compile with `fpe_checksum_unknown_scheme`; every FPE scheme other than `iban` has a `_SCHEME_REQUIRED_CHARSET` entry | change the plan check back to `_KNOWN_SCHEMES` |

## 7. Acceptance tests (written first)

1. Per new scheme: stdnum's documented valid examples validate; its documented invalid examples do
   not; `calc_check_digit` on the example body returns the example's check characters (the
   `it_codice_fiscale` and `fr_nir` examples include calculation examples directly).
2. Property test per new scheme (seeded, a few hundred bodies): `validate(body + calc(body))` is
   true for bodies that satisfy the scheme's format rules; changing any one character of a valid
   value makes `validate` false for the schemes whose algorithm detects all single-character errors
   (Luhn, Verhoeff, mod 11, mod 97, mod 23 letter, codice fiscale letter).
3. Cross-check: the hand-written NHS and TFN calculators agree with stdnum's validators over every
   body in the property test, and return `ValueError` exactly when no digit validates.
4. Malformed bodies raise `ValueError` (not a stdnum exception) for every new scheme.
5. Guard tests in section 5.
6. Dark guarantee: plan compile of an FPE column with each new scheme fails with
   `plan.fpe_checksum_unknown_scheme`; all existing FPE and checksum tests stay green unchanged.

Verification: `scripts/dev/gates.sh` T1 (ruff, format, mypy, sentries, impact-selected tests).

## 8. Known limits

- `it_codice_fiscale` covers the personal 16-character form; the 11-digit company form is a Luhn
  variant stdnum also validates, out of scope until a detector needs it.
- `au_tfn` covers the 9-digit form; legacy 8-digit TFNs are out of scope.
- `fr_nir` follows stdnum's Corsica handling (`2A`, `2B`); stdnum version changes could change
  edge cases, which is why the vectors pin today's behavior.
