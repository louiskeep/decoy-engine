## 1. Findings that change or qualify the plan's premises

The plan listed the r3.1 bundle, the reserved signing fields, `verify.py`, `api/passport/` and `api/keys/` as "asserted, verify before build". All five exist in the sibling repos. Three of them differ from what the plan assumed.

**G-1. A signed passport already exists, and it is Ed25519, not ES256/JWS.** `decoy-platform/api/passport/{core,signing,router}.py` plus `api/crypto/signed_envelope.py` implement `output-passport/v1`: an Ed25519 instance key persisted as a PEM file under `DECOY_KEY_DIR`, signing `json.dumps(sort_keys=True, ensure_ascii=False, separators=(",", ":"))` bytes, with a base64 signature and an embedded PEM that the verifier must pin. `router.py` documents that `POST /api/passport/sign` signs whatever fields an admin supplies, so it is an operator attestation and not a run-bound emission. `signed_envelope.py` itself records "not yet RFC 8785 JCS". The CLI ports the verify side at `decoy/src/decoy/distribution/signing.py` for `decoy upgrade`.
Consequence: F33 is a second, stronger signature system, not the first one. The plan's profile (ES256 detached JWS over JCS, `typ`/`cty`, `crit`, `VerificationContext`) shares nothing on the wire with it, and the two must not be confusable. The distinct `typ` and `cty` values already guarantee that for the verifier. **Open decision for S4/S7 (not blocking S1/S2):** whether `output-passport/v1` is kept as a labeled operator attestation, superseded, or re-expressed as an F33 statement. Until decided, F33 does not touch it and does not reuse its key.

**G-2. There is no JCS anywhere in the legacy stack, and the canonicalizer is copied five times.** All of these are Python `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` variants with slightly different guards:
- `decoy-platform/api/evidence/hashing.py:53` (`canonical_json`, rejects non-finite floats, the locked R3.1 rule),
- `decoy-platform/api/jobs/routes_evidence.py:80` (a verbatim copy inside `_VERIFY_PY_TEMPLATE`, line 45),
- `decoy/src/decoy/cli/evidence.py:103` (`compute_manifest_hash`, another copy),
- `decoy-platform/api/crypto/signed_envelope.py:43` (`canonical_bytes`, no non-finite guard),
- engine `src/decoy_engine/generation/_pinned_plan.py:167` (`_canonical`, ASCII-escaping, no `ensure_ascii=False`).
The legacy docstring calls itself a "subset of RFC 8785"; Python number formatting differs from JCS (verified: `100.0` is `100.0` vs `100`, `-0.0` vs `0`, `1e-07` vs `1e-7`, `1e-06` vs `0.000001`, `1.2345678901234568e+20` vs `123456789012345680000`, and ints above 2^53 pass in Python but are outside the JCS domain). The plan's decision to preserve these under their own version and start a new JCS profile is confirmed necessary. The legacy hash functions must stay byte-for-byte unchanged (A10).

**G-3. `api/keys/kms.py` is wrap/unwrap only.** The merged KMS envelope exposes `KmsClient.encrypt` / `.decrypt` (`kms.py:37-39`) behind `EnvelopeMasterKeyProvider` (`kms.py:124`) for the master key. There is no `sign`, no public-key lookup, no key-version resolution. This is exactly the case the plan's S4 gate names ("a merged encryption envelope alone does not pass the asymmetric-signing gate"). S4 must add a narrow signing capability inside that abstraction. Engine S2 therefore defines the seam only (a `Signer` protocol) and ships a local test/CLI signer; it does not bridge to `api/keys/`.

## 5. Dependency spike (joserfc + rfc8785): result GO, no return to the plan gate

Run on Python 3.12/3.13 with `joserfc 1.7.7` (BSD-3-Clause), `rfc8785 0.1.4` (Apache-2.0, Trail of Bits) and `cryptography` (already a base dependency).

| Plan requirement | Result |
|---|---|
| Detached flattened JWS | `joserfc.jws.sign_flattened_json` emits `{payload, protected, signature}`; `jws.detach_content` removes `payload` (RFC 7515 Appendix F). Round-trips. |
| External-signer / KMS seam | Supported extension point: a `JWSAlgModel` subclass whose `sign(msg, key)` delegates to a signer that only ever sees the signing input and returns P1363 bytes. `JWSRegistry.register` writes a **class-level** dict, so it MUST be used on a private `JWSRegistry` subclass with its own `algorithms`/`recommended`, never on the shared registry (that would replace `ES256` process-wide). |
| Verify over transmitted protected bytes | `verify_signature` builds `protected_segment + "." + payload_segment` from the received segment verbatim; it does not re-serialize. |
| Strict P1363 | `ESAlgorithm.verify` returns false when `len(sig) != 2*32`, so DER, truncated and over-long signatures are rejected by the library. |
| Algorithm restriction | `JWSRegistry(algorithms=["ES256"])`, `get_alg` rejects anything else (`none`, HS256, ES384, ...). |
| JCS | `rfc8785.dumps` gives RFC 8785 bytes and raises `FloatDomainError` (NaN/Inf) and `IntegerDomainError` (>2^53) rather than rounding. |
| Gaps the profile layer must close itself | (a) joserfc decodes the protected header with `json.loads`, which keeps the last of a duplicated member: Decoy parses the transmitted header bytes strictly (duplicate rejection) before handing them over. (b) `max_header_length` 512 bytes and `max_signature_length` 1024 by default: sizes are set explicitly. (c) It does not enforce `typ`/`cty`/`crit` policy or key pinning: the Decoy-profile verifier does. |

Packaging note for S3: both libraries are pure Python wheels (`py3-none-any`); only `cryptography` needs per-platform wheels, as the plan already assumed.

## 6. S1 package decision (the plan required this to be fixed in S1)

The shared verifier core lives in one self-contained subpackage, `src/decoy_engine/signed_evidence/`, whose modules import only the standard library, `joserfc`, `rfc8785`, `cryptography` and each other (relative imports). It never imports `decoy_engine` siblings, pandas, polars or pyarrow. A test loads it with the `decoy_engine` package `__init__` bypassed and asserts the heavy libraries stay unimported, so the CLI's offline artifact can ship that directory unmodified instead of a copy. Engine-facing glue (check ledger, staging coordinator wiring) lives outside it.
