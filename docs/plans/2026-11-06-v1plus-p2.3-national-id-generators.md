## 1. FRAME

**Problem.** Masked or generated values for non-US national identifiers must pass the receiving
system's validation. The engine has checksum-valid generators only for US and global identifiers
(`synthetic_ssn`, `synthetic_npi`, `synthetic_iban` and others in `providers_v2/identifiers/`).

**Definition of done.**

1. Nine `decoy_native` providers, one per V1P-2.1 scheme: `synthetic_gb_nhs`, `synthetic_ca_sin`,
   `synthetic_in_aadhaar`, `synthetic_au_tfn`, `synthetic_de_idnr`, `synthetic_fr_nir`,
   `synthetic_es_dni`, `synthetic_es_nie`, `synthetic_it_codice_fiscale`.
2. Every generated value passes `checksums.validate(scheme, value)`, including the non-checksum
   format rules (Aadhaar leading digit and palindrome rule, IdNr repetition rule, SIN leading digit,
   codice fiscale pattern and real birth date).
3. Deterministic mode follows the existing identifier pattern: `derive_value(seed, namespace,
   canonical_source, domain=...)`, same output for the same inputs across processes; random mode
   uses a NumPy generator like the others.
4. Generation never fails for lack of a valid value: bodies are valid by construction (no
   rejection loop that can exhaust).
5. Dark: no default configuration, disguise or starter config names these providers; V1 runs are
   unchanged. The providers do appear in registry listings (section 9).

**Non-goals.** FPE for the national schemes (a later slice); detectors (V1P-2.2); realistic
issuer-specific ranges beyond the published formats; locale-aware names (V1P-2.4); a codice fiscale
that encodes a generated person's real name and birth place (the body is format-valid, not
derived from a person).

**Risk: R2.** New public provider names and capability rows (compatibility surface, read by the CLI
cockpit and the platform's capability registry), and privacy-relevant output.

**Reuse check.** `providers_v2/identifiers/_ssn.py`, `_npi.py`, `_iban.py` (Domain, Adapter,
Validator, `generate_random` pattern); `determinism.derive_value`; `generation.pool._canonicalize`;
`checksums` (V1P-2.1) for check digits and validation; existing provider reason codes
(`unknown_provider`, `unsupported_locale`, `missing_seed`, `missing_namespace`,
`invalid_input_length`, `batch_deterministic_unsupported`). No new reason codes.

## 2. Established solutions

Search to run at PLAN review (and record here): Faker's `ssn` providers per locale (`en_GB`,
`fr_FR`, `es_ES`, `it_IT`, `de_DE`, `en_CA`, `en_IN`, `en_AU`) and how they build checksum-valid
values; Mimesis `Person.identifier` style providers; python-stdnum's own `calc_check_digit`
functions (already wrapped by V1P-2.1). Expected finding: Faker builds random bodies and appends a
computed check digit, which is the same construction; we keep our own deterministic Domain because
Faker's generators are not keyed (the reason the existing identifier providers exist).

## 3. Design notes

- **One adapter, a table of specs**, not nine copies of the SSN module. Each spec is data:
  provider name, scheme, supported locale, and a `body_from_bytes(b) -> str` builder that produces
  a format-valid body from derived bytes. One `NationalIdDomain` and one `NationalIdAdapter`
  serve all nine. Principle (`architecture.md`): a new identifier registers a spec; nothing
  branches on the provider name.
- **Valid by construction.**
  - NHS and TFN bodies whose check digit does not exist (about 1 in 11) are repaired
    deterministically: step the last body digit until a check digit exists. NHS weight 2 and TFN
    weight 9 are both units modulo 11, so at most 10 steps always reach one. No rejection loop.
  - Aadhaar: first digit drawn from 2 to 9; a palindrome is impossible once the computed check
    digit differs from the first digit, and the builder flips one interior digit if it would not.
  - IdNr: 10 digits where exactly one digit appears twice (sample 9 distinct digits, repeat one,
    order by derived bytes), first digit not 0.
  - SIN: first digit drawn from 1 to 7 and 9.
  - NIR: sex 1 or 2, year 00 to 99, month 01 to 12, department 01 to 95 or 2A or 2B, then 6
    digits.
  - Codice fiscale: 6 letters, a 2-digit year, a month letter, a day 01 to 28 (plus 40 for the
    female form), a place code (letter plus 3 digits), then the check letter; dates are always
    real.
- **Where facts live.** Formats and their sources live in the spec table docstrings; check digits
  and validation live only in `checksums` (V1P-2.1). Capability rows are built from the spec table,
  so the registry and the specs cannot disagree.
- **Uniqueness.** Same as the existing identifiers: deterministic mode is a keyed function of the
  source value, so distinct sources collide only as often as the body space allows. Body spaces
  are 10^8 or more except DNI/NIE (10^8, 3 x 10^7); the capability row states
  `supports_uniqueness` the same way the existing providers do, and the plan review checks it.

## 6. Acceptance tests (written first)

1. Per provider, 2,000 deterministic values from distinct sources and 2,000 random values all pass
   `checksums.validate(scheme, value)`.
2. Determinism: the same seed, namespace and source give the same value in-process and in a
   subprocess; a different namespace gives a different value.
3. Repair path: NHS and TFN builders hit the repair branch in the property test (assert it ran) and
   still validate.
4. Registry guard and capability rows (section 4); the CLI cockpit test (which compares its output
   with the registry) still passes unchanged.
5. Errors: wrong locale, missing seed or namespace, and wrong byte length raise the existing codes.
6. Dark guarantee: no disguise, starter template or default config references the new names (test
   walks the disguise YAMLs and templates).

## 7. Failure modes

| Failure | Behavior |
|---|---|
| Unsupported locale | `provider.unsupported_locale` naming the provider and locale, not the value |
| Deterministic call without seed or namespace | existing `missing_seed` or `missing_namespace` |
| Deterministic batch | existing `batch_deterministic_unsupported` |
| A builder bug producing an invalid value | caught by the property tests; at run time the adapter does not re-validate (same as the existing identifiers) |

## 8. Known limits

- Bodies are format-valid, not realistic: NIR departments and codice fiscale place codes are not
  checked against real registries.
- DNI and NIE body spaces are smaller than the others; very large deterministic columns will see
  more collisions, as with any keyed mapping into a small space.

## 9. Owner decision before build

New provider names are additive and opt-in, but they are visible: the CLI's `decoy cockpit` lists
`registry.known_providers()`, so once an engine release carrying this slice is pinned into the CLI,
CLI V1 lists nine more providers. Options:

1. Accept: additive names in listings count as dark (no run changes).
2. Hold the merge (not the build) until after CLI-REL, keeping the branch rebased.

Recommendation: option 2 unless V1 docs and tests already treat the provider list as open-ended;
it keeps the V1 surface frozen at launch at no cost to the head start.
