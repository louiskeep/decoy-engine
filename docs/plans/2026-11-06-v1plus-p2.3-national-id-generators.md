## 1. FRAME

**Problem.** Masked values for non-US national identifiers must pass the receiving
system's validation. No config can produce such values today: Faker has no NHS, TFN or IdNr
generator and produces invalid SIN and Aadhaar values (section 2), and the engine's own identifier
providers (`synthetic_ssn` and the rest) are library-only (below).

**Execution path.** `strategy: faker` with `provider: <name>` always builds a pool
(`FakerStrategyHandler` to `PoolBuilder`), and `plan/_checks.py::check_non_poolable_provider_with_pool_backend`
refuses any provider declaring `poolable=False`. Every existing `decoy_native` identifier declares
`poolable=False`, so none is reachable from a config; they are called only through the library.
The new providers declare `poolable=True` and implement a **seeded** `generate_batch`, so the pool
builder can build a reproducible pool of valid values and a `strategy: faker` column samples it
deterministically per source value, exactly as `person_name` does. `classify_provider` already
classes every `decoy_native` backend as `pool_native`, so the native route agrees. No new strategy,
no new reason code. Under `execution/` only catalogue data rows change (section 5). The native
and out-of-core routes do **not** admit these providers (their allowlists name only
`person_first_name` and `person_last_name`); such a column falls back to the Python path with a
coded route-decline reason, as any other non-allowlisted pooled provider does.

**Definition of done.**

1. Nine `decoy_native` providers: `synthetic_gb_nhs`, `synthetic_ca_sin`, `synthetic_in_aadhaar`,
   `synthetic_au_tfn`, `synthetic_de_idnr`, `synthetic_fr_nir`, `synthetic_es_dni`,
   `synthetic_es_nie`, `synthetic_it_codice_fiscale`, each with the capability row in section 4.
2. A config column `strategy: faker`, `provider: synthetic_<x>` compiles and runs, and every output
   value passes `checksums.validate(scheme, value)` and the provider's `format_regex`.
3. Pools are reproducible: the same job seed, provider, locale and config build the same pool in
   a new process. The library `generate(..., deterministic=True)` path is kept (keyed by
   `derive_value`, like the existing identifiers).
4. Generation never fails for lack of a valid value: bodies are valid by construction.
5. Dark: no default configuration, disguise or starter template names these providers. They do
   appear in registry listings, which is why the merge is held (section 9).

**Non-goals.** FPE for the national schemes; detectors (V1P-2.2); realistic issuer ranges beyond the
published formats; locale-aware names (V1P-2.4); codice fiscale derived from a person's real name
and birthplace; making the existing US identifier providers reachable from config (recorded as a
finding for the roadmap, section 10); `generate:` mode (its `faker` columns resolve through the
legacy reflection pool, not the registry), so these providers are masking-only.

**Risk: R2.** New public provider names and capability rows, read by the CLI cockpit, the
capability matrix, the proof manifest and the platform's capability registry; privacy-relevant
output.

**Reuse check.** `providers_v2/identifiers/_ssn.py`, `_npi.py` (Domain, Adapter, Validator,
`generate_random` pattern); `determinism.derive_value`; `generation.pool._canonicalize`;
`generation/pool/_builder.py` (pool build with `seed=pool_seed`); V1P-2.1 `checksums` for check
digits and validation; existing provider reason codes.

## 2. Established solutions

Search run 2026-11-06 (engine venv, Faker 40.23.0; 2,000 values per generator, checked with V1P-2.1
`checksums.validate`):

| Scheme | Faker generator | Result |
|---|---|---|
| fr_nir | `fr_FR.ssn` | 2,000 of 2,000 valid |
| es_dni | `es_ES.nif` | 2,000 of 2,000 valid |
| es_nie | `es_ES.nie` | 2,000 of 2,000 valid |
| it_codice_fiscale | `it_IT.ssn` | 2,000 of 2,000 valid |
| ca_sin | `en_CA.ssn` | 1,548 of 2,000 valid (emits SINs starting with 8) |
| in_aadhaar | `en_IN.aadhaar_id` | 184 of 2,000 valid (Luhn instead of Verhoeff; ignores the leading-digit rule) |
| gb_nhs | none (`en_GB.ssn` is a NINO) | — |
| au_tfn | none | — |
| de_idnr | none (`de_DE.ssn` is US-shaped) | — |

Test ranges: the NHS reserves numbers starting 999 for testing; they pass the check but are never
issued (cited by Ruby Faker's NHS generator, which moved to this range so it never emits a real
patient's number, and by cardinal_pythonlib and the `nhs-number` crate, which link NHS Digital's
"Synthetic data in live environments" guidance). The NHS generator draws only from 999. No
equivalent reserved range was found for the other eight schemes; their outputs can collide with
real numbers, as Faker's do, and section 8 says so.

Design follows: Faker's construction (random body plus computed check digit) where Faker is right;
python-stdnum and the national specifications (as cited in `checksums.py`) for the rules Faker gets
wrong or lacks. We keep our own adapters because Faker's generators are not keyed and two of the
six that exist produce invalid values.

## 3. Design notes

- **One adapter, a table of specs.** Each spec is data: provider name, scheme, locales, compact
  output format and regex, and a `body_from_bytes(b) -> str` builder. One `NationalIdDomain`, one
  `NationalIdAdapter` and one validator serve all nine. A new identifier registers a spec; nothing
  branches on the provider name (`architecture.md`).
- **Two entry points, one builder.** `generate(..., deterministic=True)` derives 32 bytes with
  `derive_value` and calls the builder. `generate_batch(spec)` requires `spec.seed` (the pool seed)
  and draws 32 bytes per value from `numpy.random.default_rng(seed)`, then calls the same builder,
  so the pool is reproducible. Without a seed `generate_batch` uses an unseeded generator, as the
  Faker adapter does.
- **Valid by construction** (each docstring states why):
  - NHS: `999` plus 6 body digits; if no check digit exists, step the last body digit. Its weight
    (2) is a unit modulo 11, so the ten digits give ten distinct remainders and at most one is bad:
    at most one step.
  - TFN: 8 body digits; same repair on the last body digit (weight 9, a unit modulo 11).
  - Aadhaar: first digit 2 to 9. If the result would be a palindrome, flip one interior digit;
    Verhoeff detects every single-digit change, so the new check digit cannot recreate the
    palindrome.
  - IdNr: 9 distinct digits plus one repeat, ordered by the derived bytes; a leading 0 is fixed by
    rotating the digit order one place to the first non-zero digit (deterministic).
  - SIN: first digit drawn from 1 to 7 and 9.
  - NIR: sex 1 or 2, year 00 to 99, month 01 to 12, department 01 to 95 except 20, or 2A or 2B,
    then 6 digits.
  - Codice fiscale: 6 letters, 2-digit year, month letter, day 01 to 28 (plus 40 for the female
    form), place code (letter plus 3 digits), check letter; dates are always real.
- **Output format.** Compact, upper case (`9991234560`, not `999 123 4560`), matching each
  `format_regex`. `checksums.validate` accepts both forms; compact avoids separator mismatches with
  the source column.
- **Locales.** Each spec lists the locales it serves (`gb_nhs`: `en_GB`; `ca_sin`: `en_CA`,
  `fr_CA`; `in_aadhaar`: `en_IN`, `hi_IN`; `au_tfn`: `en_AU`; `de_idnr`: `de_DE`; `fr_nir`:
  `fr_FR`; `es_dni` and `es_nie`: `es_ES`; `it_codice_fiscale`: `it_IT`). A `None` locale means the
  spec's first locale, not `en_US`; any other locale raises `provider.unsupported_locale`.
- **Where facts live.** Formats live in the spec table; check digits and validation only in
  `checksums`; capability rows are built from the spec table, so registry and specs cannot drift.

## 4. Capability rows (pinned)

All nine rows share these values; per-spec values are the locales above and the format regex.

| Field | Value | Why |
|---|---|---|
| `backend_type` | `decoy_native` | engine-owned adapter |
| `backend_version` | `national_id/v1` | bumped if any builder changes its output |
| `supports_deterministic` | True | `derive_value` path; pool sampling is deterministic per source |
| `supports_uniqueness` | False | pool sampling maps distinct sources onto a finite pool, so values repeat; DNI (10^8 bodies) and NIE (3 x 10^7) also have small spaces |

| `poolable` | True | the config path (section 1) |
| `supports_coherent_link` | False | |

## 7. Acceptance tests (written first)

1. Per provider, 2,000 values from the deterministic path and 2,000 from a seeded batch all pass
   `checksums.validate(scheme, v)` and `re.fullmatch(format_regex, v)`.
2. Determinism: same seed, namespace and source give the same value in-process and in a
   subprocess; a seeded batch is identical across two calls and across processes; over 200 sources,
   a different namespace changes at least 95 percent of values.
3. Repair paths: the NHS and TFN repair branches and the Aadhaar and IdNr fix-ups run in the
   property test (asserted by counting), and all outputs still validate.
4. End to end: a `strategy: faker` column with each provider compiles (no
   `non_poolable_provider_with_pool_backend`) and runs; outputs validate; rerunning with the same
   seed gives the same output.
5. Locales: `None` uses the spec's first locale; an unsupported locale raises
   `provider.unsupported_locale` naming provider and locale, not a value.
6. Guards in section 5, including the draw-site inventory with `NationalIdAdapter`.
7. Dark: no disguise YAML, starter template or default config references the new names (test walks
   the files).

## 8. Known limits

- Except NHS (999 test range), outputs can coincide with real issued numbers, as Faker's do.
- Bodies are format-valid, not realistic: NIR departments and codice fiscale place codes are not
  checked against real registries.
- Pooled sampling repeats values; not for key columns (section 4).
