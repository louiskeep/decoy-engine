## Problem

B2 made the auto-chunk route mask on B1's chunked dispatcher, and B7 sends each independent table of a multi-table job through the same lane. Both still materialize every routed table's whole output before returning it:

- `_pipeline_auto_chunk._run_dispatcher` drains B1's iterator into a list (`list(_chunked_entry.run_mask_chunked(...))`, `src/decoy_engine/execution/_pipeline_auto_chunk.py:254-268`) and `join_dispatcher_chunks` concatenates and combines it (`:119-120`), a second full copy of the output.
- The chunk-result list `chunk_results` (`_pipeline_auto_chunk.py:303`) also pins every output chunk: B1 appends one `ExecutionResult` per chunk whose `outputs` holds that chunk's masked table, on the native route (`native/_chunked_entry.py:227-232`) and on the oracle route (`native/_chunked_entry.py:135-141`). So even if the joined list were dropped, the evidence list would keep the whole output alive until `run_auto_chunk` returns.
- B7's executor holds each dispatched table's finished output while the next table runs (`_pipeline_multi_table.py:256, 279`).
- B2's own Known issues say so: "The routed output is still fully materialized and concatenated; peak memory includes the whole output (B6a)" (`docs/plans/2026-10-01-dispatcher-auto-chunk.md:239`).

Measured on this base (probe `b6a/b2_probe.py`, B2's section 11 workload scaled up, companion venv, one process under the devbox test lock, `run_pipeline` with no sink, input read from Parquet before the run): at 2,000,000 rows the output is 210,000,000 bytes (`Table.nbytes`) and the run adds about 320 MB of RSS above the post-load floor; at 10,000,000 rows the output is 1,050,000,000 bytes and the run adds about 1.6 GB (peak 3.05 GB against a 1.43 GB floor). The increment grows linearly with rows at roughly 1.5 times the output size. A scratch prototype that consumes the same B1 iterator into a Parquet writer one row group at a time, with output-free evidence, added about 230 MB at 2M and about 83 MB at 10M (probe `b6a/b6a_proto.py`; allocator reuse makes small increments noisy, which is why section 10 measures with a peak reset). These are plan-time probe figures from single runs, not merge evidence.

A sink already exists on the public surface. `run_pipeline(..., sink: TransactionalSink | None = None)` (`_pipeline.py:164`) is consumed today only by the sequential and out-of-core routes, which stream each table into it, commit on success and abort on failure, and return `outputs == {}` (`_sequential.py:542-559, 579-590`; `out_of_core/_runner.py:274-285`; `_pipeline_route_exec.py:169, 438`). The full-frame continuation, which is where auto-chunk and the B7 split run, never touches it: it stamps `sink=None` into its telemetry (`_pipeline.py:642-649`), and the unified slice documents the sink as inert on that route (`_unified_slice_admission.py:252-262`). The engine's isolated worker hands every run a `ParquetTransactionalSink` and already accepts both result shapes, using `quality_metrics["execution"]["outputs_streamed"]` to tell them apart (`_isolated_worker.py:144-168, 217-226`).

## How established engines write incremental output

- **Arrow `ParquetWriter`.** The writer is opened with a fixed schema and appended to with `write_batch` / `write_table`; every call produces at least one row group, and the default row-group cap is 1024 x 1024 rows (pyarrow 25.0.1 `parquet/core.py:1163-1166, 1182-1186, 1198-1201`). The row group is the unit of buffering: a streaming writer holds one row group, not the file. The engine already uses this pattern in `ParquetTransactionalSink.write_batches` (`_transactional_sink.py:172-223`, citing the Arrow docs).
- **DuckDB `COPY ... TO 'x.parquet'`.** The pipeline streams into the Parquet writer, which flushes a row group when it reaches `ROW_GROUP_SIZE` rows (default 122,880) or `ROW_GROUP_SIZE_BYTES`; the result schema is bound before execution starts.
- **Polars `LazyFrame.sink_parquet`.** The streaming engine writes row groups (`row_group_size`) as morsels complete; the output schema comes from the lazy plan before any data is read.
- **Spark's commit protocol** (`HadoopMapReduceCommitProtocol` over Hadoop's `FileOutputCommitter`). Tasks write into a temporary attempt directory, job commit moves the results into the destination with renames, and abort deletes the temporary tree, so readers see all output or none. `ParquetTransactionalSink` is the single-writer form of the same idea: stage in a private sibling directory, publish with one `rename(2)`, remove the staging directory on abort (`_transactional_sink.py:1-28, 251-298`).

Common to all four: the schema is fixed before the first byte is written, output is buffered one row group at a time, and visibility is decided once, at commit. Decoy's oracle route cannot give the schema up front for every column (B1's schema rule pins hash, truncate, string redact and passthrough types and leaves every other strategy at "the type its route produced", `native/_chunked_schema_rule.py:1-16`), so B6a adds one adaptation: chunks that arrive before every column's type is known are held back, and held-back chunks beyond one row group spill to disk as Arrow IPC (Design 3).

## Guarantee (pinned)

For every `run_pipeline` call:

1. **Output equals B2.** When the run streams (Design 2), the table set the sink receives is exactly the key set of the `outputs` dict the same call returns with streaming off (`stream_chunked_output=False`, today's B2 / B7 behavior), and for each table:
   - (a) the batches the sink receives, read as `pa.Table.from_batches(batches, schema=schema)`, `equals` that resident table with `check_metadata=True`: same column names and order, same rows and order, same values and null positions, same field types, nullability and field metadata, and `schema.metadata is None` where the resident table has none;
   - (b) with `ParquetTransactionalSink`, the published `<table>.parquet` is byte-identical to `pq.write_table(<resident table>, path)` with pyarrow's defaults, which is what the isolated worker writes for the resident shape today (`_isolated_worker.py:119-141`), whenever no row group was cut by the byte cap (Design 3; the evidence records it). When the byte cap cut a row group, (a) still holds and only row-group boundaries differ;
   - (c) a streamed B7 split contains only dispatched tables. Each table follows (a) and (b), in config order. B6a never streams a split that still needs a resident full-frame group or an echoed extra frame.
2. **Bounded output.** On a streamed run, no more than one row group of a table's output (at most `ROW_GROUP_ROWS = 1,048,576` rows and, at chunk granularity, `ROW_GROUP_BYTES = 256 MiB` of buffered Arrow data), its combined copy, one in-flight chunk and the sink writer's own buffers are resident at once, independent of the table's row count. The per-chunk evidence keeps no output table. Chunks held back for schema resolution beyond that bound live on disk, not in memory. The input stays resident (B6b), and the vault writer's distinct-entry set is unchanged (Known issues).
3. **Atomic publish.** On a streamed run, `run_pipeline` calls `sink.commit()` exactly once, as its last action before returning, after finalize, telemetry and every `quality_metrics` stamp. If anything raises after the run decided to stream (Design 2) and before `commit()` returns, it calls `sink.abort()` exactly once (best-effort, an abort error is suppressed) and re-raises the original exception unchanged; it does not intentionally call `abort()` after `commit()` returns; see the accepted asynchronous interrupt window in Known issues. With `ParquetTransactionalSink`, nothing appears at the target until the single rename. Cleanup of the `_decoy_stage_*` and spill directories is attempted best-effort; ordinary tested failures leave none (the sink documents best-effort abort, `_transactional_sink.py:288-298`). This is the sequential route's contract (`_sequential.py:542-590`), reused.
4. **Who streams.** A run streams only when all of Design 2's conditions hold; the decision is made once, before the first chunk is masked, and is recorded with its reason. A run that does not stream behaves exactly as today: outputs returned in memory, the sink untouched, `quality_metrics` as today except the routed-only `auto_chunk.output` block (guarantee 6).
5. **Side channels equal B2.** Timings, `boundary_conversion_ms`, warnings, `code_set_corpora`, `chunked_route` / `chunked_route_by_table` evidence, vault entries and `table_kinds` are equal to the same call with streaming off. Row errors fail closed with `RowErrorsFailedError`, as in B2, and publish nothing. Errors keep their type and code (Design 8 lists the one message difference).
6. **Evidence, never silent.** Every routed run carries `quality_metrics["auto_chunk"]["output"]` (single table) or the same block per dispatched table in `auto_chunk.tables` (split), with `mode` (`streamed` or `resident`), `reason`, and on streamed tables `row_groups`, `byte_cut_row_groups`, `held_back_chunks` and `spilled_chunks`. A streamed run sets `quality_metrics["execution"]["outputs_streamed"] = True`; every other `execution` key keeps today's value. The payload is JSON-safe and deterministic.
7. **Non-routed calls unchanged.** A call that does not route chunked and does not split never enters the new code: outputs, sink behavior and `quality_metrics` are byte-identical to today for any valid value of the new knob.

## Non-goals

`LazySource` batch input and bounded input (B6b); the platform's sub-256-MiB eager route and platform adoption of the sink (B6c); CLI adoption (the CLI calls `run_pipeline` without a sink and writes CSV or Parquet itself, `decoy/src/decoy/cli/run.py:618-637`; B4 or a follow-up decides); CSV, fixed-width or cloud sinks (the sink protocol is unchanged, and `ParquetTransactionalSink` is the reference); streaming on the unified slice, the plain full-frame route, the legacy (kill-switch) lane or generate tables; changing `ParquetTransactionalSink`, the `TransactionalSink` protocol, B1's `run_mask_chunked`, B2's resident lane and `join_dispatcher_chunks`, B7's split decision, `classify_job` or the chunk size; streamed validators, quarantine, fidelity reports or post-validation (they need the whole output, see Design 2; program breadth item R8); a bounded vault; changing what `run_pipeline_isolated`'s driver reads back (`_isolated_run.py:575-578`); the Phase E 100M gate.

## Design

### 1. API: the caller decides by passing a sink

No new entry point. `run_pipeline`'s existing `sink` argument is the switch:

- A caller that wants an in-memory table passes no sink (the default) and gets today's B2 / B7 result unchanged. Every current in-memory caller works this way: the platform worker (`decoy-platform/api/jobs/v2_runner.py:298-310` calls `run_pipeline` without a sink, and `v2_full_frame.py` writes the outputs itself), the CLI, notebooks and tests.
- A caller that wants bounded output passes a `TransactionalSink`. Today that is the engine's isolated worker (`_isolated_worker.py:225-226`, so `run_pipeline_isolated` and everything built on it) and library callers. In this repo and the platform, `run_pipeline_isolated` is called only by the routing probe (`_probe.py:255-263`, with `execution_mode="full_frame"`). The probe is computed for any job whose static estimate does not fit (`_transforms_admission.py:320-337`), but its verdict is read only for relationship-bearing pure-mask jobs (`_transforms_admission.py:309-310`), and those never auto-chunk. A downscaled single-table probe child that auto-chunks may now stream, which lowers a peak nobody reads. So no production job changes shape or route until a caller opts in (Known issues). On a streamed run the result carries `outputs == {}`, exactly as the sequential and out-of-core routes already return when given a sink, and the isolated worker's existing streamed branch (`_isolated_worker.py:166-167`) enumerates the published files.
- One new keyword-only knob, `stream_chunked_output: bool = True`, next to `chunked_dispatcher_enabled`. `False` keeps the routed output resident even with a sink: today's B2 behavior, sink untouched. It is B6a's kill switch, separate from B2's, so B6a can be rolled back without losing the dispatcher. Validated with `require_bool` in the fail-early block, before profiling (`ExecutionError(code="invalid_execution_knob")`), like the other lane knobs (`_pipeline.py:321-325`). A runtime resource knob, never a config field, so it stays out of `pipeline_config_hash`.

This changes the documented meaning of `sink` on the full-frame continuation from "never consumed" to "consumed by the auto-chunk dispatcher lane and the B7 split when Design 2 holds". The compatibility contract, the `run_pipeline` docstring and `_unified_slice_admission.py`'s comment record it (Design 9).

### 2. Stream eligibility (decided once, before the first chunk)

`decide_output_mode(...) -> tuple[str, str | None]`, a free function, evaluated in `_pipeline_generate_mask.run_generate_and_mask_steps` after the route and split are known and before any masking. In this order, the first failing condition names the reason and the run stays resident:

1. the mask step takes the routed single-table lane or a B7 split (otherwise the new code is not entered at all, guarantee 7);
2. `stream_chunked_output` is true, else `streaming_disabled`;
3. `sink is not None`, else `no_sink`;
4. the sink has callable `write_batches`, `commit` and `abort` (`isinstance(sink, TransactionalSink)`, `_transactional_sink.py:51-90`), else `sink_not_streaming` (a plain callable sink stays resident; it never was transactional);
5. the lane is the dispatcher (`chunked_dispatcher_enabled`), else `legacy_lane`. A split already requires it (`_pipeline_multi_table.py:108`). For a B7 split, `split.full_frame` must be empty and every resident source name must be in `split.dispatched`; otherwise the run remains resident with reason `split_full_frame_present` or `split_extra_sources_present`. B6a never invokes the full-frame adapter while its publish session is open;
6. no `validators` in the config, else `validators_present`; quarantine not enabled, else `quarantine_enabled`; `fidelity_report` false, else `fidelity_report`; `post_validation` false, else `post_validation`. Each of these reads the whole output after the mask step (`_pipeline_finalize.py:374-460`, `_pipeline_generate_mask.py:251-257`, `_pipeline.py:665-678`). Declining is the established rule: the sequential and out-of-core routes decline the same consumers (`_pipeline.py` docstring on `post_validation`).

The decision is fixed before the first chunk and never changes mid-run (B2 guarantee 7's rule, and the program's "no fallback after output is published").

### 3. The streamed lane

New module `execution/_chunked_output_sink.py` (orchestration cap 600 lines). `run_auto_chunk` gains `sink: TransactionalSink | None = None`; with a sink it runs the dispatcher lane through the module below and returns `({}, timings, boundary_conversion_ms, warnings, quality_metrics)`; without one it is today's function, line for line.

**Output-free evidence.** The lane passes B1 a `chunk_result_sink` whose `append` stores `dataclasses.replace(result, outputs={})`. B1 only calls `append` on it (`native/_chunked_entry.py:135, 229`; `_chunked_oracle.py:371-372`), and the aggregators B2 uses read timings, warnings, `boundary_conversion_ms` and `quality_metrics`, never `outputs` (`_pipeline_auto_chunk.py:298-348`). Test 5 pins that the aggregates are equal.

**Schema resolution: B2's join rule, applied incrementally.** For each column, the target field is the field of the first chunk whose type is not `null`; if every chunk is `null`-typed, the first chunk's field. That is exactly what `_target_field` returns (`_pipeline_auto_chunk.py:130-141`): when all fields are equal it returns the first, which is also the first non-null one; otherwise it returns `typed[0]`. A chunk whose column names differ from the first chunk's, or whose non-null type differs from the resolved type, raises `ExecutionError(code="chunked_schema_mismatch")` naming the table, as `join_dispatcher_chunks` does (`:111-116, 138-140`). Each chunk is cast to the target schema when it differs (`check_metadata=True`), and the schema carries no metadata (`:119-120`). The schema is resolved when every column has a non-null type, or when the stream ends.

**Row-group assembly.** Cast chunks go into a buffer. Whenever the buffer holds at least `ROW_GROUP_ROWS` rows, its first `ROW_GROUP_ROWS` rows are sliced off, `combine_chunks()`-ed and passed on as one record batch; at end of stream the remainder becomes the last batch. If, after a chunk is added, the buffer's `nbytes` reaches `ROW_GROUP_BYTES`, the whole buffer is passed on as one batch even though it is short (a byte cut, counted in the evidence). `ParquetTransactionalSink.write_batches` writes each batch as one row group (`_transactional_sink.py:189-192, 212-223`). Probe `b6a/rg_probe.py` and `rg_probe2.py` (pyarrow 25.0.1): feeding 50,000-row chunks to `ParquetWriter` one call each gives 50 row groups and different bytes; accumulating to 1,048,576-row groups without `combine_chunks` also gives different bytes; accumulating and combining each group gives bytes identical to `pq.write_table` of the whole table, including through `ParquetTransactionalSink.write_batches` and with an all-null `string` column. `ROW_GROUP_ROWS` is defined as pyarrow's documented default; test 2 fails if a pyarrow upgrade changes it. `ROW_GROUP_BYTES` (256 MiB) protects wide rows, where 1,048,576 rows could be gigabytes; B2's workload at 1,048,576 rows is about 110 MB, well under it. Its value is frozen with the section 10 bars.

**Hold-back and spill.** `held_back_chunks` counts the chunks received before the schema resolved, the resolving chunk excluded. A column whose type B1's schema rule fixes (`build_schema_rule(...)`'s `string_columns` and `passthrough_fields`, `native/_chunked_schema_rule.py:47-88`, enforced on every chunk by `normalize_chunk`) counts as resolved from chunk 0 with chunk 0's field, so a passthrough column whose source type is `null` never holds the stream back. Until the schema is resolved, the lane cannot open the writer (`write_batches` takes the schema before the first batch). Held-back chunks stay in the row-group buffer, uncast, while it is under both caps, and are cast once the schema resolves. If a cap is reached while the schema is still unresolved, every buffered chunk is written to its own Arrow IPC file in a private directory (`tempfile.mkdtemp(prefix="_decoy_hold_")`, mode 0700) and dropped from memory, and later unresolved chunks go straight to disk. On resolution, or at the end of the stream, the lane calls `sink.write_batches(table, batches, schema=resolved)` with a generator that replays the spilled chunks in order (each read back whole with `pa.ipc.open_file(pa.OSFile(path, "rb"))`, cast, its file deleted), then continues with the buffer and the live iterator. `pa.OSFile`, not a memory map: the out-of-core sorter measured mapped pages staying resident (`out_of_core/_external_sort_run.py:23-37`). The directory is removed in a `finally`. Only a column outside the rule (an oracle-route strategy such as categorical, bucket_perturb or date_shift) can be unresolved; test 4 forces the path with a small cap.

Masking runs inside the sink's `write_batches` loop, pulled by the generator, so an error in chunk k propagates through `write_batches`, which closes its writer best-effort and re-raises (`_transactional_sink.py:213-222`).

### 4. Publish: commit and abort

A small session object (`OutputPublish`, logic in free functions) created in `run_pipeline` with the caller's sink, inert until `run_generate_and_mask_steps` decides to stream (Design 2), which opens it before the first chunk is masked. Opening it calls nothing on the sink; `ParquetTransactionalSink.abort()` before any write is a no-op (`_transactional_sink.py:288-298`), so a failure before the schema resolves is aborted the same way as a later one. `run_pipeline` wraps everything from the mask step to the return in one `try`: on `BaseException`, if the session is open and not committed, it calls `abort()` (suppressing an abort error) and re-raises; after `compute_post_validation` it calls `commit()` if the session is open, and only then returns. A commit failure (for example a non-empty target, `_transactional_sink.py:258-286`) propagates as the sink raised it after the session aborts, as on the sequential route. `_pipeline.py` is at its 679-line ratchet (`tests/sentry/test_module_size.py:479`); the builder keeps it there by moving lines out, never by raising the ratchet.

Why commit in `run_pipeline` rather than in the lane: after the last batch is written, `run_pipeline` still stamps evidence (`_pipeline_generate_mask.py:233`), runs finalize and builds telemetry (`_pipeline.py:632-649`). A failure in any of them must leave nothing published, so the commit comes after all of them; test 6 injects failures there.

### 5. B7 multi-table split

A split streams only when every resident output is dispatched. `run_multi_table_split` calls `run_auto_chunk(..., sink=sink)` one table at a time and returns `outputs == {}`. If `split.full_frame` is non-empty, or a resident source is not dispatched, the whole split stays on today's resident path and the sink is untouched; no pandas output-size prediction is used.

### 6. Side channels

- **Vault.** B1 adds each chunk's entries to the vault writer as before (`native/_chunked_entry.py:257-259`), and the caller writes the vault file after `run_pipeline` returns. On failure the run raises before the caller's write, so no vault file appears; the writer object may hold the entries of chunks before the failure, as in B2. The keyed-writer check still runs before any chunk (B2 test 6), so a mismatch publishes nothing. Single-table streaming works with a vault; a split never has one.
- **Row errors.** Fail closed at the chunk, as in B2 (`_pipeline_auto_chunk.py:293-296`); the session aborts.
- **Quarantine, validators, fidelity, post-validation.** Resident (Design 2).
- **Evidence and warnings.** Built from the output-free chunk results exactly as B2 builds them; `auto_chunk.output` is added (guarantee 6). The INFO log line gains the output mode.
- **`table_kinds`, `explain_plan`, `execution_plan`.** Unchanged.

### 7. Result shape

On a streamed run: `outputs == {}`, `row_errors == ()`, `quality_metrics["execution"]["outputs_streamed"] is True` (the full-frame telemetry function gains the flag; every other key unchanged), and the `output` block of guarantee 6. On every other run: today's result plus, on routed runs only, `auto_chunk.output` with `mode: "resident"` and its reason.

### 8. Failure modes and cleanup

| Failure | Behavior | Visible after |
|---|---|---|
| Error while masking chunk k (kernel error, row error, schema drift, `chunked_schema_mismatch`) | Propagates through `write_batches` with its own type and code; session aborts | Nothing at target; cleanup attempted best-effort, ordinary tested failures leave no staging or spill |
| A later chunk disagrees with the resolved type | `chunked_schema_mismatch` at that chunk. B2 raised the same code after masking every chunk; the message may name fewer types (only those seen so far) and a name mismatch after a type mismatch is reported as the type mismatch | Nothing |
| Sink rejects the table name (`_transactional_sink.py:239-249`) | `ValueError` at the first write, after the first chunk masked; session aborts | Nothing |
| Disk full while staging or spilling | `OSError` propagates; session aborts; spill cleanup attempted best-effort (ordinary tested failures leave none) | Nothing |
| `commit()` fails (target exists and is non-empty, permissions) | Session aborts (staging cleanup attempted best-effort), the sink's exception propagates | Target unchanged |
| `abort()` itself raises | Suppressed; the original exception propagates | Best effort |
| `KeyboardInterrupt` or other `BaseException` | Same as an error | Nothing |
| Process killed (SIGKILL, OOM killer) | No cleanup runs | Orphaned `_decoy_stage_*` beside the target and `_decoy_hold_*` in the temp directory; never a partial target. The isolated driver discards its staging root |
| Failure after the last batch, before commit (evidence stamping, finalize, telemetry) | Original exception propagates; session aborts once; no commit | Nothing |
| Split with a full-frame group or extra frame | Not streamed (Design 2); resident as today, sink untouched | As today |

### 10. Merge evidence: performance and memory

Bounded local benchmark, merge evidence under the standing Rust rule, not the Phase E gate.

- **Harness.** Extends `scripts/bench-auto-chunk`. Each measured subprocess does what the isolated worker does (`_isolated_worker.py:225-235`): read the source with `pq.read_table`, then `run_pipeline(config, sources, sink=ParquetTransactionalSink(staging), ...)`, then `_isolated_worker._finalize_outputs(result, staging)`. Between the read and `run_pipeline` it writes `5` to `/proc/self/clear_refs`, which resets `VmHWM` on Linux (verified on the devbox), and records `VmRSS` as the floor. After `_finalize_outputs` returns it records `VmHWM`. Run increment = `VmHWM - floor`. It also records lifetime peak (`ru_maxrss`) and `pa.default_memory_pool().max_memory()` for information. This fixes the B2 run's blind spot (B2 build record, dennis LOW 2: source construction dominated peak RSS).

## Known issues (tech debt, not blockers)

- **Input stays resident.** Peak memory still includes the whole source table; B6b bounds it.
- **Small jobs see no change.** A table of at most 1,048,576 rows fits in one row group, so its streamed peak is about B2's minus the join copy and the chunk list. The gain starts above one row group.
- **Who benefits today.** Only callers that pass a sink: `run_pipeline_isolated` and library users. The platform worker and the CLI keep resident outputs until they adopt the sink (B6c, B4 or a follow-up), so B6a by itself lowers no production job's memory; it builds and proves the lane those slices switch on.
- **Vault memory.** The vault writer's distinct-triple set is unbounded in distinct values (`vault.py:199-237`); a streamed job with `vault: true` columns is bounded in output but not in vault entries.
- **Whole-output consumers force resident.** Validators, quarantine, fidelity reports and post-validation keep the job resident (Design 2); streaming them is program breadth item R8.
- **Late discovery of a non-empty target.** `ParquetTransactionalSink` learns that its target is non-empty only at commit, after all masking, as on the sequential route.
- **Orphans after a hard kill.** `_decoy_stage_*` and `_decoy_hold_*` directories remain after SIGKILL; both prefixes are documented for cleanup.
- **Driver read-back.** `run_pipeline_isolated`'s driver reads every staged table back into the parent process (`_isolated_run.py:575-578`), as it already does for the sequential and out-of-core routes. The bound holds in the child, which is the process under the memory cap.
- **Two result shapes.** A caller that passes a sink must accept `outputs == {}` on streamed runs; that was already true for the sequential and out-of-core routes.
- **Byte identity is pyarrow-version-bound.** It rests on the writer defaults matching `pq.write_table`'s; test 2 turns a pyarrow change into a failing test. Logical equality (guarantee 1 (a)) does not depend on it.
- **Wide rows.** A byte-cut row group makes the file's row-group layout differ from `pq.write_table`'s; values, types and schema are unchanged.
- **Error timing.** A chunk-level schema mismatch surfaces at that chunk instead of after the last one, with the same code; its message may list fewer types.
- **Whole-stream spill.** A column outside B1's schema rule that is all-null across the whole table never resolves, so every chunk spills once and is replayed at the end: memory stays bounded, the output is written to disk twice, and `spilled_chunks` shows it.
- **String offsets.** Each row group is combined with `combine_chunks`, which B2 already does over the whole table; a single string column above 2 GiB within one row group fails as it would in B2.
- **Post-commit interrupt window.** An asynchronous `BaseException` can land after `sink.commit()` returns but before the publish session records the committed state. This is the same minimal bytecode window documented for the sequential route at `_sequential.py:548`; `ParquetTransactionalSink.abort()` is harmless after its successful rename.
- **No temporary-disk budget for hold-back.** Whole-stream schema hold-back has no temporary-disk budget. It can require both the Arrow IPC spill and staged Parquet space. ENOSPC fails closed, but capacity is not predicted.
- **Best-effort cleanup.** Cleanup is attempted best-effort; ordinary tested failures leave none.
- **Mixed splits stay resident.** A B7 split with any full-frame group table or extra resident frame keeps every output resident (Design 2), so a large non-chunk-safe table next to a dispatched one gets no memory bound from B6a.
- **Allocator retention.** Freed pages may stay mapped; section 10 measures the result rather than assuming the structure.
