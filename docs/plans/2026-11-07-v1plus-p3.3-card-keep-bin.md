## 1. FRAME

**Problem.** Fraud models, payment routing tests and BIN-mix dashboards break on masked card
numbers, because the shipped `fpe` mask with `checksum: luhn` encrypts every digit except the
check digit. What it keeps today (`transforms/_fpe_checksum.py`, luhn branch): the digit count,
the separator positions (with `preserve_separators`) and Luhn validity. It does not keep the
issuer prefix, so the brand and issuer of every masked card are random.

**Property kept.** With `keep_bin: 6` or `keep_bin: 8` on an `fpe` column with `checksum: luhn`,
every masked value:

1. has the same digit count and the same separator positions as its source;
2. starts with the same first 6 (or 8) digits as its source (the BIN, or the ISO/IEC 7812-1:2017
   8-digit IIN), and so the same brand;
3. FF1-encrypts the remaining account digits, excluding the check digit, under the column's
   existing FF1 key, with the kept prefix bound into the tweak;
4. ends with a recomputed Luhn check digit, so it is Luhn-valid;
5. is deterministic and reversible (`unmask`) under the same key, namespace and column.

**The leak it accepts.** The BIN is in the clear: it reveals the issuer, the brand, the issuing
country and often the product (debit, credit, prepaid, corporate). A small issuer's BIN can narrow a
row to few people. The digit count is kept too. Masked numbers stay unique within a column (FF1 is
a permutation; see section 4), so a count of distinct cards per BIN is exact. This goes into
`docs/what-we-cannot-prove.md`.

**Definition of done.**

1. The property above holds on every output row (property test, section 7).
2. Plan compile refuses every misuse with a coded reason; values that cannot be masked safely fail
   the job closed with a coded reason; no value passes through unmasked.
3. Every route that accepts the option gives the same output; routes that cannot (the native
   kernels) decline to the Python oracle through the existing checksum decline.
4. Dark: a config without `keep_bin` is byte-identical to main.
5. The leak is in `docs/what-we-cannot-prove.md`; the option is in `docs/strategies.md`.

**Non-goals.** Keeping the last 4 digits (section 2 explains why it is out of scope). Keeping any
other part of the number (expiry, service code, track data). Keeping a prefix for any other
checksum scheme. A BIN-lookup table or brand detection. Wizard exposure (open question Q1).
Changes to text-span masking (`text_mask`'s `pan` detector).

**Risk: R2.** Privacy logic (a new partial-plaintext mode on a reversible cipher) and a public
config contract plus new reason codes. Rollback: revert the commit; nothing is persisted, the
registry minor is renumbered at merge, and no V1 path changes.

## 2. Established solutions

**Searches run (2026-11-07).** NIST SP 800-38G and its Rev. 1 second public draft (FF1, FF3-1,
domain floor, tweak guidance); the NIST ITL Bulletin of April 2016 on SP 800-38G; PCI DSS 4.0
masking (Req. 3.4.1) and truncation (PCI SSC FAQ 1091) and the 8-digit-BIN guidance from the PCI
SSC, Visa and Mastercard; ISO/IEC 7812-1:2017 (8-digit IIN, PAN length); vendor docs for Voltage
SecureData, Protegrity, Delphix, Tonic and Talend/Qlik. The `nvlpubs.nist.gov`, `csrc.nist.gov`,
`masking.delphix.com` and `help.qlik.com` pages could not be fetched from this session (host not
allowed), so those findings rest on search excerpts; the build re-checks the NIST text if the
host is opened.

**Findings.**

- **NIST SP 800-38G (FF1).** FF1 is the remaining approved method (FF3/FF3-1 withdrawn in the
  Rev. 1 second public draft after the Beyne 2021 attack). The Rev. 1 drafts turn the minimum
  domain size into a requirement: `radix ** length >= 1,000,000`. The engine already pins this as
  `_ff1.FF1_MIN_DOMAIN` and enforces it in `transforms/fpe.py::_permute`, the one function every
  FF1 call goes through. For digits that is at least 6 encrypted digits.
- **Tweak guidance.** The ITL Bulletin (April 2016) uses this exact case: when the first six and
  last four digits of a card stay in the clear and only the middle digits are encrypted, about a
  hundred cards share each middle value; encrypted under one tweak they would all get the same
  ciphertext middle. SP 800-38G recommends using information statically associated with the
  plaintext (the clear digits) as the tweak, so those ciphertexts almost certainly differ.
  Voltage's published pattern (patent and NIST workshop slides) does the same: clear digits as
  tweak, middle encrypted.
- **PCI DSS.** Displayed PANs are masked to at most the BIN and last four (4.0 Req. 3.4.1; 3.2.1
  said first six and last four). For stored truncation, FAQ 1091 gives a table by PAN length and
  brand; first 6 / last 4 is accepted by all brands, and some brands allow first 8 / any other 4 for
  16-digit PANs with an 8-digit BIN. A masked dataset is not a PCI truncation, but the table sets
  the most a card standard would ever show.
- **ISO/IEC 7812-1:2017.** The IIN grew from 6 to 8 digits; the PAN stays at most 19 digits; an
  issuer with an 8-digit IIN issues PANs of at least 10 digits. The last digit is the Luhn check
  digit.
- **Products.** Protegrity FF1 (AES-256) has "left" and "right" clear-character settings, and can
  use them as the tweak. Delphix's Payment Card framework has "Preserve Starting Digits" (counts
  maskable characters only, so separators do not count), a "minimum masked positions" floor, keeps
  non-digits in place, and keeps Luhn validity. Talend/Qlik "Mask Credit Card and keep bank" keeps
  the BIN/IIN, uses FF1, and recomputes the last digit with Luhn. No Tonic Structural source on BIN
  preservation was found.

**Source followed.** NIST SP 800-38G FF1 on the account digits with the kept prefix in the tweak
(SP 800-38G tweak guidance, ITL Bulletin 2016-04), the ISO/IEC 7812-1 PAN structure, and the
"preserve starting digits, separators do not count" convention shared by Delphix and Protegrity.

**Codebase first.** The engine already has every primitive:

- FF1, its deployable profile and the domain floor: `transforms/_ff1.py`, `fpe.py::_permute`.
- Luhn-mode FPE: `_fpe_checksum.py`, luhn branch (permutes `s[:-1]`, appends `calc_check_digit`).
- A pinned-prefix precedent: the `isbn13` branch pins `978`/`979` and permutes the rest; `npi`
  pins its leading digit.
- Separator handling, source Luhn validation, length fail-closed, key derivation and tweak framing.
- `derived` and `formula` cannot express this: `derived`'s closed grammar has no keyed function,
  and `formula`'s `MASK_GLOBALS` has no FF1 or Luhn helper and draws from an unkeyed RNG (not
  reversible, not stable per value). So the slice is a named option over the existing FPE
  checksum code, not new logic.

**Why custom code is still needed.** About 30 lines: split the body at the kept prefix, bind the
prefix into the tweak, refuse lengths the standard does not allow, and resolve the option in one
place. No new cipher, no new key, no new dependency.

**Keeping the last 4: out of scope.** The last four digits include the check digit, so keeping
them fixes the check digit and forces one more digit to be a Luhn compensator (or cycle-walking
over the Luhn-valid subset). The free domain for a 16-digit PAN is then 10^5 with a 6-digit BIN
and 10^3 with an 8-digit IIN, below the 1,000,000 floor, so the engine would refuse the most
common card length. It also leaves 10^5 candidates per row, which an attacker holding the masked
value can enumerate. Recorded as a follow-up (section 8) for 17-to-19-digit PANs if a customer asks.

## 3. Behavior

`keep_bin` is a `provider_config` key on an `fpe` column. Allowed values: absent or null (off),
the integer `6`, or the integer `8`.

| Case | Behavior |
|---|---|
| Luhn-valid PAN, digits only, 13 to 19 digits with `keep_bin: 6`, 15 to 19 with `keep_bin: 8` | first `k` digits kept; digits `k` to `n-2` FF1-encrypted (tweak = column tweak + prefix); Luhn digit recomputed |
| Same with separators, `preserve_separators: true` (handler default) | digits are taken in order, skipping non-digits; the prefix is the first `k` digits (separators do not count, as in Delphix); separators go back in place |
| Separators with `preserve_separators: false` | job fails closed, existing `fpe_unencryptable_value` (unchanged) |
| Fewer encrypted digits than the FF1 floor (fewer than 13 digits with 6, fewer than 15 with 8) | job fails closed, existing code `fpe_unencryptable_domain`; message names `keep_bin` and the digit counts, never the value |
| More than 19 digits | job fails closed, existing code `fpe_checksum_unsupported` (`FpeChecksumError`, the scheme-length error): not an ISO/IEC 7812 PAN |
| Source fails Luhn | job fails closed, existing `fpe_checksum_invalid_source` (unchanged) |
| Letters or other non-digits inside the number | treated as separators and kept, the existing partial-plaintext rule; the existing `fpe_partial_plaintext_disclosure` warning fires (unchanged) |
| Null | null (unchanged); empty string stays empty (unchanged) |
| Decrypt (`unmask`) | the prefix is read from the ciphertext, the middle is FF1-decrypted under the same tweak, Luhn recomputed: round-trips a Luhn-valid source exactly |

Plan-compile refusals (new codes, `plan` namespace, `since` 1.7.0):

| Config | Code |
|---|---|
| `keep_bin` not exactly the integer 6 or 8 (7, 0, -6, `"6"`, `6.0`, `true`) | `plan.fpe_keep_bin_invalid` |
| `keep_bin` set without `checksum: luhn` (absent, `npi`, any other), or with a charset that does not resolve to `digits` | `plan.fpe_keep_bin_requires_luhn` |
| `keep_bin` on a column whose strategy is not `fpe` | `plan.fpe_keep_bin_non_fpe_strategy` |
| `fpe_join_group` members that differ in `keep_bin` | existing `plan.fpe_join_group_config_mismatch` |

Messages name the table, column and the config key; they never contain a data value (config values
such as `7` are not data). No new runtime or route codes: every runtime failure reuses an existing
FPE code, and the native routes decline with the existing `fpe_checksum_not_native`.

Why strict `digits` charset: the prefix is "the first k digits"; with `alphanum` a letter would be
read as part of the number and the source would fail Luhn anyway. Refusing at compile time is clearer.

## 4. Design notes

**Config shape.**

```yaml
tables:
  - name: payments
    columns:
      - name: card_number
        strategy: fpe
        namespace: card
        provider_config:
          checksum: luhn          # required with keep_bin
          keep_bin: 6             # or 8 (ISO/IEC 7812-1:2017 8-digit IIN)
          preserve_separators: true
```

`4539 5787 6362 1486` -> `4539 57xx xxxx xxxc`: same first six digits, same spaces, nine
FF1-encrypted digits, a fresh Luhn digit.

**Where each fact lives (one place each).**

- `keep_bin_problem(cfg) -> "invalid" | "requires_luhn" | None` and `resolve_keep_bin(cfg) -> int`
  in `transforms/_fpe_checksum.py`. The plan check maps the problem to a plan code; the resolver
  raises `FpeChecksumError` (value-free) for the runtime callers. No other module reads the
  `keep_bin` key.
- The split and the tweak binding live in `_fpe_checksum_permute`'s luhn branch, next to the
  `isbn13` prefix pin. The FF1 floor stays in `fpe._permute` (the existing choke point); the
  `keep_bin` branch only adds a clearer message before it.
- `fpe_encrypt_value` and `fpe_decrypt_value` take a keyword-only `keep_bin: int = 0` and pass it
  down through `_fpe_value` and `_fpe_pure_value`. The default keeps all 23 existing test modules
  and the `text_mask` caller unchanged; the guard in section 5 stops a production site forgetting it.
- `FpeConfig` (native contract) gains `keep_bin: int = 0`, set by `from_mapping` through the
  resolver, so the reference oracle passes it and the compiled kernel refuses it (as it refuses
  `checksum`). `_resolve()`'s 4-tuple is unchanged.

**Tweak.** `tweak' = build_ff1_tweak(scope, identity) + prefix_ascii`. The base tweak is
length-prefixed (`VERSION || SCOPE || LEN || identity`), so the suffix is unambiguous and cannot
collide with any other (identity, prefix) pair or with the no-`keep_bin` tweak (which has no
suffix). The longest suffix is 8 bytes; the existing 256-byte tweak cap still applies in
`_permute` (an identity within 8 bytes of the cap fails closed with `fpe_unencryptable_length`).
Binding the prefix follows SP 800-38G's tweak guidance and stops cards that share middle digits
across BINs from sharing a ciphertext middle (section 2).

**Determinism and keys.** Same key as today: `derive(mask_key, namespace, FF1_KEY_LABEL)`, same
column or join-group tweak plus the prefix. No new key, label, draw or secret-bearing parameter:
the draw-site catalogue entry `mask.fpe` and its pinned digest stay unchanged, and the
secret-material census does not grow. Output depends only on (mask key, namespace, column or join
group, value), so it is stable across runs, chunking and routes.

**Uniqueness and collisions.** Within one column, PANs with the same prefix and length map to
outputs through one FF1 permutation of the middle digits (the tweak is fixed by the prefix), so
distinct inputs give distinct outputs; PANs with a different prefix or length give outputs with a
different prefix or length. The Luhn digit is a function of the body. So the mask is injective on
the Luhn-valid PANs of a column, and `keep_bin` columns stay join-safe (as `fpe` is today) when
every member uses the same `keep_bin` (join-group homogeneity check). An output can equal its
input with probability 10^-m for m encrypted digits (at worst 10^-6), as with any FPE; this is
recorded, not prevented.

**Routes.** The option rides the existing checksum path, so every route treats it as it treats
`checksum: luhn` today:

| Route | `checksum` today | With `keep_bin` |
|---|---|---|
| Full-frame pandas (`FpeStrategyHandler.run`) | Python | Python, passes `keep_bin` |
| Chunked oracle / auto-chunk | handler per chunk | same |
| Native chunked and unified (`_real_type_admission`) | declines, `fpe_checksum_not_native` | declines (unchanged code path) |
| Sequential FK, native seam (`_fpe_admit`) | declines to the handler | same |
| Physical shadow binding | leaves the node unbound (oracle) | same |
| Out-of-core (`_mask_group_b.fpe_array`, `_fpe_native`) | Python `fpe_array`; native declines | Python `fpe_array`, passes `keep_bin` |
| `unmask` | `fpe_decrypt_value` | passes `keep_bin` |
| Native reference oracle (`_crypto_reference`) | test oracle | passes `config.keep_bin` |

Plan compile guarantees `keep_bin` only appears with a truthy `checksum`, so every native decline
fires. The compiled kernel and `FpeConfig` also refuse `keep_bin` directly (backstop for a caller
that skips compile).

**Principles applied.** One place per fact (resolver; tweak rule); open for extension through the
existing per-scheme branch rather than a new strategy; no flag argument that switches behaviour
other than the one named option. No new structure: no new module in `src/`.

**Collisions with parallel work.** V1P-3.1 and V1P-3.4 also bump the registry to 1.7.0, edit
`docs/strategies.md`, `docs/what-we-cannot-prove.md`, `CHANGELOG.md` and the reason fixtures; this
slice only appends there. V1P-2.1 (unmerged) edits the scheme-set import in `_fpe_checksum.py`;
this slice edits the luhn branch and the signature, so the merge is mechanical. `plan/_checks.py`
(over the maximum) and `plan/_compile.py` (census-pinned) are not touched: the new check runs inside
the existing `check_fpe_charset_config` loop, already wired into both compile branches and
`run_config_only_checks`.

## 7. Acceptance tests (written first)

All in `tests/unit/card_keep_bin/` unless named otherwise. Keys are fixed test keys.

1. **Property (Hypothesis, `tests/property/test_fpe_keep_bin.py`, derandomized, pinned
   examples).** Generate Luhn-valid PANs (prefix from a list of real-shaped BINs and random
   digits, length 13 to 19 for 6, 15 to 19 for 8, optional spaces or dashes in 4-digit groups).
   For every output: same length; same non-digit characters at the same positions; the first `k`
   digits equal the source's; `checksums.validate("luhn", digits)` is true; decrypt returns the
   source exactly.
2. **Uniqueness.** 5,000 distinct PANs sharing one BIN and length give 5,000 distinct outputs; the
   same for 5,000 PANs spread over 20 BINs.
3. **Tweak binding.** For 200 middles, two PANs with the same middle digits and different BINs
   (Luhn digit fixed up) give different encrypted middles in at least 199 of 200 cases (the chance
   of a match is 10^-9 each); and the output equals an independent recomputation with
   `_permute(middle, key, digits, base_tweak + prefix)`.
4. **Determinism and pinned vectors.** Same (key, column) gives the same output twice; a different
   column or join group gives a different one; five pinned known-answer outputs (6 and 8, 13, 15,
   16, 19 digits, with and without separators) so any change to the construction is caught.
5. **Routes.** The same frame through the full-frame handler, the chunked oracle (`auto_chunk`
   forced), the sequential route and out-of-core `fpe_array` gives identical outputs; the native
   chunked, sequential and out-of-core admissions decline a `keep_bin` column with
   `fpe_checksum_not_native:<col>`; `unmask` of the masked table returns the source; the native
   reference oracle (`_ReferenceFpe`) matches the handler; the compiled kernel (when the companion
   is installed) refuses a `keep_bin` config.
6. **Fail closed.** `keep_bin: 6` with a 12-digit PAN and `keep_bin: 8` with a 14-digit PAN raise
   `fpe_unencryptable_domain` and the message names `keep_bin`; a 20-digit Luhn-valid value raises
   the checksum length error (`fpe_checksum_unsupported` at the handler); a Luhn-invalid PAN raises
   `fpe_checksum_invalid_source`; `preserve_separators: false` with spaces raises
   `fpe_unencryptable_value`. For each, at both the value function and the handler: no digit run of
   the source of length 4 or more appears in the message, and the new value-level raises have
   `__cause__` and `__context__` None.
7. **Plan compile.** `keep_bin` 6 and 8 with `checksum: luhn` compile, with and without an explicit
   `charset: digits`; `7`, `0`, `-6`, `"6"`, `6.0`, `true` give `fpe_keep_bin_invalid`; no checksum,
   `checksum: npi`, `charset: alphanum` give `fpe_keep_bin_requires_luhn`; `keep_bin` on a `hash`
   column gives `fpe_keep_bin_non_fpe_strategy`; two join-group members with 6 and 8 give
   `fpe_join_group_config_mismatch`; the same checks fire from `run_config_only_checks`.
8. **Dark.** Before any code change, record the outputs of the existing luhn-mode, npi-mode and
   plain-fpe columns over a fixed corpus (snapshot in the test file); after the change they are
   byte-identical, and `keep_bin: null` gives the same output as no key.
9. **Guards.** Section 5, each with its seeded violation.
10. **Registry.** `scripts/dev/registry_renumber.py --check` passes; the three codes resolve with
    `since == "1.7.0"`; the release pin test still passes (1.6.0 unchanged).

Fail-before: tests 1 to 7 and 9 fail on the base tree (the option does not exist: compile ignores
the key, so test 7's refusals and test 1's prefix assertion fail); test 8 passes before and after
by design.

## 8. Known limits

- Keeping the last 4 digits is not offered (section 2). Follow-up if asked: a 17-to-19-digit-only
  option with a Luhn compensator digit, refused below the floor.
- PANs of 10 to 12 digits (allowed by ISO/IEC 7812 with an 8-digit IIN) and 13 or 14 digits with
  `keep_bin: 8` fail the job closed: too few digits remain for FF1. The fix is `keep_bin: 6` or
  another strategy for that column.
- One bad row fails the whole job, as every FPE fail-closed case does today.
- The prefix is "the first k digits"; the engine does not check that it is a real BIN. A value that
  is not a card but is Luhn-valid is masked the same way.
- Letters or other non-digits inside a number stay in the clear (existing partial-plaintext rule,
  warned).
- Some web sources (NIST PDF, Delphix and Qlik docs) were read through search excerpts only.

## 9. Open questions

- **Q1. Strategy catalog.** The brief asks to add the option to `strategy_catalog()`. The `fpe`
  row offers only `charset` and `preserve_separators`; `checksum` is not offered, and the catalog
  has no way to say "only with `checksum: luhn`". Offering `keep_bin` alone would let the wizard
  write a config that plan compile refuses, and the catalog's "option changes the output" probe
  would fail. Proposal: leave the catalog unchanged in this slice and record a follow-up to offer
  `checksum` and `keep_bin` together once the catalog can express a dependent option. The
  alternative is to make `keep_bin` imply `checksum: luhn`; that would need every native decline
  site to learn the new key, which this plan avoids.
- **Q2. Name.** `keep_bin` (the term PCI, Visa and Mastercard use) rather than `keep_iin` (the
  ISO term). The docs give both.
