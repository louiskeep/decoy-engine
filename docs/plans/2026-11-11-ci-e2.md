## 1. Guarantee and non-goals

The change promises:

1. Every hosted lane that the self-hosted merge gate does not cover runs automatically on every
   pull request: `ci.yml` profile lanes (packaging, ml, ner, dp-certified, determinism),
   `native-companion.yml`, and the `docs.yml` build.
2. Every workflow has an automatic trigger (`pull_request`, `push` or `schedule`), or is listed
   in `ci/unlaned.toml` with a reason. The profile lanes and the native lanes also run nightly on
   main. The determinism harness (`-m determinism_harness`) runs on every PR and every night.
3. No restored trigger starts a self-hosted runner. Self-hosted jobs stay on `push` and
   `workflow_dispatch` only, so `gate-vm-watch` never starts a VM for a PR or a nightly.
4. No job runs twice per merge for the same purpose. The hosted full suite (`regression-gate`),
   `ruff`, `mypy` and `layers-gate` leave the PR path because the self-hosted gate already runs
   them. The determinism harness leaves `gates.sh` because its own lane owns it.
5. A sentry fails when a registered pytest marker has no automatic lane, when a workflow has no
   automatic trigger, when a workflow uses a path filter, or when `ci/required-jobs.toml` and the
   workflows disagree. Each listed miss is a seeded red case.
6. `engine-v2-substrate-matrix.yml` is deleted. The dead `run-bench` condition in `benchmark.yml`
   is removed.
7. (Slice 2) One script reads the required list from the `origin/main` tip and says whether a head
   has every required job green on its first attempt, and whether last night's schedule runs on
   main are fresh and green.

Non-goals (a finding here is a follow-up, not a blocker):

- Moving the hosted `regression-gate` onto `gates.sh` with xdist. FU-1.
- `--strict-markers` (an unregistered marker is silently ignored by `-m`). FU-2.
- A Slack line for nightly results. That is devbox ops on top of slice 2's `--tier nightly`. FU-3.
- The CodSpeed decision. `CODSPEED_ENABLED` is `true` and the last `codspeed.yml` runs failed; it
  stays manual and unlaned. FU-4.
- CLI and platform CI. See section 14 for a roadmap truth issue found while planning.
- Deliberate evasion of the sentry (`PYTEST_ADDOPTS` in a step `env`, config-file indirection,
  command substitution). V2-LOG, per the class 5 scope rule.

## 3. Established solutions

Searched: GitHub Actions documentation (events, `concurrency`, job conditions, protected branches
and required status checks, usage limits, scheduled events), pytest documentation for `-m`, the
CLI repo's CI-L1 work, and this repo's CI sentries.

- Required checks: GitHub branch protection "required status checks" enforces named checks on the
  PR head. The design follows it and only keeps the list in the repo (Q1 decides whether to apply
  it). GitHub documents that a job skipped by an `if` reports success and does not block a merge
  even when required, so a required job must carry no `if` (sentry rule R2).
- Superseded runs: workflow-level `concurrency` with `cancel-in-progress` on pull requests, the
  documented pattern. A shared group with `cancel-in-progress: false` keeps only one pending run
  and cancels the rest, which would cancel required PR builds (the current `docs.yml` `pages`
  group). The design moves that group to the deploy job.
- Schedules: documented caveats are that scheduled runs can be delayed or dropped at busy times,
  run only from the default branch, are disabled after 60 days without repo activity, and send
  failure notices to the user who last edited the cron line. Crons here avoid the top of the hour,
  and the slice 2 verifier treats a missing or old run as "no fresh run", never green.
- Marker expressions: pytest's `-m` grammar is `and`, `or`, `not`, parentheses and names. That is a
  subset of Python boolean syntax, so the sentry evaluates it with stdlib `ast`, accepting only
  `BoolOp`, `UnaryOp(Not)` and `Name` nodes and failing closed on anything else. pytest's own
  evaluator lives in the private `_pytest.mark.expression` module (recurring defect 6), so it is
  not imported.
- Shell parsing: the shared `ci_scan._shell_tokens.commands` is the one parser (CI-X). The lane
  sentry calls it and adds no tokenizer.
- Suite-ran-clean guard: `ci.yml` `dp-certified-gate` already has an inline JUnit check (passed >
  0, nothing skipped, errored or failed). It moves to one script that both that job and the new
  determinism job call.
- actionlint (the CLI uses it) lints workflow syntax. It does not know lanes, markers or required
  lists, so it does not replace this sentry. Adopting it in the engine is FU-5.

Custom code that remains: the lane walk (about 250 lines) and, in slice 2, the required-check
derivation and verifier (about 200 lines). No library maps pytest markers to workflow jobs.

### Lane sentry rules (slice 1)

A job's events are its workflow's triggers when it has no `if`; the triggers minus
`pull_request` when its `if` is exactly `github.event_name != 'pull_request'`; and none for any
other `if`. Automatic events are `push`, `pull_request` and `schedule`. Workflow triggers are
decoded in one place: `_ci_lanes.workflow_events(doc)`, which reads the scalar, list and mapping
forms of `on`. It replaces `_trigger_names` and `_triggers` in `tests/sentry/test_ci_config.py:64`,
which are deleted; `selfhosted_violations` (`test_ci_config.py:85`) imports `workflow_events`.
One characterization test feeds the scalar, list and mapping forms through both consumers (lane
events and `selfhosted_violations`) and pins the same event set.

A pytest invocation is a command from `commands(step["run"])` whose tokens contain `pytest` as a
command word (`pytest`, `python -m pytest`, `uv run [opts] pytest`, inside `bash -c "..."`). Its
expression is the last `-m X` or `-mX` value; with none it is the `addopts` expression, or "all"
after `-o addopts=`. It is whole-suite when it names no path or only `tests`.

- M1. A marker that `addopts` selects (a default marker) needs a whole-suite invocation in a job
  with an automatic event whose expression selects a test carrying only that marker.
- M2. A marker that `addopts` excludes (an opt-in marker) needs a dedicated invocation in a job
  with an automatic event: the expression selects that marker and does not select an unmarked
  test. So `-m "perf or not perf"` is not a lane for `benchmark`.
- M3. A marker with no lane must be in `ci/unlaned.toml`. An `unlaned` entry for a marker that has
  a lane, or that is not registered, fails (the list may only shrink).
- M4. An expression with any other syntax (a call, an operator, a bad token) is a finding, not a
  pass.
- M5. `gates.sh` `PYTEST_ARGS` and the `regression-gate` `-m` are the same expression after
  whitespace is collapsed. Both are "the default full suite"; they must not drift.
- M6. A marker in `[[dedicated_marker]]` follows the M2 rule even though `addopts` selects it: it
  needs an invocation whose expression selects it and does not select an unmarked test, in a job
  with an automatic event. A `[[dedicated_marker]]` entry for an unregistered marker fails.
- T1. Every workflow has an automatic trigger or a `[[workflow]]` entry in `ci/unlaned.toml`. A
  stale entry fails.
- T2. No `paths` or `paths-ignore` on any trigger of any workflow.
- T3. Every job in every workflow has `timeout-minutes` (replaces the `ci.yml`-only test).
- T4. Every workflow with `pull_request` declares the concurrency block above, and no workflow has
  workflow-level `cancel-in-progress: false`.
- T5. Self-hosted jobs run only under `push` and `workflow_dispatch` (extends
  `selfhosted_violations` in `test_ci_config.py`, which now reads events through
  `_ci_lanes.workflow_events`; `schedule` and any other event are refused).
- R1. Both registries have a closed schema: unknown keys, a missing or empty `reason`, or a
  duplicate entry fail.
- R2. Each `merge` job exists, its workflow has `pull_request`, it has no `if` and no `needs` on a
  job outside the merge tier, it is not self-hosted, and its `name` is absent or a literal. In
  CI-E2b, through the shared derivation, R2 also asserts that every derived check name is unique
  across all workflows with `push`, `pull_request` or `pull_request_target`, so a push-only job
  cannot report a context that satisfies a required PR check. The docs job's literal
  `name: docs-build` exists for this reason.
- R3. In a workflow with `pull_request` or `pull_request_target`, every job that may run on a PR
  (no `if`, or an `if` other than the not-PR form) is in `merge` or in `merge_exempt`. A new PR job
  therefore needs a reviewed edit of the registry. Jobs in workflows without those triggers are
  out of scope for R3.

`test_paid_runner_workflows_are_manual_dispatch_only` and `TRIGGERED_ON_PURPOSE` are deleted; T1,
T2, T5 and R3 replace them.

### Required-check verifier (slice 2)

`scripts/dev/required_checks.py`:

- `contexts`: prints the GitHub check names of the merge tier as JSON, for branch protection. Names
  are derived from the workflow at the given ref: the job key or its literal `name`, and for a
  matrix job one name per leg, `key (v1, v2)` in axis order. The derivation supports list axes
  plus `include` entries that only add keys to existing legs (the shapes in use today). An
  `exclude`, an `include` that adds a leg, or a templated `name` exits 2 with the job named.
- Main tip: the verifier gets the `main` branch sha from the API, runs `git fetch origin main`,
  and asserts that `origin/main` equals that sha. On a mismatch it exits 2 ("stale origin/main").
  It reads `ci/required-jobs.toml` and the workflows with `git show <sha>:<path>`, never the
  working tree, and prints the sha it used.
- `verify --sha H --tier merge`: uses the registry and workflows at that main sha. For each merge workflow it takes the
  newest run with `event == pull_request` and `head_sha == H`. Every derived name must be present
  with conclusion `success` (`skipped`, `neutral`, `cancelled` and missing all fail), and the run
  must have `run_attempt == 1` unless `--allow-rerun <workflow>=<reason>` names it; the reason is
  printed so the gate log records it.
- `verify --tier nightly`: for every workflow with a `schedule` trigger at the main tip, the newest
  `schedule` run must have `head_sha` equal to the main tip, be at most 26 hours old, and have
  every job `success`. Otherwise it prints "no fresh run" or the red job and exits 1.
- Exit 0 only when everything checks. Exit 1 on a red, missing or stale item. Exit 2 on a usage or
  API error. An API error is never a pass.
- GitHub access goes through an injected `fetch`. The default reuses `gate_tree_proof`'s urllib
  call, renamed from `_api` to a public `github_fetch` so both scripts share it. Tests run offline
  on fakes, the same shape as `gate_tree_proof.decide`.

## 5. Failure modes

| # | Failure | Handled by |
|---|---|---|
| F1 | A required job is skipped by an `if` and GitHub counts it as success | R2: no `if` on merge jobs; verifier fails `skipped` |
| F2 | A path filter means a lane silently never runs, or a required check never reports | T2 |
| F3 | A lane is restored with no trigger, or a marker loses its only lane | T1, M1 to M3 |
| F4 | A broad expression (`perf or not perf`) is counted as a lane for an opt-in marker | M2 dedicated rule |
| F5 | A narrow-path job is counted as the lane for a default marker | M1 whole-suite rule |
| F6 | An unparseable or unusual `-m` is treated as harmless | M4 fails closed |
| F7 | `gates.sh` and the hosted full suite drift to different marker sets | M5 |
| F8 | A scheduled or PR-triggered self-hosted job makes `gate-vm-watch` start VMs | T5 |
| F9 | A shared `pages` concurrency group cancels pending PR doc builds | moved to `deploy`; T4 |
| F10 | Superseded PR runs fill the 20-job hosted limit and delay `fast` and `tree-proof` | T4 cancel-in-progress; measured in the first week (section 9) |
| F11 | The determinism harness passes by skipping (empty golden) | `junit_ran.py` refuses skips and zero passed |
| F12 | A hung hosted job holds a concurrency slot for 6 hours | T3 timeouts on every job |
| F13 | The `gates.sh` marker change makes a stored full-suite baseline refuse the compare (collected count drops by the 3 harness tests) | slice 1 T3 is a `gate-selfhosted.yml` dispatch with `mode=full` (no stored baseline); the orchestrator refreshes the `decoy-vm-t3` stored baseline after merge |
| F14 | A branch deletes a job from its own required list | verifier reads `origin/main`; with Q1, GitHub protection lives outside the repo |
| F15 | A flaky lane is re-run until green | verifier requires `run_attempt == 1` or a named, logged `--allow-rerun` |

## 10. Design notes

New structure: one sentry helper and two small scripts.

- `tests/sentry/tooling/_ci_lanes.py` is the one walk from workflows to lanes and the one workflow
  trigger decoder (`workflow_events`; the `test_ci_config.py` copy is removed). It owns job events,
  pytest invocations and expression evaluation. Its sources are the real files:
  `.github/workflows/*.yml`, `pyproject.toml` markers and `addopts`, `scripts/dev/gates.sh`
  `PYTEST_ARGS`, the two `ci/*.toml` files. Pure functions take parsed data, so seeded cases need no
  files on disk.
- Shell parsing stays in `ci_scan._shell_tokens` (the CI-X choke point). Nothing here is added to
  `ci_scan/`, because that directory holds only ledger-pinned shared files. The `ci_scan` row
  (`CODEMAP.md:138`) today says every new CI scan helper goes there, which the ledger forbids for
  engine-only code. CI-E2a edits that row to: "`ci_scan/` holds shared, ledger-pinned,
  repo-neutral CI scanners; engine-only CI lane policy lives in `tests/sentry/tooling/`." The
  engine policy (job events, lane rules, registries) then lives in `tests/sentry/tooling/` as the
  row says. The pytest-invocation walk is repo-neutral. When CLI L1b
  lands, it moves that walk into `tests/sentry/ci_scan/` through the `SHARED_LEDGER` procedure
  (both repos, byte-identical), and the engine imports it from there instead of keeping a copy
  (FU-7).
- JUnit counting already exists: `scripts/dev/_gates_report.py:79-95` (`_suites_of` and
  `_counts`) reads bare `testsuite` and wrapped `testsuites` roots and sums `tests`, `failures`,
  `errors` and `skipped`. CI-E2a extracts that sum into one public function in the same module,
  `junit_totals(paths) -> JunitTotals` (a frozen dataclass with `tests`, `failures`, `errors`,
  `skipped`, `passed`). `_counts` calls it and prints the same line as before. The module and its
  sibling `_gates_baseline.py` are stdlib only, so the hosted jobs can import it.
- `scripts/dev/junit_ran.py` holds only the verdict: it calls `junit_totals` and exits 0 when
  `passed > 0` and `failures`, `errors` and `skipped` are all 0. It parses no XML itself. The
  `dp-certified-gate` and `determinism` jobs both call it. So counting has one place
  (`junit_totals`) and the "ran clean" rule has one place (`junit_ran.py`).
- Slice 2: the check-name derivation lives in `scripts/dev/required_checks.py`, and the sentry
  imports it (the same pattern as `test_ci_config.py` importing `gate_tree_proof`), so contexts,
  verifier and sentry share one rule.
- Principles: one place per fact (the marker expression is checked for agreement rather than
  copied a third time; the nightly tier is derived); single-purpose functions; no flag arguments
  that switch behavior (the verifier's tiers are subcommands with separate functions).
