## 1. Problem and evidence (reproduced from the lock)

`_build_cdf` (`src/decoy_engine/execution/_strategies/_categorical.py:69-119`) computes `total = sum(weights)` (`:75`), a plain running sum (`:92`), then `int(running / total * _WEIGHTED_CDF_RES)` (`:94`). CPython 3.12 made builtin `sum()` of floats compensated (Neumaier summation; CPython gh-100425, cited from memory, behaviour confirmed by the probe below), so `total` differs from 3.10/3.11 for many weight vectors and the truncated thresholds move by one slot. Every weighted-categorical route consumes this one list (section 3.2), so the band boundaries, and therefore masked output, depend on the interpreter.

Probe, run from `uv.lock` (`uv sync --frozen --extra dev --python 3.X` into three scratch venvs; CPython 3.10.20, 3.11.18, 3.12.3; same checkout `545d913`):


## 2. Invariants as properties

- P1 (interpreter independence). For every weight vector `w`, `_build_cdf(w)` returns the same tuple, or raises the same registered code with the same message text, on every CPython in `requires-python` (`pyproject.toml:13`, `>=3.10,<3.13`), on any numpy version, and on any platform. After rule N1 converts each weight to its exact rational value, the builder and every message it formats use integer operations only: no true division, no float literal, no `float()`, no `sum()`, no `math` call, no `repr` (T12 enforces this over the AST).
- P2 (exactness). `cdf[i] = floor((2 * C_i * RES + T) / (2 * T))` where `C_i` and `T` are the exact rational prefix sum and total of the weights (round half up to the nearest slot). Hence `cdf[-1] == RES` by construction, `cdf` is non-decreasing, a zero weight has zero width, and every band width is within one slot of `w_i / T * RES`.
- P2a (representable total). A vector whose exact total exceeds the largest finite double (`sys.float_info.max`), or that holds a NaN or an infinity, is rejected with the registered `categorical_weights_nonfinite`. This keeps today's decline of overflowing sums (pinned by `tests/native/test_chunked_nondet_categorical_admission.py:122` and the `weight-overflow` case at `tests/parity/test_phase_d_d1b2_categorical_disposition.py:150`) while making the test exact instead of a float overflow.
- P3 (resolution rule is exact and position-free). A positive weight is rejected with `categorical_weight_below_resolution` if and only if `w_i * RES < T` exactly. Every accepted positive weight has width at least one slot.
- P4 (one builder). Every route that maps a bucket to a weighted category reads a CDF produced by `_build_cdf` and by nothing else.
- P5 (guard equals consumer). Every admission or sampler guard that decides on a weight total computes the same quantity, in the same order, as the consumer that draws with it.
- P6 (error precedence is total and interpreter-free). The code raised for an invalid vector depends only on the vector. At the route layer the shape check (`categorical_weights_shape`) runs first, as today on every route (`_categorical.py:165`, `_mask_group_b.py:335`, `_categorical_prepared.py:66`). Inside the builder, each pass completes over the whole vector before the next starts: (1) not numeric (rule N1), (2) a NaN or infinite element (`categorical_weights_nonfinite`), (3) a negative element, (4) the exact total: above the largest double is `categorical_weights_nonfinite`, zero is `categorical_weights_nonpositive`, (5) below resolution. Each pass reports the lowest failing index.
- P7 (validation precedes memoisation). Every call runs N1 and the P6 passes on its own input before any memo is consulted; the memo key is a tuple of exact Python `int`s (rule K1), so two inputs share an entry only when their exact scaled weights are equal integers.
- P8 (admission agrees with execution). For every vector and every admission entry, admission declines with exactly `{code}:{name}` if and only if the Python route raises `StrategyError(code)` for the same config, and admits if and only if the Python route builds; an admitted column carries the tuple the Python route would build. No admission entry runs a weight check of its own.

## 4. Method, source pattern, and output consequence

Method. Every finite IEEE 754 binary64 value is a dyadic rational `n / 2**k`, available exactly through `float.as_integer_ratio()` (IEEE 754-2019 section 3.3; Python `float.as_integer_ratio` documentation). Scale every weight to the largest power-of-two denominator in the vector, so each weight is an exact Python `int` and the prefix sums and total are exact integer sums, independent of order and interpreter. Thresholds are `(2 * C_i * RES + T) // (2 * T)`: integer division, round half up. This is the integer-frequency normalisation used where a CDF must be bit-identical across encoder and decoder, such as range coding and asymmetric numeral systems (Witten, Neal, Cleary 1987, "Arithmetic coding for data compression", CACM 30(6); Duda 2013, arXiv:1311.2540), with the exact input taken from the float rather than pre-quantised. `fractions.Fraction` gives the same values and is the independent test oracle (T1), not the implementation, because per-step `gcd` normalisation is slower.

Rule N1 (weight normalisation; closed by exact type, revised in revision 4 for Codex finding 4). The builder takes the raw config values; the three route-entry `float(w)` conversions (section 3.1) are deleted. One helper, `_exact_ratio(w, i) -> tuple[int, int]` in `_categorical.py`, turns each weight into an exact `(numerator, 2**k)` pair. It decides on `type(w)` only, never `isinstance`, so no subclass and no type registered with `numbers.Integral` or `numbers.Real` gets in:

1. `type(w) in _EXACT_INT_TYPES`, where `_EXACT_INT_TYPES = frozenset({int} | {numpy.dtype(c).type for c in "bBhHiIlLqQ"})`: the pair is `(int(w), 1)`. The set is built from the C integer type codes, not from the names `numpy.int8` to `numpy.uint64`, because the named set is platform-dependent: on Linux with numpy 2.5.0 the codes give ten distinct types and `numpy.longlong is numpy.int64` is false (probed from the lock, 3.12.3), while on Windows `numpy.int64` is `numpy.longlong`, so a named list would accept `numpy.longlong(1)` on one platform and reject it on the other (a P1 break). `bool` and `numpy.bool_` are not in the set (their exact types are `bool` and `numpy.bool_`), so they fall to step 3. `int(w)` on these exact types is exact for every value; `2**53 + 1` stays `2**53 + 1`.
2. `type(w) in _EXACT_FLOAT_TYPES = frozenset({float, numpy.float16, numpy.float32, numpy.float64})`: `x = float(w)` (exact: a widening for `float16` and `float32`, the identity for the other two), then `math.isfinite(x)` or `categorical_weights_nonfinite`, then `float.as_integer_ratio(x)`, called on the built-in type, never `w.as_integer_ratio()`. The ratio of a finite binary64 value always has a power-of-two denominator (probed: `float.as_integer_ratio(float(numpy.float16(0.1))) == (819, 8192)`, `(-0.0)` gives `(0, 1)`).
3. Anything else is `categorical_weights_not_numeric` with the index only (rule M2): `bool`, `numpy.bool_`, `str`, `None`, `decimal.Decimal`, `fractions.Fraction` (`Fraction(1, 3).as_integer_ratio() == (1, 3)`, probed), `numpy.longdouble` (platform-dependent precision), complex values, any subclass of an allowed type (probed: a `float` subclass whose `as_integer_ratio` returns `(1, 3)` reports `(1, 3)` through the method and `(1, 2)` through `float.as_integer_ratio(float(x))`, and `type(x) in {float}` is false), and any class registered as `numbers.Integral` (probed: `numbers.Integral.register(C)` makes `isinstance(C(), numbers.Integral)` true).

Both allowlists are module constants by name in the T9d allowlist and `frozenset`s, so they cannot be extended at runtime. T12n pins the helper's shape (section 5.1): it calls `type`, `int`, `float`, `float.as_integer_ratio` and `math.isfinite` only, and never `isinstance`, `issubclass` or a method of `w`.

The common denominator is the largest `2**k` among the pairs, so scaling is a shift and every scaled weight is an exact `int`.

Rule M1 (below-resolution bound). The exact minimum admissible weight is `T / RES` as a rational `n / d` (`n` the scaled integer total, `d` the common denominator times `RES`). The message prints the smallest decimal with three significant digits that is not below `n / d`, computed with integer arithmetic only: the decimal exponent `e` is found by integer comparison of `n * 10**max(0, -e)` against `d * 10**max(0, e)` (no logarithm), the mantissa is `m = ceil(n * 10**(2 - e) / d)` by integer ceiling division (`-(-num // den)`), with `m == 1000` carried to `m = 100, e + 1`, and the text is `f"{m // 100:d}.{m % 100:02d}e{e:+03d}"`. Known answers from the lock (revision 2 probe on 3.10.20, 3.11.18 and 3.12.3): `[1.0, 1e-20, 1.0]` prints `2.01e-06` (today `2.00e-06`, a float path), `[1e-9, 1]` prints `1.01e-06` (today `1.00e-06`), `[1.0, 2.0e-6, 1.0]` prints `2.01e-06`. Ceiling, not rounding, so that the printed bound always satisfies P3: today's `2.00e-06` for a total of `2 + 1e-20` is itself below the resolution it recommends.

Rule M2 (canonical message text; Codex finding 5). A builder message never renders a weight. Its only replacement fields are Python `int`s formatted with an integer spec (`d`, `02d`, `+03d`): the index `i` from `enumerate`, `_WEIGHTED_CDF_RES`, and the M1 parts. So the text is a function of the error family, the index and (for below-resolution) the exact total; it cannot vary with the input type, the numpy version or the interpreter. Rule A1 (admission reason; Codex finding 1). Every admission entry (E4 to E10) runs no weight check of its own; E9 and E10 carry no reason string and return E5's verdict as an artifact or a bool. It calls the builder through `prepare_categorical`, and maps `StrategyError` to `f"{exc.code}:{name}"`. Today's reasons that already match (`not_numeric`, `negative`, `shape`) keep their text; `categorical_weights_unbuildable_cdf` is deleted. Rule K1 (memo key; Slice 2a). The memoised function is the threshold loop only, `_thresholds(scaled: tuple[int, ...]) -> tuple[int, ...]`, keyed on the tuple of exact scaled integer weights that N1 and the P6 pass produce. N1 and P6 run on every call before the memo is consulted (P7). An all-`int` key cannot collide across types: `(1, 0) == (1.0, -0.0) == (True, False)` with equal hashes (probed on all three interpreters), but after N1 the first two are the same validated vector by value and the third never reaches the memo. The memo stores tuples (immutable).

Rule R1 (memo ownership; Codex finding 6, decided). There is no process-wide cache: no `functools.lru_cache`, `functools.cache` or module-level memo anywhere on the CDF path. A `CdfMemo` (a small class in `_categorical.py` holding a `dict` from K1 key to threshold tuple, no eviction) is owned by a run:

- `StrategyContext.cdf_memo` (`field(default_factory=CdfMemo)`), so the in-memory run and the sequential run (one `StrategyContext` per run, `_pandas_adapter.py:236`, `_sequential.py:326`) each build a weight vector once.
- The chunked oracle creates one `CdfMemo` per chunked run and passes it to every per-chunk `adapter.run(..., cdf_memo=...)`, exactly as it already passes `code_set_records` (`_chunked_oracle.py:439`, seeded at `_pandas_adapter.py:251`); `PandasExecutionAdapter.run` uses it when given, else a fresh one.
- The out-of-core `TableCategoricalPlan` (one per table per run, built by `decide_table` from `_hash_run.py:358-366`) owns one `CdfMemo`; `mask_column` (`out_of_core/_mask.py:455-468`) forwards it to `categorical_array`, which reads it instead of building per batch at `_mask_group_b.py:387`.
- `prepare_chunked_categoricals`, `decide_table` and the physical shadow binding already build once per run and need no memo.

Structural form of R1 (Codex finding 3, revision 4). Revision 3 forbade names (`lru_cache`, `cache`, variables containing `cdf` or `memo`); a module dict named `_CACHE` passed. The rule is now about structure, in the builder modules `BUILDER_MODULES` = `execution/_strategies/_categorical.py`, `execution/native/_categorical_prepared.py`, `execution/native/_categorical_positional.py`, `execution/native/_categorical_ext.py`, `execution/out_of_core/_categorical_native.py`, `execution/out_of_core/_mask_group_b.py` (the modules that compute, convert, hold or search a threshold tuple):

- R1a. Every module-level `Assign` or `AnnAssign` binds a name in the per-module allowlist `FROZEN_MODULE_NAMES` (at `545d913`: `_WEIGHTED_CDF_RES`, `_POSITION_DOMAIN_CODE`; `GROUP_B_STRATEGIES`; `REASON_UNAVAILABLE`, `REASON_NOT_STRING`, `_NO_BACKEND_RAN`, `_REASON_NO_NATIVE_CALLS`; `__all__` in each module that has one; slice 1a adds `_EXACT_INT_TYPES`, `_EXACT_FLOAT_TYPES`), and its value is a `Constant`, a `Name` or `Attribute` reference, a `Tuple` of those, a call to `frozenset` or `tuple`, or (for `__all__` only) a `List` of `str` constants. A module-level `AugAssign` is rejected. So `_CACHE: dict = {}`, `_CACHE = dict()`, `_CACHE = defaultdict(...)` and `_STORE = []` are rejected by structure, whatever the name.
- R1b. No `global` or `nonlocal` statement in any function of these modules.
- R1c. No function default that is not a `Constant`, `Name` or `Attribute` (rejects `def _thresholds(key, _seen={})`).
- R1d. No class-body assignment other than a `Constant`, `Name`, `Attribute`, a `Tuple` of those, `__slots__`, or a dataclass `field(default_factory=...)` call without `default=` (a per-instance value, which slice 2a uses for `TableCategoricalPlan.memo`); rejects `class CdfMemo: _shared = {}`, a dict shared by every instance.
- R1e. Decorators only from the closed set `dataclass` (any arguments), `staticmethod`, `classmethod`, `property`, `overload`: `functools.lru_cache`, `functools.cache`, `cached_property` and any custom memoiser are rejected by not being in the set, not by name.
- R1f. No assignment to an attribute of a module-level function, class or imported module (rejects `_thresholds.store = {}` and `sys.modules[__name__].x = ...`).

The modules' own state at `545d913` passes R1a to R1f (checked by AST for revision 4: the module-level assignments are the names listed in R1a; the only decorators are `dataclass` at `_categorical_prepared.py:26` and `_categorical_native.py:49,84,119` and `property` at `_categorical_native.py:101,136`; no `global`, no non-constant default, no non-constant class attribute). The structural rule is the first line; T9e is a module-agnostic backstop that does not depend on the rule's completeness: no allocation made by code in a builder module survives the end of a run.

Memory ceiling: a run holds at most one tuple per distinct weighted-categorical weight vector in its own plan, each of `len(weights)` ints (about 36 MB at the 999,000-category ceiling, the same order as the plan's own list of 999,000 floats, which the run already holds); everything is released when the run returns, so retention across jobs is zero by construction. Alternative rejected: a bounded process-wide cache, because any bound above zero still retains one job's profile-derived CDF into the next job of a long-lived worker.

Rejected alternatives for the arithmetic:

- `math.fsum` for the total (Shewchuk 1997, correctly rounded): interpreter-independent, but the division, multiplication and truncation stay in floating point, the guard stays phase-dependent, and `[0.6, 0.3, 0.1]` becomes `899999` on every interpreter (the audit checked this). It fixes P1 only.

## 14. Architecture view (third remediation)

Is this the smallest design that closes the defect? No. The defect is P1: `_build_cdf` returns different thresholds on different interpreters. The smallest closure is slice 1r plus 1a (exact builder, N1, M1, M2, the two codes) with T1, T2, T2b, T2c, T3m, T12 and T13, plus 1c and the T3 and T16 parts of 4a, because a builder change that one route does not see is not a fix (P4, P8). Everything else is either a second defect found on the way or machinery to offset a cost the fix introduced. What I would cut, in order of value:

1. The memo (slices 2a, 2b, 2c; rules K1, R1; T9 to T9e; most of T10). It exists only to pay back the 5x build cost on routes that rebuild per batch or per chunk, and it produced every class 3 finding in three rounds. The same saving needs no cache: `decide_table` already builds `PreparedCategorical.cdf` once per column per table per run (E6), so `categorical_array` can take that tuple from the table plan instead of rebuilding per batch, and the chunked oracle can build once per chunked run and pass the tuple, as it already passes `code_set_records`. No dict, no key, no lifetime, no structural sentry; T9's call counts and T10b stay as the proof of one build per run. I recommend revision 5 makes this cut if the gate agrees; it removes three slices and the R1 rule set.
2. Slice 3 (window admission left fold, T6). A real P5 defect in a different sampler, found while enumerating sum sites; it shares no code with the CDF. Its own plan.
3. Slice 1d (route-layer messages, T11b). A real class 1 defect found in revision 4's re-read; its own S plan is as good, provided it is not dropped.
4. Slice 4b and the T4 workflow job. GitHub Actions is off for this repo, so the workflow edits and their sentries (T4 sentry, T15) prove a configuration nobody runs; the evidence is the local command in every case. Keep T14 as a test in the native suite; defer the workflow edits until Actions is on.

Kept and why: rule A1 and T3 over E1 to E10 (the route-dependent precedence is itself a defect the exact builder exposes); T16 at its computed 50-site inventory (two rounds missed a route by hand); the contract digest test (cheap, closes a class 10 gap permanently). With the four cuts the plan is five slices (1r, 1a, 1c, 1b, 4a) instead of eleven.
