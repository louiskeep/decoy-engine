## 1. Problem and evidence (reproduced from the lock)

`_build_cdf` (`src/decoy_engine/execution/_strategies/_categorical.py:69-119`) computes `total = sum(weights)` (`:75`), a plain running sum (`:92`), then `int(running / total * _WEIGHTED_CDF_RES)` (`:94`). CPython 3.12 made builtin `sum()` of floats compensated (Neumaier summation; CPython gh-100425, cited from memory, behaviour confirmed by the probe below), so `total` differs from 3.10/3.11 for many weight vectors and the truncated thresholds move by one slot. Every weighted-categorical route consumes this one list (section 3.2), so the band boundaries, and therefore masked output, depend on the interpreter.

Probe, run from `uv.lock` (`uv sync --frozen --extra dev --python 3.X` into three scratch venvs; CPython 3.10.20, 3.11.18, 3.12.3; same checkout `545d913`):

```

3.11.18 sum= 0.9999999999999999 cdf= [600000, 900000, 1000000]
3.12.3  sum= 1.0                cdf= [600000, 899999, 1000000]
```

## 2. Invariants as properties

- P1 (interpreter independence). For every weight vector `w`, `_build_cdf(w)` returns the same tuple, or raises the same registered code with the same message text, on every CPython in `requires-python` (`pyproject.toml:13`, `>=3.10,<3.13`) and on any platform. After rule N1 converts each weight to its exact rational value, the builder and every message it formats use integer operations only: no true division, no float literal, no `float()`, no `sum()`, no `math` call (T12 enforces this over the AST).
- P2 (exactness). `cdf[i] = floor((2 * C_i * RES + T) / (2 * T))` where `C_i` and `T` are the exact rational prefix sum and total of the weights (round half up to the nearest slot). Hence `cdf[-1] == RES` by construction, `cdf` is non-decreasing, a zero weight has zero width, and every band width is within one slot of `w_i / T * RES`.
- P2a (representable total). A vector whose exact total exceeds the largest finite double (`sys.float_info.max`), or that holds a NaN or an infinity, is rejected with the registered `categorical_weights_nonfinite`. This keeps today's decline of overflowing sums (pinned by `tests/native/test_chunked_nondet_categorical_admission.py:122` and the `weight-overflow` case at `tests/parity/test_phase_d_d1b2_categorical_disposition.py:150`) while making the test exact instead of a float overflow.
- P3 (resolution rule is exact and position-free). A positive weight is rejected with `categorical_weight_below_resolution` if and only if `w_i * RES < T` exactly. Every accepted positive weight has width at least one slot.
- P4 (one builder). Every route that maps a bucket to a weighted category reads a CDF produced by `_build_cdf` and by nothing else.
- P5 (guard equals consumer). Every admission or sampler guard that decides on a weight total computes the same quantity, in the same order, as the consumer that draws with it.
- P6 (error precedence is total and interpreter-free). The code raised for an invalid vector depends only on the vector: not numeric (rule N1), then non-finite, then negative, then non-positive total, then below-resolution, checked in that order over the whole vector, each check completing over every element before the next starts.
- P7 (validation precedes memoisation). Every call runs N1 and the P6 pass on its own input before any cache is consulted; the cache key is a tuple of exact Python `int`s (rule K1), so two inputs share an entry only when their exact scaled weights are equal integers.

## 4. Method, source pattern, and output consequence

Method. Every finite IEEE 754 binary64 value is a dyadic rational `n / 2**k`, available exactly through `float.as_integer_ratio()` (IEEE 754-2019 section 3.3; Python `float.as_integer_ratio` documentation). Scale every weight to the largest power-of-two denominator in the vector, so each weight is an exact Python `int` and the prefix sums and total are exact integer sums, independent of order and interpreter. Thresholds are `(2 * C_i * RES + T) // (2 * T)`: integer division, round half up. This is the integer-frequency normalisation used where a CDF must be bit-identical across encoder and decoder, such as range coding and asymmetric numeral systems (Witten, Neal, Cleary 1987, "Arithmetic coding for data compression", CACM 30(6); Duda 2013, arXiv:1311.2540), with the exact input taken from the float rather than pre-quantised. `fractions.Fraction` gives the same values and is the independent test oracle (section 5, T1), not the implementation, because per-step `gcd` normalisation is slower.

Rule N1 (weight normalisation, finding 2; source pattern: the PEP 3141 numeric tower, `numbers.Integral` and `numbers.Real`, which NumPy registers its scalar types with). The builder takes the raw config values; the three route-entry `float(w)` conversions (section 3.1) are deleted. Each weight `w` becomes an exact `(numerator, denominator)` pair:

1. `bool` and `numpy.bool_` are rejected with `categorical_weights_not_numeric` (checked first: `bool` is an `Integral`). Today a `bool` is a silent `1.0`/`0.0` on the Python routes and a native decline (`_categorical_prepared.py:68`); the chunked admission test `weights_bool` (`tests/native/test_chunked_nondet_categorical_admission.py:116`) already expects the decline and is unchanged.
2. Any other `numbers.Integral` (`int`, `numpy.integer`) becomes `(int(w), 1)`. `int()` is exact for integers of any size; `2**53 + 1` stays `2**53 + 1`. (`numpy.int64` has no `as_integer_ratio`, probed from the lock on 3.10.20, 3.11.18 and 3.12.3 with NumPy 2.2.6, 2.4.6 and 2.5.0, so Integral values never go through it.)
3. Any other `numbers.Real` (`float`, `numpy.floating`, `fractions.Fraction`): NaN and infinity are rejected with `categorical_weights_nonfinite`; otherwise `w.as_integer_ratio()`, which is exact for every finite value (probed: `float`, `numpy.float64`, `numpy.float32` on all three interpreters; `(-0.0).as_integer_ratio() == (0, 1)`, so a signed zero is the exact zero and is accepted as a zero-width band, as today). `int.as_integer_ratio` and `bool.as_integer_ratio` exist on 3.10 to 3.12 (probed) but are not used: rule 1 and rule 2 run first.
4. Anything else (`str`, `None`, `decimal.Decimal`, an arbitrary object) is rejected with `categorical_weights_not_numeric`. The message carries the index only, never the object's `repr` or type name (class 1: a hostile `__repr__` or class name is value-bearing).

The common denominator is the largest `2**k` among the pairs (every denominator from `as_integer_ratio` is a power of two; an Integral has denominator 1), so scaling is a shift and every scaled weight is an exact `int`.

Rule M1 (below-resolution message, finding 1). The exact minimum admissible weight is `T / RES` as a rational `n / d` (`n` the scaled integer total, `d` the common denominator times `RES`). The message prints the smallest decimal with three significant digits that is not below `n / d`, computed with integer arithmetic only: the decimal exponent `e` is found by integer comparison of `n * 10**max(0, -e)` against `d * 10**max(0, e)` (no logarithm), the mantissa is `m = ceil(n * 10**(2 - e) / d)` by integer ceiling division (`-(-num // den)`), with `m == 1000` carried to `m = 100, e + 1`, and the text is `f"{m // 100}.{m % 100:02d}e{e:+03d}"`. Known answers from the lock, identical on 3.10.20, 3.11.18 and 3.12.3: `[1.0, 1e-20, 1.0]` prints `2.01e-06` (today `2.00e-06`, a float path), `[1e-9, 1]` prints `1.01e-06` (today `1.00e-06`), `[1.0, 2.0e-6, 1.0]` prints `2.01e-06`. Ceiling, not rounding, so that the printed bound always satisfies P3: today's `2.00e-06` for a total of `2 + 1e-20` is itself below the resolution it recommends. The weight itself is printed as the `repr` of the Python scalar the builder normalised (`repr(float)` is the shortest round-trip form since CPython 3.1 and is platform-independent; an Integral prints as `repr(int(w))`), never the raw object.

Rule K1 (memo key, finding 2; Slice 2). The memoised function is the threshold loop only, `_thresholds(scaled: tuple[int, ...]) -> tuple[int, ...]`, keyed on the tuple of exact scaled integer weights that N1 and the P6 pass produce. N1 and P6 run on every call before the cache is consulted (P7). An all-`int` key cannot collide across types: `(1, 0) == (1.0, -0.0) == (True, False)` with equal hashes (probed on all three interpreters: a cache keyed on the raw tuple serves `(True, False)` from the `(1, 0)` entry and the function never sees the `bool`), but after N1 the first two are the same validated vector by value and the third never reaches the cache. The cache stores tuples (immutable), `maxsize=8`.

Rejected alternatives:

- `math.fsum` for the total (Shewchuk 1997, correctly rounded): interpreter-independent, but the division, multiplication and truncation stay in floating point, the guard stays phase-dependent, and `[0.6, 0.3, 0.1]` becomes `899999` on every interpreter (the audit checked this). It fixes P1 only.
- Pin the reduction order (an explicit left fold reproducing the 3.10 total): zero output change on 3.10, but it keeps float truncation and the phase-dependent guard, and any later `sum()` or vectorised refactor silently reintroduces the drift. Kept as Q1's fallback.
- Exact arithmetic with floor (truncation): the `[0.6, 0.3, 0.1]` thresholds become `[599999, 899999]` because binary `0.6` is below `0.6`, and `[1.0, 1e-20, 1.0]` passes the phase guard; two existing tests go red for no gain.

6. NaN or infinity escapes as a bare error on the in-memory route: T3.
7. Error precedence still depends on the total for mixed-sign input: T3 row 3.
