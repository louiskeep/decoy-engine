# int+null+hash supported consistently across all routes

## 0. Why

Hashing an integer column that contains a null is REJECTED on every route today (`null_bearing_int_unsupported`, from `reject_null_bearing_int` keyed on `_INT_NULL_REJECTED_STRATEGIES = {truncate, hash, categorical}`). Cam's decision (2026-10-16): hashing is deterministic, a null stays null, so it must be SUPPORTED - and it must behave the SAME whether the job is small (full-frame) or large (out-of-core), not succeed on one route and reject on another.

The real blocker is substrate-specific, not semantic: the pandas full-frame path converts Arrow `int64+null` to pandas `float64+NaN` (pandas cannot hold a null-bearing integer natively), so the hash kernel then sees `1.0` and raises `float_canonicalization_unsupported` (a separate PO-locked hard error on floats). The Arrow/native fast paths keep `int64+null` and hash it correctly against the FROZEN integer encoding (`_encode_int`), so the native result is already right; the pandas path is the one that loses the integer.

This slice makes the pandas path feed INTEGER values into the (unchanged, frozen) canonicalization, so hash of int+null produces byte-identical output on every route. It does NOT touch the determinism envelope (`_canonicalize_source` / `_encode_int` are unchanged; same frozen bytes). Truncate and categorical stay rejected (Cam's call was hash-specific; the original truncate fail-open closure on OOC is preserved).

## 3. Risks (reproduce, do not smooth)

- **Byte-parity + uint64 losslessness (Codex HIGH-1).** The pandas hash (fed the snapshot's TYPED Arrow array) MUST equal the native/OOC output byte-for-byte (same `_encode_int`). The uint64 path must NOT go through inferred conversion (`OverflowError`). Pin cross-route parity on the D1a config + an int-width sweep: int8/16/32/64 + uint8/16/32/64, each with interior values, type min AND max (incl. `2**63`, `2**64-1`), interleaved nulls; full-frame == sequential(both companion states) == native, exact tokens + null positions, per width.
- **companion-present vs companion-absent sequential (Codex, confirmed).** `seq.hash_column` reconstructs Arrow via `_pinned_array(type=pinned_type)`; fed the exact integers it preserves the width. Pin companion-present == companion-absent == native across all widths incl. uint64 max.
- **Passthrough / faker / sibling isolation.** Only the hash handler reads the snapshot; the frame is never converted, so passthrough int+null still emits float64, faker exact-int registration + output unchanged, and a sibling column's values are unchanged. ## 3a. Explicit boundary: GATED (`when:`) hash on int stays rejected (out of scope)

Gated hash on an integer column fails serialization TODAY even without nulls (probed: partial-match `when:` hash on a non-null int column -> `pa.Table.from_pandas` ArrowTypeError on the mixed string+int object column). That is a PRE-EXISTING limitation unrelated to this slice and unrelated to Cam's decision (he asked for hashing number-columns-with-blanks, the ungated case). This slice therefore keeps GATED int+null+hash REJECTED (part A) - matching the status quo and avoiding a worse late failure - and records the broader "gated hash on any integer column fails serialization" as a V2/backlog bug (surface to Cam, do NOT fix here). No mixed-type sink handling is designed or attempted.
