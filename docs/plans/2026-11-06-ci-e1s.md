## 1. Guarantee and non-goals

The change promises:

1. `uv.lock` resolves no version with a known advisory: the `security.yml` audit
   (`uv export --frozen --all-extras`, then `pip-audit==2.10.1 --strict --require-hashes`) exits 0
   on each of 3.10, 3.11 and 3.12, measured on the build head on the day of the gate.
2. Only the eight vulnerable packages change version in `uv.lock` (table in section 2). No other
   locked version moves, and `pyproject.toml` does not change (no constraint raised or lowered).
3. The certified DP profile keeps its exact package set: the same 77 distribution names from
   `uv sync --frozen --extra dev --extra lint --extra vault --extra cloud` on Linux x86-64 CPython
   3.10.20. Five of its versions move (certifi, cryptography, pyasn1, urllib3, werkzeug), so
   `_CERTIFIED_STACKS` gains exactly one fingerprint. Every existing row stays.
4. A lock change that moves the certified profile without a re-pin fails the sentry step on every
   gate host (static guard), instead of turning the `dp_certified` tests into silent skips.
5. The `security.yml` audit guard refuses every input-narrowing or result-hiding form the owner
   listed and the ordinary spellings in AT-8 to AT-12: the audit starts exactly
   `uvx --python "$PY" pip-audit==<exact version>`; the export starts exactly `uv export`; accepted
   options after those prefixes are allowlisted; a dry run, a fix run, an export that drops extras
   or groups, an audited file that is not the exported file, a custom shell or
   `defaults.run.shell`, `needs` on the audit job, and workflow/job/step `env` other than the audit
   step's `PY` are refused. Each listed shape is a seeded red case. Deliberate indirection through
   `$GITHUB_ENV`, `$GITHUB_PATH` or a tool config file is V2-LOG, not part of this guarantee.
6. The certified row's CPython and the `dps-dependency-matrix.yml` certified leg both equal
   `scripts/dev/lock_version.sh --python`.

Non-goals (a finding here is a follow-up, not a blocker):

- The `decoy` CLI pristine runtime profile (CLI `requirements-certified.txt`). It pins certifi
  2026.7.22, cryptography 49.0.0, pyasn1 0.6.4 and urllib3 2.7.0, which carry advisories, but it is
  re-pinned and verified in the CLI repo (its rows in `_CERTIFIED_STACKS` stay). FU-1, Q4.
- New `_CERTIFIED_STACKS` rows for 3.11 or 3.12. The dps matrix prints them; certifying them is a
  separate decision (FU-5).
- Win32-only pins (colorama, tzdata) in the audit: a Linux runner never evaluates them (CI-E1 named
  limit). FU-3.
- Automatic triggers for `security.yml` (manual dispatch since X0a; CI-E2 restores triggers).
- An engine release in P1 or P2. The engine version stays 0.18.0. FU-1's paired CLI slice requires
  a later engine release before CLI users can install the new CLI certified row.
- Dennis CI-E1 low 4 (`bootstrap.sh:16` can pass an empty `--python`). It is not on the owner list.
  FU-2.

## 3. Established solutions

Searches run: uv's `uv lock --upgrade-package` (a `<package>==<version>` argument moves one package
and keeps every other pin) and `uv export --help` (0.11.19); pip-audit 2.10.1 `--help`; upstream
changelogs for the eight packages (cryptography `CHANGELOG.rst`, setuptools `NEWS.rst`, urllib3
`CHANGES.rst`, soupsieve, werkzeug, anyio, pyasn1), fetched on the VM; how Dependabot and Renovate
shape security updates; in-repo: the `dp_provenance.py` re-pin notes, `test_dp_prior_release_rows.py`,
`ci.yml` `dp-certified-gate`, `dps-dependency-matrix.yml`, `licenses_write.sh`, the CI-E1 scanner.

- Targeted lock upgrade. `uv lock --upgrade-package pkg==ver` is uv's documented targeted upgrade
  (the same model as `pip-compile --upgrade-package`). Dependabot and Renovate security updates move
  the vulnerable package to the lowest fixed version and touch nothing else. Followed.
- Re-pin. The repo's own procedure (`dp_provenance.py:240-330`): fresh `uv sync --frozen` with the
  four extras on 3.10.20, `compute_lock_fingerprint(installed_distribution_set())`, add the literal,
  keep released rows, record the delta. Followed.
- Audit guard. An allowlist of accepted options, not a denylist (OWASP input-validation guidance
  prefers allowlists; the CI-E1 scanner already uses exact allowlists for write scopes and the Mac
  exemption). Followed for the pip-audit and the `uv export` options.
- Lock-to-row tie. `uv export --frozen` with the profile extras gives the profile's pins with PEP
  508 markers; `packaging.markers.Marker.evaluate(environment)` selects them for Linux x86-64
  CPython 3.10.20. Both are established and already locked. Followed; no resolver is written.

Custom code left: the option allowlists and the path binding in the existing scanner (about 70
lines) and one static guard test (about 60 lines). No maintained tool checks a GitHub workflow's
audit step for narrowed input.

## 4. Design notes

- **Lowest fixed version, not latest (Q1).** Each package moves to the first release that clears
  every listed advisory. It is the smallest change to a frozen proof stack, keeps soupsieve on 2.x
  with no marker fork, and is what Dependabot proposes. "Pin forward, never back": every move is
  upward and none is reverted.
- **One lock, one row, one commit.** The `uv.lock` change, the new `_CERTIFIED_STACKS` literal, the
  rewritten comment and the regenerated `NOTICE` land in one commit, so no commit on the branch has
  a lock whose profile is uncertified.
- **Add the row, retire nothing (Q2).** `b9b42047...` joins the 3.10.20 set beside `31ecf945...`
  (0.18.0), `5a76ea92...` (0.17.0) and the two CLI rows. The comment above the literal records: 77
  dists, same names, the five version moves, and that putting those five back reproduces
  `31ecf945...`. The file stays at 605 lines: the existing re-pin history comment is condensed by
  the lines the new literal and its note add (the history is in git and in this plan).
- **Static lock-to-row guard (Q3).** A new sentry test computes the profile fingerprint from
  `uv.lock` without installing: `uv export --frozen --no-emit-project --no-hashes --no-header
  --extra dev --extra lint --extra vault --extra cloud`; keep each requirement whose marker
  evaluates true against an explicit target dictionary containing every PEP 508 environment key:
  `implementation_name=cpython`, `implementation_version=<lock_version.sh --python>`, `os_name=posix`,
  `platform_machine=x86_64`, `platform_release=""`, `platform_system=Linux`,
  `platform_version=""`, `platform_python_implementation=CPython`, `python_version=3.10`,
  `python_full_version=<lock_version.sh --python>` and `sys_platform=linux`. Empty fixed values are
  intentional for the two kernel-version fields, which are not part of the certified platform;
  no value may fall through from the host. Add
  `decoy-engine==<pyproject version>`; canonicalize names with `packaging.utils.canonicalize_name`;
  hash with the public `dp_provenance.compute_lock_fingerprint`. The result must be a member of
  `_CERTIFIED_STACKS[(CERTIFIED_PLATFORM, "<py>.final")]`. It runs on the Mac gate and the VMs (uv
  is on PATH on both, and the gate's env step fails without uv); missing `uv` is an assertion
  failure with a clear message, never a skip. The hash keeps one definition. The extras list is
  read from `scripts/dev/bootstrap.sh`'s `EXTRAS` line by the same parser the guard uses. The guard
  also parses `scripts/release/release_checks.sh`, `.github/workflows/ci.yml`'s
  `dp-certified-gate`, and `.github/workflows/dps-dependency-matrix.yml` and asserts all three
  copies equal bootstrap's set.
- **Allowlists in the audit guard.** `_audit_command_findings` accepts a fixed set of pip-audit
  command prefix only when the tokens before the exact `pip-audit==<version>` token are exactly
  `uvx --python "$PY"`. After that token it accepts only `--strict`/`-S`, `--disable-pip`,
  `--require-hashes`, exactly one `-r`/`--requirement`, `-f`/`--format`, `--desc`, `--aliases`,
  `--progress-spinner`, `--timeout` and `-v`; any other option is a finding that names it. A new
  `_export_findings(cmd)` requires the first two tokens to be exactly `uv export`, with no uv global
  option between them. It applies the export allowlist to every remaining token, requires
  `--frozen`, `--all-extras`, `--no-emit-project`, `--format requirements-txt` and exactly one
  `-o`/`--output-file`, and accepts only `--no-header`, `-q`/`--quiet` and `--no-progress` besides.
  If `pyproject.toml` ever declares `[dependency-groups]`, the export must also carry `--all-groups`
  (today it declares none).
- **Bind the audited file to the exported file.** Exactly one export command and one audit command
  in the job, the export in an earlier step; the audit's `-r` value equals the export's `-o` value
  as written (after the shared parser's quote stripping); no other step's text names that value.
- **Shell, defaults, env, needs.** `audit_findings(job, workflow)` takes the workflow too.
  Findings: `shell:` on the export or audit step; any `defaults.run` key on the job or the
  workflow; `needs` on the audit job; any `env` key at workflow or job level, or on the export or
  audit step, other than `PY` on the audit step. The real `security.yml` already meets all of these,
  so neither part edits a workflow.
- **Profile Python agreement.** `test_lock_profile_lives_in_lock_version_only` asserts that the dps
  matrix `python-version` list contains the `lock_version.sh --python` value, that the corresponding
  `<value>.final` key is present in `_CERTIFIED_STACKS`, and that every certified key's Python patch
  appears in the dps matrix. It does not require that key to be the only one, so future 3.11 or 3.12
  certification can extend the manifest. The YAML literal stays because a matrix cannot call a
  script; the test ties it.
- **Certified-extras sameness.** The same profile extras predate this change in four places:
  `scripts/dev/bootstrap.sh:10`, `scripts/release/release_checks.sh:46`,
  `.github/workflows/ci.yml:245` and `.github/workflows/dps-dependency-matrix.yml:68`. P1 adds no
  fifth copy. The static guard treats bootstrap as the current reference and fails if any of the
  other three differs. FU-6 moves the four existing declarations to one shared home in a separate
  design slice; this plan does not introduce an abstraction solely to land the security bump.
- **House style.** Plain typed functions in the existing scanner, one finding string per rule, no
  flag arguments, comments that say why. No new helper module.

## 12. Pre-mortem

- cryptography 50 changes an engine crypto path. The complete inventory is FF1 AES-ECB/AES-CBC,
  token-vault Fernet, protected-quarantine Fernet, Fernet/AESGCM key validation, and paramiko's SSH
  use. The 50.0.0 changelog does not touch those APIs. The targeted FF1, quarantine, vault,
  pre-bump compat-vault, secret-provider and SFTP tests plus T3 cover them. Any FF1 drift, vault or
  quarantine read failure, key-validation regression, or connector failure stops the build. Never
  edit a golden or compat fixture to clear it.
- urllib3 2.8.0's proxy-TLS change breaks a cloud connector behind an HTTPS proxy. The engine sets
  no `proxy_ssl_context`, and the connector tests use moto with no proxy. The CHANGELOG entry tells
  operators who route S3 or GCS through an HTTPS proxy.
- setuptools 84 breaks spaCy at import (the `ner` extra). The default full suite does not install
  `ner`, so P1 runs the `ner` tests once on a VM with `--extra ner` and records the result.
- A new advisory lands before the gate. Move that package forward to its lowest clean version and
  re-run AT-1 and AT-3; the record names the new fingerprint.
- The VMs' default uv 0.13.7 rewrites the lock format, which CI's 0.11.19 would then see as a
  different lock. P1 runs `uv lock` only as `uvx --from uv==0.11.19 uv` and checks `uv lock --check`
  with it.
- The static guard disagrees with a real install (a marker the environment dict misses). AT-3 and
  AT-5 compute the fingerprint both ways on the same head; a mismatch stops the build.
- The CLI runtime rows stay on vulnerable pins. Out of scope (FU-1, Q4); the CLI has no audit job
  yet.
