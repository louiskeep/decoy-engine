## FRAME

### Problem, boundary, and root cause

The atomic half already has substantial implementation and tests. The missing half is durable knowledge of **which complete result committed**. A successful return, a directory's existence, a plan hash, and a job status cannot answer that question after the response is lost.

The reference protocol returns `None` from `commit()` at `src/decoy_engine/execution/_transactional_sink.py:81`. Its Parquet implementation stages beside the target at `:262`, then performs one `os.replace` at `:295`. A non-empty target is refused. A fresh instance cannot distinguish an identical committed result from an unrelated occupant. With no writes, `:287` creates a directory directly, so there is no complete-result marker even for an intentionally empty publication. An exception during `write_batches` closes the writer best-effort at `:220`; the sink does not latch a terminal failed state that would prohibit a later direct `commit()` on a readable but truncated prefix.

The root fix is a publication protocol with a validated, immutable descriptor and one storage-specific binding that makes it committed. Catching `ENOTEMPTY`, comparing file names, retrying the rename, or adding a post-commit manifest cannot establish this invariant.

**Pinned guarantee:** An admitted publication operation either publishes one complete validated result, reports an already-committed identical result without another data effect, or returns an explicit refusal/failure/uncertain outcome. It never makes incomplete or rejected staging releasable, and never corrupts the previous approved result. All required checks precede the publication binding. A failure after that binding cannot truthfully be reported as proof that nothing committed.

The engine owns this contract and the local reference implementation. Connectors implement the declared protocol. CLI and platform consume receipts and the descriptor resolver. This plan does not implement distributed transactions across unrelated destinations, a new database connector, cloud-provider guarantees absent from an adapter, a checkpoint engine, an encryption system, a retention daemon, or F33 signing. Those omissions must never turn into an implicit F22 success.

### Established solutions

Online searches covered Delta transaction identifiers/idempotent writes, Iceberg atomic metadata pointers, Git content addressing, and rename/fsync durability. The design follows these source patterns:

1. **Content-addressed identity:** Git derives object names from content and composes trees from object references. Use the pattern with SHA-256 over a versioned artifact inventory, rather than a path or attempt timestamp. This is not a proposal to use Git as the output store. [Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects).
2. **Read committed identity before retry:** Delta records transaction identifiers with data changes and checks committed progress before applying a repeated write. F22 similarly reads a committed descriptor and records operation identity within the same commit boundary. [Delta transaction identifiers](https://github.com/delta-io/delta/blob/master/PROTOCOL.md#transaction-identifiers).
3. **Immutable data plus atomic reference update:** Iceberg creates immutable data/metadata and switches the table metadata reference with an atomic operation. Adopt that pattern for replaceable multi-file datasets; a list of files alone is insufficient. [Iceberg specification](https://iceberg.apache.org/spec/).
4. **Local visibility and durability are distinct:** rename replaces a name atomically on supported filesystems, but cannot replace a non-empty directory with another directory. File fsync does not persist the containing directory entry. F22 therefore specifies ordered file and directory syncs and does not claim power-loss durability from `os.replace` alone. [rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html), [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html).
5. **Remote conditional publication:** S3 conditional writes and GCS generation preconditions provide provider-specific compare-and-set primitives. A qualified adapter must use the provider's supported operation at the descriptor boundary; copy-then-delete across many keys does not substitute for it. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [GCS preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions).

Reuse `hashlib`, strict JSON serialization, existing Arrow/Parquet writers, and supported filesystem primitives. Do not import Delta/Iceberg or build a distributed transaction coordinator. Custom code is limited to Decoy's descriptor schema, validation binding, typed outcomes, and adapters around these established storage operations.

### Publication descriptor: the single commit truth

Introduce **new** immutable types `PublicationRequest`, `PublicationDescriptor`, `PreparedPublication`, `CommitReceipt`, and `CommitProtocol`. Suggested home: **new** `src/decoy_engine/publication/`, with schema/codec, protocol, and local storage responsibilities separated. Exact filenames are build decisions, not existing prerequisites.

`PublicationRequest` is fixed before the first output write. It carries destination identity, caller job ID, stable operation ID, unique attempt ID, expected table/artifact inventory, validation-policy fingerprint, publication-unit choice, overwrite policy, optional expected predecessor, ownership/fencing context, and retention/backup requirements. Retry callers must preserve the operation ID and pinned execution inputs. Automatically generated IDs support one-shot calls but cannot identify an arbitrary historical operation after process loss.

The proposed persisted schema is `decoy-publication/v1`:

| Field group | Binding and validation rule |
|---|---|
| Identity | Schema version; destination identity without credentials; publication unit and protocol version; original job/operation/attempt IDs. Attempt IDs isolate staging and never define content equality. |
| Content | Sorted, unique artifact entries: logical table/artifact role, contained relative path or immutable provider object/version, byte size, SHA-256 of exact bytes, row count, and schema digest. Record zero-row tables explicitly. Count table rows separately from side-artifact records. |
| `result_id` | Domain-separated SHA-256 of the canonical content inventory. Includes artifact roles, table names, schemas, counts, sizes and digests. Excludes timestamps, attempt IDs, staging paths, destination location, operational timings, and the descriptor's own digest. Identical rows encoded into different bytes are not identical physical results in V1. The V1 contract is physical identity, not logical: any change to Parquet encoding (compression, dictionary settings, row-group size) or internal data ordering that alters an artifact's final bytes yields a different `result_id`, which is the intended behavior. |
| Validation | Expected inventory digest; actual counts and digests; pinned plan/source-snapshot references; validation-policy fingerprint; required check IDs with pass/fail/inconclusive/not-required dispositions. Any missing, failed, or inconclusive **required** check denies prepare. No silent downgrade of requested checks. |
| Evidence | Immutable pre-publication evidence-core reference, schema version, byte size and SHA-256. This core binds `result_id`, validation decisions and safe provenance. It excludes the eventual publication receipt. |
| Publication lineage | For replacement: prior committed descriptor digest/reference, expected generation, and any protected-backup reference with its verified digest. Committed history is reachable through this chain, not through arbitrary files found by scanning staging. |
| Guarantees | Declared atomic scope, supported durability mode, ownership model and required reader protocol. These describe capabilities; the receipt records observed durability and operation outcomes. |

Canonical encoding is versioned: strict JSON-native types, sorted object keys, fixed separators and UTF-8 rules, deterministic array order, no duplicate keys, no NaN/infinity, no `default=str`, bounded metadata size, and explicit numeric ranges. Calculate `descriptor_digest` externally over the descriptor bytes, avoiding a self-hash. Preserve table and row order as represented; do not sort data values to manufacture equality.

Hash actual closed files with bounded reads. Reconcile file footers/counts with the requested inventory and producer counts. A finished Parquet footer alone does not prove all planned rows arrived. A write/iterator/close failure permanently invalidates the attempt, even if a caller catches it and later invokes commit. No writes are allowed after prepare. Sealing must close producer handles and enforce attempt ownership; a frozen Python object alone does not seal files. Reverify candidate artifacts and evidence under the commit guard before binding, or use an adapter's qualified immutable-version guarantee. Verify existing committed artifacts before returning an identical-result receipt; a marker with missing or changed data is corruption, not success. Arbitrary mutation by a privileged process outside this storage protocol is outside the local concurrency guarantee and is detected by subsequent verification.

**Binding rule:** A descriptor in staging is only a prepared claim. A result is committed only when the designated destination's commit binding resolves to that descriptor and the descriptor resolves to the complete validated artifact set. The same resolver governs retries, returned artifacts, evidence export and release gates. There is no independent mutable `committed: true` file, status flag, or job row that can overrule it.

Current evidence is not this binding. `ExecutionResult` at `src/decoy_engine/execution/_adapter.py:42` has outputs, timings and `quality_metrics`, but no receipt. `QualitySummary` at `src/decoy_engine/validation/post/_types.py:61` includes failed checks and timings. The evidence test at `tests/unit/validation/test_failed_evidence_manifest.py:55` deliberately preserves a failed-check report. Existence of that report must not imply approval. The config hash at `src/decoy_engine/plan/_compile.py:624` deliberately excludes sources and targets, so it cannot identify an output. `SubsetManifest` at `src/decoy_engine/subset/_types.py:203` is a separate preprocessing manifest.

**F33 integration without a hash cycle:** First freeze content inventory and `result_id`; then freeze the pre-publication evidence core; then hash the descriptor that binds both. The post-publication evidence envelope references the descriptor digest and receipt. The descriptor never hashes that later envelope. Reuse F33's canonical codec if its owning implementation can be verified before build; do not assume one exists in this checkout. F22 does not claim that unkeyed hashes provide signatures or approval authority. Different retry timings do not alter identity; an identical retry returns the original evidence binding, never rewrites it with the latest attempt's evidence.

### Publication units, overwrite defaults, and backup

Two concrete local protocols are needed because the current directory layout and a replaceable dataset have different storage constraints:

| Unit | Commit binding | Reader and overwrite contract |
|---|---|---|
| `immutable_directory/v1` | A fully staged directory containing table files, required evidence and `_decoy_publication.json` is renamed once into the destination. That destination location binds the descriptor. | Retains `<target>/<table>.parquet`. Default `error_if_different`; identical retries return the existing receipt. Replacing a different non-empty directory is unsupported and refused. Empty datasets also use a staged descriptor and rename. |
| `managed_dataset/v1` | Immutable generation directories under a private dataset root; one atomically replaced `CURRENT` file binds a generation path and descriptor digest. Unreferenced generations are not published results. | Readers resolve `CURRENT` once and pin that immutable generation for the whole read. Supports replacement. A bare directory listing is not the reader protocol. Applies to one-file and multi-file datasets alike. |

This is an explicit publication-unit choice, not a hidden fallback. The default Parquet unit stays `immutable_directory/v1`. A caller requiring replacement selects `managed_dataset/v1` before the first run. An old descriptorless directory or a different immutable-directory result is never automatically adopted, deleted, or converted in place. Copying/validating an existing output into a **new** managed destination is an explicit migration operation outside this build. This limitation must be visible in the API and consumer help. A sanctioned F22 migration utility (validate and copy a legacy descriptorless directory into a new managed destination) is tracked as a separate backlog item, so the upgrade path is owned rather than left as a support burden.

Single-file payload plus an independently renamed JSON sidecar is not a valid third protocol. For F22 a CSV, Parquet or fixed-width payload is an artifact within one of the units above. A raw-file export can still be provided as a separately reported derivative, but cannot carry a stronger dataset guarantee.

The policy is a typed sum, not booleans:

- `error_if_different` is the default. A verified identical result returns `already_committed`. Any unrelated, corrupt, descriptorless, or incompatible target is refused with a stable reason.
- `replace(expected_descriptor_digest, backup=none)` authorizes a different result only for a protocol that supports atomic replacement. The predecessor must still match under the commit lock/CAS. A stale expected predecessor conflicts. This is not append and does not authorize destructive migration of legacy directories.
- `replace(expected_descriptor_digest, backup=protected(policy_ref))` additionally requires a verified, durable backup of the prior descriptor and every artifact it binds before switching the current binding. Backup failure prevents publication. Existing verified backups are reused on retry.

For managed local storage, protected backup means a private, immutable copy of the prior generation plus a durable hold that F26 cleanup must honor. Do not hardlink writable payloads or call ordinary old-generation retention a protected backup. Default local modes are 0700 for private directories and 0600 for metadata/payloads unless an explicit approved output-access policy changes final payload access. This protects against accidental engine modification and unauthorized filesystem access under the declared OS policy; it is not WORM protection against the OS owner. Encryption-at-rest requirements come from F25. If those requirements cannot be met, protected backup is unsupported and the replacement fails before publication.

Backup creation, publication, abort, and cleanup each have their own result. A successful backup followed by a failed publication leaves a valid held backup and the old current binding. No backup is created on an identical retry. Neither successful replacement nor failed cleanup deletes prior bytes in the commit critical section. Retention may later remove eligible unprotected generations, subject to history, readers and recovery holds. Restore is a new authorized replacement with an expected predecessor, never an implicit rollback after a reported commit.

### Per-sink protocol and durability contract

**Local immutable directory.** Close and validate every artifact; fsync payloads, evidence and descriptor; sync staging directories bottom-up; acquire the destination's stable writer lock; reread the destination and ownership state; decide identical/conflict; rename once; sync the destination parent before acknowledging durable success. Stage and destination must be on a supported common filesystem. No copy fallback on `EXDEV`. Protect against path escape, symlink substitution and duplicate/reserved artifact names; operate relative to trusted directory handles where supported. A sibling path alone is not proof that a hostile or mounted destination shares the filesystem.

**Local managed dataset.** Stage and validate an immutable generation; sync it and its parent. Under the same stable destination lock, read and validate `CURRENT`, inspect committed lineage, validate ownership and the expected predecessor, and create/verify a requested backup. Write and fsync a temporary `CURRENT` in its own directory, then replace only that file and fsync the directory. The old generation and old descriptor remain intact. A crash can leave an unreferenced prepared generation; it is not releasable. Never implement replacement as `old -> backup`, then `staging -> old`, which leaves a missing-target interval.

For the first local implementation, qualify a POSIX local-filesystem profile with process-scoped advisory locking, held through compare-and-publish and reconciliation. The lock file is stable and is never unlinked while contenders can hold it. All supported writers must use it. Release the kernel lock on process death, not by PID-file guessing. Platforms/filesystems without qualified locking, rename and directory-sync behavior return a capability refusal for strict F22; they may expose an explicitly weaker legacy byte-writer result, never an F22 success. NFS/SMB/FUSE and arbitrary S3-compatible vendors are not presumed equivalent. Multi-host lease fencing needs the F23 adapter's storage-enforced CAS/fencing mechanism, not a callback checked long before rename.

**Database output.** Required adapter contract: in one database transaction publish all rows/tables within the declared atomic scope **and** the unique `(destination, operation_id)` record containing the descriptor/result identity. On retry, read that committed row and compare content/validation bindings; do not insert again. Serialize conflicts by an actual uniqueness constraint plus appropriate transaction isolation/locking. Backup must precede destructive mutation or belong to the same transaction, with its own retention protection. Transactional DDL, isolation, readers, disconnect-at-COMMIT reconciliation and vendor limitations require real adapter tests. Cross-database/table operations outside a common transaction are unsupported as one atomic dataset. No engine DB implementation or passing DB golden is claimed here.

**Object store.** Qualified adapters upload to immutable generation keys, verify sizes/digests and required evidence, then conditionally create/update one descriptor reference using the provider's concurrency token. Competing publishers reread the winning descriptor on precondition failure. Readers pin the referenced immutable objects. ETags/generation numbers are CAS tokens, not substitutes for content SHA-256. Multipart completion can finalize one object; it does not finalize a set of objects. Missing conditional updates, nonconforming gateway semantics or uncontrolled readers mean no atomic dataset guarantee. Current in-tree cloud `FileSink` classes are transfer primitives and remain unqualified until adapted. SFTP requires a separately qualified server protocol or an explicit unsupported result.

### Idempotent commit, cancellation, and outcomes

The public operation is conceptually `commit(prepared) -> CommitReceipt`, with storage logic centralized. The descriptor is constructed from frozen request, measured staging and completed validation, not accepted as an arbitrary caller assertion. `PreparedPublication` is issued by the finalizer only after those checks. A restart must revalidate staging to recreate it.

1. Before writing new data where possible, resolve the committed binding using the request's expected result/operation identity. A request with a known expected result may recover a lost receipt without re-executing the pipeline. Without such identity, stage and measure before claiming equality.
2. At commit, always repeat the read and identity comparison under the destination lock or transaction/CAS. Reuse requires matching actual content identity, destination and acceptance context. A reused operation ID with different bound content or acceptance context is `operation_conflict`, even if overwrite was requested.
3. A verified identical current result returns `already_committed` with the original descriptor, original artifact locations/counts/digests/evidence and `is_current=true`. No second rename, insert, backup, append or evidence rewrite occurs. Cleanup of redundant staging is separately reported.
4. In managed storage, the committed descriptor lineage also answers retries of operations superseded by a newer commit. Return the historical result with `is_current=false` if its bound artifacts still exist and verify. Never restore it automatically. Retain operation tombstones/descriptor history for the destination lifetime in V1; if payload retention has removed an old result, report `committed_artifacts_expired` and never replay it. A future bounded history policy requires an explicit retry-expiry contract.
5. Otherwise apply the explicit overwrite policy. Persist the operation association in the same descriptor/binding as the data effect. Independent jobs with identical content may reuse the original result; their attempt record references that original operation. This does not create a new committed operation alias. Such callers retain the expected result identity for subsequent lookup.

State machine: `OPEN -> PREPARED -> COMMITTED` or `OPEN/PREPARED -> ABORTED/REJECTED`. A failed write is terminal. Only PREPARED can acquire the final publication right. `abort()` after COMMITTED is a no-op with respect to published or backed-up data. Direct no-write commit is legal only for a declared empty inventory; it still prepares a descriptor. Missing planned tables are not an empty success.

Cancellation revokes the right to enter the final publish critical section. A shared local commit guard arbitrates cooperative cancellation versus publication; checking a flag once during execution is insufficient. If cancellation wins, no new binding occurs. If the atomic binding wins, the result is complete and the outcome is committed, even if the response is lost or a later interrupt arrives. Never promise that a signal can reverse a completed rename. For isolated execution, killing the child prevents publication; the parent must also check cancellation after validating the envelope and before its own commit. The child must not emit a releasable descriptor at its private intermediate target.

Return/error carriers distinguish:

| Outcome | Required meaning |
|---|---|
| `published` | Binding verified, requested durability established, new result identity returned. |
| `already_committed` | Existing binding/history and artifacts verified; no duplicate data effect. |
| `conflict` / `unsupported` / `rejected` | No new binding by this attempt; safe reason code, existing result unchanged. |
| `cancelled_before_commit` | Publication right revoked before binding; no releasable new result. |
| `commit_uncertain` | Rename/remote commit may have succeeded but acknowledgment, sync or authoritative reread failed. Preserve data and reconcile; never delete the possible committed generation or blindly retry writes. |
| Separate backup/abort/cleanup status | `not_requested`, `succeeded`, `failed`, `retained` or equivalent typed states, with safe identifiers and retryability. These cannot rewrite the publication outcome. |

After a successful rename followed by a directory-fsync error, visibility may already have changed. Report `commit_uncertain` with observed visibility and durability separately; do not say nothing published. Reconciliation verifies the binding and completes the required sync before returning durable `already_committed`. A cleanup or reporting failure after commit likewise must not be reported as a pre-commit cancellation. Strict release consumers use the reconciled receipt, not an exception type or `outcome="completed"` alone.

## PLAN

### Design notes and build entry gate

The stable invariant belongs in a deep publication module: descriptor validation, equality, result resolution and typed outcomes each have one owner. Route executors supply execution facts and call it; storage adapters supply atomic binding and readback. This removes the current separate sink/isolated commit truth without putting provider-specific switches in route code. Use typed context objects and frozen values; keep pure descriptor construction separate from mutation. Respect the repository's module-size limits rather than adding all policy to `_sequential.py`.

The smallest alternative, a JSON file written after today's rename, fails on response loss and post-commit evidence failure. A loop replacing files fails multi-file atomicity. Deleting or moving the old directory before rename fails old-output preservation. The two local units are justified by the existing direct-directory API and the present requirement for replaceable datasets; no generic catalog server is needed.

Before build, Gemini and Dennis review this exact plan. Resolve all BLOCKER/HIGH findings and record accepted limitations. This confirmation is a formal Slice 0 deliverable: a dependency-verification report marking every "asserted, verify before build" item as verified-with-location or absent, and classifying each as REQUIRED-and-non-substitutable or OPTIONAL-reuse. The REQUIRED set for the engine core is F22's own evidence carriers, already verified present and sufficient for the pre-publication evidence core (`_adapter.py:42`, `validation/post/_types.py:61`, `tests/unit/validation/test_failed_evidence_manifest.py`). F22 defines its own canonical descriptor codec, so the F33 shared codec and bundle schema are OPTIONAL reuse: their absence degrades to F22's own codec and is NOT a build-blocker. The DB/CLI/platform consumer interfaces and the F23/F25/F26/F45 seams are required only before enabling their own surface, not before the engine core. This turns the distributed dependency risk into one upfront decision point without manufacturing a phantom F33 prerequisite. This is an integration discovery gate, not a requirement that all of F23/F25/F26/F33/F45 ship first. Local safe defaults are possible; an unavailable required protection/capability is an explicit refusal.

All slices follow **tests first -> implementation -> verification -> adversarial review**. No slice enables a partially wired F22 release claim. Protocol admission needed for safety starts in slice 1; slice 4 completes the adapter declarations. The five slices are ordered as requested.
