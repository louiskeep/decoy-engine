# Corpus Datasheet: Decoy Engine STORM Extended Fixture Corpus

Gate reference: ml-benchmarking-and-privacy.md §B.3 (7-section datasheet).

---

## 1. Motivation

**Why was this dataset created?**

To train and evaluate the Decoy Engine STORM LightGBM column classifier
(lgbm-v1, Sprint B / ML2.x). A synthetic-only corpus is required so that
no real PII enters the model weights, feature vectors, or evaluation reports
(§B.4 privacy invariant).

**Who created the dataset and on whose behalf?**

Created by the Decoy Engine engineering team (automated generation via
`src/decoy_engine/storm/eval/fixtures.py`). No external parties were
involved.

**Was there existing data that was not used?**

The original 5-column baseline fixture (`build_fixtures()`) was kept separate
and was NOT used for LightGBM training. It is used only for the regex-baseline
golden test.

---

## 2. Composition

**What does each instance represent?**

Each instance is a synthetic tabular column: a sequence of N=60 string cell
values, a column header, and a ground-truth semantic-type label.

**How many instances are there in total?**

291 columns in the extended corpus:

| Semantic type | Clear-header columns | Cryptic-header columns | Total |
|---|---|---|---|
| ssn | 10 | 10 | 20 |
| email | 10 | 10 | 20 |
| pan | 10 | 10 | 20 |
| iban | 10 | 10 | 20 |
| icd10 | 10 | 10 | 20 |
| iso_date | 10 | 10 | 20 |
| npi | 10 | 10 | 20 |
| cvv | 10 | 0 | 10 |
| mrn | 20 | 20 | 40 |
| health_plan_id | 20 | 20 | 40 |
| none | 61 | 0 | 61 |
| **Total** | | | **291** |

Additionally, 30 OOD (out-of-distribution) columns with single- or
double-character headers are generated by `build_ood_fixtures()` for
adversarial evaluation (§B.2). These are evaluated separately and not
included in training.

**Does the dataset contain all possible instances or is it a sample?**

A sample. The corpus is a small proof-of-concept sufficient to demonstrate the
lift gate (>=5 ppt macro-recall improvement). Pre-GA training should expand to
500+ columns per type.

**Is there any information that is missing from individual instances?**

No. Every instance has a header, values, and a label.

**Are there any known errors, sources of noise, or redundancies?**

- CVV type: 10 columns, all with clear headers. All land in the training fold
  due to value-level grouping (§A.3 leakage guard); no held-out CVV evaluation
  is possible with this corpus size.
- `none` class is intentionally heterogeneous (61 columns spanning counts,
  amounts, codes, dates, identifiers, etc.) to teach the model about the
  diversity of non-PII column types.

**Is the dataset self-contained, or does it link to or otherwise rely on external resources?**

Fully self-contained. All values are generated at runtime from Python
`random.Random(seed=20260627)` and manual format templates. No external
databases, APIs, or third-party datasets are used.

---

## 3. Collection Process

**How was the data acquired?**

100% procedurally generated in Python. No data acquisition from any external
source. Specific generation methods per type:

| Type | Generation method |
|---|---|
| SSN | `{ddd}-{dd}-{dddd}` pattern via seeded RNG |
| Email | `user{N:06d}@{domain}` with per-column unique indices |
| PAN | Luhn-valid 16-digit card numbers |
| IBAN | `GB{kk}NWBK{sort_code}{account}` templates |
| ICD-10 | Slices of `_EXT_ICD10_POOL` (3510 unique E/G/M/R codes) |
| ISO date | `YYYY-MM-DD` with per-column 200-day offset gaps |
| NPI | 10-digit strings matching NPI Luhn check |
| CVV | 4-digit integers 1000-9999 via seeded RNG |
| MRN | `MR{dddddd}` (clear) or short numeric (cryptic) |
| Health plan ID | `HP-{dddddddd}` (clear) or short alphanumeric (cryptic) |
| None | 61 subtypes: counts, amounts, codes, hashes, order IDs, etc. |

**Who was involved in the data collection process?**

Automated code generation only. No human labellers or annotators.

**Over what timeframe was the data collected?**

Generated at build time during Sprint B (2026-06-27). Reproducible from any
checkout at the same commit hash by running `build_extended_fixtures()` with
the fixed seed `_EXT_SEED = 20260627`.

**Were any ethical review processes conducted?**

Not applicable; the dataset contains no real persons' data.

---

## 4. Preprocessing, Cleaning, and Labelling

**Was any preprocessing or cleaning of the data done?**

Values are generated in their final format; no post-processing is applied.
Each column header is tokenised by splitting on `[^a-z0-9]` (after lower-
casing) into a list of tokens used as header-indicator features.

**What software was used to preprocess the data?**

`decoy_engine.storm.eval.fixtures` (generation) and
`decoy_engine.storm.eval.split:make_split_inputs` (feature extraction via
`decoy_engine.storm.features.builder:build_column_features`).

**Was the "raw" data saved in addition to the preprocessed data?**

The raw generated values are NOT persisted on disk (§B.4 privacy invariant:
raw cell values must never appear in the model artifact, report, or logs).
They exist only transiently in memory during training.

**Were labels generated by humans or by machine?**

Labels are deterministic: each fixture is assigned its semantic type at
generation time by `_make_fixture()`. No human labelling step exists.

## 5. Uses

**Has the dataset been used for any tasks already?**

Yes: training and evaluating lgbm-v1 (this sprint).

**What other tasks could the dataset be used for?**

- Training alternative classifiers (random forest, SVM, etc.).
- Ablation studies on feature subsets (content-only vs. header-only).
- Regression testing: the frozen golden hash in
  `tests/snapshots/golden/ml_lightgbm/lightgbm.sha256` is derived from
  this corpus.

**Is there anything about the composition of the dataset or the way it was collected that might impact future uses?**

- Small corpus (291 columns): downstream models trained here may not
  generalise to production-scale schema diversity.
- Synthetic only: the model may not generalise to unusual real-world
  formatting variants (locale-specific date formats, non-Luhn PANs, etc.).
- CVV ambiguity: 4-digit CVV values overlap numerically with some non-PII
  integer columns; the model's CVV recall is unknown from this corpus alone.

**Are there tasks for which the dataset should not be used?**

- Must not be used to claim the model is robust to all PII formats.
- Must not be used without the accompanying model card and this datasheet.

## 6. Distribution

**Will the dataset be distributed to third parties?**

No. The corpus is generated at runtime from source code. There is no
distributable dataset file; the source code IS the dataset.

**How will the dataset be distributed?**

Via the `decoy-engine` git repository. The generation code is open (internal).

**Are there export controls or other regulatory restrictions?**

Not applicable (no real data; no PII).

---

## 7. Maintenance

**Who is supporting, hosting, or maintaining the dataset?**

Decoy Engine engineering team.

**Will the dataset be updated over time?**

Yes. Planned updates:
1. Expand to 500+ columns per type (pre-GA).
2. Add locale-aware date/currency variants.
3. Add more `none` column subtypes (XML, JSON snippets, free-text).
4. Resolve CVV held-out evaluation gap (add more CVV columns to allow a
   proper test-fold split).

**Will older versions be archived?**

The corpus is reproducible from the git history (generation code + seed).
No separate archive is needed.

**If others want to extend the dataset, should they contact anyone?**

Open a PR against `decoy-engine` modifying `fixtures.py`. Ensure:
- All new column types use value-unique generation (no value sharing across
  columns of the same type that would merge them in union-find).
- `_EXT_SEED` or per-type seeds are documented.
- The golden SHA-256 file (`lightgbm.sha256`) is updated with
  `UPDATE_SNAPSHOTS=1`.
